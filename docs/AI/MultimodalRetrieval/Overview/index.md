# 总览：三种范式与五个必失点

多模态检索的工程决策，**百分之八十在写第一行代码之前就已经决定了**：你选哪条范式、索引里放什么、评估集怎么建。这三件事选错，后面调参只能在小数点后第二位挣扎。

这一页给出一张决策地图：三条范式的适用边界、五类任务各自的最短路径、五个一错就全错的决策点，以及「什么情况下不该做多模态检索」的止损判据。

## 判据族声明

本页判据族 `MMO-A` ~ `MMO-H`，共 8 条。定义表在第七节。

## 一、先分清四种「多模态」

「多模态」这个词在四个不同层次上被使用，混着说就会做出错误的架构决策：

| 层次 | 含义 | 典型问题 | 归属 |
| --- | --- | --- | --- |
| **多模态输入** | 模型能吃图、音、视频 | 这张发票金额是多少 | [多模态应用](../../Multimodal/index.md) |
| **多模态输出** | 模型能生成图、音、视频 | 生成一张海报 | [多模态应用](../../Multimodal/index.md) |
| **多模态表示** | 不同模态映射到同一向量空间 | 这句话和这张图像不像 | **本专题** |
| **多模态检索** | 用 A 模态的查询，从 B 模态的库里取结果 | 用截图找文档 | **本专题** |

本专题只管后两层。这个区分不是文字游戏：**多模态输入只需要一次模型调用，多模态检索需要一个索引、一套召回、一层重排和一套评估**——后者是前者的十倍工作量。

## 二、三条范式：索引里到底存什么

![三种范式：存文本、存单向量、存多向量](../assets/mmr-paradigms.svg)

| 范式 | 索引里存什么 | 查询怎么比 | 典型代表 | 索引体积（相对） |
| --- | --- | --- | --- | --- |
| **文本代理**（text proxy） | OCR / 字幕 / 图片描述转成的文本 | 文本检索 | OCR + BM25 + 文本嵌入 | 1× |
| **统一向量**（unified embedding） | 一条定长向量（图文共享空间） | 余弦 / 点积 | CLIP、SigLIP 2、jina-clip-v2、jina-embeddings-v5-omni | 1×~2× |
| **视觉原生多向量**（late interaction） | 每页几百条 patch 向量 | MaxSim 逐块取最大 | ColPali、ColQwen2.5、ColNomic | 100×~400× |

三条范式不是替代关系，而是**精度与成本的三个档位**。真实系统里最常见的组合是：**文本代理做兜底（保证能搜到字）+ 统一向量做粗排（保证跨模态召回）+ 多向量做精排（保证版面细节）**。

### 什么时候必须上第三条

| 条件 | 说明 |
| --- | --- |
| 文档里的信息**只在版面里** | 合并单元格的表格、跨栏排版、图注与图的对应关系、印章与签名 |
| OCR 错误率**结构性偏高** | 扫描件、低分辨率、手写、公式、多语言混排 |
| 查询本身就是**视觉的** | 用户上传一张截图问「这个报错在哪一页」 |
| 答案需要**引用原页** | 合规、审计、合同——必须指回原始页面而不是一段被切碎的文字 |

四条里满足两条以上，OCR 管线的天花板就会挡住你；一条都不满足，直接用文本链路。

::: danger 三个最常见的误判
1. **「我们有 PDF，所以要用视觉检索」**——PDF 是容器不是内容。文字版 PDF 用 `pdftotext` 抽出来的文本质量极高，先抽再检索，成本是视觉方案的百分之一。
2. **「CLIP 分数低就是不相关」**——CLIP 类模型的相似度是**排序信号**不是**概率**。它与「相关」的关系依赖语料分布，阈值必须在自己的评估集上标定。
3. **「多向量就是把向量存多份」**——多向量是**打分算子**变了（MaxSim 代替单次点积），存储格式、索引方式、查询计划全都要跟着变。
:::

## 三、五类任务的最短路径

| 任务 | 查询 | 目标 | 最短路径 | 不要做的事 |
| --- | --- | --- | --- | --- |
| **文搜图** | 文本 | 图片 | 统一向量（SigLIP 2 / 多语言 CLIP）+ 元数据过滤 | 不要给每张图生成描述再走文本检索，除非图里有大量文字 |
| **图搜图** | 图片 | 图片 | 纯视觉编码器（DINOv2/v3 或 CLIP 图像塔）+ 近重复去重 | 不要用文本塔参与打分 |
| **文搜页** | 文本 | PDF/幻灯片页 | 视觉文档多向量（ColQwen 系），或 OCR 文本 + 版面块 | 不要把整页拍扁成一条向量 |
| **图搜页** | 截图 | 原文档页 | 多向量 + 页面级去重 | 不要只比对文字区域，截图往往只截了局部 |
| **混合查询** | 图 + 文字约束 | 任意 | 图像向量 + 文本向量加权，或分路召回后融合 | 不要把文字硬拼进图像提示词 |

「混合查询」是最容易被低估的一类：用户上传一张沙发照片，再打上「北欧 三人位 布艺」。图像向量负责「长得像」，文本向量负责「属性对」，两路必须**分开召回再融合**——拼成一句提示词会同时污染两个信号。

## 四、五个必失点

这五处只要错一个，系统会「看起来能用但一直不准」，而且**每一处都不会报错**。

### 必失点 1：把「相似」当成「相关」

嵌入模型优化的是**语义相似**，业务要的是**任务相关**。这两者在三种情况下会分叉：

- 同一产品的不同颜色：视觉极相似，但用户只要黑色；
- 同一模板的不同合同：版面几乎相同，但条款完全不同；
- 同一主题的正反观点：语义相似，但答案相反。

对策：**相似度只用于召回，相关性必须由重排或业务规则判定**。相关定义见 [重排](../Rerank/index.md)。

### 必失点 2：patch 预算没有上限

视觉文档模型把页面切成 patch，patch 越多越准，但存储与算力是**线性甚至超线性**增长的。一个没有上限的 patch 预算，会在数据量涨到十万页时突然变成事故。

算一笔账（100 万页、每页 768 个 patch、每 patch 128 维）：

```text
float32: 1,000,000 × 768 × 128 × 4 B ≈ 393 GB
float16: ≈ 197 GB
int8   : ≈ 98 GB
对照：单向量 1024 维 float32 ≈ 4.1 GB
```

对策与完整推导见 [视觉文档检索](../VisualDocument/index.md)；结论是**先算存储再选模型**，不要反过来。

### 必失点 3：页面身份在切片时丢了

视觉文档检索的单位是「页」，但很多管线在入库时把页拆成图块（tile），出库时却拼不回去。用户点开结果看到的是「某张图」，而不是「第 42 页第 3 段」。

对策：**每一级切片都必须带 `doc_id` / `page_no` / `tile_no`，并且能反查到原页**。这条在 [视觉文档检索](../VisualDocument/index.md) 与 [实战](../Practice/index.md) 都有对应判据。

### 必失点 4：过滤条件在召回之后才生效

多租户、权限、时间范围这些条件，如果在拿到 top-100 之后才过滤，会出现两个后果：**过滤后不够 10 条**、**本该出现的结果根本没进候选**。

对策：**过滤必须下推到检索层**（向量库的 payload filter / 分区），或者在召回阶段就按分区隔离。这在多租户系统里是安全边界，不只是效果问题。

### 必失点 5：没有评估集

没有评估集的多模态系统，所有「感觉好多了」都无法证伪。更糟的是**换模型**这件事：向量空间一换，旧索引全废，没有评估集你无法判断这次重建是升级还是退步。

对策：**200 条标注查询起家**，按查询类型分层，指标固定为 Recall@k + nDCG@10。做法见 [评估](../Evaluation/index.md)。

## 五、决策树：三十秒选路线

```text
语料里有图片/扫描件吗？
├─ 没有 → 文本 RAG（见 ../RAG），结束
└─ 有
   ├─ 图里的文字能被高质量 OCR 抽出来吗？
   │  ├─ 能，且版面信息对答案不重要 → 文本代理 + 统一向量（图文共享空间）
   │  └─ 不能，或版面/表格/图表是关键 → 视觉原生多向量
   └─ 查询里有「以图搜图」的需求吗？
      ├─ 有 → 必须保留纯视觉编码器通道（CLIP 图像塔或 DINOv2/v3）
      └─ 没有 → 文本塔 + 图像塔共用一个空间即可
```

决策树只在两个分支上做判断：**OCR 是否够用**、**是否需要图搜图**。其余维度（模型大小、维度、量化）都是这两个分支之后的调优。

## 六、什么时候不该做

四条止损判据，满足任意一条就应该先解决上游问题：

| 判据 | 现象 | 先做什么 |
| --- | --- | --- |
| 语料本身没有价值 | 重复、过期、无结构 | 治理语料，不做索引 |
| 查询量极低 | 每天几十次 | 人工检索 + 缓存，不上向量库 |
| 答案需要精确计算 | 金额汇总、计数 | 走结构化查询，检索只负责定位 |
| 团队没有评估能力 | 无法判断好坏 | 先建 200 条评估集，再谈模型 |

## 七、判据定义表

| 判据 | 约定 | 定错了会怎样 | 怎么验证 |
| --- | --- | --- | --- |
| `MMO-A` | 范式选择必须写明「为什么不选更便宜的那条」 | 用视觉方案做纯文本检索，成本涨百倍、效果不变 | 设计文档里有三范式对照表与淘汰理由 |
| `MMO-B` | 索引单位必须与出库单位一致（页进页出） | 结果无法回指原页，用户无法核对 | 检索响应里含 `doc_id` + `page_no` |
| `MMO-C` | 相似度只用于召回，相关性由重排或规则判定 | 把「像」当「对」，准确率长期卡住 | 重排阶段存在且有权重记录 |
| `MMO-D` | 权限与租户过滤必须下推到检索层 | 过滤后候选不足，或越权结果进候选 | 检索请求携带过滤条件，日志可见 |
| `MMO-E` | patch 预算必须有上限并写明依据 | 数据量涨十倍时存储失控 | 索引体积估算表与上限值成对出现 |
| `MMO-F` | 多模态链路必须复用文本链路的评估口径 | 两套指标无法比较，换模型无法判断 | 评估集与指标定义只有一份 |
| `MMO-G` | 混合查询必须分路召回后融合 | 图文拼成一句，两个信号互相污染 | 请求结构里图像与文本字段分离 |
| `MMO-H` | 上线前必须有「不该做」的止损结论 | 在无价值语料上持续投入 | 评审记录里有止损判据核对 |

## 如何验证

```shell
# ① 存储量级核对：把你的真实页数代进去，看落在哪个档位
/Users/cuifendemac/.workbuddy/binaries/python/envs/default/bin/python3 - <<'PY'
pages, patches, dim = 1_000_000, 768, 128
for name, size in [("float32", 4), ("float16", 2), ("int8", 1)]:
    multi = pages * patches * dim * size / 1e9
    single = pages * 1024 * 4 / 1e9
    print(f"{name:8s} 多向量 {multi:6.0f} GB   单向量 {single:5.1f} GB   倍数 {multi/single:5.0f}x")
PY
```

**预期输出**：`float32 多向量 393 GB 单向量 4.1 GB 倍数 96x`、`int8 多向量 98 GB … 倍数 24x`。倍数低于 20 时，视觉原生方案的成本劣势已经不明显，可以优先考虑精度。

```shell
# ② 止损判据的量化版：日查询量 × 单次成本 是否小于人工检索成本
/Users/cuifendemac/.workbuddy/binaries/python/envs/default/bin/python3 - <<'PY'
qpd, cost_per_q, human_minutes, hourly = 40, 0.004, 3, 120
machine = qpd * 30 * cost_per_q
human = qpd * 30 * human_minutes / 60 * hourly
print(f"机器月成本 {machine:.1f} 元，人工等价 {human:.0f} 元")
print("结论：", "不值得建索引" if machine * 5 > human else "值得建索引")
PY
```

**预期输出**：`机器月成本 4.8 元，人工等价 7200 元` 与 `结论： 值得建索引`。判读要点是**分母不是查询量而是「人工替代成本」**——查询量低但每次人工要 3 分钟时，索引依然划算。
