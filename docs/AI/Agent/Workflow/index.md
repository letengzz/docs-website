# 工作流编排

复杂任务需要把 Agent 的步骤**编排成工作流**：定义状态、条件分支、循环与终止条件。从手写循环到框架（LangGraph、Coze、Dify、n8n），按复杂度选择。

## 从代码到工作流

```text
简单：单 Agent 循环（max_steps）
中等：顺序步骤 + 条件分支
复杂：图编排（节点 + 边 + 状态）
```

## 工作流核心元素

| 元素 | 说明 |
| --- | --- |
| 节点（Node） | 一个处理步骤（LLM 调用/工具/判断） |
| 边（Edge） | 节点间流转 |
| 状态（State） | 共享的上下文与中间结果 |
| 条件分支 | 根据状态决定下一步 |
| 循环/终止 | 重试、最大步数、完成条件 |

## 顺序工作流示例

```text
输入 → 提取意图 → 查数据库 → 生成回答 → 格式校验 → 输出
                          ↓ 查询失败
                      重试 / 兜底回答
```

## 条件分支

```text
意图 = 查询天气 → 调用天气工具
意图 = 订票     → 调用订票流程（需确认）
其他           → 转人工 / 通用回答
```

## 图编排（LangGraph 示例）

```python [workflow.py]
from langgraph.graph import StateGraph

builder = StateGraph(dict)
builder.add_node("classify", classify)
builder.add_node("query", query_tool)
builder.add_node("answer", generate)
builder.add_edge("__start__", "classify")
builder.add_conditional_edges(
    "classify",
    route,
    {"weather": "query", "default": "answer"},
)
builder.add_edge("query", "answer")
builder.add_edge("answer", "__end__")
graph = builder.compile()
```

## 低代码平台

| 平台 | 特点 |
| --- | --- |
| Coze | 拖拽编排，插件丰富，适合快速原型 |
| Dify | 开源，RAG + 工作流一体 |
| n8n | 通用自动化，AI 节点扩展 |
| LangGraph | 代码化，灵活可控，适合深度定制 |

## 工作流设计原则

1. **显式状态**：中间结果存入 state，避免靠模型记忆。
2. **失败兜底**：每个工具/节点定义重试与降级。
3. **可观测**：记录每步输入输出，便于排查。
4. **人工确认点**：写操作、高影响动作插入确认节点。
5. **尽早退出**：意图明确时不要跑完整图。

## 易错点

::: danger 常见错误
1. 把工作流写成“不可变管道”：真实任务需要条件分支与循环。
2. 状态管理混乱：节点之间通过隐式上下文传数据，出错难查。
3. 没有超时/步数上限：卡死或无限循环。
4. 每步都调大模型：能用规则判断的分支用规则，省成本降延迟。
5. 忽略中间结果校验：错误数据流入后续节点。
6. 一上来就用重型框架：简单任务先手写循环，复杂再上 LangGraph。
:::

## 验证方式

1. 用一个三节点顺序工作流跑通端到端。
2. 给“查询失败”分支加兜底，模拟故障验证。
3. 记录每步耗时与 Token，评估成本。

## 低代码编排平台与代码编排的分工边界

「编排」有两种完全不同的形态：一种是**画布**（n8n / Coze / Dify），连线就是流程；一种是**代码**（LangGraph 及各类状态机），图结构写在代码里。两者不是替代关系，而是各自擅长一类问题。

| 能力维度 | n8n | Coze（扣子） | Dify | 纯代码编排（如 LangGraph） |
| --- | --- | --- | --- | --- |
| 编排形态 | 画布 + 数百个连接器，可插入 JS / Python 代码节点 | 画布拖拽，以对话 Bot 为中心 | 画布 + LLM 应用一站式（RAG + 工作流 + Agent） | 显式状态机：节点是函数、边是转移条件 |
| 调试与版本管理 | 单步执行与运行记录直观，**版本控制机制偏弱** | 平台内调试方便，版本能力受平台限制 | 画布调试成熟，版本与应用发布绑定 | 断点、单测、`git diff` 全在工程体系内 |
| 能否私有化部署 | 可自托管（源码可见许可 BSL） | **仅云端，不可私有化** | Apache 2.0 社区版可私有化 | 完全自主，随应用一起部署 |
| 适合的团队 | 要快速串联大量 SaaS / 数据库 / Webhook 的自动化团队 | 要快速做对话机器人并发布到国内渠道的团队 | 要做 AI 产品、又要求数据合规的团队 | 分支与状态复杂、要单测与 CI 回归的工程团队 |

三条判据：

1. **「触发源多不多、集成多不多」是低代码的强项**：当流程要把 Slack / 飞书 / 数据库 / Webhook / 各类 SaaS 串起来自动跑，平台的几百个连接器能省下大量胶水代码——自己写适配器反而更贵、更难维护。
2. **「分支与状态复杂、要单测、要灰度」是代码的强项**：状态机、重试与幂等、单元测试在拖拽界面上都很难表达。一旦流程出现「多路条件 + 可恢复 + 要按比例灰度」，画布就会变成一团看不清的线。
3. **什么时候该从 n8n 迁到代码**：当出现「同一份流程要按环境差异化、需要 code review、需要在 CI 里回归」这三件事中任意一件时，就该迁——画布无法把这三件事做扎实，而它们正是流程从「临时工具」变成「生产资产」的标志。迁移的承接方案见 [LangChain · LangGraph 编排](../../LangChain/LangGraph/index.md)。

## 2026 平台现状（截至 2026-09 核对）

- **n8n**：通用自动化工作流引擎，**不是 AI 专用工具**——AI 只是其中的一个节点。源码可见许可（BSL）、自托管免费、内置数百个第三方服务集成，支持 JavaScript / Python 代码节点。弱项：内置存储非持久化（生产需额外工程化）、版本控制机制偏弱。
- **Dify**：**LLM 应用开发平台**，Apache 2.0 社区版开源、可云端可私有化。核心是 RAG 引擎 + 工作流引擎 + Agent 框架一体，可视化画布成熟，RAG 采用「关键词 + 向量 + ReRank」混合策略。强项是工程化与模型中立（不绑定云厂商）；弱项是高并发生产环境需额外优化，社区版的多租户 / 审计日志 / SSO 等企业能力不完整。
- **Coze（扣子）**：字节跳动出品的**对话 Bot 低代码搭建平台**，非开源、**仅支持云端部署**。插件生态丰富，可一键发布到抖音 / 微信公众号 / 飞书等国内渠道，学习曲线最低。弱项是深度定制能力弱于 Dify，**对数据安全有要求的企业不适用**。
- **社区热度参考**（GitHub 公开数据，2026 年年中）：n8n 约 6.8 万 star，Dify 约 9.2 万 star；Coze 国内版不开源。

::: tip 结论式一句
三者**不是一类东西**——Coze 解决「做个机器人」、Dify 解决「做个 AI 产品」、n8n 解决「把一堆系统串起来自动跑」。**选错层级比写错提示词更耽误事**。私有化 + 数据合规场景的常见组合是 **Dify（做 AI 应用）+ n8n（兜底跑流程）**。
:::

::: warning 说明
上述热度与能力描述为 **2026-09 核对**结果，具体功能与许可条款**以各项目官网为准**。
:::
