# 角色与上下文

角色设定（System Prompt）和上下文管理是让模型“进入状态”的关键：角色决定知识视角与语气，上下文决定模型能看到什么。

## 角色设定

```text
你是资深数据库管理员，熟悉 MySQL 8 与慢查询优化。
回答时先给结论，再给操作步骤，并说明适用版本。
```

角色设定的价值：

1. 激活对应领域的先验知识。
2. 统一语气与表达方式。
3. 约束回答范围，减少跑题。

## System / User / Assistant

| 消息角色 | 用途 |
| --- | --- |
| system | 全局指令、角色、规则（优先级最高） |
| user | 用户请求与输入 |
| assistant | 模型回复（few-shot 中可提供示例） |

```text
system: 你是一个简洁的中文客服，回答不超过 50 字。
user: 我的订单什么时候到？
```

## 上下文管理

上下文窗口有限，长对话需要管理：

| 策略 | 说明 |
| --- | --- |
| 截断 | 丢弃最早的消息 |
| 摘要 | 把旧对话压缩成摘要 |
| 滑动窗口 | 只保留最近 N 轮 |
| RAG | 只注入与问题相关的片段 |

```text
对话摘要：用户咨询过订单状态，已发货，单号 SF123。
当前问题：...
```

## 上下文注入的注意事项

1. **关键信息放前面**：模型对开头与结尾更敏感（“Lost in the Middle”现象）。
2. **避免冗余**：无关信息会稀释指令权重。
3. **指令幂等**：即使对话很长，核心指令也要重申。

## 指令优先级

当 system 与 user 冲突时，多数模型会优先遵循 system；但用户输入中的恶意指令仍可能影响行为，需要：

1. 把用户输入与指令用分隔符隔离。
2. 关键约束在 system 中重复。
3. 必要时用“指令 vs 数据”校验。

## 易错点

::: danger 常见错误
1. system 里塞大量背景：指令被淹没，突出核心规则。
2. 长对话全量塞入：上下文超限或关键信息被稀释，用摘要/检索。
3. 角色切换混乱：同一会话中途换角色，输出不稳定。
4. 忽略多轮一致性：让模型先“复述约束”再回答，提升一致性。
5. 把敏感信息放进上下文：注意数据权限与日志脱敏。
6. 依赖模型记忆“上上轮说过的话”：显式把关键状态写进当前消息。
:::

## 验证方式

1. 同一问题分别用“无角色”和“专业角色”提示词，对比回答质量。
2. 构造 20 轮长对话，观察上下文截断/摘要后的表现。
3. 测试 system 与 user 冲突时的优先级。
