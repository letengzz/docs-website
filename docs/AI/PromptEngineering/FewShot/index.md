# few-shot 示例设计

few-shot 是在提示词里给出输入输出示例，让模型模仿格式与推理方式。它是提升输出稳定性最有效的手段之一。

## 三种范式

| 范式 | 示例数 | 适用 |
| --- | --- | --- |
| zero-shot | 0 | 简单任务、探索阶段 |
| one-shot | 1 | 格式示范 |
| few-shot | 2~5 | 复杂格式、边界情况 |

## 示例的作用

1. **定格式**：模型照着示例的格式输出。
2. **定判断标准**：边界案例教会模型“什么算对”。
3. **演示推理**：带推理步骤的示例能激发思维链。

## 好示例的设计

```text
把评论分类为 积极/消极/中立：

评论：这个手机拍照太棒了！ → 积极
评论：客服根本不理人。   → 消极
评论：一般般，能用。     → 中立
评论：屏幕碎了，但售后很快换了。 → ?
```

设计原则：

1. **多样性**：覆盖不同句式与边界情况。
2. **一致性**：格式完全统一，否则模型混淆。
3. **代表性**：示例接近真实输入分布。
4. **数量克制**：3~5 个足够，过多占用上下文。

## 带推理的 few-shot

```text
问题：小明有 3 个苹果，又买了 2 个，吃掉 1 个，还有几个？
推理：3 + 2 = 5，5 - 1 = 4
答案：4

问题：...
```

推理示例能显著提升数学/逻辑类任务准确率。

## 反例（Label 错误示例）

有时故意放一个**错误边界示例**说明“哪些不算”：

```text
以下内容不算“投诉”：用户询问价格（非投诉）。
```

## 易错点

::: danger 常见错误
1. 示例之间格式不一致：模型学到“平均风格”，输出飘。
2. 示例太少且单一：真实输入的多样性没覆盖。
3. 示例泄露答案：测试时模型直接抄示例，失去评估意义。
4. 示例与任务无关：浪费上下文还干扰。
5. 每轮都重复塞大量示例：考虑把示例放进 system 或模板缓存。
6. 用错误示例当正确答案：模型被误导，输出错误模式。
:::

## 验证方式

1. 对同一任务分别用 zero-shot 与 few-shot，对比准确率与格式合规率。
2. 逐步增加示例，观察效果曲线（通常 3~5 个后趋平）。
3. 检查模型是否“抄示例答案”：用与示例不同的输入测试。
