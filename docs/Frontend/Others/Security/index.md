## SSR 与缓存引入的两类新风险

本专题讲的是浏览器侧的安全问题（XSS、CSRF、CSP 等）。当服务端参与渲染、当 CDN 参与缓存时，会多出两类风险——它们不在浏览器侧，所以常规的前端安全清单覆盖不到。

### 风险一：服务端渲染把「服务端的能力」带进了风险面

| 风险 | 表现 | 规避 |
| --- | --- | --- |
| **密钥泄漏到客户端产物** | 把密钥放进 `runtimeConfig.public`，被打进 JS | 私有值只放非 public 段；**CI 里 grep 产物，命中即失败** |
| **服务端注入** | 把用户输入直接拼进模板 / SQL / 命令行 | 服务端同样要做校验与参数化；不要因为「服务端」就放松 |
| **SSR 的错误详情外泄** | 错误页把堆栈、SQL、文件路径返回给浏览器 | 生产环境只给错误码 + 通用文案，详情只进日志 |
| **`runtimeConfig` 被客户端读** | 客户端代码里读 `process.env`（构建期被替换成真实值） | 客户端只能用 `useRuntimeConfig()`，且只能读 public 段 |

::: danger 注意：`public` 段的判断标准只有一条
**「你能接受它出现在网站源码里吗？」**
不能 → 必须放私有段。站点名、公开 API 地址、埋点 ID 可以放 `public`；`sk-` 开头的密钥、内部域名、JWT 签名密钥、数据库连接串**一律不行**。
:::

### 风险二：缓存把「某个用户的内容」发给了别人

这是 SSR 应用最严重、也最容易被忽略的事故：

```text
1. 用户 A 打开「我的订单」，CDN 缓存了这份 HTML
2. 用户 B 打开同一个 URL → CDN 直接返回 A 的订单页面
3. 事故范围：所有访问同一路径的用户
```

| 规避手段 | 说明 |
| --- | --- |
| 用户相关路由 `ssr: false` | **最稳**：客户端取数，服务端 HTML 天然不含用户数据 |
| `Cache-Control: private, no-store` | 并确保 CDN 排除这些路径 |
| 按用户维度做缓存键 | 成本高，一般不划算 |

**上线前必做的检查：用 A / B 两个账号访问同一路径，确认看不到对方的数据。** 这条与 [Nuxt 部署](../../Frame/Nuxt/Deployment/index.md) 里的缓存策略一一对应。

### 风险三：独立部署带来的「旧代码访问新接口」

微前端场景下，子应用的新旧版本可能同时在线上（缓存、回滚、灰度），于是：

- 旧版子应用调用新版接口 → 字段缺失、语义变化；
- 旧版 entry 引用已被删除的 chunk → 白屏（严格说不算安全问题，但影响面同等）。

**规避**：接口做「只增不改」的兼容期；部署保留最近 3 个版本的分块；契约变更走三步流程（见 [微前端工程化](../../MicroFrontend/Practice/index.md)）。

## 桌面应用这一侧的安全边界

纯 Web 的安全模型有一条硬边界：**页面里的代码永远拿不到系统能力**。桌面应用把这条边界挪了位置——渲染层里跑的仍然是 Web 代码，但主进程（Electron）或 Rust 核心（Tauri）握有文件、进程、网络与自动更新。于是本页的三大块之外，多出一类**「桥」上的风险**：

| 风险 | 典型表现 | 属于哪一侧 |
| --- | --- | --- |
| 桥暴露过宽 | 预加载脚本把整个 `fs` 或 `ipcRenderer` 原样交出去，页面被 XSS 后即可读写任意文件 | 桌面侧 |
| 能力默认开放 | 自研命令 / 插件默认对所有窗口生效，新增一个窗口时访问面被动扩大 | 桌面侧 |
| 内容与能力混用 | WebView 加载远程站点，同时又对该窗口开放本地能力 | 两侧交界 |
| 更新通道被劫持 | 更新包没有签名校验，中间人可下发任意可执行文件 | 交付侧 |

**分工是**——本页讲 Web 侧的威胁原理（XSS / CSRF / CSP / HTTPS）与 SSR 引入的两类新风险，**不进桌面**；桌面侧的能力 / 权限 / scope 三层模型、默认拒绝的配置写法、官方威胁模型「防什么、不防什么」的口径，见 [桌面应用深入 · 安全模型](../../DesktopApp/Security/index.md)；落到 Electron 的 `webPreferences`、`contextBridge` 与 fuses，见 [Electron 安全实践](../../Frame/Electron/Security/index.md)。

一条跨两侧的判据：**「谁能触碰系统」不取决于页面怎么写，而取决于桥怎么开。** 页面里的 CSP 与转义决定「攻击者能不能在页面里执行代码」，桥的配置决定「执行了代码之后还能做什么」——两道都得有，缺一道前面的功课就白做。
