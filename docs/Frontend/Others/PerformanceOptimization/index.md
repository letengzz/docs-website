# 前端性能优化

<p style="text-align:center;"><img src="./assets/perf-logo.png" style="zoom:75%;" /></p>

前端性能优化的目标是用**可测量的指标**驱动改进：让页面更快加载、更快可交互、更流畅运行，并通过监控与性能预算防止回归。本专题从指标、加载、资源、运行时、构建、监控到实战，形成完整的优化方法论。

参考基线：Core Web Vitals 2026 年标准（LCP ≤ 2.5s、INP ≤ 200ms、CLS ≤ 0.1），构建工具以 Vite 生态为主。

## 相关专题与分工

- [WebAssembly](../../WebAssembly/index.md)：本专题负责**工程级性能**——加载、渲染、包体积、缓存、Core Web Vitals 与性能预算，手段是「让既有的代码跑得更少、更早、更省」；WebAssembly 专题负责**算法级加速**——把一个热点函数整体换成另一种实现（如 Rust/C++ 编译成 Wasm），把单次计算本身做快。两者的度量口径与手段不重叠：先在本专题把工程侧的水分挤干，剩下真正的计算热点才值得搬进 Wasm。
- [高性能 Java · 性能工程全景](../../../Backend/HighPerformanceJava/Overview/index.md)：本专题的对手是**浏览器与网络**（资源体积、加载时序、渲染与交互），判据是 Core Web Vitals；那边是**服务端进程内部**（JIT 预热、对象分配、锁竞争、GC 停顿），判据是延迟分位与吞吐。两端最容易互相甩锅的是「接口慢」，判据只有一条：**浏览器 Network 面板里的 TTFB 高，而服务端火焰图平坦**，说明时间花在排队或下游等待上，既不在本专题的加载优化范围，也不在那边的方法级优化范围。

## SSR 与微前端的性能代价核算

本专题讲的是通用的加载、构建与运行时优化。有两类方案的代价需要单独核算，因为它们**看起来是性能优化，实际可能引入新的瓶颈**：**服务端渲染（SSR）**与**微前端**。

### SSR：首屏变快，但指标要重新定义

| 指标 | 纯 SPA | SSR |
| --- | --- | --- |
| **FCP / LCP** | 需等 JS 下载并执行完 | **明显更早**（HTML 里已有内容） |
| **TTI / INP** | 与 FCP 接近 | **可能更晚**（要先 hydration 才可交互） |
| 服务端成本 | 零 | 与用户量等量的 CPU |
| 首屏 JS 体积 | 全部 | 全部（**SSR 不会减少 JS**，只是让它晚一点生效） |

::: danger 注意：SSR 最常见的性能错觉
「上了 SSR 首屏就快了」——只对 LCP 成立。如果 hydration 需要下载 1 MB JS，那么在 hydration 完成前**页面点了没反应**，用户体感比 SPA 的「白屏」更困惑（页面看着正常但按钮无效）。

三条控制手段：
1. **按路由分包**，别把后台管理组件打进首页 bundle；
2. 重组件用 `defineAsyncComponent` / `<Lazy*>` 延迟加载；
3. 定期跑构建分析（Nuxt 用 `nuxi analyze`），把「不小心全量引入的 UI 库」找出来。

**判据**：首屏 JS（gzip）控制在 **200 KB 以内**，超过就要查构成。完整方法见 [Nuxt 部署与实战](../../Frame/Nuxt/Deployment/index.md)。
:::

### 微前端：体积与请求数会成倍增长

| 代价 | 表现 | 控制手段 |
| --- | --- | --- |
| **框架本体重复** | 每个子应用各带一份 Vue/React | 共享运行时（external）或 Module Federation 的 `shared` |
| **请求数增加** | 每次切换子应用至少多 1 个 entry + N 个 chunk | 预加载策略（`prefetch`）；合并子应用粒度 |
| **首屏不可控** | 运行时才知道要加载哪个子应用 | 关键子应用走构建期集成或预渲染 |
| **累积开销** | 切换多次后内存不回落 | `unmount` 里清理实例、事件、定时器 |

::: tip 微前端的性能验收标准
1. **子应用从「路由切换」到「首次可交互」的耗时** —— 这是微前端专属指标，会随子应用数量增长而恶化；
2. **连续切换 10 次后 DOM 节点数与堆内存回到基线附近** —— 验证 `unmount` 是否清理干净；
3. **首屏请求数与总体积** —— 与「不拆」的版本对比，确认增量在可接受范围。

这三条不达标时，微前端的收益（独立部署）通常抵不过性能损失。核算与优化细节见 [微前端工程化](../../MicroFrontend/Practice/index.md)。
:::
