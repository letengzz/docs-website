## monorepo 与微前端：两条路线的分工

「多团队协作 + 代码拆分」有两条常见路线，经常被混为一谈：**monorepo 的包级拆分**（本专题）与**微前端**（应用级拆分）。它们解决的问题不同，成本结构也不同。

| | monorepo（包级拆分） | 微前端（应用级拆分） |
| --- | --- | --- |
| 独立部署 | 否（通常一起发版） | **是** |
| 技术栈自由 | 否（同一构建体系） | **是** |
| 依赖去重 | 天然（同一 lockfile） | 需专门处理（external / MF shared） |
| 隔离性 | 无（共享运行时） | 有（沙箱 / Shadow DOM / iframe） |
| 契约同步成本 | **低**（契约包是本地包） | 高（要发版本、要留兼容期） |
| 工具成本 | 构建编排（Turborepo / Nx） | 沙箱、通信协议、独立部署与回滚 |
| 适用 | 同一团队、同技术栈 | **多团队、异构栈、必须独立发布** |

::: tip 决策顺序：先试包级拆分
**先问「能不能用 monorepo 解决」**。monorepo 的 `packages/` 拆分能做到「代码边界清晰、依赖复用、统一工具链」，只在**「必须独立部署」或「技术栈必须异构」**时才需要升级到微前端。

反之，如果一开始就上微前端而团队规模没到「多个团队各自有发布节奏」，付出的沙箱与通信成本换不回任何收益。完整的判断前置条件、边界判据与集成方式选型见 [微前端](../../MicroFrontend/index.md)。
:::

::: warning 说明：两条路线可以并存，但要分清「谁是权威」
一个可行的组合：**应用之间用微前端集成（独立部署），每个应用内部用 monorepo 组织（统一构建与依赖）**。这样每个应用拥有自己的构建体系与发布节奏，应用内部仍然享受依赖复用与统一规范。

**要避免的是「两套体系都想要权威」**——比如既用 Monorepo 的共享 UI 包（要求同步升级），又用微前端的版本契约（要求独立升级）。这种混合会让升级路径变得无法推理：改一个组件到底要不要同时发所有应用？**先定一条主路线，另一条只做补充。**
:::
