# 常见问题与分诊

「页面数据不对」是最没有信息量的 bug 描述。它可能意味着缓存太新鲜、太不新鲜、有两份、被回滚了、被乱序覆盖了，或者根本是服务端返回了旧值。本页给出一张**按症状走的分诊表**，让排查从「猜」变成「排除」。

## 判据族声明

本页判据族 `SDQ-A` ~ `SDQ-H`，共 8 条。定义表在第七节。

## 本页不讲什么

- 不讲具体库的 API 参考，归框架专题与官方文档。

- 不讲服务端缓存与数据库一致性，归 [分布式缓存](/docs/Backend/DistributedCache/index.md)。

## 一、十类症状分诊表

先定位「是哪一类」，再往下钻。**每行的第一列是用户的原话**，不是技术描述。

| 用户说的 | 最可能的原因 | 第一步查什么 | 再往下读 |
| --- | --- | --- | --- |
| 「刷新一下就好了」 | 写后没失效，或只失效了部分 key | 保存后 Network 有无列表重取 | [缓存失效](../CacheInvalidation/index.md) |
| 「切到别的页面再回来就变了」 | `staleTime: 0`，挂载重取 | 同一接口 30 秒内请求次数 | [本地态与远端态](../LocalRemote/index.md) |
| 「有时候是空的，刷新又有了」 | 首次渲染读到未就绪状态，或缓存被回收 | 是否有 `gcTime` 过短 + 条件渲染 | [本地态与远端态](../LocalRemote/index.md) |
| 「两个人改的不一样」 | 缺版本校验（LWW 静默覆盖） | 写请求有无 `If-Match` | [多端同步](../RealtimeSync/index.md) |
| 「我明明拖过去了，别人看到还是原来的」 | 乐观更新失败未回滚，或事件没广播 | 断网时是否弹回；另一端是否收到事件 | [乐观更新](../OptimisticUpdate/index.md) |
| 「卡片闪一下又回去了」 | 事件重复应用，或在途重取覆盖了乐观值 | 是否 `cancelQueries`；判序是否用 `>` | [乐观更新](../OptimisticUpdate/index.md) |
| 「筛选切了没反应」 | query key 漏参数，缓存命中旧结果 | key 是否包含全部筛选参数 | [本地态与远端态](../LocalRemote/index.md) |
| 「列表在滚动时跳回顶部」 | 整表替换 / key 变化导致重挂载 | 事件落地是否用局部补丁 | [多端同步](../RealtimeSync/index.md) |
| 「保存后按钮转很久」 | 写后读用了策略 A（等待重取） | 是否 `await invalidateQueries` 阻塞提交 | [缓存失效](../CacheInvalidation/index.md) |
| 「偶现，复现不了」 | 缺状态日志与快照 | 有没有导出诊断包的能力 | [状态可观测](../Observability/index.md) |

::: tip 一个 30 秒的初筛
打开 DevTools 的 Network，做一次「复现动作」，看三个数：**请求数**（多了是重复，少了是缓存/失效）、**状态码**（409/412 是冲突，5xx 是服务端）、**响应体时间戳**（服务端自己返回的是旧值，前端再对也没用）。三个数看完，基本能定位到上面十行里的某一行。
:::

## 二、十四问

### 1. `staleTime` 和 `gcTime` 到底哪个是「缓存时间」？

都不是「缓存时间」，它们回答两个不同问题：`staleTime` = 多久算新鲜（决定**要不要发请求**），`gcTime` = 不用之后多久扔掉（决定**内存占多久**）。调「数据总是旧的」要动 `staleTime`；调「内存涨」要动 `gcTime`。

### 2. 为什么设了 `staleTime` 还是会请求？

三种可能：① 你设在了某个 `useQuery` 上，而别处用的是另一个 key（不同 key 各自计时）；② 有代码调了 `invalidateQueries`；③ 组件重新挂载时用了 `refetchOnMount: 'always'`。

### 3. 远端数据能不能放进 Zustand / Pinia？

能，但**只能放「已经从远端拿回来并且不再自动更新」的快照**，比如「上一次导出的结果」。一旦它需要跟随服务端变化，就必须留在查询层，否则你会手动实现一套失效逻辑，而且一定会漏。

### 4. 什么数据该放 URL？

决定「看到哪一份数据」的：页码、筛选、排序、当前 tab、选中的实体 id（如果可分享）。判断标准是**发给同事、他打开链接能不能看到同样的内容**。

### 5. 乐观更新失败了，用户已经走了怎么办？

回滚仍然要发生（改的是缓存，不是组件 state），但**不要再弹提示**——用户已经不在这个页面，弹了也只会困惑。正确做法是记一条状态日志 + 在下次进入该页面时用最新数据覆盖。

### 6. 为什么我的乐观更新会「闪两下」？

两个常见原因：① 没有 `cancelQueries`，一个在途后台重取在你的补丁之后落地，把旧值写回来；② 自己触发的广播也应用了一遍，中间插入一次渲染。前者在 `onMutate` 开头解决，后者靠 `seq` 判序解决。

### 7. 临时 ID 什么时候可以替换成真 ID？

在「服务端确认 + 本地已收到最新实体」之后。不要在请求一发出就替换（服务端可能失败），也不要在列表重取后立刻替换（重取结果里可能还没有它）。稳妥做法是保留临时 ID 作为渲染 key，另存 `realId` 用于后续请求。

### 8. 冲突提示应该多强？

取决于数据价值：结构化字段（标题、状态、负责人）用**阻塞式**提示（必须选一个），非结构化字段（描述草稿）用**非阻塞**提示（横幅 + 可恢复）。永远不要「静默取最新」，那等于让用户以为自己改成功了。

### 9. 多标签页不同步必须用 WebSocket 吗？

不必。改完发一条 `BroadcastChannel` 消息让其他标签页失效即可，成本几乎为零。只有跨设备才需要服务端推送。

### 10. 归一化一定要做吗？

数据超过几百条、或者同一实体出现在多处时才值得。判据：**你是否有过「改了一处、另一处没变」的 bug**——有，就该归一化。

### 11. `useMemo` 能不能解决大列表卡顿？

通常不能。`useMemo` 只避免重复计算，不减少一次计算的成本；两万条的一次深比较就要 11.78 ms（本机实测），已接近一帧。真正的解法是减少数据量（分页/服务端过滤）或建索引。

### 12. 状态日志会不会拖慢应用？

只要「记操作不记数据」，每条日志不到 100 B，开销可以忽略。真正贵的是全量快照（单份 13 KiB 级），必须按关键节点采集。采样率 1%~5%、错误 100% 是常见配置。

### 13. 推送和轮询能一起用吗？

不建议。两者并存会出现「同一份数据两条更新路径」，且轮询会在推送已更新后又用稍旧的结果覆盖。要么用推送 + 断线补拉，要么纯轮询（间隔大于接口 P95）。

### 14. 怎么证明「这次改动没让状态变差」？

三条：① 状态断言（纯逻辑测试，输入状态 + 事件，输出新状态）；② 关键链路的验收序列（如 [实战](../Practice/index.md) 的 S1~S10）；③ 诊断包对比（改前改后同一操作的事件序列应一致）。

## 三、十二项上线自查

上线前逐条打勾，任一条为「否」都不要发：

| # | 检查项 | 通过标准 |
| --- | --- | --- |
| 1 | 每个查询有 `staleTime` | 无「无理由的 0」，例外有注释 |
| 2 | 每个写操作有失效或补丁 | `mutation` 数 ≤ `invalidate/setQueryData` 数 |
| 3 | 写请求带版本条件 | 冲突返回 409/412 并有文案 |
| 4 | 乐观写入有回滚 | 断网操作 2 秒内弹回 |
| 5 | 乐观写入有幂等键 | 超时重试不产生重复 |
| 6 | 跨标签页有同步 | 双窗口改一侧，另一侧 ≤ 2 s 更新 |
| 7 | 推送落地有判序 | 重放同一事件状态不变 |
| 8 | 断线有补拉 | 断网 30 s 恢复后数据完整 |
| 9 | 派生值不落库 | store 里无「能算出来」的字段 |
| 10 | 状态布尔 ≤ 1（或已改枚举） | 无 `isLoading && isError` |
| 11 | 有状态日志与快照 | 能导出 ≤ 2 MB 诊断包 |
| 12 | 已修 bug 有断言 | 回归用例覆盖已知状态类缺陷 |

## 四、反模式清单

| 反模式 | 为什么错 | 改法 |
| --- | --- | --- |
| `useEffect` 里 `fetch` 后写 store | 两套真相、多一轮渲染 | 交给查询层 |
| `useEffect(() => setX(y), [y])` | 能派生却存了 | 直接算 |
| 用 `index` 作列表 key | 重排后状态错位（输入框内容跟着跑） | 用稳定 id |
| `invalidateQueries()` 不带 key | 全量失效，一次保存打爆接口 | 精确到 key 或前缀 |
| 把 token 存 `localStorage` | XSS 可直接读 | HttpOnly Cookie |
| 用时间戳判序 | 客户端时钟不可信 | 服务端单调 `seq` |
| 冲突自动重试 | 把可见冲突变成静默覆盖 | 提示用户选择 |
| 每次都存全量快照 | 体积 70 倍于差量 | 差量 + 关键节点全量 |

## 五、术语表

| 术语 | 含义 | 常见误解 |
| --- | --- | --- |
| **远端态**（server state） | 所有者在服务端、本地只是副本的数据 | 误以为「取回来就是我的」 |
| **陈旧**（stale） | 超过 `staleTime`，下次触发会重取 | 误以为「stale = 已删除」 |
| **失效**（invalidate） | 标记为 stale 并（可选）立即重取 | 误以为「失效 = 清空缓存」 |
| **归一化**（normalize） | 把嵌套数据拍平成「实体表 + id 顺序」 | 误以为「只是换个数据结构」 |
| **乐观更新** | 本地先应用，失败回滚 | 误以为「先改 UI 就算乐观」 |
| **LWW** | 最后写入者赢 | 误以为「有时间戳就不会丢」 |
| **收敛**（converge） | 多端最终得到同一状态 | 误以为「推送到了就收敛」 |
| **判序** | 按业务序号而非到达顺序应用事件 | 误以为「TCP 有序所以不用判」 |

## 六、三条「查不出来」时的兜底

1. **二分数据源**：把页面切成「只读缓存」与「强制重取」两个版本，哪个正常就锁定在哪一层。
2. **固定随机**：若问题与「顺序」有关（事件、请求返回顺序），用 DevTools 的请求阻塞人为固定顺序，看是否稳定复现。
3. **换环境复现**：本地正常、测试环境异常，先比 `buildId` 与 `staleTime` 配置——九成是配置差异，不是代码差异。

| `SDQ-F` | 每条「偶现」有兜底三步记录 | 同类问题重复排查 | 排障记录含「二分/固定随机/换环境」结论 |

## 验证方式

```text
SDQ-A：取最近 5 个状态类线上问题，逐个标注分诊表行号
  期望：5/5 能对应；对应不上的补进表格（表格是活的）

SDQ-B：拿上线自查表逐项检查当前分支
  期望：12/12 通过；不通过的写进发布阻断项
  判读：超过 2 项不通过，说明这一版不该发

SDQ-E：制造一次 409 冲突与一次断网失败
  期望：两次提示文案不同，且都能说明原因与下一步
  判读：两次都是「操作失败」= 文案没区分场景
```
