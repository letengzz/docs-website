# 演练：五级金字塔与可证伪判据

**没有演练过的多活，等于没有多活。** 这不是一句口号——多活的失效方式极其隐蔽：不是「挂了」，而是「一部分用户的数据不对」。只有把故障真的注入进去，才能知道它到底能不能切、切完对不对。本页给出五级演练的分层、每条演练必须写死的三要素、五种常见的假通过，以及一份可抄的演练记录表。

![五级演练：从桌面推演到全链路数据校验](../assets/ma-drill.svg)

## 一、五级金字塔

| 级别 | 演练内容 | 成本 | 能证明 | **不能**证明 |
| --- | --- | --- | --- | --- |
| **L1 桌面推演** | 念一遍步骤，确认权限与顺序 | ≈ 0 | 流程存在、有人有权按按钮 | 任何技术事实 |
| **L2 单组件** | 提升备库、切缓存、切对象存储 | 低 | 组件能反向 | 流量能不能过去 |
| **L3 单元级** | 摘掉一个单元的入口与网络 | 中 | 路由与降级正确、影响面可控 | 站点级灾难 |
| **L4 站点级** | 整站切走并保持 N 小时，再回切 | 高 | RTO/RPO 是真实数字 | 数据没差 |
| **L5 全链路 + 校验** | L4 + 切完后跑对账与不变量 | 最高 | **切过去还能正确做生意** | — |

::: danger 最常见的假通过
只做 L1 + L2，然后宣称「多活已验证」。这两级证明的是「组件可以被反向」，与「用户能不能继续用」没有任何关系。**至少要 L3，才配说「切得动」；要到 L5，才配说「切得对」。**
:::

## 二、每条演练必须写死的三要素

一条不可证伪的演练等于一次团建。三要素缺一不可：

| 要素 | 含义 | 反例 | 正例 |
| --- | --- | --- | --- |
| **观测点** | 从哪里看结果（指标名 / 日志字段 / 命令） | 「观察系统状态」 | `gateway_route_hit_ratio{cell="b"}` |
| **期望值** | 具体到什么数算通过 | 「错误率不升高」 | `5xx 率 < 0.1%`，`P99 < 800ms` |
| **持续时间** | 保持多久才算稳定 | 「持续观察」 | 故障注入后持续 15 分钟 |

```text
# 一条合格的演练条目
编号：DR-03
级别：L3 单元级
注入：切断单元 A 的入口网络（保留其数据库可达）
观测点：
  1) gateway_route_hit_ratio{cell="a"}          → 期望跌到 0（流量已不在 A）
  2) http_5xx_ratio{cell="b"}                   → 期望 < 0.1%
  3) app_log{cell="a"} 中 "cell_unavailable" 计数 → 期望 > 0（明确报错而非静默）
持续时间：注入后 15 分钟
通过判据：三条同时满足；且归属 A 的租户访问时返回 503 与重试建议，不返回假数据
```

## 三、五种「假通过」

| 假通过 | 表现 | 为什么不算通过 | 怎么识别 |
| --- | --- | --- | --- |
| **① 只验证健康检查** | `/healthz` 返回 200 | 健康检查不碰数据库与归属表 | 注入后调一次「读一条业务数据」，看是否真的返回 |
| **② 流量没真的切** | 网关显示「已切」，但旧单元仍有流量 | 缓存 / 长连接 / DNS 仍在旧路 | 看旧单元 QPS 是否降到 0 |
| **③ 没有真实用户请求** | 用脚本自己造请求，量很小 | 小流量绕过了瓶颈（连接池、锁、队列） | 按生产 10% 的流量压 |
| **④ 只切了读没切写** | 页面能打开，保存失败 | 写路径的归属没切 | 演练必含「写一条并读回」 |
| **⑤ 数据没校验** | 切完就宣布成功 | 「能用」不等于「对」 | 切完跑 L3 不变量校验 |

::: warning 第 ② 条最容易被忽略
网关的「已切」是**配置状态**，不是**流量事实**。判定流量真的切走了，唯一可靠的证据是**旧单元的入口 QPS 降到 0**（而不是「接近 0」）。演练记录里必须贴这个读数。
:::

## 四、L3 单元级演练：逐步操作

这是性价比最高的一级，建议每月一次。

### 4.1 注入

```shell
# 方式 A：网关层面把单元 A 的权重置 0（最温和，先验证降级）
curl -X POST http://gateway/admin/weights -d '{"cell-a": 0, "cell-b": 100}'

# 方式 B：网络层面隔离单元 A 的入口（更真实）
# 用 NetworkPolicy 或安全组切断 ingress，但保留 A 到其数据库的连通
kubectl apply -f - <<'YAML'
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: deny-ingress-cell-a, namespace: cell-a }
spec:
  podSelector: {}
  policyTypes: [Ingress]
  ingress: []          # 拒绝所有入站；出站不受影响
YAML
```

### 4.2 观测（在注入期间持续看）

```shell
# ① 旧单元入口流量是否归零
curl -s "http://gateway/admin/route-stats" | jq '.cells["cell-a"].qps'
# 期望：0

# ② 新单元是否接住（若有接管）
curl -s "http://gateway/admin/route-stats" | jq '.cells["cell-b"].qps'
# 期望：上升到「cell-a 原流量 + 自身流量」（接管场景）；不接管时保持原值

# ③ 错误是否「明确」而不是「静默」
kubectl logs -n cell-a deploy/app --since=5m | grep -c "cell_unavailable"
# 期望：> 0，且对应 HTTP 503 + Retry-After
```

### 4.3 恢复与校验

```shell
# 恢复入口
kubectl delete networkpolicy deny-ingress-cell-a -n cell-a

# 恢复后必须校验：断流期间是否丢了写
psql "$DSN" -c "SELECT count(*) FROM cards WHERE updated_at > now() - interval '20 minutes';"
# 与客户端记录的「成功写入条数」比对；不相等即存在静默丢失
```

## 五、数据校验：演练的「最后一公里」

L4/L5 演练结束后，必须跑三层校验（与[冲突裁决](../Conflict/index.md)第 5 节同口径）：

| 层 | 命令 | 期望 |
| --- | --- | --- |
| L1 行数 | `SELECT count(*) FROM <表>` 两侧对比 | 差值 = 断流期间写入量（应为已知值） |
| L2 哈希 | 分段 `md5(string_agg(... ORDER BY pk))` | 两侧相同 |
| L3 不变量 | `qty = 期初 + sum(delta)` 一类业务等式 | 0 行违例 |

::: danger 「差值是已知的」才是通过
演练期间一定有写入差异（断流时的写丢了或有补偿）。**通过的标准不是「差值为 0」，而是「差值等于预先算出的期望值」**。差值为 0 反而可能说明「演练期间根本没有真实写入」——那是一条假通过。
:::

## 六、演练记录表（可抄）

```text
# 多活切换演练记录

演练编号：DR-YYYYMMDD-01
级别：L3 / L4 / L5
范围：单元 A → 单元 B（租户 1001~2500）

## 一、前置
- [ ] 归属表已备份，`epoch` 已记录（值：______）
- [ ] 目标单元预热完成（CPU ___%，连接池 ___%）
- [ ] 反向同步通道已建立（延迟 ___ s）
- [ ] 值班与业务方已通知（时间：______）

## 二、时间线（精确到秒）
| 时刻 | 动作 | 观测读数 |
| --- | --- | --- |
| t0 | 开始注入 | 旧单元 QPS ____ |
| t1 | 旧单元 QPS 归零 | 耗时 ____ s |
| t2 | 错误率峰值 | ____%（类型：____） |
| t3 | 开始回切 | 追平延迟 ____ s |
| t4 | 全量恢复 | 总耗时 ____ s |

## 三、判据核对
| 判据 | 期望 | 实测 | 结论 |
| --- | --- | --- | --- |
| 旧单元 QPS | 0 | ____ | ✅/❌ |
| 新单元 5xx | < 0.1% | ____ | ✅/❌ |
| 归属用户写成功率 | > 99% | ____ | ✅/❌ |
| 不变量校验违例 | 0 行 | ____ | ✅/❌ |
| 数据差异 | = 期望值 ____ | ____ | ✅/❌ |

## 四、结论
- 实际 RTO：____（承诺：____）
- 未通过项与处置：____
- 下次演练需调整：____
```

::: tip 记录表的价值在「时间线」那一栏
「实际 RTO 180 秒」这个数字没有信息量；「t0→t1 用了 95 秒，因为 DNS TTL 是 45 秒而客户端缓存又加了 50 秒」才有。**时间线是唯一能把 RTO 拆回三段的东西。**
:::

## 七、频率建议

| 级别 | 频率 | 谁组织 |
| --- | --- | --- |
| L1 桌面推演 | 每季度 | 值班负责人 |
| L2 单组件 | 每月 | DBA / SRE |
| L3 单元级 | 每月（可与 L2 合并） | SRE |
| L4 站点级 | 每半年 | 架构 + SRE |
| L5 全链路 + 校验 | 每年至少一次（大促前必做） | 跨团队 |

## 八、验证方式

```shell
# ① 演练是否真的注入过（看注入期间的日志痕迹）
kubectl logs -n cell-a deploy/app --since=24h | grep -c "cell_unavailable\|connection refused"
# 期望：> 0。为 0 说明注入没生效，演练是假的

# ② 旧单元 QPS 是否真的归零（这是「流量真的切走」的唯一证据）
curl -s "http://gateway/admin/route-stats" | jq '.cells'
# 期望：cell-a 的 qps 为 0（不是 0.1）

# ③ 演练后不变量校验
psql "$DSN" -c "SELECT count(*) FROM qty_sum s LEFT JOIN evt_all e USING (sku)
  GROUP BY s.sku, s.qty HAVING s.qty <> 1000 + COALESCE(sum(e.delta),0);"
# 期望：0 行

# ④ 演练记录是否含三要素
grep -c "观测点\|期望值\|持续时间" docs/ops/drill/DR-*.md
# 期望：每条记录三项都出现；缺一项即不可证伪
```

## 九、判据族 `MAD`

| 判据 | 内容 | 怎么验证 |
| --- | --- | --- |
| `MAD-A` | 每条演练必须有观测点、期望值、持续时间三要素 | 记录表里三项齐全，缺一不算通过 |
| `MAD-B` | 至少做到 L3，才可宣称「单元级可切」 | 演练记录里有 L3 及以上的条目与读数 |
| `MAD-C` | 「流量已切走」的证据是旧单元 QPS = 0，不是配置状态 | 记录里有 `route-stats` 的读数截取 |
| `MAD-D` | 演练必须包含一次真实写入并读回 | 记录里有「写一条并读回成功」的条目 |
| `MAD-E` | L4/L5 必须跑三层数据校验，且差异等于期望值 | 记录里有 L1/L2/L3 三层读数与期望值对比 |
| `MAD-F` | 演练必须记录时间线，能把 RTO 拆回三段 | 记录表有 t0~t4 的时刻与读数 |
| `MAD-G` | 演练频率必须写进制度并有人负责 | 制度文档列出五级频率与组织者 |
| `MAD-H` | 未通过项必须有处置与复查时间 | 记录第四节有「未通过项 + 处置 + 复查日期」 |
