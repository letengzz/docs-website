# 性能与成本

CDN 与边缘计算的「值不值」最终落在两个数上：**用户侧的第 1 个字节什么时候到**、**这个月的账单是多少**。这两件事看起来一个管性能一个管钱，但在边缘这一层它们是**同一件事**：它们都由「请求数 × 响应体大小 × 走没走到边缘」决定。

一句话定位：**把 TTFB 拆成可归因的几段、把账单拆成可归因的几个维度，然后只优化那个既影响体验又影响钱的变量。** 适用于要给 CDN 定预算、要解释「为什么接了 CDN 还是慢」、要做降本的人。

## 一、TTFB 拆解：把「慢」拆到能追责的粒度

用户感受到的「快不快」，在边缘链路上由五段构成：

| 段 | 内容 | 经验量级 | 谁能改 |
| --- | --- | --- | --- |
| ① DNS | 解析到就近节点 | 几十毫秒（未缓存时更高） | TTL、调度策略、解析器 |
| ② TCP + TLS | 握手（含 TLS 1.3 的 1-RTT/0-RTT） | 一个到两个 RTT | 协议版本、会话复用、就近程度 |
| ③ 边缘处理 | WAF 判定 + 边缘函数 | 通常 < 10 ms；重逻辑可能几十毫秒 | 你的规则与代码 |
| ④ 缓存查找 | 本地查找（命中时就在这里结束） | 亚毫秒到几毫秒 | 缓存键与命中率 |
| ⑤ 回源 | 只有未命中才发生 | 跨城 RTT + 源站处理时间 | TTL、中间层、源站性能 |

**只有第 ⑤ 段属于「源站问题」。** 把五段混成一个 TTFB 去优化，最常见的后果是「扩了源站，用户还是慢」——因为瓶颈在第 ② 或第 ④ 段。

::: tip 一个立刻可用的判据
比较两次请求：**命中的那次**与**未命中的那次**（可以用带随机查询参数强制未命中）。两者的差值就是「回源成本」。如果这个差值很小，说明你的瓶颈不在回源，那么调 TTL、加中间层的收益都会很有限。
:::

## 二、计费维度：先知道自己被怎么收钱

四个维度，不同平台收其中一两个：

| 维度 | 什么时候被计 | 缓存命中是否免费 | 备注 |
| --- | --- | --- | --- |
| **请求数** | 每次到达边缘的请求 | **否，命中照样计** | 静态资源请求通常被单独优待（有的平台免费且不限） |
| **出网流量** | 从边缘发往用户的字节 | 否 | 大文件业务的成本主项；有的平台完全不计（如 Cloudflare） |
| **回源流量** | 边缘到源站的字节 | 与命中率直接相关 | 有的平台对「从自家对象存储出网」免费 |
| **CPU 时间** | 边缘函数实际执行代码的时间 | 命中且未执行函数时不计 | 只算执行，不等 I/O |
| **存储与额外能力** | KV 读写、图片处理、日志投递 | —— | 量小时可忽略，量大时是第二成本项 |

::: danger 不要用「接了 CDN 之后源站流量下降」推导「总成本下降」
源站流量下降是**确定的**，总成本不一定：如果计费维度包含「出网流量」或「请求数」，那么用户量的增长会同时推高这两项。**判断降本是否成立，必须用「改造前后的总账单」比，而不是用「源站带宽」比。**
:::

## 三、一个可复用的成本算例

用量假设（把它换成你自己的数）：

- 每月 **5000 万次请求**
- 缓存命中率 **92%**
- 命中响应平均 **180 KB**、回源响应平均 **240 KB**
- 边缘函数覆盖 **30%** 的请求、平均 **6 ms CPU**

先算可观测的量：

| 量 | 计算 | 结果 |
| --- | --- | --- |
| 命中请求 | 5000 万 × 92% | 4600 万 |
| 回源请求 | 5000 万 × 8% | **400 万（8%）** |
| 回源流量 | 400 万 × 240 KB | **约 915 GB** |
| 总出网流量 | 5000 万 × 180 KB = 9,000,000,000 KB | **8583.1 GB = 8.38 TiB** |
| 边缘函数调用 | 5000 万 × 30% | 1500 万次 |
| 边缘函数 CPU | 1500 万 × 6 ms | 9000 万 CPU 毫秒 |

再套两种典型计费口径（数字为本机实算，价格为 2026-10 官方页口径）：

| 口径 | 计算 | 月成本 |
| --- | --- | --- |
| **A · 按请求 + CPU 计费，出网不计费** | 请求 `(5000万 − 1000万) ÷ 100万 × $0.30 = $12.00`；CPU `(9000万 − 3000万) ÷ 100万 × $0.02 = $1.20`；订阅 $5.00 | **$18.20**，即每千次请求 **$0.000364** |
| **B · 按流量 + 请求计费** | 流量 `8583 GB × ¥0.31 = ¥2661`；请求 `5000 万 ÷ 100 万 × ¥5 = ¥250` | **¥2911 ≈ $410**（按 7.1 折算） |

::: warning 关于上表的两个诚实说明
1. **口径 B 的单位价取自第三方对比文中给出的「国内阶梯起步价 0.31 元/GB」与「5 元/百万次请求」**，仅用于演示「计费维度不同会带来量级差异」，**任何预算必须以厂商官方计价页当场核对为准**。
2. 两种口径相差约 **22.5 倍**，差异的主体不是「谁更便宜」，而是**出网流量是否计费**。选型时先问这一条，再谈价格。
:::

## 四、降本杠杆：按量级排序

同一份用量，四个杠杆的收益差距很大：

| 顺序 | 手段 | 本算例的收益 | 代价 |
| --- | --- | --- | --- |
| ① | **减小响应体**（压缩、现代图片格式、按需加载） | 体积 −30% ≈ 省 **¥798/月** | 需要改构建与图片管线 |
| ② | 大文件走专门的分发通道（视频、安装包） | 视占比而定，通常量级最大 | 多一套链路 |
| ③ | **提高命中率**（92% → 96%） | 只省回源流量约 **458 GB ≈ ¥142** | 需要规范缓存键、治理参数 |
| ④ | 减少边缘函数调用（不改变响应体的逻辑下移到规则） | 省 CPU 与请求两项 | 需要重构规则 |

上表最关键的一行是 ③：**在「按流量计费」的口径下，提高命中率的收益远小于直觉**——因为用户侧的流量一分也不会少。而在「按请求计费」的口径下，命中率同样不影响请求数计费。**命中率真正的收益是「源站压力」与「回源延迟」，而不是账单**（个别平台对回源流量单独计费时例外）。

::: tip 所以「先优化哪个」有明确答案
**先减响应体，再减请求数，最后才谈命中率。** 这条顺序在两种计费口径下都成立（只有当平台对回源流量单独计价、且单价与出网相近时，命中率才会挤进前两名）。
:::

## 五、单位成本口径：让成本可比较

不要用「本月花了多少钱」比较不同方案，用**单位成本**：

| 口径 | 公式 | 适合比较 |
| --- | --- | --- |
| **每千次请求成本** | 月成本 ÷ (请求数 ÷ 1000) | 请求密集、响应小的接口类业务 |
| **每 GB 交付成本** | 月成本 ÷ 交付流量（GB） | 大文件、视频类业务 |
| **每千次成功交互成本** | 月成本 ÷ (成功的业务交互数 ÷ 1000) | 与业务价值挂钩；**注意「成功」要排除 4xx/5xx 与机器人流量** |

第三个口径最有价值也最容易被算错：如果分母用的是「全部请求」，那么爬虫量与攻击量会把单位成本人为拉低，看起来「更便宜」，实际是业务没增长而流量在涨。

## 六、必须监控的五个指标

| 指标 | 阈值示例 | 它回答的问题 |
| --- | --- | --- |
| 静态命中率 | < 80% 告警 | 缓存策略是否还有效 |
| 回源比 | > 20% 告警 | 源站是否承受了不该承受的压力 |
| 边缘错误率 | > 0.1% 告警 | 边缘函数与配置是否引入了新故障 |
| 边缘函数 CPU 超限次数 | > 0 告警 | 逻辑是否已接近配额边界 |
| 单位成本（每千次） | 环比上升 > 20% 告警 | 成本是否在失控（与发布、爬虫、参数打散相关） |

## 七、易错点与最佳实践

::: danger 六个坑
1. **把「命中率」当成唯一 KPI**：见第四节——在多数计费口径下它不省钱，只省源站压力。正确做法：把「命中率」与「单位成本」并列看。
2. **用十进制与二进制单位混算预算**：8583.1 GB（十进制）与 8.38 TiB 是同一个量的两种写法，按哪个算差约 7%。正确做法是**在文档里写死一个口径**。
3. **忽略缓存命中仍计请求数**：以为「命中就是免费」。正确做法：把请求数计费写进容量模型，尤其是「页面里有几百个静态资源」的站点。
4. **只看平均值**：促销日与平时的 P95 差好几倍，平均值会把峰值成本藏起来。正确做法：看时间序列，并按路径下钻。
5. **把爬虫流量算进业务单位成本**：会让单位成本持续下降，掩盖真实问题。正确做法：分母排除机器人与失败请求。
6. **没有预算护栏**：突发流量（含攻击）能在一天内吃掉一个月预算。正确做法：设置用量告警与用量上限（很多平台支持）。
:::

::: tip 三条实践
- **每月做一次「单位成本复盘」**：不是看总花费，而是看「每千次成功交互成本」的环比，并解释变化来自哪一类流量。
- **把「响应体预算」写进前端规范**：单页首屏资源总量、单张图片上限、字体文件上限——这是唯一直击账单的规范。
- **给边缘函数设 CPU 预算并巡检**：一旦有函数长期贴住限额，它的下一次改动就是一次事故。
:::

## 八、验证方式

```shell
# 1) 比较「命中」与「未命中」的 TTFB 差（回源成本）
curl -s -o /dev/null -w "hit  ttfb=%{time_starttransfer}\n" https://www.example.com/a.js
curl -s -o /dev/null -w "miss ttfb=%{time_starttransfer}\n" "https://www.example.com/a.js?nocache=$RANDOM"

# 2) 量一次响应体大小，作为「响应体预算」的基线
curl -sI https://www.example.com/ | grep -i content-length
curl -s -o /dev/null -w "size=%{size_download}\n" https://www.example.com/

# 3) 统计首屏静态资源请求数（决定请求数计费的分母）
curl -s https://www.example.com/ | grep -oE 'src="[^"]+"|href="[^"]+"' | wc -l

# 4) 检查是否被追踪参数打散（未命中率异常高的常见原因）
for u in "a.js?utm_source=x" "a.js?utm_source=y"; do
  curl -sI "https://www.example.com/$u" | grep -Ei 'age|x-cache|cache-status'
done

# 5) 用压测工具估一次「单位成本」的量级（把 QPS 换算成月请求数后套第三节公式）
#    只在小流量下做，避免把自己打上用量告警
```

| 观察 | 结论 |
| --- | --- |
| 第 1 步两次差很小 | 瓶颈不在回源，优先查握手与缓存键 |
| 第 2 步响应体远大于预期 | 成本主项是体积，先做压缩与图片治理 |
| 第 3 步资源数非常多 | 请求数计费口径下的成本主项是请求数，考虑合并与内联 |
| 第 4 步两次都未命中 | 参数打散：命中率与成本同时受损，优先修 |
