# 常见问题与最佳实践

![边缘问题分诊表：先按现象定位到页](../assets/ec-faq-triage.svg)

这一页是本专题的收口。前面八页各自讲一层，这一页回答一个问题：**当现象摆在你面前、但你还不知道它属于哪一层时，先做什么。** 顺序是先分诊（第一节）、再问答（第二节）、再排误区（第三节）、最后拿清单和术语收尾（第四~六节）。

::: tip 一句话理解
边缘链路上的绝大多数「玄学问题」，本质都是**信息不对称**：你看不到那台机器，只能看到自己造出来的那几个观测点。所以本页所有答案都回到同一个动作——**先造出一个能把「命中/未命中」「边缘/源站」区分开的观测点，再谈修。** 没有观测点时的任何「我改好了」，都只是猜测。
:::

## 一、分诊表：从现象到页

下表按「现象 → 先跑什么 → 翻哪页 → 最常见真因」组织。**先按这张表走完一圈，再去翻具体页**，能省掉一半排查时间。

| 现象 | 先跑什么 | 翻哪页 | 最常见真因（按概率排序） |
| --- | --- | --- | --- |
| 改了配置/内容，线上没变化 | 连续请求两次，看 `Age` 是否增长、`Cache-Status` 是否 `hit` | [缓存策略](../CacheStrategy/index.md) | ① 缓存键把参数带进去了，你以为改的是同一个对象 ② 平台侧另有 TTL 覆盖了源站头 ③ 命中的是上一级（L2/浏览器）缓存 |

| 命中率突然掉 | 对比掉头时间点与发布/配置变更记录 | [缓存策略](../CacheStrategy/index.md) | ① 换了 URL 规则（带 hash 或不带 hash）② 新上了追踪参数 ③ 某类响应头从 `public` 改成了 `private` |
| 账单比预期高 | 先看**计费维度**（流量 / 请求数 / CPU 时间），再看各自占比 | [性能与成本](../PerformanceCost/index.md) | ① 小文件多导致请求数费用占比超过流量费 ② 边缘函数 CPU 超时重试 ③ 未命中导致回源流量被双向计费 |

| 边缘读到的数据是旧的 | 在响应里回显读到的版本号/时间戳 | [边缘数据](../EdgeData/index.md) | ① 读写走了不同的副本 ② KV 的写是**最终一致**的，传播有窗口 ③ 缓存层把上一次的读取结果也缓存了 |
| 证书告警 / 浏览器报不安全 | `openssl s_client -servername` 看证书链与有效期 | [边缘安全](../Security/index.md) | ① 边缘证书自动续期失败（DNS 验证记录被改） ② 源站回源证书（origin certificate）过期 ③ 混用了裸域与 `www` 的证书 |
| 静态资源 403 / 签名失效 | 比对签名串的**全部参与字段**与 UTC 时间 | [边缘安全](../Security/index.md) | ① 时间戳时区错（用了本地时间） ② 签名 URL 里带了会被缓存键忽略的字段 ③ 密钥轮换后旧链接未过期策略 |
| 要迁站，不知道从哪开始 | 先做「路径四分法」，只迁第一类 | [实战](../Practice/index.md) | ① 一上来就全站切，把带身份路径也缓存了 ② 没有接入前基线，事后无法证明收益 |
| 担心 CDN 挂了怎么办 | 做一次「关掉边缘」的推演 | [总览](../Overview/index.md) | ① 把 CDN 当成容灾（它防距离，不防源站故障） ② 源站容量按「有边缘时的 10%」规划，边缘一挂必崩 |

::: warning 分诊的前提
分诊表能用的前提是**你手上有区分能力的数据**。至少要能回答三个问题：请求最终命中了没（`Age` / `Cache-Status`）、回源了吗（源站 access log 或回源流量指标）、边缘逻辑跑了吗（边缘侧日志或自埋计数器）。三个都答不上来时，**第一件事不是修，是先把观测点加上**——见 [性能与成本 · 必须监控的五个指标](../PerformanceCost/index.md)。
:::

## 二、高频十二问

### Q1：有了 CDN，还需要自己做缓存吗？

需要，两者不在同一层。CDN 是**中间跳**，浏览器缓存是**最后一跳**，反向代理缓存是**中间的另一跳**。同一条响应头在不同跳上的含义不同：`s-maxage` 只约束共享缓存（边缘、代理），`max-age` 约束浏览器。多层叠加时，**最终生效的时效是各级里最早到期的那个**，不是最长的那一个。设计时先画出「用户 → 边缘 → 代理 → 应用」四跳，再逐跳决定存多久。

### Q2：把 `Cache-Control: no-cache` 当成「不缓存」用，为什么线上还出了问题？

因为 `no-cache` 的语义是**「可以存，但每次用前必须回源验证」**，不是「不存」。真正的不存是 `no-store`。在边缘这一层，`no-cache` 仍然会让内容落到节点上，只是每次请求都发一次条件请求——它降低不了源站压力，也降低不了存储占用，只增加了往返。要立刻止血，写 `no-store`；要避免陈旧内容，用短 `max-age` 配 `stale-while-revalidate`。详见 [缓存策略](../CacheStrategy/index.md) 的对照框。

### Q3：`stale-while-revalidate` 是不是等于「用户一定看到旧内容」？

不是。它的语义是：在 `max-age` 过期后的这段窗口内，**先把旧副本返回给用户，同时在后台发起回源刷新**。所以窗口内的用户看到的是「上一次的副本」，但窗口结束后会切到新副本。它的价值在于**把回源的等待从用户身上挪走**——前提是业务能容忍一个窗口的陈旧。对价格、库存、余额这类不能容忍的，不要用它，改用主动失效。

### Q4：命中率低，应该先做预热还是先查缓存键？

先查键。预热解决的是「冷启动期的长尾请求」，缓存键解决的是「同一份内容被拆成很多份存」。后者是**持续性的浪费**，前者是**一次性的**。经验上，命中率异常时按这个顺序排查：① 键里是否混入了无意义参数（`utm_*`、`gclid`、毫秒时间戳）② `Vary` 是否声明了高基数的头（`User-Agent` 几乎等于按会话缓存）③ `Authorization`/`Cookie` 是否让所有请求都变成私有。这三条通常能解释掉绝大多数异常。

### Q5：边缘函数能不能直接查数据库？

个别平台有边缘数据库产品，但通用答案是**不能，或代价很高**。原因不是性能而是**拓扑**：边缘节点在全球几百个点，数据库在你的机房里，跨点查库等于把「就近访问」又变回「远距离访问」，还额外引入了连接数与超时的不确定性。可行替代是三种：把结果**预生成**推到边缘、用边缘 KV **读**（接受最终一致）、或者**回源**去查（用边缘做鉴权与路由，不做数据面）。

### Q6：边缘 KV 的「最终一致」到底意味着多久？

取决于平台，但工程上要按「**不能假设秒级**」来设计。它的传播路径是「写入 → 主区域 → 各边缘区域」，跨区域必然有窗口。所以正确的做法是给业务定一个可接受的陈旧上限（比如 30 秒），并把**版本号放进值的载荷里**，在响应里回显，这样出问题时你能确切知道边缘拿到的是哪一版，而不是靠猜。绝不能把边缘 KV 当成「强一致的共享变量」用。

### Q7：`Vary` 该写吗？

该写，但只写**真正影响响应体、且基数低**的头。`Vary: Accept-Encoding` 是标准且划算的（压缩与不压缩是两份内容）。`Vary: User-Agent` 几乎一定是错的——UA 基数极高，等于把缓存打散成会话级。如果确实需要按设备类型区分，就在边缘**归一化**成 `mobile`/`desktop` 两个值，再按归一化后的值分键。

### Q8：源站 IP 已经隐藏了，还需要回源鉴权吗？

需要。DNS 上把源站指向 CDN 只是**降低暴露面**，不是访问控制——域名史、证书透明度日志、历史 DNS 记录都能反查出来。真正的回源保护是：源站只接受边缘回源（来源 IP 白名单或边缘注入的共享密钥头），并且**验证这个头是边缘注入的、不是客户端伪造的**。凡是直接信任 `X-Forwarded-For` 的源站，等于没有保护。

### Q9：签名 URL 和 Referer 防盗链，用哪个？

用签名。Referer 是客户端可控的头，伪造成本极低，只能挡住「顺手引用」，挡不住任何有意的盗链。签名的正确做法是：**明确列出所有参与签名的字段**（路径、过期时间、客户端标识），用 UTC 时间戳，密钥存在密钥管理里而不是配置文件里，并给密钥轮换留出重叠期。另外要注意签名参数本身会不会被缓存键吞掉——那会让不同签名的请求命中同一份副本。

### Q10：TTFB 已经从 800 ms 降到 120 ms，为什么用户说还是慢？

因为 TTFB 只覆盖了链路的前半段。用户感知的完整时间还包括：HTML 下载、首屏关键资源（CSS/字体/首屏图）的**串行发现与下载**、JavaScript 解析与执行、以及渲染。边缘能把前三段压下去，但**压不掉解析与执行**。做法是把 TTFB 与「 Largest Contentful Paint 」分开量，分别归因：TTFB 慢查边缘与回源，LCP 慢查资源体积、加载顺序与阻塞脚本。两者相乘而不是互替。

### Q11：接入 CDN 之后，日志去哪了？

去了边缘厂商那边，这是接入的**真正代价**。三个应对动作是必做的：① 确认厂商提供**实时日志投递**到你的对象存储/日志服务，并开启；② 在边缘**注入一个每请求唯一标识**（如 request id），让边缘日志和源站日志能对上；③ 明确日志的**保留期与取回延迟**——很多平台是分钟级甚至小时级延迟，这直接决定你的故障响应能做到多快。

### Q12：什么时候「不应该」上边缘？

五种情况先别上：① 业务只有单一区域用户、且延迟已达标（上边缘只增加一层故障域）；② 内容几乎全是带身份、高频变化的（命中率会趋近零，只剩转发价值）；③ 团队还没有任何边缘侧观测手段（接了也证明不了什么）；④ 法规或合规要求数据不得出境/不得经第三方（边缘节点是第三方基础设施）；⑤ 当前源站是唯一能兜住峰值的地方，而边缘被当成容灾（见 [总览](../Overview/index.md) 的「先别上」判据）。判断标准不是「别人都在用」，而是**「接上之后我能测出什么变化」**。

## 三、八个常见误区

::: danger 误区一：把 CDN 当容灾
CDN 有几百个节点，看起来「很可靠」，但它的作用是**缩短距离**。你的源站挂掉时，所有未命中的请求依然会打到源站——**边缘不会替你算业务逻辑**。把源站容量按「有 CDN 时的 10%」规划，是这类事故最常见的成因。正确做法：定期做「关掉边缘会怎样」的推演。
:::

::: danger 误区二：把 CDN 当对象存储
边缘缓存的对象有大小上限（不同平台从 512 MB 到 5 GB 不等），且**随时可能被逐出**——缓存不是存储，没有持久性承诺。用它存视频原片、安装包、用户上传件，会在某个流量高峰后突然大面积回源。大文件要么回源，要么用真正的对象存储 + 边缘分发。
:::

::: danger 误区三：认为「配置改了就生效」
边缘配置的生效是**分布式的**：要传播到几百个节点，必然有窗口；再加上已缓存内容的失效本身也有传播时间。所以「改完立刻验证」常常验的是**没更新的那个节点**。正确做法是：改完记下时间点，等一个明确的传播窗口，再在**多地域**（至少两个）各验一次，并观察命中率的台阶式变化。
:::

::: danger 误区四：边缘函数当普通服务器写
本地跑在 Node 上毫秒级的代码，在边缘常见的是「超 CPU 预算」「子请求超限」「循环超上限」。这不是平台小气，而是**定价模型的必然结果**：边缘按廉价并发卖，就必须限制单请求的算力。写法上要遵守：把重活挪回源站、依赖尽量小、循环必须有硬上限、每个子请求都要有超时。见 [边缘计算](../EdgeCompute/index.md) 的三类失败代码。
:::

::: danger 误区五：用厂商私有头做判据
`X-Cache`、`X-Served-By` 这类头很好用，但它们是**厂商私有的**，换一家就没有了。做判据时优先用标准：RFC 9211 的 `Cache-Status` 表达「命中与否、命中在哪层」，`Age` 表达「副本存了多久」。标准头能让你把诊断脚本沉淀下来，换平台时只改平台特有的那部分。
:::

::: danger 误区六：只看平均命中率
平均命中率会被热点内容拉高。真实体验由**长尾**决定：首页命中 99%，但某个用户恰好访问的是冷门路径，体验依然很差。要看**分位**（P50/P95 回源时间）和**分类命中率**（静态 / HTML / API 分开看），而不是一个笼统的总数。
:::

::: danger 误区七：源站信任客户端传来的 `X-Forwarded-For`
这是最危险的一条。客户端可以随便伪造这个头。如果源站用它做限流、审计或权限判断，等于把控制权交给了攻击者。正确做法：源站只信任边缘注入的**单一可信头**，并且用边缘与源站之间的**共享密钥**验证这个头确实来自边缘。
:::

::: danger 误区八：没有「回源」的预算意识
未命中意味着一次回源：既是延迟成本，也是流量成本（很多平台回源流量与出网流量分别计费）。所以「命中率」不是性能指标，是**性能与成本共同的指标**。设计缓存策略时要一并估算：命中率从 92% 提到 96%，能省下多少回源流量、折多少钱。具体算法见 [性能与成本](../PerformanceCost/index.md) 的算例。
:::

## 四、上线自查清单

清单按「接入前 / 接入中 / 上线前 / 上线后」四段组织，前两段对开发，后两段对运维与负责人。**能全答上来再开生产流量**。

### 4.1 接入前（设计与基线）

| # | 检查项 | 通过标准 |
| --- | --- | --- |
| P1 | 路径已按「静态产物 / 入口 HTML / 公开接口 / 带身份接口」四类划分 | 每一类都有明确的缓存结论（缓存多久 / 不缓存 / 只转发） |
| P2 | 已量过接入前的基线 | 至少有一组 TTFB 与出口带宽数字，作为事后对比依据 |
| P3 | 已明确「哪些路径绝不能共享缓存」 | 带 `Authorization`、带租户标识、返回个人数据的路径都列了出来 |
| P4 | 已确认用的协议能力够用 | 需要 WebSocket / TCP 的业务，已确认所选平台支持（部分平台仅 HTTPS） |
| P5 | 已估算成本会落在哪个维度 | 知道自己是「流量为主」还是「请求数为主」，并有量级估算 |

### 4.2 接入中（配置）

| # | 检查项 | 通过标准 |
| --- | --- | --- |
| C1 | 缓存键已显式声明白名单 | 默认不把全部查询参数纳入键；无意义参数（`utm_*` 等）已被剥离 |
| C2 | `Vary` 只声明低基数的头 | 没有出现 `Vary: User-Agent` 这类会打散缓存的写法 |
| C3 | 时效策略分层且已落表 | 有单一事实来源（配置文件或策略表），不靠控制台手点 |
| C4 | 失效流程已写成可执行动作 | 明确「改完内容后执行什么、多久生效、怎么确认」 |
| C5 | 边缘逻辑有限额意识 | CPU、子请求、内存、循环数都对照过平台限额，且留有余量 |
| C6 | 每个边缘函数都有降级路径 | 边缘报错时是回源还是返回 5xx，是**决定过的**而不是碰运气 |

### 4.3 上线前（安全与可观测）

| # | 检查项 | 通过标准 |
| --- | --- | --- |
| S1 | 证书续期路径明确 | 知道谁在续、用哪种验证方式、失败了谁会收到告警 |
| S2 | 源站不是裸奔的 | 源站只接受边缘回源，且回源鉴权不可被客户端伪造 |
| S3 | 命中有观测能力 | 能看到命中率 / 回源比，且静态、HTML、API 分开看 |
| S4 | 边缘错误有告警 | 边缘函数错误率与 CPU 超限都有阈值告警 |
| S5 | 日志可投递且可取回 | 已开启日志投递，且知道取回延迟与保留期 |
| S6 | 有跨点验证手段 | 能从至少两个地域各验一次「内容确实换了」 |
| S7 | 有 kill switch | 能在不改源站的前提下，把一个路径从缓存里摘出去 |

### 4.4 上线后（验证与复盘口径）

| # | 检查项 | 通过标准 |
| --- | --- | --- |
| V1 | 命中率达标 | 各类路径的命中率与设计目标一致；静态资源通常应显著高于 HTML |
| V2 | 回源量下降符合预期 | 回源请求数与回源流量都按预期下降，且构成本身合理（长尾占多数） |
| V3 | TTFB 分层改善 | 命中与未命中的 TTFB 差（即回源成本）被量了出来 |
| V4 | 成本口径可核对 | 账单能对上「流量 × 单价 + 请求数 × 单价（+ CPU 时间 × 单价）」的拆解 |
| V5 | 做过「关掉边缘」推演 | 知道边缘不可用时源站能撑多少，以及降级动作是什么 |

## 五、一页速查：五条命令

诊断时最常用的五个动作。**注意**：这些命令的结论必须结合响应头一起读，单看一个数字容易误判。

```bash [诊断五连：命中、时效、回源、TTFB、证书]
# 1) 连续请求两次，比较 Age 是否增长 —— 判断「是否命中、副本多大年纪」
curl -sI https://cdn.example.com/index.html | grep -iE '^(age|cache-status|x-cache|date)'

# 2) 看标准化的命中信息（RFC 9211）—— 命中在哪一层
curl -sI https://cdn.example.com/index.html | grep -i '^cache-status'

# 3) 对比「走边缘」与「直连源站」的 TTFB —— 量出回源成本
curl -s -o /dev/null -w 'edge  ttfb=%{time_starttransfer}s\n' https://cdn.example.com/index.html
curl -s -o /dev/null -w 'origin ttfb=%{time_starttransfer}s\n' https://origin.example.com/index.html

# 4) 确认带身份路径没有被缓存 —— 期望 Cache-Status 里没有 hit
curl -sI -H 'Authorization: Bearer test' https://cdn.example.com/api/me | grep -iE '^(cache-status|age)'

# 5) 证书链与有效期 —— 期望 notAfter 在告警覆盖范围内、issuer 符合预期
echo | openssl s_client -connect cdn.example.com:443 -servername cdn.example.com 2>/dev/null \
  | openssl x509 -noout -subject -issuer -dates
```

::: warning 命令的读法与陷阱
① `Age` 是**副本在边缘已存放的秒数**，不是剩余时长；两次请求的 `Age` 增长说明命中了同一个副本。② `Cache-Status` 是标准头，比 `X-Cache` 更值得作为长期判据。③ 第 3 条里的「直连源站」必须真的绕过边缘（用源站 IP 或独立域名），否则量到的是同一条链路。④ 第 4 条若无 `Authorization` 也会返回，所以必须**带与不带各做一次**对比着看。⑤ 第 5 条在 macOS 上 `openssl` 是 LibreSSL，输出格式与 OpenSSL 略有差异，缺 `-dates` 时改用 `-enddate`。
:::

## 六、术语表

边缘领域最容易望文生义的十几个词。**统一口径是后面所有讨论的前提**。

| 术语 | 一句话定义 | 最容易错的理解 |
| --- | --- | --- |
| 源站（Origin） | 持有权威内容的你的服务 | 以为它「有了 CDN 就不重要」——它仍承担全部未命中与全部写 |
| 边缘节点（PoP / Edge） | 离用户近、能缓存与执行代码的接入点 | 把「节点多」当性能——关键是那个节点有没有你要的内容 |
| 回源（Origin Fetch） | 边缘没有可用副本时向源站取内容 | 以为回源只有「未命中」一种原因（另有校验、失效、过期） |
| 命中率（Hit Ratio） | 命中缓存的请求占全部请求的比例 | 只看平均值——长尾与分位才决定真实体验 |
| 回源比（Origin Fetch Ratio） | 回源请求占全部请求的比例 | 把「回源比低」等同于「没问题」——静态与动态要分开看 |
| 缓存键（Cache Key） | 判定「是不是同一份内容」的输入集合 | 以为默认键只有 URL——实际上查询参数、`Vary` 头都会进门 |
| `Age` | 副本在共享缓存中已存在的秒数 | 当成剩余时间 |
| `s-maxage` | 只约束**共享缓存**（边缘、代理）的时效 | 与 `max-age` 混用同一层语义 |
| `stale-while-revalidate` | 过期后窗口内先给旧副本、后台刷新的扩展 | 以为用户一定看到旧内容（只持续一个窗口） |
| `no-cache` | 可以存，但每次使用前必须回源验证 | 当成「不缓存」（那是 `no-store`） |
| `no-store` | 任何缓存都不得存储 | 拿来「临时调小缓存」——它是彻底不存，代价是零命中 |
| 边缘函数 | 在边缘节点上按请求执行的短生命周期代码 | 当成「小服务器」——受 CPU/内存/子请求硬限额约束 |
| 边缘 KV | 边缘侧的最终一致键值存储 | 当成强一致的共享变量 |
| `Vary` | 声明响应体随哪些请求头变化 | 写成 `Vary: User-Agent`，把缓存打散成会话级 |
| 签名 URL | 携带时效与权限签名的受保护资源地址 | 只用 Referer 防盗链（可伪造） |
| 预热（Preheat） | 主动把内容推到边缘，避免首批用户踩冷启动 | 当成提升长期命中率的手段（它只解决冷启动） |
| 失效 / 刷新（Purge / Invalidate） | 主动让边缘上的副本作废 | 以为「立刻、全局、同时」生效（有传播窗口） |
| `Cache-Status` | RFC 9211 定义的标准命中状态响应头 | 继续依赖厂商私有头作为长期判据 |
| 边缘侧最终一致 | 写入后各节点在窗口内陆续可见 | 按「秒级」假设设计——应按「不保证秒级」设计 |
| 回源鉴权 | 源站验证请求确实来自你的边缘 | 只靠「源站域名不公开」来保护（等于没保护） |

## 七、最佳实践总览（十条）

把前面八页反复出现的纪律浓缩成十条，可以直接当评审清单用：

1. **先造观测点，再做优化。** 没有命中率、回源比、TTFB 分层数据的接入，等于把成本与体验一起交给运气。
2. **缓存键显式白名单，不显式声明的一律不进键。** 无意义参数剥离是提升命中率性价比最高的一步。
3. **时效策略落表，落进版本管理。** 控制台手点的配置无法评审、无法回溯、无法复现。
4. **带身份的路径默认不缓存。** 需要加速就用转发，不要用缓存；这一条越界一次就可能是数据泄露。
5. **限额是可行性判据，不是优化项。** 写边缘代码前先看 CPU、内存、子请求、循环数四个数。
6. **每个边缘逻辑都要有降级路径。** 边缘报错时回源还是报错，必须是决定过的。
7. **源站只信任边缘注入的、带共享密钥的单一可信头。** 绝不直接信任客户端传来的 `X-Forwarded-For`。
8. **用标准头做判据（`Age` / `Cache-Status`），厂商私有头只作补充。** 这样诊断资产能跨平台迁移。
9. **把 CDN 和容灾分开。** 定期做一次「关掉边缘会怎样」的推演，避免源站容量按有边缘时规划。
10. **验证要跨点、要等待传播窗口。** 单点单次验证几乎一定会得出错误结论。

## 与「证书与信任链生命周期」专题的分工

| 你想知道 | 去哪 |

**本页特有的坑（与证书专题的分工）**：边缘节点的证书往往由平台代管，于是「续期」这件事在团队内部**没有 owner**——出问题时既不在应用侧、也不在运维侧。本页的分诊表负责「定位到哪一层」，**「续期为什么失败、失败后还能撑几天」要看证书专题的阈值与缓冲计算**：47 天证书的缓冲只有 16 天，比多数团队的故障响应周期还短。
