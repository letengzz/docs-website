# 总览：上云先要决定的五件事

云上架构最常见的失败方式不是「选错了产品」，而是**顺序错了**：先把机器开出来，再想网段；先买了负载均衡，才发现它所属的 VPC 改不了；先按峰值买了一年预留，才知道业务有两班倒的波谷。本页把这类「改起来要停机」的决定集中列成五件，并给出每一件的判据。

![云上架构专题地图：五个决定与四个横切面](../assets/ca-topic-map.svg)

::: tip 一句话定位
本页不教你怎么点控制台。它的用途是：**在还没有业务跑起来的时候，把五个字段填对**。五个字段填完，后面所有页面才是在它们之上的展开。
:::

## 五件不可逆（或高代价）的决定

「不可逆」在这里是一个工程判断，不是绝对概念：**判断标准是「改它需不需要停业务、需不需要搬数据」**。

| # | 决定 | 一次的代价 | 判据（怎么填） | 改起来的代价 |
| --- | --- | --- | --- | --- |
| 1 | **地域（Region）** | 一次表单选择 | 离**真实用户**最近，而不是离你的办公地最近；同时核对目标地域在售的规格族是否齐 | 极高：机器可重建，**数据搬迁与域名切换是项目级工作量** |
| 2 | **网段（VPC CIDR）** | 一次表单选择 | 预留足够大：**「先大后小」**，一个大段切成多个子网很容易，把小段改大要重建 | 高：VPC 与子网一旦有资源，扩容受限；网段重叠会直接堵死「后续与公司 IDC 打通」 |
| 3 | **可用区数量** | 一次选择 | 先回答「哪种故障要能扛住」：**单机 → 2 AZ；单区 → 2 AZ 起步；需要滚动维护不降级 → 3 AZ** | 中高：加 AZ 要重划子网、重建后端、重配负载均衡 |
| 4 | **入口形态与 TLS 终止位置** | 一次选择 | 有域名/路径/Header 路由需求 → 七层；只需连接透明转发且追求极致并发 → 四层 | 中：换层数要重新验证超时、会话与流式响应行为 |
| 5 | **计费与弹性模型** | 一次「基线 + 峰值」拆分 | 稳态基线买预留，波动部分按量，无状态可中断部分用竞价 | 低到中：预留买错只能等它到期；弹性策略随时可调 |

::: danger 五个字段里，第 2 个（网段）是最多人后悔的一个
网段选小的直接后果是**后续无法与 IDC / 其他 VPC 打通**——因为你没有可用的地址空间做对等连接。

一条经验规则：**先按「未来三年会有的资源数」估一个段，再往上取一个整块**。一个 200 台机器的环境用 `/16` 不是浪费（IPv4 私网地址在 VPC 内不额外计费），但**用 `/24` 几乎一定会撞墙**。
:::

## 为什么顺序是 1 → 2 → 3 → 4 → 5

这五件事之间有**硬依赖**，跳过一步表面上看不出问题，但会在后面某一步集中爆发：

| 顺序 | 依赖关系 | 跳过的后果 |
| --- | --- | --- |
| 1 → 2 | 网段属于某个地域内的 VPC | 先建网段再选地域 = 全部重建 |
| 2 → 3 | 每个可用区需要**独立的子网**（子网不能跨可用区） | 只划一个子网，就无法做多可用区——这是最隐蔽的一条 |
| 3 → 4 | 负载均衡决定它把流量分发到**哪些子网**的后端 | 后端分散在多个 AZ，但负载均衡只绑了一个 AZ 的子网 |
| 4 → 5 | 入口层是少数「成本随流量同步上涨」的组件 | 按量入口 + 未设告警，会在流量突增时同时收到可用性与账单两个告警 |
| 3 → 5 | 跨可用区流量按**出向**计费 | 「为了容灾」把所有高频读写都跨区做，容灾没提升，账单先涨 |

::: warning 第 2 → 3 那条最值得单独记
**「一个可用区一个子网」是硬约束**（同可用区可以有很多子网，但一个子网只能属于一个可用区）。

所以「我先把应用都放在一个子网里，以后再拆」这句话，等价于「我以后再重建一次网络」。正确做法是**第一天就把两个可用区、两组子网划出来**，即使第二个可用区暂时空着——空着的子网不花钱，重建网络很花钱。
:::

## 什么时候不该做云上架构改造

云上架构有真实的成本：多可用区意味着跨区流量费，多 AZ 意味着两倍的实例数，弹性意味着更复杂的排障路径。以下情况应**先不要动架构**：

| 情况 | 为什么先不动 | 该做什么 |
| --- | --- | --- |
| 还没上线、没有真实流量 | 你不知道峰值在哪，多 AZ 只是在为想象中的故障买单 | 先单区跑通业务，同时**把两个子网划好**（免费） |
| 有单点但不是可用区级单点 | 挂掉服务的是那个**没做重试的下游**，不是 AZ | 先按 [响应式编程专题](/docs/Backend/ReactiveProgramming/index.md) 把超时、重试、降级补齐 |
| 团队还没有值班能力 | 多 AZ 会在半夜自动切换，而没人知道它切了 | 先建 [监控告警](../../Monitoring/index.md)，再谈容灾 |
| 成本压力大但账单很小 | 小账单上的优化空间也小，做架构改造的收益低于风险 | 先做 [闲置与孤儿资源](../Cost/index.md) 的清理 |
| 业务本身就是单点 | 例如单体数据库且短期不拆 | 先加只读副本与备份，把「恢复时间」而不是「可用性」做上来 |

::: info 一条判断线
**先问「这次改造要挡的是哪种故障」，再问「它多少钱」。** 挡不住的故障（例如应用自身的死锁、下游的雪崩）买再多 AZ 也没用；能挡住的故障（单机、单 AZ、单入口）往往用很低的成本就能挡住——[可用性拓扑](../Availability/index.md) 给了取舍表。
:::

## 最小起步：三步

不要一次把五件事全做完。推荐的最小路径是：

**第一步：定地域与网段，把两个可用区的子网划出来（不建任何业务资源）。**
此时判据是：两个子网在不同可用区、网段不重叠、路由表只有本地路由。**这一步不产生任何实例费用。**

**第二步：在其中一个子网起一台最小实例，验证「出网与入网」的边界。**
验证两件事：它能通过 NAT 出网（说明私网出口通），并且**从公网访问它必须超时**（说明它没有公网入口）。这一步把「私有子网」从一个说法变成一个事实。

**第三步：把它注册进负载均衡的一个后端组，验证健康检查的摘除与放回。**
手动停掉实例上的服务，观察它多久被摘除；再启动，观察它多久被放回。**这两个时间就是你的真实故障恢复时间**，也是后面所有 SLA 讨论的基准。

## 验证方式

| 步骤 | 命令 / 操作 | 预期 | 验证的是 |
| --- | --- | --- | --- |
| 子网划对了吗 | 列出 VPC 下子网的可用区与网段 | 至少两个子网，分属不同可用区，网段不重叠 | 决定 3 的可执行性 |
| 是否需要公网入口 | `curl -m 5 -I http://<实例公网IP>` | **超时**（不是 403/401） | 私有子网名副其实 |
| 私网能否出网 | 在实例内 `curl -s -o /dev/null -w '%{http_code}' https://example.com` | `200` | NAT / 私网端点可用 |
| 私有 DNS 是否生效 | 在实例内 `nslookup <内部域名>` | 返回**私网**地址 | 解析没被公网解析覆盖 |
| 健康检查是真的在拦 | 停掉服务 → 查后端组健康状态 | 在 `间隔 × 失败阈值` 内变为不健康 | 摘除逻辑有效 |
| 摘除后有影响吗 | 停掉服务后持续请求入口 | 错误率为 0（其他后端接住） | 多后端确实分摊 |
| 空闲子网不花钱 | 查看账单中网络类费用 | 无实例的子网不产生实例费 | 「先划好两个子网」是免费的 |

::: warning 判据不是实测记录
上表是**判据**。在你自己环境里执行后，应把真实输出记进实测列；**没有条件验证的写「未验证 + 原因」，不要抄期望值**。
:::

本页的验证只有一个目标：**证明你填的五个字段是自洽的**。最短路径是「最小起步三步」：两个子网分属两个可用区（说明字段 2、3 一致）→ 实例能出网且不能从公网入（说明字段 2 的分类是对的）→ 健康检查能摘除并放回（说明字段 4 与后端拓扑一致）。

三条全过，再去读 [网络边界](../Network/index.md) 把网段与出口细化。
