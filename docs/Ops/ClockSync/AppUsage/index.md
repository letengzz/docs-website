# 应用侧四条纪律

时钟同步能把偏差压到毫秒级，但**它不能阻止时钟跳变**——step 是同步机制的正常组成部分。所以应用层的正确性不能建立在「时钟不会跳」这个假设上。这一页把最容易踩的四条写成可检索、可评审的纪律，并给出每条纪律对应的失效读数。

![应用侧四条纪律与各自的失效读数](../assets/ck-app.svg)

## 一、纪律一：间隔用单调时钟

| 场景 | 错误写法 | 正确写法 | 失效读数 |
| --- | --- | --- | --- |
| 超时判定 | 记录 `now()` 再与 `now()` 比 | 记录单调时刻再求差 | 回拨 1 s 使 20 s 剩 21 s |
| 重试退避 | 用墙钟算「下次重试时刻」的间隔 | 用单调时钟（`clock_gettime(CLOCK_MONOTONIC)`）算间隔 | 前跳 0.35 s 使退避提前触发 |
| 耗时统计 | 结束墙钟 − 开始墙钟 | 单调时钟差 | 跨 step 的耗时出现负数 |
| 限流令牌桶 | 用墙钟补令牌 | 用单调时钟补 | 回拨时令牌被多补一次 |

本机实测：一次 −1.00 s 的 step 发生在第 10 秒，30 s 超时的剩余时间从 **20.00 s** 变成 **21.00 s**；前跳 0.35 s 时变成 **19.65 s**。两者都没有任何日志。

## 二、纪律二：去重窗口必须能容忍回拨

按「最近 N 秒内见过这个键」做去重，实现上几乎总是拿墙钟相减。回拨之后，**窗口的起点被推后，已经处理过的事件重新落进窗口**。

| 回拨量 | 300 s 窗口的有效长度 | 缩水 | 会被重放的已处理事件（每 2 s 一条） |
| --- | --- | --- | --- |
| 0 s | 300 s | 0.0% | 0 条 |
| 1 s | 299 s | 0.3% | 0 条 |
| 5 s | 295 s | 1.7% | **2 条** |
| 30 s | 270 s | 10.0% | **15 条** |
| 90 s | 210 s | 30.0% | 45 条 |
| 300 s | 0 s | 100.0% | 150 条 |

「缩水 1.7%」听起来无害，但第四列才是真正的后果：**回拨 5 秒就有 2 条已处理的事件被当成新事件**。如果这些事件是「扣款」「发券」「发通知」，重复执行的代价远大于窗口缩水本身。

::: danger 把去重键做成「时间 + ID」并不能救
用「分钟桶 + 业务 ID」当去重键，回拨时桶号会重复，于是**同一个桶被写两次**——看着是幂等的，实际是两次不同时间戳的写入。判据不是「键里有没有时间」，而是：**去重状态是否只依赖单调时钟或持久递增序号**。
:::

## 三、纪律三：租约用「期限 + 余量」表达

租约的本质是「我允许你在一段时间内独占」。当时钟有偏差时，**持有者和裁决者对「什么时候到期」的看法不同**：

```text
持有者 A 的时钟慢 skew 秒
裁决者 B 认为 A 在 T 到期
A 认为自己到 T + skew 才到期
→ 重叠窗 = skew（若 skew > T，则整段租约都重叠）
```

| 时钟偏差 | 租约 30 s 的重叠窗 | 占比 | 结论 |
| --- | --- | --- | --- |
| 0.1 s | 0.1 s | 0.3% | 可忽略 |
| 1.0 s | 1.0 s | 3.3% | 需要 Fencing token 兜底 |
| 5.0 s | 5.0 s | 16.7% | 必须有 Fencing |
| 25.0 s | 25.0 s | 83.3% | 租约机制基本失效 |
| 35.0 s | 30.0 s | 100.0% | 整段租约都可能双主 |

::: tip 租约的三条正确表达
1. **不要用「我还没到期」当独占依据**，要用 **Fencing token**（单调递增的持有序号）——下游拒绝更小的 token。
2. **续租周期 r 不影响重叠窗，它影响「多久发现你死了」**。重叠只由偏差 skew 决定，这一点常被搞反。
3. **余量按 skew 的 3 倍取**：若观测到偏差 σ = 100 ms，租约应比「业务需要」长 300 ms 以上，且 Fencing 必须存在。
:::

## 四、纪律四：排序存「时间 + 误差界 + 序号」

第 6 章算过判错概率：真实差 10 ms、偏差 σ = 10 ms 时判错 **23.98%**。所以「按时间戳排序」在跨机场景里不是「大致对」，而是「有明确错误率」。

| 做法 | 能支持什么结论 | 不能支持什么 |
| --- | --- | --- |
| 只存时间戳 | 「大概什么时候发生」 | 「谁先谁后」 |
| 时间戳 + 误差界 | 「这两条的顺序是否确定」（差值 > 误差界之和才确定） | 仍不能给全序 |
| 时间戳 + 误差界 + 单调序号 | 「同一写入方内严格有序」 | 跨写入方仍需因果 |
| 逻辑时钟 / Lamport | 因果序 | 真实时间 |

::: danger 一个具体的坑：UUIDv7 当排序键
UUIDv7 的前 48 位是毫秒时间戳，看起来「天然有序」。但**时钟回拨**会让后生成的 ID 排在前面；同一毫秒内的随机位也不保证顺序。判据：**UUIDv7 可以做索引前缀，但不能当唯一排序依据**；需要严格序就再加一个单调计数器。
:::

## 五、最小可运行：算「我的租约与去重窗口够不够」

```python
#!/usr/bin/env python3
"""去重窗口在回拨下的有效长度；租约在时钟偏差下的双主重叠窗。"""


def effective_window(window_s, back_s):
    """回拨 back_s 秒后，window_s 窗口还剩多少。"""
    return max(0.0, window_s - back_s)


def overlap(lease_s, skew_s):
    """持有者时钟慢 skew_s 秒时，双主重叠窗 = min(skew_s, lease_s)。"""
    return min(abs(skew_s), lease_s)


print("去重窗口 300 s，回拨后有效长度")
for b in (0, 1, 5, 30, 90, 300):
    print(f"  回拨 {b:3d} s -> 有效 {effective_window(300, b):5.0f} s"
          f"（缩水 {b/300*100:5.1f}%）")

print("\n租约 30 s，不同时钟偏差下的双主重叠窗")
for s in (0.0, 0.1, 1.0, 5.0, 25.0, 35.0):
    ov = overlap(30, s)
    print(f"  偏差 {s:5.1f} s -> 重叠 {ov:5.1f} s（占租约 {ov/30*100:5.1f}%）")

# 反推：给定可接受的缩水比例，允许的最大回拨
WINDOW = 300
for ratio in (0.01, 0.05, 0.10, 0.30):
    print(f"\n允许缩水 {ratio*100:4.0f}% -> 最大可容忍回拨 {WINDOW*ratio:.1f} s")
```

输出：

```text
去重窗口 300 s，回拨后有效长度
  回拨   0 s -> 有效   300 s（缩水   0.0%）
  回拨   1 s -> 有效   299 s（缩水   0.3%）
  回拨   5 s -> 有效   295 s（缩水   1.7%）
  回拨  30 s -> 有效   270 s（缩水  10.0%）
  回拨  90 s -> 有效   210 s（缩水  30.0%）
  回拨 300 s -> 有效     0 s（缩水 100.0%）

租约 30 s，不同时钟偏差下的双主重叠窗
  偏差   0.0 s -> 重叠   0.0 s（占租约   0.0%）
  偏差   0.1 s -> 重叠   0.1 s（占租约   0.3%）
  偏差   1.0 s -> 重叠   1.0 s（占租约   3.3%）
  偏差   5.0 s -> 重叠   5.0 s（占租约  16.7%）
  偏差  25.0 s -> 重叠  25.0 s（占租约  83.3%）
  偏差  35.0 s -> 重叠  30.0 s（占租约 100.0%）

允许缩水   1% -> 最大可容忍回拨 3.0 s
允许缩水   5% -> 最大可容忍回拨 15.0 s
允许缩水  10% -> 最大可容忍回拨 30.0 s
允许缩水  30% -> 最大可容忍回拨 90.0 s
```

::: danger 最后那四行的正确读法
它不是「我可以容忍 30 秒回拨」，而是「**如果我只允许 10% 的缩水，那么系统必须保证回拨不超过 30 秒**」。这个方向的差别很关键：

- 前者是「接受风险」；
- 后者是「提出要求」，并且这个要求可以写进 NTP 配置与监控（`makestep` 阈值、回拨告警）。

工程上永远写第二种。
:::

## 六、另外三处硬边界

| 边界 | 阈值 | 本地偏差多少会失败 | 处置 |
| --- | --- | --- | --- |
| 证书 `notBefore` | 签发时刻 | 本地**慢 1 s** 即 `certificate is not yet valid` | 部署前校时；容忍窗口靠 CA 回溯签发 |
| JWT `nbf` / `exp` | 秒级 | 偏差 ≥ 30 s 就可能整窗失效 | 校验方留 30~60 s 时钟偏移容忍 |
| TOTP | 30 s 窗口 | 偏差 ≥ 30 s 全部失效；偏差 ≥ 15 s 半窗失效 | 客户端与服务端都校时；允许 ±1 个窗口 |
| cron 定时任务 | 分钟级 | 跨 DST 折叠日会重复或漏跑 | 用「业务日 + 单调去重」而不是纯本地时间 |

第一行值得单独说：**本地偏快不会让 `notBefore` 失败，偏慢 1 秒就会**。所以「新证书一上线就报 not yet valid」几乎总是本地时钟慢，而不是证书有问题。

## 本页判据

本页判据族 `CKP-A` ~ `CKP-H`，共 8 条。

| 判据 | 约定 | 定错了会怎样 | 怎么验证 |
| --- | --- | --- | --- |
| `CKP-A` | 超时/退避/耗时/限流四类一律读单调时钟 | step 时这些逻辑同时错位 | 代码检索墙钟做差 |
| `CKP-B` | 去重状态只依赖单调时钟或持久递增序号，不依赖墙钟窗口 | 回拨 5 s 重放 2 条已处理事件 | 去重实现里无墙钟相减 |
| `CKP-C` | 租约必须配 Fencing token，不以「我还没到期」为独占依据 | 偏差 25 s 时 83.3% 租约重叠 | 下游校验 token 单调性 |
| `CKP-D` | 租约余量按观测偏差的 3 倍取，且写进配置注释 | 余量不足，双主窗口打开 | 配置里有偏差读数与余量推导 |
| `CKP-E` | 排序存「时间 + 误差界 + 单调序号」三件套 | 判错率与设计预期不符 | 表结构里有误差界字段 |
| `CKP-F` | UUIDv7 可作索引前缀，不作唯一排序依据 | 回拨后 ID 顺序反了 | 排序 SQL 里不单用 id |
| `CKP-G` | 证书失败先查本地是否偏慢，再查证书链 | 误判为证书问题，反复重签 | 分诊表里有这一条 |
| `CKP-H` | 允许缩水比例写成「对时钟的硬性要求」而非「接受的风险」 | 要求无人执行 | 变更单里有可核对的回拨上限 |
