# 常见问题与最佳实践

本篇汇总安全加固落地中最常遇到的 15 个问题、一份易错点清单，以及一份团队可直接执行的检查表。

## 一、高频问答

### Q1：我们是小团队，没有专职安全，从哪里开始性价比最高？

按「成本低、收益高」排序，依次做这三件：

1. **密钥扫描（gitleaks）+ 依赖扫描（Trivy fs）接到 CI**——各半天工作量，能挡住最常见的两类事故；
2. **镜像扫描 + 禁止非 root**——见 [Docker 安全加固](../../Docker/Security/index.md)；
3. **主机 SSH 加固 + 自动安全更新**——见 [Linux 安全加固](../../Linux/Advanced/SecurityHardening/index.md)。

不要一上来就搞 SIEM、威胁情报平台，那是规模上去之后的产物。

### Q2：合规通过了，是不是就安全了？

不是。**合规是「达到最低要求的证明」，不是安全的上限。** 攻击者不看你的证书。正确顺序是先用基线把技术面做扎实，再让合规评审去取证。

### Q3：扫描出来几千条漏洞，怎么办？

三步走：

1. **基线化**：把存量记为基线，门禁只对**新增**问题阻断（ratchet 策略）；
2. **按优先级排序**：用 CVSS + EPSS + KEV 排序（见[漏洞管理](../VulnerabilityManagement/index.md)），先修 KEV 与公网可达的；
3. **批量处理**：同一依赖的多个 CVE，往往一次升级就能全修完，不要逐个当独立任务排期。

### Q4：CVSS 9.8 的漏洞，但组件不可达，要立刻修吗？

不需要「立刻」，但**必须有记录**。用可达性分析确认不可达后，登记为例外（带到期时间），排入常规迭代。**关键区别是「有意识接受」 vs 「不知道」**。

### Q5：SBOM 生成出来给谁用？感觉没人看。

SBOM 的价值不在「看」，而在**「事后能查」**。典型场景：某天 log4j 级别的 0day 爆发，你能在 5 分钟内回答「我们哪些版本受影响」，而不是全量重新扫描。平时它静静地躺在归档里即可。

### Q6：镜像签名了，但集群不验签，有意义吗？

**没有意义。** 只签名不验签 = 没签名，攻击者推一个未签名镜像照样能跑。签名与验签必须成对出现。

### Q7：托管 K8s（EKS/GKE/AKS）里 CIS 一堆 fail，怎么办？

托管集群的控制面（etcd、apiserver）由云厂商负责，**你无法也不应该修改**。正确做法：

1. 把控制面检查项（通常 `1.x`）视为 notapplicable 排除；
2. 关注你真正能控制的：节点（`4.x`）与工作负载（`5.x`）；
3. 使用面向托管场景的 CIS 变体或云厂商自己的基线。

### Q8：密钥泄漏了，第一步做什么？

**立刻轮换/吊销该凭据**——不是先删代码。代码删了密钥还在 Git 历史里，攻击者照样能用。顺序是：轮换 → 排查使用点 → 查审计 → 清历史 → 补检测。

### Q9：`.env` 文件能提交吗？

**绝对不能**，且必须在 `.gitignore` 里。CI 需要配置时应通过平台的 Secret 机制或 OIDC 换短期凭据注入，而不是提交文件。

### Q10：Falco 告警太多，都没人看了，怎么办？

告警疲劳是检测失效的前兆。处理方式：

1. **收敛规则**：把噪声大的规则调成 `WARNING` 或加白名单；
2. **分级**：只有 P0/P1 才实时通知，其余进日报；
3. **闭环**：每条告警都要有「谁处理、怎么处理」的流程，无人处理的规则直接关掉。

### Q11：运行时检测和镜像扫描，哪个更重要？

都重要，但**分工不同**：

- 镜像扫描是**快照**——「门锁了没有」；
- 运行时检测是**流**——「有人正在撬锁吗」。

镜像扫描无法发现 0day，运行时检测无法替代「上线前拦下已知漏洞」。缺一不可。

### Q12：安全门禁太严，开发总是绕过，怎么破？

先自问门禁是否**合理**：

1. 是否只阻断真正紧急的（密钥 + 高危）？中低危应进看板而非阻断；
2. 是否有**快速例外通道**（登记 + 到期时间）？没有通道就会催生「绕过」；
3. 是否在**开发者最关注的地方**反馈（PR 评论）？

门禁的目标是「让安全成为默认路径」，而不是「阻止上线」。

### Q13：Trivy 为什么必须升级到最新？

Trivy 曾在 **v0.69.5 / v0.69.6** 遭遇**投毒事件**（CVE-2026-33634）。**安全工具本身也是攻击目标**。请使用 **0.74.0+**，并在 CI 中固定版本 + 校验校验和。

### Q14：SBOM 用 SPDX 还是 CycloneDX？

| 你的重点 | 选 |
| --- | --- |
| 许可证合规、法务审计 | SPDX |
| 漏洞管理、安全流水线 | CycloneDX |

拿不准就选 **CycloneDX**（安全生态支持更广，且支持 VEX）。两者可互转。

### Q15：怎么证明安全投入有效？

用四个指标（详见[方法论](../Overview/index.md)）：

- 基线覆盖率（是否有漏网资产）；
- 高危存量数（趋势是否下降）；
- MTTR（修复效率）；
- 复发率（是否治本）。

把它们放进看板，和监控大盘放一起。**能看到的数字才会被优化。**

## 二、易错点清单

:::danger 注意
以下每条都是真实项目里的高频坑，逐条对照自查：

1. **`--ignore-unfixed` 用得不一致**——有人开有人关，门禁结果来回抖动。必须统一策略。
2. **基线例外没有到期时间**——豁免变成永久漏洞，半年后无人记得原因。
3. **自动修复脚本直接上生产**——OpenSCAP/CIS 生成的脚本可能重启服务、改内核参数。必须先预发验证。
4. **升级依赖只看「修掉了什么」**——不看「新引入了什么」，按下葫芦浮起瓢。
5. **审计日志只存本地**——攻击者提权后第一件事就是删日志。必须实时转发到远端。
6. **不检测「审计系统被关闭」**——auditd 被 stop、规则被清空本身就该是最高优先级告警。
7. **CI 中打印环境变量**——`echo "token=$TOKEN"` 是教科书级事故，日志常被上传到可搜索存储。
8. **base64 当加密用**——编码不是加密，一眼可解码。
9. **全环境共用同一密钥**——测试环境泄漏即生产失守，无法单独吊销。
10. **轮换不做双密钥并行**——直接替换导致正在用旧密钥的服务立刻中断。
11. **门禁只扫不阻断**——`exit-code` 没开，扫描形同虚设。
12. **禁用 TLS 校验「图省事」**——`curl -k`、`verify=False`，MITM 直接得手。
13. **容器以 root 运行**——逃逸后即宿主 root，见 Docker 安全篇。
14. **CIS 基线与系统版本不匹配**——拿到错版本的基线，误报一片。
15. **越权风险只靠前端控制**——后端必须独立校验，前端校验只是体验。
:::

## 三、团队检查表

把下面这份清单当成「每月安全巡检」的最小集：

### 3.1 资产与基线

- [ ] 主机/集群/云资源清单完整，能回答「有多少资产」
- [ ] 基线标准与系统版本精确对应
- [ ] 基线覆盖率 ≥ 90%，漏网资产有明确原因
- [ ] 例外清单每条都有负责人与到期时间

### 3.2 漏洞管理

- [ ] 依赖/镜像/主机扫描接入 CI 或定时任务
- [ ] 高危 SLA 有落地载体（Issue due date）
- [ ] 修复后必做复扫，确认修掉且未引入新问题
- [ ] 高危存量趋势下降

### 3.3 供应链与密钥

- [ ] 关键镜像已签名，且部署时强制验签
- [ ] 构建产物有 SBOM 并归档
- [ ] 仓库历史无残留密钥（gitleaks 全历史扫描为 0）
- [ ] CI 使用 OIDC 换取短期凭据，无长期 AccessKey
- [ ] 密钥托管在 Vault/KMS，配置文件里只有引用

### 3.4 审计与检测

- [ ] auditd 关键规则已加载（提权、敏感文件、凭据读取）
- [ ] K8s 审计日志已开启并落地
- [ ] Falco（或等价运行时检测）已部署并有告警渠道
- [ ] 日志实时转发到远端，本地删除不影响远端
- [ ] 「审计被关闭」有独立告警规则
- [ ] 有响应预案并做过演练

## 四、推荐的落地节奏

| 阶段 | 时间 | 目标 | 验收 |
| --- | --- | --- | --- |
| 起步 | 1~2 周 | 资产盘点 + 选基线 | 资产清单 + 基线版本确认 |
| 加固 | 2~4 周 | 主机/集群基线加固 + 扫描接入 | 基线覆盖率 ≥ 90% |
| 自动化 | 1~2 月 | 基线进 CI、漏洞进 SLA、密钥进托管 | 门禁能阻断 |
| 运营 | 持续 | 审计 + 运行时检测 + 响应 | 告警闭环 + 指标看板 |
