# 安全加固

<p style="text-align:center;"><img src="./assets/security-logo.png" style="zoom:75%;" /></p>

安全加固（Security Hardening）是**在系统上线前后，持续削减攻击面、降低被利用概率并缩短暴露窗口**的一整套工程实践。它不是某一台机器的配置清单，而是覆盖「身份 → 主机 → 容器 → 集群 → 应用 → 数据」六层的**横向治理体系**。

本专题讲的是**跨层的治理与流程**：如何选基线、如何管理漏洞生命周期、如何治理密钥、如何做审计与检测、如何把工具串成流水线。**具体某一层的命令级加固**（SSH、防火墙、capability、RBAC、NetworkPolicy 等）分别见下表的既有专题，本专题与之互补而不重复。

| **跨层治理（本专题）** | 方法论、基线合规、漏洞管理、SBOM、密钥、审计、工具链 | 本页以下各篇 |
| **云账号与网络边界** | 身份与最小权限（角色 / 临时凭证，不用长期密钥）、`0.0.0.0/0` 暴露面清点、对象存储桶权限、静态加密与操作审计 | [云上架构 · 云上安全边界](../CloudArchitecture/Security/index.md) |

这张表按**「管的是哪一层」**切分：主机层管进程与内核，运行时层管容器，编排层管 K8s 的权限与网络策略，**网格层管服务身份与调用授权**，本专题负责跨层的基线、扫描、漏洞、密钥与审计。**云上架构专题补的是这张表之外的两层边界**——**身份边界**（谁的密钥、权限多大、是不是临时凭证）与**网络边界**（哪些端口对公网开放、桶是否公开）：它们既不在主机里，也不在集群里，而在**账号与资源编排层**。两者不互相替代：主机加固挡不住「主账号密钥被写进配置文件」，而最小权限也挡不住「内核参数没关」。

最容易混淆的是「集群与编排」与「服务间调用」这两行——它们看着都在管「谁能访问谁」，粒度完全不同：

| | NetworkPolicy（编排层） | AuthorizationPolicy（网格层） |
| --- | --- | --- |
| 判据 | Pod 的 IP / 标签 | **服务身份**（SPIFFE ID）与 HTTP 路径、方法 |
| 生效层 | L3/L4 | L7 |
| 能否防「同集群内横向移动」 | 能限制可达范围，但同命名空间内默认全通 | 能——即使网络可达，身份不匹配也拒绝 |
| 是否需要改应用 | 否 | 否（Sidecar/ztunnel 代理） |

生产上两者是**叠加而不是替代**：先用 NetworkPolicy 收紧可达范围，再用 mTLS + AuthorizationPolicy 做身份级零信任。落地步骤与验收判据见[网格安全](../ContainerOrchestration/ServiceMesh/Security/index.md)。

## 核心概念速览

| 概念 | 英文 / 缩写 | 一句话解释 |
| --- | --- | --- |
| 攻击面 | Attack Surface | 外部可触达的入口总和；加固的本质是持续缩小它 |
| 纵深防御 | Defense in Depth | 多层独立控制叠加，单层失守不等于全局失守 |
| 最小权限 | Least Privilege | 主体只拿到完成当前任务所需的最小权限、最短时限 |
| 基线 | Baseline | 一组「必须满足」的安全配置，通常来自 CIS/等保等标准 |
| 合规即代码 | Compliance as Code | 把基线检查写进流水线，回归即失败，而非人工抽查 |
| 软件物料清单 | SBOM | 一份列出软件全部组件与版本关系的「配料表」 |
| 漏洞可利用性 | EPSS / KEV | 预测漏洞被利用的概率 / 已确认在野被利用的目录 |
| 安全 SLA | MTTR | 从发现高危到修复完成的时间目标，按等级约定 |

## 适用对象

- 需要把安全从「出事再补」变成「持续可运营」的运维 / DevSecOps 工程师；
- 要落地合规（等保 2.0、ISO 27001、SOC 2）却不知从哪一控制项下手的团队；
- 需要给 CI/CD 加安全门禁、给集群加准入与运行时检测的平台工程师。

:::tip 一句话理解
安全加固不是「把一堆参数调严」，而是**用工程化手段让「不安全」在流水线里就通不过**——基线进 CI、漏洞进 SLA、密钥进托管、检测进运行时。
:::

## 云上身份与最小权限

自建环境的第一道门是**主机基线与容器加固**（见本页上方分工表）；托管环境（Lambda、托管 K8s、各类云服务）里机器不是你的，**第一道门就变成了「执行身份」**——谁以什么身份去调云 API。托管场景下真正决定爆炸半径的，往往不是这台机器怎么配，而是**这个工作负载拿到了什么角色**。

| 托管形态 | 身份载体 | 常见叫法 |
| --- | --- | --- |
| Serverless 函数 | 函数绑定一个执行角色 | Lambda Execution Role、函数服务账号 |
| 托管 K8s | Pod 关联云身份，无需把密钥塞进容器 | IRSA（EKS）、Workload Identity（GKE / Azure）、RRSA（阿里云 ACK） |
| 托管数据库 / 消息 | 实例级访问策略 + 调用方角色 | 实例 RAM 角色 / 服务关联角色 |

三条纪律：

1. **一个函数（工作负载）一个角色**：不要所有负载共用一个「万能角色」。共用意味着任何一处被攻破，等于全部权限被拿走；审计时也分不清是谁调的。
2. **只列必需的 Action，并写全资源 ARN**：`"Resource": "*"` 与 `"Action": "s3:*"` 这类通配符等于没有限制——一旦触发 SSRF 或依赖投毒，攻击者就能读写整个账号的资源。把资源限定到具体的桶、前缀、表名。
3. **密钥放密钥管理服务，不要塞进环境变量明文**：环境变量会出现在控制台、日志与崩溃转储里。优先用云密钥管理服务（KMS / Secrets Manager / 参数仓库）在运行时注入，或用上面说的身份载体免密钥调用。

```json [最小权限 IAM 策略片段]
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ReadWriteOneBucketPrefix",
      "Effect": "Allow",
      "Action": [
        "s3:GetObject",
        "s3:PutObject"
      ],
      "Resource": "arn:aws:s3:::shop-order-attachments/prod/uploads/*"
    },
    {
      "Sid": "WriteLogs",
      "Effect": "Allow",
      "Action": [
        "logs:CreateLogStream",
        "logs:PutLogEvents"
      ],
      "Resource": "arn:aws:logs:cn-north-1:123456789012:log-group:/aws/lambda/order-processor:*"
    },
    {
      "Sid": "ReadOneSecretOnly",
      "Effect": "Allow",
      "Action": "secretsmanager:GetSecretValue",
      "Resource": "arn:aws:secretsmanager:cn-north-1:123456789012:secret:order/db-*"
    }
  ]
}
```

::: danger 托管环境里最容易踩的三个坑
1. **给函数挂 `AdministratorAccess`「先跑起来再说」**：省下的十分钟，会在某次依赖投毒或 SSRF 时以整个账号为代价还回来。正确做法是从最小集合起步，缺什么补什么，用云审计日志反推还缺哪些 Action。
2. **用一个角色给所有环境（dev/staging/prod）**：一处泄漏全环境沦陷。按环境拆分角色与资源 ARN，prod 角色只挂到 prod 函数上。
3. **把密钥写进环境变量或代码**：环境变量在控制台可见、可能进日志；代码进了 Git 就永久留痕。正确做法是走密钥管理服务 + 免密钥身份，轮换时无需改代码。
:::

更细的密钥生命周期与轮换见 [密钥与凭据治理](SecretGovernance/index.md)，函数侧的身份配置与最小权限实践见 [云原生 · 函数工程](../CloudNative/FunctionEngineering/index.md)。

## 与故障应急体系的分工（第 129 天补充）

安全事件与可用性事件**走两条不同的流程**，不要混在一套预案里：

| 维度 | 本专题（安全加固） | 故障应急体系 |
| --- | --- | --- |
| 触发条件 | 数据被窃取 / 篡改 / 假冒、权限被滥用、被入侵 | 服务对用户不可用或结果不正确 |
| 第一优先级 | **保全证据与止损影响面**（不能为了恢复而破坏现场） | **恢复服务**（止损优先于定位） |
| 对外义务 | **有法定报告义务**：较大以上网络安全事件需按 [报告时限（关键信息基础设施 ≤1 小时，其他最晚 4 小时）](../IncidentResponse/Severity/index.md) 上报 | 通常无强制报告义务（除非同时构成安全事件） |
| 分级口径 | 用**国标四级**（特别重大 / 重大 / 较大 / 一般，GB/T 20986-2023） | 用内部 SEV 分级（SEV-1~SEV-5） |

**交界处最容易出问题的一条**：一次「服务不可用」可能**同时是**安全事件（例如被 DDoS 或被入侵后删数据）。此时正确的顺序是**先按安全事件保全证据、并行启动可用性应急**——而不是先重启恢复把现场清掉。这条判断应当在预案里写成一句话，因为它需要在压力下被快速做出来。

## 与依赖治理的分工（第 130 天补充）

本专题（安全加固）与 [工具 · 依赖与安全治理](../../Tools/DependencyGovernance/index.md) 在「组件」这个词上相邻，但**治理的对象层级不同**：

| 维度 | 本专题（安全加固） | 依赖与安全治理 |
| --- | --- | --- |
| 治理对象 | **运行环境**：主机内核参数、容器镜像层、集群配置、密钥与凭证 | **构建进去的组件**：包管理器解析出的依赖树，以及它们的许可与来源 |
| 主要手段 | 加固基线、镜像扫描、密钥治理、配置审计 | SBOM 清点、漏洞优先级、许可证策略、私服准入、来源签名、门禁 |
| 扫描能看见什么 | OS 包、系统配置、镜像层、密钥泄漏 | 语言生态的包与版本、许可证、依赖关系图 |
| 判据来源 | 合规基线（CIS 一类）与内部基线 | 漏洞数据源（OSV / NVD）、SPDX 许可证清单、SLSA 与签名 |

**三处最关键的分工边界**：

1. **镜像扫描与依赖扫描不可互替**。依赖扫描器（Syft / Grype 一类）走的是包管理器视角，**结构上看不见基础镜像里的 `openssl`、`libc`**；镜像扫描能看见这些，但看不见语言生态的依赖图。**一次发布要跑两套，结论取并集**。
2. **凭证治理是两页的公共交集**。本专题的密钥治理讲「凭证怎么存与怎么轮换」；依赖治理讲「**不要用长期密钥签名**」——密钥less 签名把长期私钥这个失败模式直接消掉了。两条建议指向同一件事：**减少长期凭证的存在**。
3. **供应链攻击常常绕过主机加固**。一个被投毒的上游版本不需要任何内核漏洞就能生效，它在你的构建产物里以「正常依赖」的形态存在。**主机加固挡不住它，依赖治理才是那一层。**

**一句话分工**：**本专题回答「环境有多硬」，依赖治理回答「材料有多可信」。**

## 与「AI 安全与合规」专题的分工（第 146 天补充）

本专题处理的是**「环境」**：主机、容器、镜像、镜像里的依赖。而 [AI 安全与合规](../../AI/AISecurityCompliance/index.md) 处理的是**「管道里的内容」**：进模型的数据、出模型的回答、模型伸手去做的动作。两者的加固对象不重叠，也**不能互相替代**——这一点在 AI 场景下尤其反直觉，因为最容易被误判成「宿主安全了，AI 就安全了」。

| 边界问题 | 归本专题 | 归 [AI 安全与合规](../../AI/AISecurityCompliance/index.md) |
| --- | --- | --- |
| 加固对象 | 主机基线、容器隔离、镜像扫描、供应链 | **数据流与内容流**：字段白名单、双向审核、工具闸门 |
| 身份与权限 | 云上身份、最小权限、密钥的存放与轮换 | 工具调用的**执行身份**、审批闸门、预算与速率 |
| 审计 | [审计与检测](./AuditDetection/index.md)：日志平台的采集、留存与检测规则 | [审计链](../../AI/AISecurityCompliance/Audit/index.md)：**要写进日志的八字段**、哈希链与截断盲区、留存期三来源取最大 |
| 内容 | 不涉及（本专题不看内容语义） | [内容安全](../../AI/AISecurityCompliance/ContentSafety/index.md)：法规口径到处置动作的四层映射、两条阈值线 |
| 合规基线 | CIS 一类的**环境基线** | [合规清单](../../AI/AISecurityCompliance/Compliance/index.md)：AI 专属法规的生效日期表与六格证据包 |
| 判据形态 | 基线扫描「无高危项」 | **布尔闸门**：拆掉任一道必须看得出差异，且**把护栏关掉试一次，下游必须仍然拒绝** |

**一句话分工**：**本专题回答「环境有多硬」，AI 安全与合规回答「这条管道有没有越界」。**

::: danger 三件宿主加固挡不住的事
1. **模型把 PII 写进出站请求**。这不是漏洞利用，是**正常调用**——没有内核漏洞、没有提权、没有异常进程，防火墙上看就是一条合规的 HTTPS 出站。
2. **Agent 拿着合法凭据做了越权动作**。凭据是合法签发的，最小权限也满足了（它确实只被授予了这一件事），出问题的是**决策链**：模型被一段检索到的文本说服了。
3. **该拦的没拦、该升级的直接放行**。这属于[护栏的四种静默失效](../../AI/AISecurityCompliance/Guardrails/index.md)，表现为**一切正常**：没有告警、没有错误码、日志里只有「成功」。

这三件的共同点是**在宿主视角下全部是正常行为**——所以它们只能由 AI 侧那四道闸门自己发现。**宿主加固是底座，不是替代品。**
:::

## 与「遗留系统改造」专题的分工（第 147 天补充）
本专题讲**加固**：主机、容器、网络、依赖、密钥、审计，以及它们的检查与基线。

[遗留系统改造](../../Backend/LegacyModernization/index.md) 与它有两处必须对齐的接口：

| 边界问题 | 归本专题 | 归遗留系统改造 |
| --- | --- | --- |
| 「旧系统还要不要打补丁」 | ✅ 补丁策略与优先级 | ✅ 结论：**补丁优先于迁移**，是唯一可以插队的一类变更 |
| 「共存期两套系统的安全基线怎么定」 | ✅ 基线内容 | ✅ 双份运维清单里把「补丁与证书」列为一项 |
| 「改造后安全域变了要不要重新测评」 | ✅ 测评要求 | ✅ 责任模型里单独一行：安全合规影响面 |
| 「旁路调用的边界怎么收」 | 提供凭据管理手段 | ✅ **凭据即边界**，并把它做成可监控指标 |

一句话分工：**加固提供手段与基线；遗留系统改造负责在「两套系统并存」这个非常形态下把这些手段落到清单与责任人上。**

本页特有的一个坑：证书过期是共存期最典型的**静默故障**——新旧两套系统都在监听、指标都正常，但只有一边被盯着。所以「补丁 / 证书到期天数」必须是共存期六个日常数字之一，见 [共存期工程的日常仪表盘](../../Backend/LegacyModernization/Coexistence/index.md)。
