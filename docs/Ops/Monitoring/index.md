# 监控告警

<p style="text-align:center;"><img src="./assets/monitoring-logo.png" alt="监控告警" style="zoom:75%;" /></p>

## 应用侧接入：RED 指标与两类探针

本专题讲的是监控体系的搭建（采集、存储、可视化、告警）。**应用侧要暴露什么**，可以收敛成很少的几个约定——多了没人看，少了定位不了。

### RED 三件套覆盖 90% 的告警需求

| 指标 | 类型 | 标签（**必须有界**） | 回答什么 |
| --- | --- | --- | --- |
| `*_requests_total` | Counter | `method` / `route` / `code` | **Rate**：流量与错误率 |
| `*_request_duration_seconds` | Histogram | `method` / `route` | **Duration**：p50 / p95 / p99 |
| `*_errors_total` | Counter | `route` / `code` | **Errors**：按错误码归因 |

::: danger 注意：标签基数是指标体系的头号杀手
**绝不能把「无界」的值放进标签**：

| 禁止 | 原因 | 正确做法 |
| --- | --- | --- |
| 原始 URL（`/order/12345`） | 每个订单号一条时间序列 | 用**路由模板**（`/order/{order_id}`） |
| 用户 ID / 租户 ID | 基数等于用户数 | 需要时用「维度分桶」或改用日志 |
| 时间戳 / Trace ID | 基数无上限 | 放进日志，不放指标 |
| 错误原文 | 基数不可控 | 用错误**码** |

标签基数爆炸的后果是 Prometheus 内存暴涨甚至 OOM——**指标系统挂掉比业务挂掉更难恢复**（它挂了你连「哪里挂了」都不知道）。
:::

### 两条告警阈值原则

1. **阈值从压测基线来，不要拍脑袋**：压测拿到 p99 与容量拐点后，告警线设在 `p99 × 1.5`，错误率设在 `0.5%`。
2. **业务失败不计入 SLO 错误率**：`InvalidArgument`、`NotFound` 属于正常业务拒绝。把它们算进错误率，结果就是**用户输错一次手机号就触发告警**。实现上按状态码过滤后再统计。

### 两类探针的语义（K8s）

| 探针 | 端点 | 失败动作 | 所以它能查什么 |
| --- | --- | --- | --- |
| `livenessProbe` | `/health` | **重启容器** | **只能查进程自身**——绝不能查 DB / Redis |
| `readinessProbe` | `/ready` | **摘流量，不重启** | 应查所有关键依赖 |

::: warning 说明：把依赖检查放进 liveness 是最危险的一种「优化」
看起来「更严谨」（依赖挂了就重启），实际后果是：**依赖抖动 → 所有副本一起被重启 → 服务全挂**。小故障被放大成了完全中断。

**验收方式**：把 Redis 停掉，`/health` 必须仍是 200，`/ready` 必须变 503。这条检查成本 10 秒，能挡住的是一次全站不可用。
:::

应用侧的具体实现见 [Go 服务治理](../../Backend/GoMicroservices/Governance/index.md)（熔断只统计技术失败、Trace 与日志的 trace_id 对齐）与 [Python 服务部署](../../Backend/PythonWeb/Practice/index.md)（结构化日志、指标标签、探针实现）。

## 与故障应急体系的分工（第 129 天补充）

本专题与 [故障应急体系](../IncidentResponse/index.md) 在同一条链路上前后相接，边界是**时间点**而不是内容：

| 时刻 | 归谁管 | 回答的问题 |
| --- | --- | --- |
| 异常发生 → 告警触发 | **本专题** | 「怎么知道出事了」：指标选型、抓取模型、告警规则、`for`/`keep_firing_for`、分组与抑制的**写法** |
| 告警触发 → 有人接下 | [值班制度](../IncidentResponse/OnCall/index.md) | 「谁被叫醒、叫不醒怎么办」：轮值与升级链路 |
| 确认对用户有影响之后 | [故障定级](../IncidentResponse/Severity/index.md) 起 | 「叫多少人、拉多大响应」 |

**三条不该越界的地方**：

1. **「可行动才告警」这条门禁归本专题执行**（规则怎么写），但**「哪条告警有资格变成电话」的判定标准归值班制度**——两者必须同时成立，否则会得到「规则写得很规范、但每天夜里响六次」的结果。
2. **告警的 `runbook_url` 指向的文档由本专题保证「存在」，由故障应急体系保证「可执行」**（有没有期望输出与回退点）。
3. **业务指标（下单/支付成功率）通常不在本专题的核心篇幅里**，因为它们是业务口径；而故障应急体系把「事故判据挂在业务指标上」写成了硬要求——**这是两个专题之间最需要对齐的一处**：监控侧如果不采集业务成功率，应急侧就永远只能靠用户反馈发现故障。

## 与 AI 应用观测的分工（第 131 天补充）

本专题盯的是**基础设施与服务的健康**，[AI 应用观测与评估](../../AI/LLMObservability/index.md) 盯的是**模型输出的质量与语义**。两者可以用同一条 OTLP 管道，但**语义层完全不同**，不能互相替代：

| | 本专题（通用监控） | AI 应用观测 |
| --- | --- | --- |
| 观测对象 | 容器、接口、队列、数据库 | 一次模型调用的输入输出、token、检索命中 |
| 核心指标 | 可用性、延迟分位、错误率、饱和度（RED / USE） | 忠实度、相关性、每千次**成功**交互成本 |
| 判据来源 | 阈值与基线（可由历史数据反推） | **基线 + 采样估计**，且必须与人工标注校准 |
| 故障形态 | 硬故障（超时、5xx、进程退出） | **「正常但错」**：HTTP 200、延迟正常，但答案不对 |

**三处最容易互相误判的地方**：

1. **延迟正常不等于服务正常**。一次 RAG 请求在 400ms 内返回 200，但检索返回了空上下文、模型自己编了答案——本专题的所有指标都是绿的。这类故障需要[检索 `status` 与忠实度分数](../../AI/LLMObservability/Overview/index.md)才能发现。
2. **告警的三道闸门是同一套机制，但分组键不同**。分组 / 抑制 / 静默的写法在本专题与 [Alertmanager 配置](Alerting/index.md)一致；而质量告警的分组键是 `evaluator` / `model` / `prompt_version`，**按 `trace_id` 分组等于不分组**。另有一条硬规矩：**统计型质量分数不要接 P1 电话告警**——它是统计量，天然波动，会造成大量假警报并消耗团队对告警的信任。
3. **成本指的是两件不同的事**。本专题的成本是**基础设施成本**（CPU、内存、存储、带宽）；AI 应用的成本是**推理与评估成本**（token、裁判调用），口径与归因路径完全不同，混在一张图上会得出错误的优化方向。

要设计一条基础设施规则，回本专题；要回答「昨天那次答错为什么答错、花了多少钱」，去 [AI 应用观测与评估](../../AI/LLMObservability/index.md)。

## 与网关深入的分工（第 133 天补充）

本专题是**通用监控方法论**（RED / USE、采集、存储、告警三道闸门）；[网关深入 · 网关可观测](../../Backend/GatewayDeep/Observability/index.md) 只补**网关这一跳专属的四个信号**。两者不是替代关系——**方法论在这边，字段口径在那边**。

| | 本专题（通用监控） | 网关可观测（这一跳） |
| --- | --- | --- |
| 观测对象 | 容器、接口、队列、数据库等所有被监控对象 | 经过网关的每一次请求与每一次插件执行 |
| 核心指标 | 可用性、延迟分位、错误率、饱和度 | **路由命中率、上游延迟、插件耗时、4xx/5xx 归因** |
| 最容易缺的字段 | 业务维度标签 | `upstream_status`、`route_id`、`plugin` |
| 判据来源 | 阈值与基线 | 与「路由变更」对齐的时间线 |

**三处只能由网关侧补齐、通用监控补不了的地方**：

1. **`status` 与 `upstream_status` 必须分开采集。** 网关返给客户端的 502，上游可能根本没收到请求（连接失败 / 路由未命中）；只看 `status` 会把「网关自己的问题」和「上游的问题」混成一个数字，归因直接失败。
2. **插件耗时必须单独计量。** 网关的每一个插件都在给**全部流量**加税；插件耗时混进总延迟里，就无法回答「这次 5ms 的退化是上游变慢还是插件变慢」。
3. **基数是网关指标最大的敌人。** 把 `route`、`consumer`、`path`（含动态段）全部打成标签，会瞬间打爆时间序列存储。网关侧必须先做**标签收敛**（动态段归一、高基数维度降级为日志字段），再交给本专题的存储层。

要设计一条通用的采集与告警规则，回本专题；要回答「这一跳到底是哪一段慢、是网关还是上游」，去 [网关可观测](../../Backend/GatewayDeep/Observability/index.md)。
