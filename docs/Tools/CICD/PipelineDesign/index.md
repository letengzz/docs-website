# 流水线设计最佳实践

流水线不是“把命令串起来”就行。设计糟糕的流水线：跑 40 分钟、失败原因不明、dev 与 prod 产物不一致、并发互相踩踏。本页给出阶段划分、并行、缓存、门禁、失败处理、环境治理的完整设计方法，适用于 GitHub Actions / GitLab CI / Jenkins 任意平台。

## 设计目标

| 目标 | 指标 |
| --- | --- |
| 快速反馈 | 提交流水线 ≤ 10 分钟 |
| 高稳定性 | 非代码原因失败率趋近 0（依赖下载、环境漂移可控） |
| 可追溯 | 每个产物能对应到 commit 与构建日志 |
| 可回滚 | 任何环境都能一键回到上一个好版本 |
| 安全 | 密钥不外泄、第三方组件可审计 |

## 流水线分层

不要把所有东西塞进一条流水线，按触发时机拆成多条：

| 流水线 | 触发 | 内容 | 目标耗时 |
| --- | --- | --- | --- |
| PR 校验 | PR 更新 | Lint、单元测试、构建、覆盖率 | ≤ 10 分钟 |
| 主干流水线 | main 合并 | 全量测试、质量门禁、制品 | ≤ 15 分钟 |
| 发布流水线 | tag / 手动 | 构建发布版制品、部署 staging、冒烟 | 按需 |
| 生产部署 | 人工确认 | 部署 prod、健康检查、回滚预案 | 分钟级 |
| 夜间流水线 | cron | 全量回归、性能测试、依赖安全扫描 | 小时级 |

## 阶段划分模板

```text
check（静态检查）
  ↓
build（构建）
  ↓
test（单元 + 集成）
  ↓
quality（覆盖率 + 扫描）    ← 门禁，不通过阻断
  ↓
package（制品 + 镜像）
  ↓
deploy-staging → smoke → deploy-prod（人工/自动）
```

原则：

1. **阶段内并行、阶段间串行**：同一阶段的 Job 并行跑，提高吞吐。
2. **耗时操作后置**：全量测试放发布/夜间，提交流水线只跑关键路径。
3. **门禁唯一**：质量门禁只在一个阶段判定，避免多个 Job 各自设阈值导致口径不一。

### 部署阶段的内部顺序：数据库迁移必须排在应用替换之前

上面这张图的 `deploy-prod` 是一个阶段，但它内部有**唯一一条不可调换的顺序**：

```text
migrate（加列 / 加表 / 加索引，只加不减）
  ↓
replace-app（滚动 / 原地替换应用）
  ↓
smoke（部署后冒烟，失败即触发回滚）
```

理由是一个时间窗问题，不是风格问题：

| 顺序 | 结果 |
| --- | --- |
| **迁移 → 应用** | 迁移「只加不减」时，**旧代码忽略新列照样工作**，新代码上线时新列已存在 → 安全 |
| 应用 → 迁移 | 新代码访问尚不存在的列 → 全量报错；此时把应用回滚也救不回期间写入失败的数据 |

这条顺序同时决定了**回滚方向**：回滚时先回应用、不动数据；只有当变更已越过「不可回滚点」（删列 / 改列类型）时，才必须动备份。判定方法与三类回滚的代价排序见[自动部署与回滚](../DeployRollback/index.md)。

::: danger 流水线里最容易埋下的两个隐患
1. **迁移脚本不幂等**：流水线重跑、失败重试、容器重建都会重放迁移。建表建列一律写 `IF NOT EXISTS`，数据回填用 `WHERE` 限定未处理行——否则第二次执行就报错，而「重跑一次」恰好是故障时最常见的动作。
2. **回滚包没被验证**：流水线里的「回滚」通常是「把上一个 tag 重新部署」。如果上一个 tag 被制品仓库的保留策略清理过，或者从未以可发布形态构建过，这条命令在关键时刻会失败。**发布前置里要有一条真拉取上一个 tag 的动作**，而不是假设它还在。
:::

## 加速技巧

| 技巧 | 收益 | 实现 |
| --- | --- | --- |
| 依赖缓存 | 减少 50%+ 时间 | npm ci --cache / maven 缓存 / actions/cache |
| 并行矩阵 | 多版本同时测 | matrix / parallel stages |
| 增量构建 | 只测变更模块 | 路径过滤（paths / only.changes） |
| 构建缓存 | 编译产物复用 | Gradle build cache、Webpack cache |
| 测试分片 | 按文件拆分并行 | split tests / sharding |
| 避免重装 | 复用预装运行时 | 官方镜像已带 Node/Maven |

## 失败处理策略

| 场景 | 策略 |
| --- | --- |
| 依赖下载失败（网络抖动） | 自动重试 1~2 次，指数退避 |
| 单元测试失败 | 立即阻断，发通知，附报告 |
| 部署中途失败 | 自动回滚到上一个版本 |
| 健康检查失败 | 视为部署失败，摘流量 + 回滚 |
| 非关键检查（如 lint 警告） | `allow_failure: true`，不阻断但记录 |
| 超时 | Job 级 `timeout` 兜底，防止挂起占资源 |

::: danger 重试陷阱
重试只适合**幂等**操作：依赖下载、构建。**部署/发消息/扣费类步骤禁止自动重试**，否则会重复执行产生事故；部署失败应走“回滚”而不是“重试”。
:::

## 环境治理

### 多环境配置

```yaml
variables:
  DEV_URL: https://dev.example.com
  STAGING_URL: https://staging.example.com
  PROD_URL: https://example.com
```

按环境选择：

```yaml
rules:
  - if: '$CI_COMMIT_BRANCH == "main"'
    variables:
      TARGET_ENV: staging
  - if: '$CI_COMMIT_TAG'
    variables:
      TARGET_ENV: prod
```

### 数据隔离

- dev 用测试数据，绝不连生产库。
- staging 尽量用脱敏数据，验证真实行为。
- prod 部署后跑只读冒烟，不产生脏数据。

### 密钥按环境隔离

```text
DEV_TOKEN / STAGING_TOKEN / PROD_TOKEN 分别存储，生产密钥只授权生产 Job 使用。
```

## 制品与版本规范

制品命名统一：

```text
{应用名}-{主版本}.{次版本}.{补丁}-{构建号}-{commit短SHA}
示例：order-service-1.2.0-45-a1b2c3d.jar
```

镜像 Tag 规范：

```text
latest（最新，仅 dev 使用）
1.2.0-45-a1b2c3d（不可变，部署用）
```

::: warning 不要覆盖历史 Tag
同一 Tag 多次 push 会让“回滚”指向错误镜像。发布镜像必须不可变：一个 SHA 只对应一个镜像。
:::

## 通知与可观测

1. 成功/失败通知到 IM（钉钉/企微/Slack），失败附构建链接。
2. 构建指标（时长、成功率、排队时间）接入监控，趋势恶化提前处理。
3. 流水线日志集中检索（如 [日志体系](../../../Ops/LogSystem/index.md) 中的 ELK/Loki），排查历史构建。

## 企业级设计清单

::: tip 流水线设计十问
1. 提交流水线 10 分钟内能完成吗？
2. 每个产物都能对应 commit 与构建号吗？
3. dev/staging/prod 用的是同一个制品吗？
4. 质量门禁在合并前强制执行了吗？
5. 生产部署有人工确认（或等价的安全机制）吗？
6. 部署失败会自动回滚吗？
7. 密钥都存平台密钥库，没进代码库吗？
8. 并发部署会被互斥拦截吗？
9. 失败通知会第一时间到责任人吗？
10. 有定期备份流水线配置与制品吗？
:::

## 易错点与最佳实践

::: danger 高频翻车点
1. **阶段拆太多太碎**：每个阶段只有一条命令，调度开销大于收益；按业务阶段合并。
2. **用 `sleep` 等部署完成**：应该轮询健康检查接口（curl --retry）或等待 Deployment 就绪。
3. **并发部署互踩**：生产部署要加锁/互斥（`concurrency` / lockable resources）。
4. **流水线配置不评审**：修改 CI 配置不走过 MR，出了事故无从追溯。
5. **忽略本地复现**：流水线失败只能线上看日志，应提供本地可执行的同一脚本。
:::

## 验证方式

1. 用计时工具统计提交流水线各阶段耗时，找出最长阶段优化。
2. 做一次“模拟部署失败”，确认自动回滚与通知全流程。
3. 并发触发两次生产部署，确认第二次被拦截或排队。
4. 检查制品仓库：同一 SHA 只有一份不可变制品。

- [完整项目交付 · 测试策略与门禁](../../../Others/ProjectDelivery/Testing/index.md)：覆盖率**按模块**设阈值的理由、三档数据隔离的取舍、flaky 当天修或删
- [完整项目交付](../../../Others/ProjectDelivery/index.md)：本页讲流水线**自身**怎么设计（分阶段、制品、通知），该专题讲**阶段顺序为什么按「失败代价」排**、以及五阶段如何把既有门禁一一挂上去
- **runner 上不要依赖本机终端环境**：runner 是一个**干净、无 dotfiles、无 home 别名**的容器/机器。本机跑通的自动化脚本搬到 CI 上常因三点失败：① 依赖 `~/.zshrc` 里的别名或 `starship` 提示符（CI 用非交互 `sh`，这些根本不加载）；② 依赖只在本机装了的新 CLI（[eza/delta/ripgrep 等](../../Efficiency/ShellProductivity/index.md)），runner 上没有；③ 依赖交互式行为（分页器、确认提示），CI 里没有 TTY 会挂住。**对策一律是"显式化"**：脚本头部 `set -euo pipefail`、工具用绝对调用的基础命令或显式安装步骤、需要 TTY 的分页器一律 `--no-pager` / `| cat`。判据很简单——**把脚本丢进一个全新的 `debian:stable-slim` 容器里能不能跑**。


## 与「容量与成本治理」专题的分工（第 156 天补充）

| 问题 | 本页 | [容量与成本治理](../../../Ops/CapacityCost/index.md) |
| --- | --- | --- |
| 流水线阶段怎么切、门禁放哪一层 | **本页回答** | 只引用位置 |
| 成本门禁检查什么、阈值从哪来 | 给机制 | **那边回答**：标签四键、规格与配额上限 |
| 成本从什么时候开始算 | 不回答 | **那边回答**：PR 内成本 diff 与月度评审 |

**一句话结论**：成本门禁只有放在**合并之前**才有意义——合并后再算成本，得到的是一份通知，不是一次拦截。

**这一页特有的坑**：把成本检查做成「每日巡检」而不是「PR 门禁」，会让所有成本问题都变成事后追认。门禁的价值在于**让人在写代码时就知道要花多少钱**，而不是在账单出来时解释。

## 与「观测驱动开发」专题的分工（第 158 天补充）

本页讲**流水线的阶段划分与门禁挂载**（构建、测试、制品、部署阶段怎么排）；第 158 天的三页（[指标先行](/docs/Tools/ObservabilityDriven/MetricsFirst/index.md)、[功能开关](/docs/Tools/ObservabilityDriven/FeatureFlag/index.md)、[灰度度量](/docs/Tools/ObservabilityDriven/GrayMetrics/index.md)）讲**放量阶段的判据**。流水线负责把「放量」这件事执行出去，判据负责决定它该不该继续。

| 边界问题 | 归本页 | 归该专题 |
| --- | --- | --- |
| 灰度阶段在流水线里怎么表达 | 阶段定义、人工确认节点、制品推进 | 不涉及——阶段怎么排是工程问题 |
| 「观察 30 分钟再进下一阶段」怎么实现 | `wait` / 手动审批 / 定时触发 | 30 分钟不够：窗口必须覆盖一个业务高峰，否则周五下午放量等于没观察 |
| 门禁红的判据从哪来 | 命令退出码、报告聚合 | 判据内容：错误率相对倍数、样本量下限、P99 倍数 |
| 发布开关放哪个阶段读 | 环境变量注入时机 | 每条开关的四行必写（谁开 / 开给谁 / 何时关 / 怎么删） |

本页特有的一个坑：**「自动推进」与「自动回滚」在流水线里长得很像，语义相反**。前者在门禁通过时继续，后者在护栏越线时撤销；如果两者共用同一个「阶段状态」，会出现「回滚把阶段标记为失败、于是流水线自动重试一次放量」——这正是灰色发布里最危险的自循环。正确做法是让回滚写一个独立状态，重试必须人工触发。

## 与「变更管理」专题的分工（第 170 天补充）

本页讲**流水线长什么样**（阶段划分、并行与缓存、制品与晋级）；[变更管理与发布工程](../../../Ops/ChangeManagement/Overview/index.md) 讲**每个闸门里的判定标准是谁定的**。流水线是「路」，闸门的判据是「红绿灯的规则」。

| 环节 | 本页 | 变更管理专题 |
| --- | --- | --- |
| 闸门放在哪一段 | 阶段编排与失败即停 | —— |
| 闸门判什么 | 测试、扫描、镜像扫描的通过条件 | 变更分级、高危变更的形状规则、双人复核 |
| 谁有权跳过 | 手工重试与绕过开关 | 只有紧急变更通道能跳，且计入月度额度 |

**一条本页特有的坑：变更单号不能是自由文本。** 很多流水线在触发参数里留一个 `change_id` 的字符串输入框，结果三分之一是空的、三分之一填的是聊天里的口头编号，事后**没法把「这次发布」和「那次授权」对上**。要么把它变成必填参数并在制品上打标（`build.change_id` 进镜像 label），要么承认它不存在——半吊子的留痕比没有留痕更危险，因为它看起来像有。

## 与「研发效能度量」专题的分工（第 172 天补充）

本页设计流水线的阶段、并行与门禁；对[研发效能度量](../../EngineeringMetrics/index.md) 来说，流水线是**事件源**——它产生的部署记录、构建摘要、失败原因，正是五个指标的原料。

| 问题 | 归本页 | 归研发效能度量 |
| --- | --- | --- |
| 阶段怎么划、缓存怎么用、门禁挂在哪 | ✅ | —— |
| 一次发布里有 migrate / smoke / switch 三个 stage，算几次部署 | 归本页定义 | ✅ [交付指标](../../EngineeringMetrics/DeliveryMetrics/index.md) 的计数边界 |
| 流水线失败率能不能当「变更失败率」 | —— | ✅ 不能：前者含 lint/单测失败，后者只数生产影响 |
| 部署记录要留哪些字段才能算指标 | 归本页落地 | ✅ [数据管道](../../EngineeringMetrics/DataPipeline/index.md) 的五张表 |

**本页特有的坑**：如果按**流水线 stage** 统计「部署次数」，一次发布会被算成 3 次（migrate + smoke + switch），部署频率直接翻三倍。计数单位必须是**发布单**（一次让新版本对用户可用），stage 只是它的内部步骤。这个定义要写在流水线模板里，不能靠人记。

## 与「数据库变更与在线 Schema 演进」专题的分工

| 关注点 | 本页负责 | 由专题负责 |
| --- | --- | --- |
| 流水线怎么分层、门禁怎么排 | 构建 / 测试 / 部署阶段 | 不管 |
| 数据库迁移放在哪一步 | 一句「部署前执行」 | 迁移的锁与时长、expand/contract 批次 |
| 迁移失败怎么处理 | 不管 | 原子 DDL 的边界与恢复路径 |

完整方法见 [数据库变更与在线 Schema 演进](../../../DB/SchemaEvolution/index.md)。

::: warning 本页特有的坑
CI 里的迁移跑在**空库**上，往往几十毫秒就过；同一份脚本在生产的亿行表上可能是几十分钟的重写。「CI 绿了」只能证明语法与依赖没问题，**不能**证明生产可执行——所以变更时长必须单独用「行数 × 单行成本」算，不能拿 CI 耗时当基线。
:::
