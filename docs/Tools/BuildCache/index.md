# 构建缓存与可复现构建

<p style="text-align:center;"><img src="./assets/build-cache-logo.png" style="zoom:75%;" /></p>

**构建缓存（build cache）** 解决的是一个非常朴素的问题：同一份输入，为什么要把同一个结果算第二遍？**可复现构建（reproducible build）** 解决的是紧跟着的那个问题：你怎么证明「同一份输入」真的产出了「同一个结果」？

这两件事必须一起做，因为它们互为判据：**没有可复现性，缓存就无法被验证**（你没法说清缓存里那份产物到底对不对，只能祈祷它是对的）；**没有缓存，可复现性就永远只是 CI 里那个跑不完的额外任务**（每次全量重建、每次比对，代价高到没人愿意天天跑）。把两者接在一起的那根轴是**指纹（fingerprint）**：它是输入的函数，也是缓存条目的键；指纹定义得对，缓存才对；指纹可复现，产物才可复现。

本专题讲的是这中间**最容易做错、又最难被现有监控发现**的那一段：指纹该由哪些字段组成、本地与远程缓存的失效模式有什么不同、假命中（false hit）是怎么长出来的、以及一个产物要做到「换台机器换个人还是同一串字节」需要改哪几处。

::: tip 一句话理解
缓存的收益是**秒**，缓存的代价是**错误**。所以真正的判据不是「命中率多少」，而是**「一次假命中要多久才能被发现」**——命中率低只是慢，假命中是错，而「错」在构建系统里会一路传到线上。
:::

## 三个数字先摆出来

| 事实 | 读数 | 出处 |
| --- | --- | --- |
| 同一目录两次 `tar czf` 打包，字节**不同** | `95ae1c6b…` vs `79039b50…` | 本机实测（[可复现构建](./Reproducible/index.md)） |
| 同一目录按「排序 + 固定 mtime + `gzip -n`」打包两次，字节**相同** | `5d0c2b86…` = `5d0c2b86…` | 同上 |
| 就地写缓存文件，并发读者读到**半个文件**的比例 | **3.9%**（996 次读里 39 次） | 本机实测（[本地缓存](./LocalCache/index.md)） |

这三个数没有一个是理论值，全部来自本机可重跑的实验（脚本见 [实战](./Practice/index.md) 第六节）。它们分别对应本专题的三条主线：**可复现性是可以被字节级证伪的**、**缓存写入的原子性不是洁癖而是正确性**、**「看起来能跑」与「字节一致」之间隔着一整套工程**。
