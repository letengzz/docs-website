# 概述：代码搜索到底在解决什么问题

搜索框人人都会做，但「代码搜索」这个需求有三个别处没有的硬要求：**给出坐标**（文件 + 行 + 列）、**能解释为什么命中**（哪个 gram / 哪个词）、**能证明自己有多新**（索引对应的 commit 或 mtime）。少任何一条，用户下次就不再用它了——不是因为它慢，而是因为**它给的答案没法被信任**。

这一页先不谈实现，只做三件事：把「查询形态 → 延迟预算」这条线定下来，把「搜不到」的五种根因分层，再给一条「到底该不该上索引」的判断线。后面九页都是这三个结论的展开。

::: tip 一句话理解
代码搜索卖的不是「相关文档」，而是**「一个可以被点开的坐标，加一句为什么」**。凡是不回答这两件事的搜索，在代码场景里都会被 `git grep` 打败——因为 `grep` 至少不会骗你。
:::

## 一、代码搜索回答的是三个问题

![三种查询形态与延迟预算](../assets/cs-query-taxonomy.svg)

| 用户的问题 | 他要的答案 | 允许的形态 | 失败时他会怎么做 |
| --- | --- | --- | --- |
| 「这个符号在哪定义/被用」 | 文件 + 行 + 一段上下文 | 精确、可跳转 | 回到编辑器里 `Cmd+Shift+F`，然后不再用你的搜索 |
| 「这段逻辑为什么这样写」 | 命中的位置 + **为什么**（哪个条件命中、哪次提交引入） | 可解释、可追溯 | 去问人，或者放弃 |
| 「我看到的这份文档/代码是不是最新的」 | 索引时间 + 对应版本 | 可自证 | 认为「系统里没有」，然后重复劳动 |

第三条最容易被忽略：**搜索的信任度等于「它敢不敢说自己有多新」**。一个索引落后三天的系统，如果界面上写着「索引于 3 天前」，用户会自己去改代码确认；如果什么都不写，他会得出「这里没有这段逻辑」的结论，然后写出重复实现。

## 二、三档延迟预算，先定预算再选结构

延迟预算不是「越快越好」，而是**由交互节奏决定的硬指标**。三档之外还有一个隐形的第四档：批量巡检（CI 里跑），它的预算是分钟级，但**必须可复跑**。

| 形态 | 触发节奏 | 预算 | 预算的来历 | 由此排除掉的做法 |
| --- | --- | --- | --- | --- |
| 交互式补全 | 每敲一个字符 | **≤ 50 ms** | 一帧 16.7 ms × 3（留给渲染与网络） | 全量打分、逐文件线性扫描、同步等待 |
| 全库检索 | 回车 / 停手 300 ms | **≤ 300 ms** | 人对「按下回车到看见结果」的耐心线 | 无界候选集、无超时的正则、`OFFSET` 深翻页 |
| 批量巡检 | CI / 定时任务 | 分钟级，但可复跑 | 不受人机交互约束 | 采样、近似、依赖缓存的「上次结果」 |
| （隐形）索引构建 | 保存 / 提交 / 夜间 | 保存后 ≤ 2 s，夜间不限 | 编辑器的「保存即刷新」预期 | 每次保存都全量重建 |

::: warning 为什么补全的预算是 50 ms 而不是 100 ms
因为补全的结果**还要经过一次渲染 + 一次网络往返**才能出现在用户眼前。预算里给「检索」留的是 50 ms，剩下的 50 ms 属于传输与绘制。把检索预算花到 100 ms，用户体感就是「打字卡」——而他不会说「搜索慢」，他会说「这个编辑器有问题」。
:::

## 三、「搜不到」的五种根因：先分层，再动手

这是本专题最重要的一张表。搜不到时**不要先怀疑排序**——排序只影响「看到的顺序」，不影响「有没有」。

| # | 症状 | 根因层 | 典型原因 | 判据 |
| --- | --- | --- | --- | --- |
| 1 | 某些词搜得到、某些搜不到 | **入库/分词** | 用默认 `split()` 分词；中文整句被当成一个 token | `CSG-B` |
| 2 | 全库都搜不到某个文件里的内容 | **枚举** | 忽略规则写反（把 `src/` 排除了）、`.gitignore` 语义用错 | `CSG-A` |
| 3 | 昨天刚改的内容搜不到，重启后正常 | **增量** | 用 `mtime + size` 当指纹；`cp -p` / `git checkout` 保留 mtime | `CSI-B` |
| 4 | 删掉的文档还能搜到 | **删除可见性** | 只删文件不删 posting；查询出口没做存活反查 | `CSI-C` |
| 5 | 管理员搜得到、普通用户搜不到 | **权限** | 先取 top-k 再过滤（后过滤） | `CSP-B` |

五种里有四种**在开发机上不会复现**：开发时语料小、文件刚改、自己是管理员、用的还是英文查询。所以本专题每一页的验收都要求「**换一个语料规模 + 换一个非管理员账号 + 换一个中文查询**」各验一次。

## 四、该不该上索引：四问决策树

![索引买的是「不用读全部字节」，不是「一定更快」](../assets/cs-ngram-cost.svg)

1. **语料小于几十 MiB、只给自己用？** → 不要索引。`rg` / `git grep` 就够。本仓 15.0 MiB 全量扫一遍只要 **5.7 ms**，任何索引的维护成本都比这 5.7 ms 贵。
2. **需要给**别人**用，且要「按相关性排序」？** → 需要索引。线性扫描没有全局打分：你没法在扫完整个仓库之前知道哪 10 条最相关，而扫完就没有补全预算了。
3. **需要按权限裁剪结果？** → 需要索引，并且**权限必须能编进查询**（见[权限过滤](../PermissionFilter/index.md)）。线性扫描反而更容易做对，因为它天然是「逐文档判断」，但它做不到 300 ms。
4. **需要跨仓 / 跨分支 / 跨历史？** → 需要索引，而且需要**多版本段**。`git grep` 只能看一个工作树；要看 20 个分支就得 checkout 20 次。

四问之外还有一条否决条件：**如果团队没人能维护「增量 + 删除 + 权限」这三件事，就不要上索引**。这三件事任何一件做错，搜索都会从「不好用」变成「不可信」，而不可信的搜索比没有搜索更糟——用户会基于错误结论做决策。

## 五、索引买什么、不买什么

| 维度 | 线性扫描（grep / rg） | 索引（n-gram / 倒排） | 结论 |
| --- | --- | --- | --- |
| 冷启动延迟 | 0（没有索引要加载） | 加载段 / 建连（毫秒~秒） | 小语料上扫描赢 |
| 单次查询延迟 | 与语料字节数成正比 | 与**候选集大小**成正比 | 语料越大索引越赢 |
| 相关性排序 | 做不到（没有全局 idf） | 天然支持 BM25 / 字段权重 | 只要排序就要索引 |
| 增量成本 | 0（每次都是全量） | 每文件 3.08 ms（实测） | 索引有维护成本 |
| 权限 | 逐文档判断，天然正确 | 需要设计（预过滤/分片） | 索引更容易做错 |
| 删除一致性 | 天然一致（文件没了就没了） | 需要墓碑 + 压缩 | 索引的最大坑 |
| 中文/标识符 | 子串匹配天然正确 | 需要选对 n 与 tokenizer | 扫描不会错，只会慢 |

::: danger 三个「看起来是优化、实际是降级」的决定
1. **为了「快」把候选集截断到 1,000 条再排序**：截断依据是插入顺序，不是相关性。用户搜一个常见词，前 1,000 条全是同一篇文档的不同行，真正的答案在 5,000 名之外。判据 `CSQ-F`。
2. **为了「省体积」只索引标识符首字母缩写**：`OutboxPublisher` 变成 `OP`，于是 `Outbox` 搜不到它。任何「压缩到看不出原名」的方案，都会让前缀查询失效。判据 `CSX-E`。
3. **为了「简单」在查询时才读文件内容做二次确认**：验真本来是对的（trigram 必须验真），但如果验真要把 2,406 个文件全读一遍，增量索引的意义就没了。验真应该只读**候选集对应的块**。判据 `CSQ-D`。
:::

## 六、一条纪律：凡「索引更快」的说法，都必须给出语料规模与查询形态

这句话值得单独成节，因为它是本专题所有读数的前提。同一份索引，在两种语料上会给出完全相反的结论：

| 语料 | 全量扫描 | 3-gram 查询 | 谁赢 |
| --- | --- | --- | --- |
| 本仓 15.0 MiB / 2,406 篇 | **5.7 ms** | **0.42 ms**（「幂等键」）| 索引赢，但差距只有 13 倍，而建索引要 8.64 s |
| 100 万文件 / 约 6 GiB | 约 **4 s**（按 1.5 GB/s 读盘乐观估计） | **毫秒级**（候选集不变大） | 索引赢 3 个数量级 |

所以正确的说法不是「索引更快」，而是：**索引把「每次查询都要读全部字节」换成了「一次性读全部字节 + 每次查询读候选集」**。语料越小、查询越少，这笔账越不划算。

## 七、判据表

| 判据 | 断言 | 怎么验 |
| --- | --- | --- |
| `CSO-A` | 每个查询都能回答「在哪」（文件:行:列），而不只是「哪个文件」 | 取任意结果项，检查返回值里是否有 `line` 与 `column` 字段，且能定位到实际字符 |
| `CSO-B` | 上索引前已实测过线性扫描基线，且写下了「为什么扫描不够」 | 在仓库根目录跑 `time rg -c 关键词`；把耗时与本页的 5.7 ms 对照，写进决策记录 |
| `CSO-C` | 交互式查询的 p95 ≤ 50 ms、全库查询 p95 ≤ 300 ms，且有分桶统计 | 压测脚本按两档形态各打 1,000 次，输出 p50/p95；超过预算的查询要能按形态归因 |
| `CSO-D` | 索引侧能报出「索引时间 / 对应 commit」，用户可自证陈旧 | 界面上显示 `indexed_at` 与 `commit`；把它与 `git log -1 --format=%cd` 对比，差值为陈旧度 |
| `CSO-E` | 「搜不到」的分诊路径按五层顺序走（枚举→分词→增量→删除→权限），不跳层 | 拿一个真实的搜不到用例，逐层给出读数；跳层排查视为不通过 |
| `CSO-F` | 用默认分词器（`split()` / 空白）的代码不出现在索引器里 | `grep -n "\.split()" src/index/*.py` 在分词路径上无命中，或命中处有注释说明为何安全 |
| `CSO-G` | 每条结果带「为什么命中」的依据（命中的 gram / 词 / 规则） | 结果项里有 `matched_terms` 或 `matched_span` 字段，且能在原文里高亮出来 |
| `CSO-H` | 语料规模、查询形态、预算三者被写进同一份决策记录，改任一项都要重测 | 决策记录里有「语料 2,406 篇 / 15.0 MiB、补全 50 ms、全库 300 ms」三行；缺任一行即不通过 |

## 八、如何验证

下面三段命令都在仓库根目录执行，输出应与注释里的期望值一致（数字取自本机实测，语料就是本仓）。

```shell
# 1) 语料规模与「空白分词 vs 子串」的召回差
python3 - <<'PY'
import os
docs = {}
for base in ("docs", "project"):
    for dp, _, fs in os.walk(base):
        for f in fs:
            if f.endswith(".md"):
                p = os.path.join(dp, f)
                docs[p] = open(p, encoding="utf-8", errors="replace").read()
print("files=%d bytes=%d" % (len(docs), sum(map(len, docs.values()))))
q = "幂等"
print("ws=%d sub=%d" % (sum(1 for t in docs.values() if q in t.split()),
                       sum(1 for t in docs.values() if q in t)))
PY
# 期望：files=2406 bytes=15679054
#       ws=41 sub=394        ← 空白分词丢掉 89.6% 的召回
```

```shell
# 2) 线性扫描基线：决定「这个规模要不要索引」
python3 - <<'PY'
import os, time
docs = {}
for base in ("docs", "project"):
    for dp, _, fs in os.walk(base):
        for f in fs:
            if f.endswith(".md"):
                p = os.path.join(dp, f)
                docs[p] = open(p, encoding="utf-8", errors="replace").read()
t0 = time.time()
hits = [p for p, t in docs.items() if "幂等" in t]
print("full_scan_ms=%.1f hits=%d" % ((time.time() - t0) * 1000, len(hits)))
PY
# 期望：full_scan_ms≈5~6 hits=394
# 判读：5 ms 量级的全库扫描，说明「补全形态之外的查询根本不需要索引」
```

```shell
# 3) 三档预算的分桶统计（把真实查询日志按形态分组，看 p95 落在哪）
python3 - <<'PY'
import statistics
# 用真实日志替换；这里用一组示意读数说明输出形状
samples = {"complete": [3, 5, 8, 12, 19, 26, 31, 44, 49, 52],
           "search":   [40, 65, 88, 120, 160, 210, 240, 280, 295, 310]}
for k, v in samples.items():
    v = sorted(v)
    p95 = v[int(len(v) * 0.95) - 1]
    print("%-9s p50=%.1f p95=%d n=%d" % (k, statistics.median(v), p95, len(v)))
PY
# 期望：complete p95=49（≤50 达标）；search p95=295（≤300 达标）
# 判读：p95 超预算就要先按形态拆，而不是「整体调优」——两种形态的优化手段完全不同
```
