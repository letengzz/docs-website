# 埋点规范与基数控制

埋点的失败方式只有两种，但都很贵：**记不够**（出事时缺维度，无法切分）和**记太多**（基数爆炸，账单翻倍且查询变慢）。两者不是程度差异，是**两个相反方向的错误**，所以规范必须同时给上限和下限。

「记不够」的典型后果已经在上文出现过三次：缺 `tenant_id` 导致无法判断影响面、缺版本快照导致灰度期无法归因、缺 `trace_id` 导致日志与追踪对不上。本页把下限写死成四个必带字段，把上限写死成可算的序列数。

## 判据族声明

本页判据族 `IM-A` ~ `IM-H`，共 8 条。定义表在第八节。

## 本页不讲什么

- 不讲 OpenTelemetry SDK 的初始化、导出器配置与跨进程传播实现，归 [OpenTelemetry](/docs/Ops/Observability/OpenTelemetry/index.md)。
- 不讲采样算法（头部/尾部、概率/速率限制），归 [采样](/docs/Ops/Observability/Sampling/index.md)。
- 不讲前端埋点 SDK 的自动采集能力（页面停留、点击热图），本页只讲**业务事件的字段约定**。

## 一、三处埋点：各自能回答什么

一次业务动作会经过三层，三层各能看到一部分事实。分工必须写死，否则会出现两套数字：

| 层 | 能看到 | 看不到 | 该记什么 |
| --- | --- | --- | --- |
| 客户端 | 用户意图、交互结果、渲染耗时 | 服务端是否真的落库 | 意图事件（`clicked` / `submitted`）与端侧性能 |
| 服务端 | 业务结果、事务是否提交、下游调用 | 用户在端上看到了什么 | 结果事件（`created` / `failed`）——**唯一可信源** |
| 网关 / 边车 | 流量事实、状态码、上游耗时 | 任何业务语义 | 流量指标（QPS、状态码分布），不含业务名 |

一条判据：**「业务是否成功」只认服务端**。原因很直接——客户端的「提交成功」只证明它收到一个 2xx，而 2xx 完全可能是「已接受但异步失败」。

::: warning 最容易忽略的一层
网关层的指标常被当成业务指标用，例如用「`/api/cards` 的 QPS」代表「卡片创建量」。这在 REST 语义下并不成立：同一个 `POST /api/cards` 可能包含创建、复制、导入三种业务动作，网关只看到路径。业务量必须由服务端在业务分支处上报。
:::

## 二、一处一义：为什么两套数字比没有数字更糟

设一次「创建卡片」的动作，前端在提交回调里记一条 `card_create_success`，服务端在事务提交后记一条 `card_created`。上线一周后：

| 日 | 前端记 | 服务端记 | 差 |
| --- | --- | --- | --- |
| 周一 | 1,240 | 1,240 | 0 |
| 周二 | 1,318 | 1,295 | 23 |
| 周三 | 986 | 986 | 0 |
| 周四 | 1,502 | 1,470 | 32 |

差值出现在周二与周四。可能的解释有五个：网络失败但前端已提示成功、用户关闭页面导致上报丢失、服务端重试去重、前端离线续传重复上报、埋点 SDK 采样差异。**你无法从数字上区分它们**，于是这个差值永远无法结案。

结果不是「多了一个数字」，而是**两个数字都失去了决策资格**。这就是「记了不信」的成因。

正确做法：

```text
① 服务端记「结果」，作为唯一业务口径。
② 前端只记「意图」，且名字里明确体现意图（clicked / submitted，不是 success）。
③ 两端用同一个 `event_id` 关联，用于对账而不是用于计数。
```

对账的正确姿势是**按天抽样对账**，不是「让两个数相等」：抽 1000 条 `event_id`，看两端各有多少条、差集是什么特征。差集恒为「前端有、服务端无」且集中在弱网时段，说明是上报丢失；差集双向存在，说明有重复上报。

## 三、命名：三段式与两条禁令

```text
<对象>_<动作>_<结果>

card_move_success
card_move_conflict      ← 乐观锁失败，是业务结果不是错误
comment_create_failed   ← 真正的失败
board_sync_lagged       ← 状态类事件用过去分词，不用 ok/ng
```

两条禁令：

| 禁令 | 反例 | 后果 |
| --- | --- | --- |
| 不用驼峰 | `cardMoveSuccess` | 同一指标在不同服务里被写成 `card_move_ok`，永远聚不到一起 |
| 不用编号与缩写 | `metric1`、`biz_ok`、`cm_s` | 三个月后无人能解释它的口径 |

一条建议：**结果字段只用有限集合**——`success` / `failed` / `conflict` / `timeout` / `rejected`。不要在结果里塞错误信息（那是日志的职责），否则结果字段的取值集合会随错误文案增长，直接变成高基数维度。

## 四、基数爆炸：把「以后再说」算成账单

Prometheus 类系统的时间序列数近似等于**各标签取值数的笛卡尔积**：

```text
序列数 ≈ 指标数 × Π(每个标签的取值数)
```

算一遍一个看起来很节制的设计：

| 标签 | 取值数 | 说明 |
| --- | --- | --- |
| `service` | 10 | 十个服务 |
| `status` | 4 | 成功/冲突/失败/超时 |
| `app_version` | 5 | 灰度期五个版本并存 |
| `tenant` | 50 | 五十个租户 |

`10 × 4 × 5 × 50 = 10,000` 条序列。单个指标一万条，勉强可以接受。

现在加入 `board_id`（十万块板，活跃 1 万）：

```text
10,000 × 10,000 = 100,000,000 条序列
```

一亿条序列。这个指标的写入、存储、查询全部失效：查询一次要扫一亿条序列，面板打不开；存储成本按序列数与时序点计费，当月账单会多出一个零。

### 可执行的阈值

| 维度 | 上限 | 超限时怎么办 |
| --- | --- | --- |
| 单个标签取值数 | **< 100** | 超过则不进指标，改放日志或追踪属性 |
| 单个指标序列数 | **< 10,000** | 超过则降维（去掉最细的那一维）或分片成多个指标 |
| 单条事件 payload | **< 8 KB** | 超过则拆分或存引用（见项目侧事件表的 `payload ≤ 8 KB` 约束） |

判断某个维度是不是「高基数」只需一个问题：**它的取值数会不会随业务数据增长？** `status` 不会（有限集合），`tenant` 会（随客户增长），`board_id` 会（随内容增长），`url` 会（带 id）。凡是「会」的，一律不进指标标签。

::: tip 高基数维度并不是不能查
它们该去的两个地方：

1. **日志字段**：可按值检索（Elasticsearch / Loki 的标签索引或全文），量大但可按保留期控制。
2. **追踪属性**：跟着那一次请求走，天然只保留被采样的部分。

两者的共同点是**按量或按采样存储**，而不是按**序列数**存储。这就是为什么它们能承受高基数。
:::

## 五、四个必带字段

四个字段解决四类「出事时无法切分」：

| 字段 | 解决什么 | 缺失时的现场 |
| --- | --- | --- |
| `trace_id` | 把服务端、下游、日志串成一次调用 | 一行错误日志孤立无援，只能靠时间戳猜 |
| `tenant_id` | 判断影响面（1 个租户还是全部） | 只能全员公告「部分用户受影响」 |
| `app_version` + 开关快照 | 判断是新版本还是老版本、开关是开还是关 | 灰度期完全无法归因，只能全量回滚 |
| 业务主键（如 `board_id`） | 定位到具体对象，用于复现 | 只能复现「某一类」，不能复现「这一个」 |

第三条最容易被省略，也最致命。灰度期出事的第一问是「受影响的是不是只有灰度组」，如果事件里没有开关快照，这个问题只能靠**时间窗口**间接推断，而时间窗口推断在以下两种情况必然失效：灰度组与全量组有重叠时段、开关在事故期间被改过。

```text
# 建议的埋点字段模板（服务端）
event: card_move_success
fields:
  trace_id:     必带   来自入站 traceparent，缺失则生成并标注 source=self
  tenant_id:    必带   来自令牌解析后的成员关系，不来自请求头
  app_version:  必带   构建期注入，不从请求头读
  flags:        必带   本次请求评估到的开关快照（只带与业务相关的）
  board_id:     按需   用于定位，不入指标标签
  latency_ms:   按需   端到端耗时，需写明起点与终点
```

## 六、采样：先保错、再保慢、最后按比例采成功

采样算法归 [采样](/docs/Ops/Observability/Sampling/index.md)，本页只给一条业务侧原则，因为它决定**事故时有没有样本**：

| 优先级 | 采样策略 | 理由 |
| --- | --- | --- |
| 1 | 错误与超时 **全留**（100%） | 事故期间正是需要样本的时候，采掉等于自断证据 |
| 2 | 慢请求 **全留**或高比例（≥ 50%） | 尾延迟问题的样本本来就少 |
| 3 | 成功请求按比例（1% ~ 10%） | 量大且同质，少量样本足以看趋势 |

反过来的配置（成功全留、错误按比例采）在实践中并不罕见，因为它的实现更简单：一个固定概率。它的后果是**错误样本比例与错误率成反比**——错误越多，被采到的越少，因为采样率是固定的而分母在涨。

## 七、五个常见错误写法

| 写法 | 现象 | 修法 |
| --- | --- | --- |
| 在循环里读配置中心 / 埋点上报 | 单请求出现 200 次配置查询，P99 从 80 ms 涨到 400 ms | 每请求读一次并缓存，见 [功能开关](../FeatureFlag/index.md) |
| 埋点写在与业务同一事务里 | 事务回滚导致埋点丢失，恰好丢掉失败样本 | 埋点必须在事务提交后或独立异步队列 |
| 用错误文案做标签 | 标签取值随文案增长，序列数逐月上涨 | 标签只用有限枚举，文案进日志 |
| 前端在 `beforeunload` 上报 | 部分浏览器丢弃请求，成功率系统性偏低 | 用 `sendBeacon` 或改为服务端为准 |
| 埋点缺 tenant 维度 | 事故时无法判断影响面 | 从作用域统一注入，不靠每个调用点手写 |

第二条尤其隐蔽：把埋点写在事务内看起来「更一致」，实际是把**失败样本与成功样本一起丢掉**。事务回滚时埋点记录也回滚，于是你永远看不到那次失败。

## 八、判据族定义

| 判据 | 规则 | 违反时的样子 | 验证方式 |
| --- | --- | --- | --- |
| `IM-A` | 业务结果只由服务端上报，客户端只上报意图 | 前后端两套数字，差 23 条无人能解释 | 命令 1 |
| `IM-B` | 事件名用三段式、全小写下划线，结果字段取有限枚举 | 同一动作出现 `cardMoveOK` 与 `card_move_success` | 命令 2 |
| `IM-C` | 任何指标标签的取值数 < 100，且不随业务数据增长 | `board_id` 进标签，序列数到一亿 | 命令 3 |
| `IM-D` | 单指标序列数 < 10,000，超限必须降维 | 面板打不开、查询超时 | 命令 4 |
| `IM-E` | 服务端事件必带 `trace_id` / `tenant_id` / `app_version` / 开关快照 | 灰度期无法归因，只能全量回滚 | 命令 5 |
| `IM-F` | 埋点不得写在业务事务内，失败样本必须先于回滚落盘 | 失败样本恒定缺失 | 命令 6 |
| `IM-G` | 错误与超时样本全留，成功样本按比例采 | 事故期间样本被采掉 99% | 命令 7 |
| `IM-H` | 同一动作前后端用 `event_id` 对账，而非要求两个数相等 | 试图「让两个数对齐」导致互相改口径 | 命令 8 |

## 如何验证

```shell
# ① IM-A：客户端埋点里是否出现了「成功」类结果名
grep -rn "track(" web/src --include=*.ts --include=*.vue | grep -iE "success|_ok\b" | head
```

**预期输出**：空。若命中（如 `track('card_create_success')`），说明业务成功在两端各记了一次，`IM-A` 不成立。

```shell
# ② IM-C：指标标签是否包含会随业务增长的维度
grep -rn "labelNames(" src/main/java | grep -E "board_id|card_id|user_id|url|path"
```

**预期输出**：空。若命中 `path`，注意 `/api/boards/{id}` 这种模板路径不算高基数（取值有限），而原始 URI 算——判据要看**取值是否可枚举**，不是看字段名。

```shell
# ③ IM-D：按当前标签基数估算序列数（乘法累加）
python3 - <<'PY'
labels = {"service": 10, "status": 4, "app_version": 5, "tenant": 50}
n = 1
for k, v in labels.items():
    n *= v
print("序列数 =", n, " 上限 10000 →", "OK" if n < 10000 else "OVER")
labels["board_id"] = 10000
n2 = 1
for v in labels.values():
    n2 *= v
print("加入 board_id 后 =", n2)
PY
```

**预期输出**：`序列数 = 10000  上限 10000 → OVER`（等于上限即应降维）；`加入 board_id 后 = 100000000`。一亿条序列正是本节要拦下的量级。

```shell
# ④ IM-E：服务端事件结构里是否缺必带字段
grep -rn "class .*Event\b" -A 12 src/main/java --include=*.java \
  | grep -cE "traceId|tenantId|appVersion|flags"
```

**预期输出**：每个事件类命中数 ≥ 4。若某事件类只有 2 项，则该事件在灰度期不可归因。

```shell
# ⑤ IM-F：埋点是否被写在事务边界内（同一方法既 @Transactional 又上报）
grep -rn -B 4 "track\|metrics\." src/main/java --include=*.java | grep -c "@Transactional"
```

**预期输出**：0。若 > 0，需逐个确认上报是否发生在 `afterCommit` 里——写在 `@Transactional` 方法体内、且事务会回滚的路径上，失败样本必然丢失。

```text
⑥ IM-G：采样配置读法
   打开采集侧配置，确认「错误 / 超时」规则的优先级高于「成功按比例」。
   若只有一条固定概率规则，则 IM-G 不成立。

⑦ IM-H：对账读法
   取同一天的 event_id 集合：前端集合 F、服务端集合 S。
   计算 |F - S| 与 |S - F|。
     |F−S| > 0 且 |S−F| = 0  → 上报丢失（弱网）
     |F−S| > 0 且 |S−F| > 0  → 存在重复上报或补发
     两者均 0                → 正常
   注意：不要要求 |F| == |S|，那会诱使团队去改口径而不是改链路。
```

::: info 诚实标注
①~⑤ 为可在仓库内静态执行的检查，其中 ③ 的乘法示例为本页实跑的小脚本（仅估算，不含后端抓取的真实序列数）；②⑤ 已在项目侧 `SignalScope` 的施工中被引用为「本步要满足什么」。⑥⑦ 是读法，不产生命令输出。完整工程尚未构建，故 ①④ 未在真实产物上跑过。
:::
