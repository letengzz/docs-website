# 反馈闭环与指标腐化

前七页建立的是**能力**：能定口径、能埋点、能放量、能收量。这一页解决**维持**：三个月后这套东西还在不在用。

答案是悲观的，如果没有任何机制——指标会腐化。腐化不是「数据出错」，而是**意义失效**：字段还在写、图还在动，但它已经不再对应当前系统，也没人敢引用。腐化的成本不是存储费，是每次讨论都要重新争论一遍「这个数准不准」。

本页给一个可以落地的周节奏、四个腐化征兆的判据，以及每月固定要做的三件事。

## 判据族声明

本页判据族 `FL-A` ~ `FL-H`，共 8 条。定义表在第八节。

## 本页不讲什么

- 不讲指标怎么定、埋点怎么写（归 [指标先行](../MetricsFirst/index.md) 与 [埋点规范](../Instrumentation/index.md)）。
- 不讲看板工具的画法与查询语法，归 [监控系统](/docs/Ops/Monitoring/Overview/index.md) 与 [Grafana](/docs/Ops/Monitoring/Grafana/index.md)。
- 不讲研发效能的度量体系（那是 [研发效能度量](/docs/Tools/EngineeringMetrics/Overview/index.md) 的范畴），本页只讲**观测数据本身**的闭环。

## 一、闭环的判据：读数必须改变过什么

先把最容易自欺的一点说清：**开会不等于闭环**。周会开了一年、每周都看数据、每次都说「还行」，代码没有因此改过一行、阈值没有因此调过一次——这不是闭环，是仪式。

闭环的最小证据是**变更**：

| 变更类型 | 例子 | 说明 |
| --- | --- | --- |
| 代码 | 因为「同步延迟 P99 高」而把逐条广播改成批量 | 最硬的证据 |
| 阈值 | 因为分布整体下移，把 P99 告警从 800 ms 调到 400 ms | 说明有人在持续校准 |
| 看板 | 删掉一块连续 90 天无人查询的看板 | 负向证据也算闭环 |
| 埋点 | 补上事故时「想看但没有」的那个字段 | 说明事故被真正消化了 |

四周内四类变更为 0，就说明这套体系在空转。这条判据故意写得严——因为它最容易被糊弄过去。

## 二、一周六步

节奏不必是「周一」，关键是六个动作都发生，且顺序不能乱：

| 步 | 动作 | 产出 | 时长 |
| --- | --- | --- | --- |
| ① 看 | 上周上线了什么，对应指标怎么动的 | 一张「变更 → 读数」的对照 | 20 分钟 |
| ② 判 | 哪个读数与预期不符，是噪声还是真问题 | 一个或零个假设 | 15 分钟 |
| ③ 定 | 若成立，改什么：代码 / 阈值 / 埋点 | 一条具体任务（带 owner） | 10 分钟 |
| ④ 放 | 用开关放量，护栏常开 | 灰度记录 | 按发布流程 |
| ⑤ 收 | 收量或回滚，把读数写进当日文档 | 一段可回溯的记录 | 15 分钟 |
| ⑥ 清 | 过期开关、零查询看板、失效指标 | 删除或延长，二选一 | 20 分钟 |

三处最容易跳过的地方：

1. **② 允许「没有假设」**。要求每周都必须发现问题，会导致造假。一周什么都没发生是正常结果，写「无异常，本周不设假设」即可。
2. **③ 必须带 owner 与截止日**。写着「后续优化」的任务永远不做。
3. **⑥ 是最容易被砍掉的一步**，也是防腐化的唯一一步。没有它，一年后必然是一墙看板。

## 三、指标腐化的四个征兆

| 征兆 | 判据 | 为什么危险 |
| --- | --- | --- |
| 建了半年没人看过 | 查询记录为 0 或仅创建当天有 | 占用注意力，且掩盖了真正该看的指标 |
| 名字与实际口径不符 | 名字说「成功率」，公式算的是「非 5xx 比例」 | 决策依据错，且错得看不出来 |
| 依赖的字段已不再写入 | 指标有历史数据但近期为 0 或缺失 | 看起来「降为 0」，实际是断供 |
| 报警阈值还是上线时的值 | 阈值与当前历史分位差一个数量级 | 告警要么永不触发，要么持续触发 |

第二个征兆最有欺骗性。名字与口径的偏差通常源于一次「口径调整但没改名」——比如最初用「非 5xx 比例」叫成功率，后来加了超时统计，公式变了，名字没变。此后所有引用这个指标的人都在用一个他自己以为的口径。

第三个征兆的表现特别像好消息：曲线归零，看起来「问题解决了」。所以判据必须包含一条**反向检查**：核心指标连续 7 天为 0 时，先怀疑断供，不要先庆祝。

## 四、每月三件事

| 动作 | 具体做法 | 时间盒 |
| --- | --- | --- |
| **删** | 导出过去 90 天零查询的指标与看板，逐条确认后删除 | 60 分钟 |
| **核** | 抽 5 个核心指标，把口径公式与代码常量对一遍；不一致则改代码或改文档（**以代码为准**） | 45 分钟 |
| **补** | 回看本月事故，找出「当时想看但没有」的那一项，补进埋点或指标 | 30 分钟 |

三件事里「核」最难，因为它需要跨过代码与文档的边界去核对。但它也是唯一能发现「口径漂移」的动作——这类漂移没有症状，只有对照才能发现。

::: tip 「删」的心理障碍
删看板会让人觉得「之前的工作白做了」。有效的说法不是「删掉」，而是**「归档」**：移到一个默认折叠的分组里，保留 30 天，无人索取再删。

这个做法解决的是真实顾虑（可能有人在用）而不是情绪——如果 30 天内无人索取，就证明它确实没用了。
:::

## 五、把事故变成埋点：一个可复用的三问

事故是观测体系最好的输入，但需要一个固定的问法，否则复盘会变成追责。三个问题：

| 问 | 目的 | 产出 |
| --- | --- | --- |
| 当时**第一眼**想看什么？ | 找到缺失的主指标 | 一条新指标或新看板 |
| 当时**缺哪个维度**导致无法切分？ | 找到缺失的字段 | 一个必带字段（加入 [埋点规范](../Instrumentation/index.md) 的清单） |
| 当时**哪条告警**最没用？ | 找到噪声源 | 一条降级或删除的告警 |

三问的答案都必须落成任务，否则复盘只是叙事。特别注意第二问：**缺维度是最高频的复盘结论**，而它几乎总是「当初没想到」，不是「当时不想加」。

## 六、看板治理：从「有什么」到「谁什么时候看」

看板的组织方式决定了它会不会被用起来。两种组织方式：

| 组织方式 | 结构 | 问题 |
| --- | --- | --- |
| 按技术栈 | CPU / JVM / 数据库 / 缓存各一块 | 事故时不知道从哪进——因为事故不按技术栈发生 |
| 按场景 | 「用户报障时看什么」「发布时看什么」「值班交接看什么」 | 需要前期梳理，但直接影响可用性 |

判断方法很简单：**数一数有多少块看板明确写了「谁在什么情况下看」**。写不出来的，要么补上这句话，要么归档。

一个实用的约束：**每块看板的第一行必须写这句话**，形式是「<角色> 在 <场景> 时看，判断 <动作>」。写不出来就说明这块看板没有用户。

## 七、闭环的反面：四种空转

| 空转形态 | 表现 | 修法 |
| --- | --- | --- |
| 只报数不改 | 周会念数字，无人被分派任务 | 每步③强制带 owner 与截止日 |
| 只加不删 | 指标数逐月增长，无人清理 | 恢复步骤⑥，每月执行 |
| 只在大事故后动 | 平静期完全不看，出事才翻 | 把「无事」也写进周记录，形成节奏 |
| 指标与决策脱钩 | 数据只用于汇报，不用于选择 | 每次「放/收」决策必须引用具体读数 |

第四种最隐蔽：团队确实在看数据，也确实在用它写汇报，但**决策仍然靠经验**。识别方法：翻决策记录，看有没有「因为 X 指标达到 Y，所以做了 Z」这样的句子。找不到，就是脱钩。

## 八、判据族定义

| 判据 | 规则 | 违反时的样子 | 验证方式 |
| --- | --- | --- | --- |
| `FL-A` | 每四周至少出现一次「因读数而改的代码 / 阈值 / 看板 / 埋点」 | 周会开了一年，代码没因数据改过 | 命令 1 |
| `FL-B` | 每周六步必须全部发生，其中「清」不可省略 | 指标与看板只增不减 | 命令 2 |
| `FL-C` | 每周的假设任务必须带 owner 与截止日 | 「后续优化」永不做 | 命令 3 |
| `FL-D` | 90 天零查询的指标与看板必须归档或删除 | 三年后 47 块看板，不知看哪块 | 命令 4 |
| `FL-E` | 指标名与口径公式必须一致，抽检不一致以代码为准修正 | 名字说成功率、公式算非 5xx 比例 | 命令 5 |
| `FL-F` | 核心指标连续 7 天为 0 时必须先排查断供 | 曲线归零被当成「问题解决了」 | 命令 6 |
| `FL-G` | 每次事故必须产出三问答案（主指标 / 缺失维度 / 最无用告警） | 复盘只有叙事，没有任务 | 命令 7 |
| `FL-H` | 每块看板首行必须写明「谁在什么场景看、判断什么动作」 | 看板存在但无任何决策引用 | 命令 8 |

## 如何验证

```shell
# ① FL-A：近四周是否有「因读数而改」的提交
git log --since="4 weeks ago" --oneline --grep="指标\|阈值\|告警\|埋点\|看板" | head -20
```

**预期输出**：至少 1 条。为空即 `FL-A` 不成立——注意这条只证明「有相关提交」，还需人工确认它真的由读数驱动，而不是恰好改了相关文件。

```shell
# ② FL-D：统计指标定义数量随时间的变化（只增不减的信号）
git log --oneline --follow -- src/main/java/**/metrics/ | wc -l
git log --diff-filter=D --oneline -- src/main/java/**/metrics/ | wc -l
```

**预期输出**：第二个数字应 > 0。若「删除指标」的提交恒为 0，说明只加不删，`FL-D` 不成立。

```shell
# ③ FL-E：抽检指标名与常量名是否偏离（以 success 类指标为例）
grep -rn "define\|build(" src/main/java/**/metrics/*.java | grep -i "success"
grep -rn "static final.*SUCCESS\|NUMERATOR" src/main/java/**/metrics/*.java
```

**预期输出**：两处命名语义一致。若指标名叫 `xxx_success_total` 而分子常量叫 `NON_5XX`，说明口径与名字已经脱钩，需按 `FL-E` 修正。

```shell
# ④ FL-H：看板文件里是否有「谁在什么场景看」的首行说明
for f in ops/dashboards/*.json; do
  grep -q '"description".*\(值班\|发布\|报障\|交接\)' "$f" || echo "NO AUDIENCE: $f"
done
```

**预期输出**：空。列出的看板没有声明受众，按 `FL-D` 走归档流程。

```text
⑤ FL-B：六步完整性读法
   翻最近四周的周记录，逐周检查是否包含：看 / 判 / 定 / 放 / 收 / 清 六段。
   连续两周缺同一段，即该段在实际执行中已消失。

⑥ FL-F：断供读法
   对核心指标做「连续 7 天为 0」查询；命中后先查上报端是否还在上报
   （对比上报侧的成功数与后端入库数），再判断业务是否真的归零。

⑦ FL-G：三问读法
   抽一次事故的复盘记录，看是否有三条对应任务。
   只有「加强监控」这类表述即不成立——它无法被验证。

⑧ FL-C：任务可追溯读法
   查任务系统里来自「每周假设」的条目，统计带 owner 与 due date 的比例。
   < 100% 即不成立。
```

::: info 诚实标注
①~④ 为可在仓库内执行的检查，其中 ①④ 依赖提交历史与看板导出文件存在（看板导出截至本轮**尚未落盘**，故 ④ 未跑）；本文给出的 ① 命令只证明「有相关提交」，**不能单独证明闭环成立**，这一点已在预期输出里写明。⑤~⑧ 为读法，不产生命令输出。
:::
