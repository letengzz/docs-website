# 总览：三个反转与四类信号

第 158 天要解决的不是「装个监控」，而是**把观测从「事后」挪到「事前」**。这两件事的工作量差别不大，位置差别极大：事后补埋点的成本不在写代码，而在**重建当时的上下文**——而上下文不可重建。事故发生时你需要的那个维度（哪个租户、哪个版本、哪个开关状态），在当时没记，事后就永远没有。

## 判据族声明

本页判据族 `OD-A` ~ `OD-H`，共 8 条。定义表在第八节。

## 本页不讲什么

- 不讲 Prometheus / Grafana / Jaeger 怎么装、怎么查（归 [可观测性](/docs/Ops/Observability/Overview/index.md) 与 [监控系统](/docs/Ops/Monitoring/Overview/index.md)）。
- 不讲采样算法与 Collector 拓扑（归 [采样](/docs/Ops/Observability/Sampling/index.md) 与 [OpenTelemetry](/docs/Ops/Observability/OpenTelemetry/index.md)）。
- 不讲具体指标该怎么定、埋点该怎么写（分别归 [指标先行](./../MetricsFirst/index.md)、[埋点规范](./../Instrumentation/index.md)）。

本页只回答一个问题：**为什么观测必须发生在写代码之前，以及「事前」具体指哪几件事。**

## 一、反转一：顺序——从「上线后补监控」到「先写指标再写接口」

绝大多数项目的真实顺序是：

```text
需求 → 设计 → 编码 → 测试 → 上线 → （出事）→ 补监控 → 再出事 → 再补
```

这条链的问题不在于「补得晚」，而在于**补的时候缺信息**。举个真实的形状：

| 事故现场 | 想知道的 | 当时有没有 |
| --- | --- | --- |
| 「有几个客户反馈看不到新卡片」 | 受影响的是哪几个租户 | 日志里没有 `tenant_id` |
| 「新版本上线后成功率掉了」 | 掉的是新版本还是全量 | 日志里没有 `app_version` |
| 「同一个用户重试了三次」 | 三次是不是同一请求 | 没有 `trace_id`，也没有幂等键 |

这三条都不是「监控不够全」，而是**三个字段没在写代码时决定**。事后再加，历史数据永远缺这三列。

所以第一条反转的口径是：**接口设计评审时，必须同时评审「这个接口上线后怎么判断它是好的」**。答不上来的，设计未完。

::: tip 「事前」到底指什么
不是「上线前把监控装好」，而是**四件在合并前就必须写出来的东西**：

1. **指标口径**：这个功能的成功数怎么数，分母是什么。
2. **埋点字段**：为了按租户/版本/开关切开，必须带哪几个字段。
3. **放量方式**：用哪个开关，按什么维度分流，护栏是哪几个指标。
4. **回滚条件**：什么数值出现时自动停，谁在多久内决定。

四件里缺任何一件，等于把决定权留给了事故当天的时间压力。
:::

## 二、反转二：问题——从「有没有报错」到「用户有没有做成」

「有没有报错」是个极其廉价的问题，因为它有现成答案：`grep ERROR`。它的问题在于**回答不了用户的实际处境**：

| 现象 | `grep ERROR` 的答案 | 用户的实际处境 |
| --- | --- | --- |
| 写请求全部超时后重试成功 | 有 200 条 ERROR | 用户等了 9 秒，页面转过圈 |
| 前端按钮被开关关掉 | 一条错误都没有 | 用户点不动，以为系统坏了 |
| 卡片拖过去但没保存 | 只有一条 warn | 用户刷新后发现白拖了 |
| 慢查询导致列表 12 秒才出 | 没有任何错误 | 用户以为卡死，关掉重开 |

四行里三行是「没有错误但用户没做成」。所以第二条反转的口径是：**主指标必须是「用户做成了某件事」，错误率只是护栏之一**。

这件事有个直接的推论：**业务埋点不能只有前端**。前端能记「用户点了」，但只有服务端知道「这件事真的落库了」。两侧都要有，并且必须能对上号（见 [埋点规范](./../Instrumentation/index.md) 的「一处一义」）。

## 三、反转三：主人——从「运维的事」到「写代码的人的事」

指标由谁定义，决定了它会不会被维护。三种常见归属与后果：

| 归属 | 谁定口径 | 典型后果 |
| --- | --- | --- |
| 运维/平台团队 | 运维猜业务语义 | 指标名是 `http_requests_total`，事故时无法回答「拖动成功了几个」 |
| 产品/数据团队 | 数据按报表需求提 | 口径随报表变化，同一指标一年改三次，历史不可比 |
| **写这段代码的人** | 开发在 PR 里写入口径 | 口径与实现同源；改代码时能看见口径要跟着改 |

第三种是唯一可持续的，因为它让**口径与实现处在同一个变更单元里**。这也解释了一个常见现象：口径文档总是过期，而代码里的常量不会——所以本专题反复主张**把口径写成代码常量或可执行断言**，而不是写在文档里。

## 四、四类信号：各自能回答什么，不能回答什么

选信号之前先看这一张表。绝大多数「监控没用」的抱怨，根源是**拿错信号回答错问题**：

| 信号 | 能回答 | 不能回答 | 成本形状 |
| --- | --- | --- | --- |
| 指标（metrics） | 多少、多久、涨了还是跌了、哪个维度在涨 | 是哪一次、为什么这一次慢 | 按时间序列数计费，**基数敏感** |
| 追踪（traces） | 这一次慢在哪一段、跨服务调用链 | 是不是普遍现象 | 按 span 数计费，**采样敏感** |
| 日志（logs） | 这一条为什么失败、上下文细节 | 有多少条（除非专门聚合） | 按写入量计费，**基数不敏感但量敏感** |
| 事件（业务埋点） | 用户做成了没有、在哪一步流失 | 服务健不健康 | 按事件量计费，**口径敏感** |

四条判断：

1. **「有多少」只问指标**。用日志数「有多少条失败」是最常见的错，因为日志会被采样、会丢、会因级别调整而消失。
2. **「为什么这一次」只问追踪与日志**。用指标回答单次原因，只能靠猜。
3. **「用户做成没有」只问业务事件**。HTTP 200 不等于业务成功（见上一节的四行表）。
4. **高基数维度不要进指标**。`user_id`、`board_id`、带 id 的 `url` 进标签，等于给账单加零。它们的归宿是日志或追踪的**属性**，不是指标标签。

## 五、反面案例：先买 APM，再找用途

一个非常常见的顺序错误：**先采购 APM / 可观测平台，再让团队「用起来」**。它的结局几乎固定：

```text
① 采购 → ② 接入 SDK（一周） → ③ 出现大量「未命名事务」「自定义指标 0」
→ ④ 团队看不懂 → ⑤ 只剩「错误率」和「响应时间」两个图在用
→ ⑥ 第二年续费时被质疑价值
```

问题的根源在第 ③ 步：**SDK 自动采集的是框架层的信号，不是业务层的信号**。自动采集能告诉你「这个接口 P99 800 ms」，但它永远不知道「拖动卡片」这个动作的端到端包含了几次请求、哪一次是关键路径。

所以顺序必须是：**先有要回答的问题，再选信号，最后才买后端**。反过来的成本不是钱，是团队对这套系统的信任——一次「装了没用」之后，第二次推动会难十倍。

## 六、四个交付物（「事前」的具体产出）

本专题的九页最终收敛到四个可交付物。它们都是**能进代码仓库的东西**，不是文档：

| 交付物 | 形态 | 谁来写 | 缺了会怎样 |
| --- | --- | --- | --- |
| 指标契约 | 指标名 + 口径公式（分子分母）+ 维度白名单 + 谁在看 | 写接口的人，进 PR | 事故时两个团队算出两个数 |
| 埋点字段清单 | 事件名 + 必带字段（`trace_id` / `tenant_id` / 版本快照）+ 基数上限 | 前后端共同，进同一张表 | 出事时无法按租户/版本切分 |
| 开关清单 | 开关名 + 类型 + 到期日 + 默认值 + 删除计划 | 提需求的人 | 一年后开关比版本还多 |
| 告警-处置卡映射 | 告警名 → 处置卡 ID → 影响面 → 是否可自愈 | 值班负责人 | 半夜被叫起来却不知先做什么 |

四件交付物里的前三件，在项目侧的 [请求作用域与观测信号](/project/Complete/TeamBoard/SignalScope/index.md) 里各有一个具体落点（`ScopeContext` / 字段白名单 / 开关快照）。

## 七、一件事的两种失败：没记 vs 记了不信

观测体系有两种失败，**第二种更致命**：

| 失败 | 表现 | 修复成本 |
| --- | --- | --- |
| 没记 | 事故时查不到，只能靠复现 | 一次埋点改造，成本可估 |
| 记了不信 | 有数字，但团队不信它；争论「这个数不准」 | 极高：要重建信任，且期间所有决策仍靠感觉 |

「记了不信」的成因几乎总是同一个：**同一件事有两套数字**。前端说 1200 次成功，后端说 1180 次，差的 20 条没人能解释。于是所有人退回到「我觉得」。所以「一处一义」不是洁癖，是**信任的前提**。

::: warning 一个容易忽略的推论
如果一个指标没人敢在决策里引用，它就该被删掉。留着它的成本不是存储费，是**每次讨论都要重新争论一遍它准不准**。
:::

## 八、判据族定义

| 判据 | 规则 | 违反时的样子 | 验证方式 |
| --- | --- | --- | --- |
| `OD-A` | 每个上线功能在合并前必须写出至少一条「成功数」指标，含口径公式与分母 | 上线后只能回答「有没有报错」 | 命令 1 |
| `OD-B` | 同一业务动作只在一层记一次（服务端为准，前端只记意图） | 前后端两套数字，差几条无人能解释 | 命令 2 |
| `OD-C` | 每条指标必须写明「谁在什么情况下看」，无主的指标不进看板 | 三年后 47 块看板，事故时不知看哪块 | 命令 3 |
| `OD-D` | 指标标签取值必须可枚举且 < 100；高基数维度进日志或追踪属性 | 单指标产生十万级时间序列，账单翻倍 | 命令 4 |
| `OD-E` | 每个功能开关必须带类型与到期日；到期未清理由巡检报出 | 开关数超过版本数，无人敢删 | 命令 5 |
| `OD-F` | 放量与收量条件必须是数值（含样本量与窗口），不接受「观察一会儿」 | 白天全量、凌晨出事 | 命令 6 |
| `OD-G` | 每条叫人告警必须绑定一张处置卡，无处置卡的告警不进值班 | 半夜被叫起来，先花 20 分钟找文档 | 命令 7 |
| `OD-H` | 每周至少一条读数必须导致代码 / 阈值 / 看板的实际变更 | 周会开了一年，代码没因数据改过一行 | 命令 8 |

## 如何验证

八条判据里，`OD-A` / `OD-C` / `OD-E` / `OD-F` / `OD-G` 是**仓库内可静态检查的**；`OD-B` / `OD-D` / `OD-H` 需要运行时读数据。下面前四条给可执行命令，后四条给读法。

```shell
# ① OD-A：新增的接口是否有对应的成功数指标
git diff --name-only origin/main...HEAD -- 'src/main/java/**/api/**' | while read -r f; do
  base=$(basename "$f" .java)
  grep -rq "${base}" src/main/java/**/metrics/ 2>/dev/null || echo "MISSING METRIC: $f"
done
```

**预期输出**：空。若打印出 `MISSING METRIC: XxxController.java`，说明这个接口上线后只能靠日志判断成败，`OD-A` 不成立。

```shell
# ② OD-D：指标标签里是否出现了高基数维度
grep -rn "Counter.build\|Histogram.build" src/main/java | grep -E "board_id|user_id|card_id|request_id"
```

**预期输出**：空。若命中任意一条，该指标的标签取值集合会随业务数据线性增长——`board_id` 十万级、`user_id` 千万级，直接进账单。

```shell
# ③ OD-E：开关清单里是否有到期日为空或已过期的条目
yq -r '.flags[] | select(.expires_at == null or .expires_at < now)' config/flags.yaml
```

**预期输出**：空。若列出条目，说明这些开关已经是「开关债」，见 [功能开关](./../FeatureFlag/index.md) 的五态生命周期。

```shell
# ④ OD-G：每条告警规则是否都指向一张存在的处置卡
grep -h "runbook" deploy/prometheus/rules/*.yml | sed 's/.*runbook: *//' | sort -u | while read -r id; do
  test -f "docs/runbooks/${id}.md" || echo "NO RUNBOOK: $id"
done
```

**预期输出**：空。若有输出，这些告警一旦触发，值班的人要现场找文档。

```text
⑤ OD-B：同一业务动作是否只在一层记一次
   读法：取一个动作（如「创建卡片」），在服务端与前端各查一次计数，
   同一分钟内两个数是否相等。差值恒为 0 才算成立；差值稳定但非 0，
   说明有一层在丢（重试、离线续传、开关短路）。

⑥ OD-F：放量条件是否有数值
   读法：打开放量单，看「收量条件」一栏能否被机器判定。
   「观察 2 小时无异常」不可判定；「实验组错误率 > 对照组 2 倍且样本 > 1000」可判定。

⑦ OD-H：读数是否改变了代码
   读法：把近四周的周会记录与 git log 对照，找出「因某个读数而改的阈值或代码」。
   找不到即不成立——这条判据故意写得难以自证，因为它最容易被糊弄。

⑧ 反向检查：任何一条指标若连续 90 天无人查询，即为负债
   读法：从后端导出查询日志（Prometheus 的 `__name__` 使用统计或平台的看板访问记录），
   与指标清单求差集。
```

::: info 诚实标注
本节 ①~④ 给的是**判据的形状与命令**，其中 ①③④ 已在项目侧 `SignalScope` 的施工中被引用为「本步要满足什么」；**尚未在完整工程里跑过真实构建产物**（Java 侧代码截至本轮只到设计片段，见项目侧进度表）。⑤~⑧ 是**读法与口径**，不产生命令输出。凡未跑过的，本页不标 ✅。
:::
