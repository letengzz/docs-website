# 灰度度量与自动回滚

灰度发布的核心不是「先放 1% 再说」，而是**这 1% 要和谁比、比出什么结果才算过**。没有对照组的灰度，只是一个范围更小的全量——它把风险摊薄了，但没有任何判断依据。

本页把灰度写成一条可执行的条件链：分流口径怎么定 → 两组怎么看 → 护栏是哪几个指标 → 什么数值自动回滚 → 什么条件才允许收量。

## 判据族声明

本页判据族 `GM-A` ~ `GM-H`，共 8 条。定义表在第八节。

## 本页不讲什么

- 不讲分流网关 / Service Mesh / Nginx 的配置语法，归 [CI/CD](/docs/Tools/CICD/index.md) 与 [Nginx](/docs/Ops/Nginx/index.md)。
- 不讲开关本身的四类与生命周期，归 [功能开关](../FeatureFlag/index.md)。
- 不讲实验的统计显著性，归 [实验设计](../Experiments/index.md)。本页的判据是**运维判据**（要不要停），不是**科学判据**（结论是否成立）。

## 一、分流口径：按业务单元切，不按请求切

同一个用户在不同时刻落入不同分组，会得到什么？答案是**经验被撕裂**：他先看到新界面，刷新后又变回旧界面；他拖了一张卡片成功，再拖一张失败。这不是「灰度」，这是故障。

三种分流维度的后果差异很大：

| 维度 | 一致性 | 适用 | 风险 |
| --- | --- | --- | --- |
| 按请求 / 按连接 | 无 | 仅用于无状态读接口的压测分流 | 同一用户体验跳变，投诉集中在灰度期 |
| 按用户 | 请求内一致 | 面向个人的功能 | 同一租户内用户看到不同界面，协作场景下会互相困惑 |
| **按租户 / 按业务单元** | 全链路一致 | **协作类、多租户系统** | 需要租户 ID 在整条链路上可用（含异步任务与消息消费） |

判断顺序：**先问「这个功能的最小一致单元是什么」**。如果两个用户在同一块看板上协作，最小一致单元就是「这块看板」或它所属的租户，而不是用户。

::: warning 分流的隐藏难点在异步链路
同步请求带得上 `tenant_id`，异步任务与消息消费往往带不上。于是出现「同步走新逻辑、异步消费走旧逻辑」的半新半旧状态——表现为数据不一致，且只在灰度期出现。

所以分流的判据必须包含一条：**分流键在异步链路里可用**。做不到时，正确做法是把这个异步环节的分流改成「跟随上游事件里的开关快照」，而不是在消费端重新评估。
:::

## 二、两组必须同时看：对照组是同一时刻的自然对照

灰度最常被简化为「看实验组有没有问题」。这个读法有个致命缺陷：**没有问题可能只是因为流量变了**。工作日 10 点的 P99 与凌晨 2 点的 P99 没法比，大促期间与平时没法比。

对照组解决的正是这个：**同一时刻、同一流量结构下的另一批请求**。它把「时段」「流量」「数据分布」三个变量一次性消掉。

| 读法 | 能发现 | 不能发现 |
| --- | --- | --- |
| 只看实验组绝对值 | 明显崩溃（错误率 30%） | 缓慢劣化（错误率从 0.1% 到 0.4%，看起来仍很低） |
| 实验组 vs 对照组 | 相对劣化，即使绝对值很好看 | 两组共同受到的外部影响（如数据库整体变慢） |
| 两者结合 + 历史趋势 | 相对劣化 + 全局劣化 | —— |

第二行是本页的核心：**灰度期最有价值的信号是「相对」，不是「绝对」**。

## 三、主指标与护栏：分工必须写死

| 类别 | 数量 | 作用 | 越线后的动作 |
| --- | --- | --- | --- |
| 主指标 | 1 个 | 判断「这次改动是否达到目的」 | 不达标 → 不收量，继续观察或放弃 |
| 护栏指标 | 3~5 个 | 判断「是否伤到了别处」 | 越线 → **立即停**，不看主指标 |
| 观测指标 | 若干 | 解释原因，不参与判定 | 只记录，不触发动作 |

护栏的典型四件：

| 护栏 | 为什么必须在 | 越线阈值（相对对照组） |
| --- | --- | --- |
| 错误率 | 新代码路径可能抛异常 | > 2 倍且样本 > 1,000 |
| P99 延迟 | 新逻辑可能多一次查询 | > 1.5 倍 |
| 关键业务失败数 | 错误率抓不到「返回成功但结果错」 | > 0 且持续 5 分钟 |
| 分流偏差 | 分流实现有 bug 时，比例会与预期不符 | 偏差 > 5 个百分点 |

第四件最容易被忘，但它拦的是一类特别隐蔽的故障：**分流规则写错**导致 80% 的流量进了实验组。此时两组指标都正常，你看不出来；等到全量才发现「原来一直是在大流量下跑的」。

## 四、为什么不用绝对值阈值

绝对值阈值有两处必然失效：

| 场景 | 绝对值阈值的表现 | 原因 |
| --- | --- | --- |
| 低峰期（夜间） | 永不触发 | 请求量少，错误数达不到阈值 |
| 高峰期 / 大促 | 持续触发 | 请求量放大 10 倍，错误数天然翻倍 |
| 慢劣化 | 触发太晚 | 从 0.1% 到 0.4% 仍低于「错误率 > 1%」的阈值 |

相对阈值把这三个问题一次解决，因为它比的是**同一时刻的两批流量**。代价是需要一个健康的对照组——所以灰度的第一件事是「确认对照组真的在跑旧逻辑」，而不是「确认实验组在跑新逻辑」。

::: tip 一个必须先做的检查
放量前先看对照组有没有流量。分流键写错（比如按一个所有请求都取到同一个值的字段取模）会导致 100% 落入实验组，对照组为空。

此时所有相对指标都会变成 `NaN` 或不触发。表现形式是「灰度很顺利，什么都没有报警」——这是最危险的顺利。
:::

## 五、四条自动回滚条件

四条都用「与对照组比」，且都带样本量下限。样本量是必须的：没有它，两组各 10 个请求时的 1 个错误就会被算成 10% vs 0%。

```text
① 错误率：实验组 > 对照组 × 2，且实验组样本 ≥ 1,000
② 延迟：  实验组 P99 > 对照组 P99 × 1.5，且实验组样本 ≥ 500
③ 业务：  关键失败数 > 0 且持续 ≥ 5 分钟（不设倍数，因为基线是 0）
④ 分流：  |实际比例 − 期望比例| > 5 个百分点，且总样本 ≥ 1,000
```

四条纪律：

1. **样本量下限写进规则，不写进人的判断**。否则「样本还小，再等等」会成为惯性，一直等到事故变大。
2. **第三条不设倍数**。基线为 0 的指标（如「跨租户数据泄露」「支付重复扣款」）任何一次都是事故，用倍数会算出 `∞` 或 `0`，无法判定。
3. **回滚是自动的，恢复是人工的**。自动回滚只负责「停下来」；重新放量必须有人确认原因，否则会出现「自动回滚 → 自动重试 → 再回滚」的循环。
4. **回滚动作本身要演练**。开关关掉之后，缓存、连接池、已写入的新格式数据都不会自动恢复——这条在 [功能开关](../FeatureFlag/index.md) 的缓存 key 一节有具体后果。

## 六、收量条件：覆盖一个业务高峰

收量（从灰度到全量）是最容易被草率决定的动作。常见写法是「观察 2 小时无异常」——它有两个问题：**没定义「异常」**，且 **2 小时可能整段处于低谷**。

可判定的收量条件：

```text
① 主指标不劣于对照组（或达到预期改善）
② 四条护栏全部未越线，且持续覆盖 ≥ 1 个业务高峰
③ 观察窗口内样本量达到设计要求（不是「时间够了」，是「样本够了」）
④ 关键路径的人工抽查通过（如抽取 20 个租户的实际数据核对）
```

第②条的「一个业务高峰」是关键。不同系统的形状不同：

| 系统类型 | 高峰形状 | 最短窗口建议 |
| --- | --- | --- |
| 办公协作类 | 工作日 9-11 点、14-17 点 | 覆盖一个完整工作日 |
| 消费类 | 午间、晚间 | 覆盖一个晚间高峰 |
| 内部工具 | 月初/月末、周一周五 | **覆盖月结或周结**，不能只看普通日 |

按这个表，办公协作类系统的灰度「最短窗口」是一个工作日——这意味着**周五下午放量基本等于没有观察**：窗口里没有高峰，周一早上才第一次真实承压。

## 七、分阶段放量：每阶段的最短时长由样本量决定

| 阶段 | 比例 | 目的 | 最短停留 |
| --- | --- | --- | --- |
| 内部 | 内部租户 | 抓「启动就崩」「明显功能缺失」 | 半天 |
| 极小 | 1% | 抓崩溃类问题 | 到样本量 ≥ 1,000 错误基线 |
| 小 | 5% | 抓资源类问题（连接池、缓存命中率） | 覆盖一次高峰 |
| 中 | 25% | 抓容量与依赖类问题 | 覆盖一次高峰 |
| 全 | 100% | —— | 保留开关，观察一个业务周期后清理 |

每一阶段的停留时间不是「等一等」，而是**等到样本量足够**。1% 阶段在小流量系统上可能需要几小时甚至一天——这不是拖沓，是数学要求：100 个请求里出现 1 个错误，无法区分是 1% 错误率还是运气。

## 八、判据族定义

| 判据 | 规则 | 违反时的样子 | 验证方式 |
| --- | --- | --- | --- |
| `GM-A` | 分流按业务一致单元（租户/看板），不按请求 | 同一用户界面来回跳变 | 命令 1 |
| `GM-B` | 分流键在异步链路可用，或改为跟随上游快照 | 同步走新逻辑、消费走旧逻辑，数据不一致 | 命令 2 |
| `GM-C` | 灰度必须同时读实验组与对照组，禁止只看绝对值 | 缓慢劣化被「绝对值看起来还行」掩盖 | 命令 3 |
| `GM-D` | 主指标 1 个、护栏 3~5 个，职责分离且护栏优先 | 主指标好看就收量，护栏越线被忽略 | 命令 4 |
| `GM-E` | 四条自动回滚条件均带样本量下限与相对比较 | 10 个请求 1 个错误即触发回滚 | 命令 5 |
| `GM-F` | 回滚自动、恢复人工，禁止自动重试放量 | 自动回滚与自动重放形成循环 | 命令 6 |
| `GM-G` | 收量窗口必须覆盖一个业务高峰且样本量达标 | 周五下午放量，周一早上承压 | 命令 7 |
| `GM-H` | 放量前必须验证对照组非空、分流比例与预期偏差 ≤ 5% | 「灰度很顺利，什么都没报警」而对照组为空 | 命令 8 |

## 如何验证

```shell
# ① GM-A：分流键是否用了请求级或用户级字段
grep -rn "hashOf\|hash(" src/main/java --include=*.java | grep -iE "requestId|sessionId|userId"
```

**预期输出**：空。若命中 `userId`，需确认该系统的协作一致性要求——协作类系统应改用 `tenantId`。

```shell
# ③ GM-C：PromQL 是否同时读两组（实验组与对照组的错误率之比）
cat <<'QUERY'
sum(rate(http_requests_total{job="app",flag_group="experiment",status=~"5.."}[5m]))
  / sum(rate(http_requests_total{job="app",flag_group="experiment"}[5m]))
/
sum(rate(http_requests_total{job="app",flag_group="control",status=~"5.."}[5m]))
  / sum(rate(http_requests_total{job="app",flag_group="control"}[5m]))
QUERY
```

**预期输出**：一个比值（实验组错误率 / 对照组错误率）。查询合法但结果为 `NaN`，说明某一组没有流量——这正是 `GM-H` 要拦的情况。

```shell
# ④ GM-E：回滚规则是否带样本量下限
grep -rn -A 3 "rollback\|auto_abort" deploy/prometheus/rules/*.yml | grep -c "count\|increase"
```

**预期输出**：每条回滚规则命中 ≥ 1。若为 0，说明规则只用比率，低流量时会把噪声当成事故。

```shell
# ⑤ GM-H：分流比例实测（放量后）
curl -sG "$PROM/api/v1/query" \
  --data-urlencode 'query=sum by (flag_group) (rate(http_requests_total[5m]))' \
  | jq -r '.data.result[] | "\(.metric.flag_group)\t\(.value[1])"'
```

**预期输出**：两行（`experiment` 与 `control`），且 `experiment / (experiment + control)` 与期望比例之差 ≤ 5 个百分点。只有一行即为对照组为空，此时所有相对判据失效。

```text
② GM-B：异步链路读法
   在消息消费者里打一条日志，打印它看到的开关值来源。
   「上游快照」为正确；「本地重新评估」需确认评估上下文里的租户与上游一致，
   否则会出现同一租户在同步与异步两侧走不同分支。

⑥ GM-F：回滚与恢复读法
   查回滚脚本的调用方：若存在「回滚后 N 分钟自动重放」的定时任务，即不成立。

⑦ GM-G：收量窗口读法
   读放量单的「观察窗口」一栏，与业务高峰时段对照。
   办公协作类系统窗口 < 1 个工作日即不成立。
```

::: info 诚实标注
①③④⑤ 为可在仓库内或对监控后端执行的检查，其中 ③ 给出的是**查询形状**（本页未连接真实 Prometheus 实例，故未取到实际数值）；④ 依赖告警规则文件存在（项目侧告警规则截至本轮为设计片段，**尚未落盘**）。②⑥⑦ 为读法，不产生命令输出。
:::
