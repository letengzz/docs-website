# 功能开关工程

功能开关看起来是个 `if`，实际是**一套带生命周期的配置系统**。它降低发布风险的方式很具体：把「上线」与「放量」拆成两件事——代码先合进去但默认关闭，验证通过后再按租户、按比例打开，出问题时关掉而不必回滚部署。

代价也很具体：**每个开关都是一条长期存在的分支**。分支本身不难，难的是它会活下来——一年后没有人记得某个开关是干什么的、还开着哪些租户、能不能删。这就是「开关债」。

本页的目标是让开关**能被算清楚**：四类分开管、五态有终点、四行必须写、三处坑必须避。

## 判据族声明

本页判据族 `FF-A` ~ `FF-H`，共 8 条。定义表在第八节。

## 一、四类开关：先分类，再管生命周期

四类开关混在一起管，是「开关债」的起点。它们的**生命周期长度**差一个数量级：

| 类型 | 用途 | 默认值 | 典型寿命 | 到期后该做什么 |
| --- | --- | --- | --- | --- |
| release 发布开关 | 新代码先合并、后放量 | **关** | 数天到数周 | 全量稳定后**删掉分支与开关** |
| experiment 实验开关 | 按桶分组，比较效果 | 关（对照组） | 一次实验周期 | 出结论后**删掉，只留结论** |
| ops 运维开关 | 降级、限流、只读、关闭非核心功能 | **开**（功能正常） | 长期（可能永久） | 保留，但需演练：确认它能真的生效 |
| permission 权限位 | 谁能用某功能（按套餐/角色） | 按套餐 | 长期 | **不是开关**，别放进开关系统 |

第四条最容易被误放。权限位会被频繁查询、需要审计、与计费挂钩；把它塞进开关系统后，会出现「开关面板上改了权限但账单没变」这类事故。**判据很简单：需要审计追踪的，不是开关。**

## 二、五态生命周期与「到期日」

```text
① 建（created）    开关入库，默认值与到期日必须填
② 开（enabled）    对目标范围打开（租户/比例/用户）
③ 全量（ramp-up）  目标范围扩到 100%，观察一个完整业务周期
④ 清理（cleanup）  删掉代码里的分支，开关置为「已全量」不再评估
⑤ 删除（removed）  从配置与代码中彻底移除
```

关键在第 ④ 步：**「全量」不等于「可以删」**。全量之后代码里仍然留着 `if (flag) {...} else {...}` 两条路径，老路径没人走但仍在编译、仍在被静态检查、仍在被下一个人困惑。所以清理的标准动作是「删分支」，不是「关开关」。

| 状态 | 开关仍在配置里 | 代码里还有分支 | 是否算负债 |
| --- | --- | --- | --- |
| 已全量但未清理 | 是 | 是 | **是**（最常见，也最容易被忽略） |
| 已清理未删除 | 是 | 否 | 是（配置噪音，可接受一段时间） |
| 已删除 | 否 | 否 | 否 |

## 三、四行必写：写不出来的开关不许合

每条开关在配置里必须能填满四行。填不满就说明这个开关的必要性没想清楚：

```yaml
- name: card_drag_batch_write
  type: release                    # 四类之一
  default: false                   # 关闭即保持旧行为
  owner: board-team                # 谁负责
  enabled_for:                     # 开给谁：租户 / 比例 / 用户
    tenants: [acme, globex]
    percentage: 0
  expires_at: 2026-11-30           # 何时关：必须有日期
  removal_plan: "全量两周后删分支与配置，见 PR #1234"   # 怎么删
```

四行的判据化版本：

| 行 | 可判定的条件 | 不可接受的写法 |
| --- | --- | --- |
| 谁开 | 有 `owner` 字段，且是团队而非个人 | 空，或写「所有人」 |
| 开给谁 | `tenants` / `percentage` / `user_ids` 至少一项非空 | 「先都开着看看」 |
| 何时关 | `expires_at` 是具体日期 | 「稳定后」 |
| 怎么删 | 指向一个具体动作（PR / 工单 / 脚本） | 「以后统一清」 |

## 四、三处最容易出事的写法

### 4.1 在循环里读开关

```java
// 反例：每处理一张卡片查一次配置
for (Card card : cards) {
    if (flagService.isEnabled("card_drag_batch_write")) { ... }
}
```

200 张卡片的看板，一次拖动 = 200 次配置查询。若配置中心是远程调用（P99 30 ms），这个接口的 P99 直接到 6 秒。若配置中心有本地缓存，问题变成「每 200 次里可能有 1 次命中缓存过期」。

正确写法：**每请求读一次，随作用域传下去**。

```java
// 正例：在入口处取一次快照，后续全部读快照
FlagSnapshot flags = flagService.snapshot();   // 内部有本地缓存 + 变更推送
for (Card card : cards) {
    if (flags.isOn("card_drag_batch_write")) { ... }
}
```

快照还有第二个好处：**同一次请求内开关值恒定**。否则请求处理到一半开关被改，会出现「前半段走新逻辑、后半段走旧逻辑」的半新半旧状态。

### 4.2 开关值进了缓存 key 却没进失效条件

```text
// 反例
key = "board:" + boardId + ":" + (flagOn ? "v2" : "v1")
cache.get(key) ...
// 开关关掉后：新请求读 v1 的 key，但 v1 的 key 里还是关掉之前的老数据
```

问题不在 key 设计，在**没人负责失效**。开关切换是一个「全局状态变更事件」，任何把开关值编码进 key 的缓存都必须订阅这个事件。绝大多数实现没有订阅，于是出现「关了开关还生效，10 分钟后才恢复」。

两条可行做法：

| 做法 | 机制 | 代价 |
| --- | --- | --- |
| 开关值不进 key | 缓存存「与开关无关」的原始数据，开关在出缓存后判断 | 需要重新设计缓存边界，**推荐** |
| 开关值进 key + 切换时清前缀 | 变更事件触发按前缀删除 | 依赖缓存支持前缀删除；大 key 集合删除有抖动 |

### 4.3 前后端各判一次同一开关

```text
前端：flagOn('export_csv') → 显示导出按钮
后端：if (flagOn('export_csv')) { 允许导出 }
```

两份实现、两个缓存、两次评估。在以下三种情况下必然不一致：前端缓存比后端晚（按钮还能点但请求 403）、按租户分流但前端不知道租户（按钮该隐藏却显示）、实验组切换瞬间（一侧已切、一侧未切）。

正确的分工是：

| 层 | 职责 | 是否可作安全边界 |
| --- | --- | --- |
| 前端 | **展示**：决定按钮显示与置灰 | 否 |
| 后端 | **执行**：决定请求是否被受理 | 是 |
| 共享 | 同一份开关名与同一套分流规则（由服务端下发评估结果） | —— |

一句判据：**前端判开关只为体验，后端判开关才为正确性**。任何「前端判了所以后端不判」的写法，等于把开关变成了权限漏洞。

## 五、评估位置：服务端评估 + 客户端快照

三种架构，只有一种适合需要审计的业务系统：

| 架构 | 机制 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 客户端评估 | SDk 拉全量规则，本地算 | 快、离线可用 | 规则下发到端上，可被篡改；审计困难 |
| 服务端评估（每请求） | 每次请求问一次 | 规则集中、可审计 | 延迟与可用性强耦合（配置中心挂了业务就挂） |
| **服务端评估 + 本地缓存 + 变更推送** | 进程内缓存，变更时推送失效 | 延迟低、可审计、可降级 | 实现复杂，需处理「推送丢失」 |

第三种是通行做法，但有两个必须处理的失败面：

1. **推送丢失**：缓存永不失效，开关改了不生效。必须有兜底的 TTL（如 60 s）与定期全量对齐。
2. **配置中心不可用**：启动时拿不到规则，服务起不来。必须允许「用最后一次已知配置启动」并打 warn，而不是 fail-fast——否则一次配置中心故障会变成全站不可用。

## 六、开关债的量化与清理

| 征兆 | 判据 | 处置 |
| --- | --- | --- |
| 分支数 > 版本数 | `grep -c "flag("` 的行数大于近三月版本数 | 说明大部分开关没有走出第 ④ 步 |
| 没人知道某个开关还开着 | 抽查 3 条，`owner` 答不出当前状态 | 补 `owner` 与状态看板 |
| 删掉后无人能判断影响 | 没有「开关 ↔ 指标」的映射 | 补映射：每条开关对应的成功数指标 |

清理节奏建议：**每月一次，按 `expires_at` 排序**，过期的逐条处理（全量→删分支，或直接删）。不要做「季度大清理」——大清理需要重建上下文，成本高到没人愿意启动。

::: tip 一个反直觉的观察
开关最多的团队往往不是发布最稳的团队，而是**最不敢删的团队**。开关真正降低风险的前提是「关掉是安全的」，而当开关太多、无人知道彼此依赖时，关任何一个都不安全。于是开关从「降低风险」变成了「风险本身」。
:::

## 七、与灰度、实验的接口

三章共用同一份开关清单，各自只负责一段：

| 环节 | 归属 | 输入 | 输出 |
| --- | --- | --- | --- |
| 定义开关与生命周期 | **本页** | 需求 | 开关条目（四行填满） |
| 决定放量多少、什么时候收 | [灰度度量](../GrayMetrics/index.md) | 开关条目 | 分流比例变化 + 回滚判定 |
| 决定分组是否有效、结论是否可信 | [实验设计](../Experiments/index.md) | 开关条目 + 指标 | 结论与结束动作 |

缺了这份共用清单，会出现三种典型错位：开关已全量但实验还在跑、实验已结束但开关还开着、灰度已回滚但开关仍是「实验」类型。三种都会让下一次读数据的人得出错误结论。

## 八、判据族定义

| 判据 | 规则 | 违反时的样子 | 验证方式 |
| --- | --- | --- | --- |
| `FF-A` | 每条开关必须标注四类之一，权限位不得进开关系统 | 开关面板改了权限但计费没变 | 命令 1 |
| `FF-B` | 每条开关必须有 `owner` / `enabled_for` / `expires_at` / `removal_plan` 四项 | 一年后无人知道它还开着哪些租户 | 命令 2 |
| `FF-C` | 开关评估每请求一次，不得在循环内重复查询 | 一次拖动触发 200 次配置查询 | 命令 3 |
| `FF-D` | 同一次请求内开关值恒定（快照），不得中途变化 | 半新半旧状态，数据前后不一致 | 命令 4 |
| `FF-E` | 开关值若进入缓存 key，必须订阅切换事件做失效 | 关了开关仍生效，10 分钟后才恢复 | 命令 5 |
| `FF-F` | 前端判开关只作展示，安全边界必须由后端判定 | 前端改判即可越权导出 | 命令 6 |
| `FF-G` | 配置中心不可用时用最后已知配置启动并告警，不得 fail-fast | 配置中心故障导致全站不可启动 | 命令 7 |
| `FF-H` | 全量稳定后必须删分支（不止关开关），过期开关按月清理 | 分支数超过版本数 | 命令 8 |

## 如何验证

```shell
# ① FF-A：开关清单里是否混入了权限位
yq -r '.flags[] | select(.type == "permission") | .name' config/flags.yaml
```

**预期输出**：空。若列出条目，说明把权限判定放进了开关系统——它需要审计，不该在这里。

```shell
# ② FF-B：四项必填是否有空值
yq -r '.flags[] | select(.owner == null or .expires_at == null or .removal_plan == null)
        | .name' config/flags.yaml
```

**预期输出**：空。有输出即为「无法被清理的开关」。

```shell
# ③ FF-C：循环内的开关查询（for/forEach/stream 之后 5 行内出现 isEnabled）
grep -rn -A 5 "for (\|forEach\|\.stream()" src/main/java --include=*.java \
  | grep -c "isEnabled("
```

**预期输出**：0。若 > 0，需逐个确认是否在循环体内——这是 P99 突增的常见成因。

```shell
# ④ FF-E：把开关值拼进缓存 key 的位置
grep -rn "cacheKey\|keyBuilder" src/main/java --include=*.java | grep -i "flag"
```

**预期输出**：应当为空，或每个命中处附近能看到「订阅切换事件」的代码。若命中且无失效逻辑，`FF-E` 不成立。

```shell
# ⑤ FF-G：配置中心不可用时的启动行为（是否 fail-fast）
grep -rn "fail-fast\|failFast\|throw new IllegalStateException" src/main/java --include=*.java \
  | grep -i "flag\|config"
```

**预期输出**：空，或确认这些抛出点不在启动路径上。启动期因配置中心不可用而阻断，会把一次外部故障放大成全站不可用。

```shell
# ⑥ FF-H：过期开关数量（按月清理的依据）
yq -r '[.flags[] | select(.expires_at < "2026-10-18")] | length' config/flags.yaml
```

**预期输出**：一个数字。它应当稳定在个位数；持续增长说明「到期」只是字段而不是动作。

```text
⑦ FF-D：快照读法
   在同一请求内打两条日志（进入处理循环前、离开后），各打印一次开关值。
   两次不一致即不成立——说明每次判断都重新评估了。

⑧ FF-F：后端兜底读法
   直接 curl 一个被前端隐藏的接口（不带 UI 的按钮，只有 URL）。
   返回 403 说明后端有判定；返回 200 说明开关只是「藏了按钮」。
```

::: info 诚实标注
①~⑥ 为可在仓库内静态执行的检查，其中 ⑥ 依赖 `flags.yaml` 已存在（项目侧该文件截至本轮为设计片段，**尚未落盘**，故 ⑥ 未在真实配置上跑过）；③⑤ 已在项目侧 `SignalScope` 的施工中被引用为「本步要满足什么」。⑦⑧ 为读法，不产生命令输出。
:::

## 与「变更管理」专题的分工（第 170 天补充）

本页讲**开关怎么设计**（求值上下文、灰度放量、默认值、清理）；[变更管理与发布工程](../../../Ops/ChangeManagement/Overview/index.md) 讲**拨开关这个动作算不算一次变更、要不要留痕**。

| 问题 | 本页 | 变更管理专题 |
| --- | --- | --- |
| 开关该不该有默认值 | 默认值决定故障时的行为 | 默认值属于「配置形状」，高危变更规则会扫它 |
| 放量算不算发布 | 不属于发布，不需要重新部署 | **算变更**：改了线上行为，但不改产物 |
| 谁在几点拨的 | 求值日志只证明「拨过」 | 审批留痕要回答「谁批的、批的是哪个值」 |

**一条本页特有的坑：开关翻转是最容易绕过变更流程的变更。** 它不需要发布、不需要重启、常常不需要审批，一次点击就能让全量用户进入新逻辑。于是出了故障之后，最常听到的一句话是「没有人改过东西」——**因为确实没有人「发布」过东西**。可行折中不是给每次拨开关加审批（那会被人用共享账号绕过），而是：① 全量档位（`100%`）的翻转纳入标准变更白名单并要求审批；② 所有翻转强制写审计日志（含操作人、旧值、新值、`request_id`）；③ 大盘上把「当前生效的开关快照」与发布版本并列展示。
