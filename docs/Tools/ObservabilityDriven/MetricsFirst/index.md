# 指标先行与口径

指标先行只需要回答两个问题：**数什么**、**分母是谁**。第二个问题比第一个难十倍，也重要十倍——同一份数据换一个分母，结论可以从「系统很稳」翻到「系统一直在抖」，而两个数字都「没错」。

本页把这件事做到能被执行的程度：每种指标给出口径公式，每个公式给出必须写死的四个项，并给出「分位数不可再聚合」这类会导致读数作废的硬约束。

## 判据族声明

本页判据族 `MF-A` ~ `MF-H`，共 8 条。定义表在第八节。

## 本页不讲什么

- 不讲指标类型（Counter / Gauge / Histogram）的 SDK 用法与后端查询语法，归 [监控系统](/docs/Ops/Monitoring/Overview/index.md) 与 [Prometheus](/docs/Ops/Monitoring/Prometheus/index.md)。
- 不讲埋点该放几家（服务端 / 客户端 / 网关），归 [埋点规范](../Instrumentation/index.md)。
- 不讲 SLO 谈判与预算分摊的组织流程，本页只讲口径与算法。

## 一、SLI 三类，每类只选一个主指标

SLI（Service Level Indicator）在实践里只有三类值得作为主指标：

| 类别 | 口径 | 适合做主指标的条件 | 反面 |
| --- | --- | --- | --- |
| 可用性 | 成功请求数 / 有效请求总数 | 失败对用户有确定影响 | 「成功」定义含糊时，这个数会随口径漂移 |
| 延迟 | 请求耗时分布的 P95 / P99 | 慢等同于不可用（用户会放弃） | 把均值当主指标，长尾被完全掩盖 |
| 正确性 | 结果正确的请求数 / 总请求数 | 系统会「返回成功但结果错」 | 需要业务侧定义「正确」，成本最高 |

三条纪律：

1. **每类只选一个主指标**。同时上报「平均延迟、P95、P99、最大耗时、超时率」五个，等于没有主指标——五个数不一致时没人知道以哪个为准。
2. **主指标必须与用户处境一一对应**。P99 延迟对应「每 100 次里有 1 次让人等到想关页面」，而均值不对应任何具体用户体验。
3. **正确性优先于可用性**。一个返回 HTTP 200 但金额算错的接口，可用性 100%、正确性 0%。这类系统的指标设计必须把正确性放在最上面。

## 二、同一个「可用性」的四种口径

这是本页最重要的一张表。同一份访问日志，四种口径能算出四个数：

| 口径 | 分母 | 分子 | 99.9% 意味着 |
| --- | --- | --- | --- |
| A 全部请求 | 所有请求 | 2xx | 4xx 也算「不可用」，客户端传错参数同样扣分 |
| B 排除客户端错误 | 非 4xx 请求 | 2xx | 4xx 不计入，5xx 与超时计入 |
| C 成功含重定向 | 所有请求 | 2xx + 3xx | 3xx 计入成功，容易在登录跳转场景虚高 |
| D 非 5xx | 所有请求 | 非 5xx | 超时若被记为 499（客户端断开）会被算成成功 |

用一个具体例子算一遍。假设一小时 100,000 次请求，其中：

- 4xx：1,200 次（客户端参数错误，服务端行为正确）
- 5xx：60 次
- 超时后客户端断开记为 499：40 次
- 其余 98,700 次 2xx

| 口径 | 计算 | 结果 | 与口径 B 的差 |
| --- | --- | --- | --- |
| A | 98,700 / 100,000 | 98.70% | −0.56 个百分点 |
| B | 98,700 / 98,800 | 99.90% | —— |
| C | (98,700 + 0) / 100,000 | 98.70% | −0.56 |
| D | 99,940 / 100,000 | 99.94% | +0.04（**499 被算成成功，问题被藏起来**） |

口径 A 与 B 差 0.56 个百分点，在 99.9% 的门槛附近是「达标」与「不达标」的差别；口径 D 更危险——它把 40 次超时抹掉了，而这 40 次恰恰是用户真实感受到的。

::: warning 口径必须写进代码，不能写进文档
文档会过期，代码常量不会。正确做法是把口径做成一个可执行断言：

```java
// 分母定义：明确排除什么，且排除项必须写在同一处
static final Predicate<Request> DENOMINATOR =
    r -> !r.isClientError();        // 仅排除 4xx，499 与超时留在分母里
static final Predicate<Request> NUMERATOR = Request::isSuccess2xx;
```

改口径必须改这两行，改了就一定会进 code review。写在文档里的口径，改的时候没有人会看见。
:::

## 三、延迟为什么必看 P99：均值能藏多少

用一个刻意设计但完全真实的分布算一遍。1000 次请求：

- 990 次：100 ms
- 10 次：5,000 ms（超时级）

| 统计量 | 计算 | 结果 |
| --- | --- | --- |
| 均值 | (990×100 + 10×5000) / 1000 | **149 ms** |
| P50 | 第 500 个值 | 100 ms |
| P99 | 第 990 个值 | **5,000 ms** |
| 超时率（> 3s） | 10 / 1000 | 1% |

均值 149 ms 看起来很好，比 P50 只高 49%，容易被解释成「轻微长尾」。而 P99 是 5,000 ms——**每一百个用户里有一个等了五秒**。按日活 10 万算，每天有 1000 次这样的体验。

三个直接结论：

1. **均值只适合看趋势，不适合做阈值**。它的分母是所有请求，天然把长尾摊薄。
2. **P99 与 P999 一起看**。P99 修好之后，剩余问题常常藏在 P999（千分之一）。只看 P99 会出现「改完 P99 从 5s 降到 800ms，但用户投诉没减少」——因为最痛的那批还在 P999 里。
3. **慢的定义要写死**。`> 3s` 与 `> 1s` 是两个完全不同的指标，不能共用同一个名字。

## 四、分位数不可再聚合（读数作废的头号原因）

这是一个**会让所有多实例读数失效**的数学事实：

```text
实例 A：100 次请求，P99 = 1,200 ms
实例 B：9,900 次请求，P99 = 90 ms

「平均 P99」 = (1200 + 90) / 2 = 645 ms   ← 完全错误
真实整体 P99 ≈ 90 ms（因为 10,000 次里第 9,900 个值落在 B 的分布里）
```

错误在于：**分位数是分布的摘要，摘要不可再摘要**。取平均、取最大、取加权平均，三种都错，只是错的程度不同。

正确做法只有两条：

| 做法 | 机制 | 代价 |
| --- | --- | --- |
| 上报直方图（分桶） | 每个实例上报各桶计数，上游按桶求和后再算分位 | 需要预先定义桶边界；边界选错，分位精度下降 |
| 上报摘要（summary） | 每个实例本地维护分位估算 | **不可跨实例聚合**，只能看单实例 |

所以「按实例看分位、加总看总量」是唯一诚实的读法：**流量与错误率可以加总，延迟分位数不可以**。看到有人把多实例 P99 求平均，就知道那份报表不能用于决策。

## 五、四个必写项

每个指标必须写清四项，缺任何一项，三个月后一定会被重新解释一遍，且两次解释不会一致：

| 项 | 写法 | 反例 |
| --- | --- | --- |
| 指标名 | `对象_动作_结果` 三段式，不用驼峰、不用缩写 | `bizMetric1`、`cardMoveOK` |
| 口径公式 | 分子与分母都写出来，含排除项 | 「成功率」——哪个成功率 |
| 数据来源 | 哪一层上报（服务端 / 客户端 / 网关） | 不写，于是两处都上报 |
| 谁在什么时候看 | 角色 + 触发场景 | 「大家都看」= 没人看 |

第四项最常被省略，也最能筛掉垃圾指标。一个可直接用的句式：

> **「<角色> 在 <场景> 时看 <指标>，如果 <数值/趋势> 则 <动作>」**

写不出动作的指标，就是在收集数据而不是在驱动决策。

## 六、阈值从历史分位取值，不从愿望取值

一个常见的错误起点是「P99 应该 < 200 ms」，然后把它写进告警。这个数字通常来自另一个系统的经验，与本系统的实际分布无关。

正确的取法：

```text
① 取过去 4 周的 P99 序列（同一时段，排除大促/发布窗口）
② 若中位数为 X、P95 为 Y：
   告警阈值取 Y（即「比平时最差的 5% 还差」才叫）
   目标阈值取 X 的 1.2 倍（可达成的改进目标）
③ 上线后每月复核一次，分布整体下移则阈值同步下移
```

三条纪律：

1. **告警阈值取「历史 P95」，不取「历史最大值」**。取最大值等于永不触发（因为最大值会随流量增长刷新）。
2. **目标值取「中位数 × 1.2」**，不用行业数字。行业数字的唯一用途是判断「我们是不是落后一个数量级」。
3. **分布变化时同步改阈值**。只改代码不改阈值，会得到「系统变快了但告警更多」这种反直觉结果。

## 七、从 SLI 到错误预算：让「稳不稳」变成一个可花的数

SLO 的作用不是定目标，而是把「稳定性」变成一个**有余额、可消耗、会耗尽**的量：

```text
SLO = 99.9%（30 天滚动）
错误预算 = 30 天 × 0.1% = 43 分 12 秒的不可用额度
消耗率 = 当前已用 / 已过时间对应的额度
```

| 消耗率 | 含义 | 动作 |
| --- | --- | --- |
| < 1 | 比预算线更稳 | 正常发布 |
| 1 ~ 2 | 正在慢速烧预算 | 提高发布门槛（增加灰度时长） |
| 2 ~ 10 | 快速消耗 | 冻结非必要发布，优先修稳定性 |
| > 10 | 一小时内将耗尽 | 停止一切变更，全员转事故处理 |

这个表的价值在于**它把「要不要冻结发布」从会议决策变成了读数决策**。争议从「我觉得该停」变成「消耗率 11.3，按规则该停」。

::: info 常见误用
错误预算不是「可以故意用掉的额度」。它的用途只有一个：**在预算充裕时允许更激进的发布，在预算紧张时自动收紧**。把它当成「每月可以挂 43 分钟」的许可证，是把它用反了。
:::

## 八、判据族定义

| 判据 | 规则 | 违反时的样子 | 验证方式 |
| --- | --- | --- | --- |
| `MF-A` | 每类 SLI 只保留一个主指标，其余降为参考 | 五个延迟数不一致时无人知以哪个为准 | 命令 1 |
| `MF-B` | 所有比率型指标必须写明分母与排除项，且排除项只出现在一处 | 复盘时两个团队算出两个可用性 | 命令 2 |
| `MF-C` | 延迟主指标用 P99（辅以 P50 / P999），不用均值做阈值 | 均值 149 ms 而每百次有一次 5 s | 命令 3 |
| `MF-D` | 多实例延迟分位必须用直方图聚合，禁止对分位取平均 | 报表 P99 比任一实例都高/都低 | 命令 4 |
| `MF-E` | 指标名用 `对象_动作_结果` 三段式，禁止驼峰与编号 | 出现 `metric1` / `bizOk` 这类名字 | 命令 5 |
| `MF-F` | 每条指标必须写明「谁在什么场景看、看到什么值做什么」 | 看板存在但无任何决策引用 | 命令 6 |
| `MF-G` | 阈值取历史分位（P95），不取愿望值或行业默认值 | 低峰期阈值永不触发，高峰期持续触发 | 命令 7 |
| `MF-H` | 错误预算消耗率驱动发布冻结，冻结与否由读数决定 | 「要不要停」每次开会争一遍 | 命令 8 |

## 如何验证

```shell
# ① MF-B：分母与排除项是否只出现在一处
grep -rn "isClientError\|statusCode() >= 400" src/main/java --include=*.java
```

**预期输出**：命中 1 处（口径定义处）。若命中多处，说明排除逻辑散落在各接口里——任何一个接口写法不同，全站可用性就不可比。

```shell
# ② MF-C：延迟指标是否误用均值做阈值
grep -rn "avg\|mean" deploy/prometheus/rules/*.yml | grep -i "dur\|latency"
```

**预期输出**：空。若命中，说明告警基于均值，长尾完全在阈值之外。

```shell
# ③ MF-E：指标名是否违反三段式（含大写字母即驼峰或拼接）
grep -rhoE '[a-z_]*[A-Z][A-Za-z_]*' src/main/java/**/metrics/*.java | sort -u
```

**预期输出**：空（指标名全小写下划线）。若出现 `cardMoveSuccess`，同一个指标在不同服务里可能被写成 `card_move_ok`，永远聚不到一起。

```shell
# ④ MF-D：验证「分位不可再聚合」——两个实例的 P99 平均是否偏离整体
python3 - <<'PY'
import statistics, random
random.seed(7)
a = [100]*990 + [5000]*10          # 实例 A：少量长尾
b = [90]*9900                      # 实例 B：量大且稳
p99 = lambda xs: sorted(xs)[int(len(xs)*0.99)-1]
both = a + b
print("A.P99  =", p99(a))
print("B.P99  =", p99(b))
print("平均P99 =", (p99(a)+p99(b))//2, "  ← 错误读法")
print("整体P99 =", p99(both), "  ← 正确读法")
PY
```

**预期输出**：`A.P99 = 100`、`B.P99 = 90`、`平均P99 = 95`、`整体P99 = 100`。本例中两者接近是因为 A 的量太小、且长尾未进入整体前 1%；把 A 的请求数提到整体的 5% 以上，`平均P99` 会显著低于 `整体P99`——这就是「报表明明很好看但用户在骂」的成因。

```shell
# ⑤ MF-G：阈值与历史分位是否偏离过一个数量级
# 先取历史 P95，再与告警阈值比
curl -sG "$PROM/api/v1/query" \
  --data-urlencode 'query=histogram_quantile(0.95, sum by (le) (rate(http_request_duration_seconds_bucket[7d])))' \
  | jq -r '.data.result[0].value[1]'
grep -h "threshold" deploy/prometheus/rules/*.yml | head
```

**预期输出**：两个数应在同一数量级。若历史 P95 是 0.18（180 ms）而阈值写成 1.0（1 s），阈值形同虚设——真实劣化 5 倍都不会报警。

```text
⑥ MF-A / MF-F / MF-H：三条读法
   MF-A：打开延迟看板，数一数「主指标」有几个。> 1 即不成立。
   MF-F：随机抽三条指标，问「谁在什么时候看它」。三秒内答不出的即不成立。
   MF-H：把近四周「因预算消耗率而调整发布节奏」的次数数出来。0 次即不成立——
         说明 SLO 只是个数字，没有进入决策。
```

::: info 诚实标注
①~⑤ 的脚本中，②③⑤ 已在项目侧 `SignalScope` 的施工中被引用为「本步要满足什么」；**④ 的算例是本轮实跑的小样本演示**（10,000 条模拟数据，用于说明「平均 P99 ≠ 整体 P99」这一数学事实，不代表任何真实服务分布）。完整工程尚未构建，故 ①④ 未在真实产物上跑过。凡未跑过的，本页不标 ✅。
:::
