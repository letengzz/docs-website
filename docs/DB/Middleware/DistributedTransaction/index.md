# 中间件视角的分布式事务

前面几页的能力（读写分离、分片、影子库）都会带来同一个副作用：**一次业务操作可能落到多个物理库上**。一旦跨库，`@Transactional` 就不再是本地事务。本页不重复 [分布式事务专题](../../../Backend/Microservices/DistributedTransaction/index.md) 的原理与方案对比，只回答一个问题：**在中间件这一层，事务要怎么开、怎么配、怎么验、哪里会失灵。**

::: info 与既有专题的分工
- 2PC / TCC / SAGA / 本地消息表的原理与选型 → [分布式事务专题](../../../Backend/Microservices/DistributedTransaction/index.md)
- 分片场景下跨分片查询与事务的业务影响 → [跨分片查询与分布式事务](../../Relational/Sharding/CrossShard/index.md)
- **本页**：中间件提供了哪几种事务模式、配置写在哪、怎么用故障注入验证它真的回滚了、以及它的能力边界在哪
:::

## 1. 先分清：什么时候事务真的变成分布式了

| 场景 | 事务性质 | 中间件要做什么 |
| --- | --- | --- |
| 单库、读写分离，事务内全走主库 | **本地事务** | 保证事务内不切走从库（见 [读写分离工程化](../ReadWriteSplit/index.md)） |
| 分片后写落在同一个分片 | **本地事务** | 无需额外配置，但仍要保证路由不跨片 |
| 分片后写落在**多个分片** | 分布式事务 | 需要 XA / BASE 事务模式 |
| 分片库 + 缓存/MQ 同时更新 | **跨资源事务** | 中间件管不了 MQ 与 Redis，要靠业务补偿 |

::: danger 最常见的误解
「我用了分库分表中间件，所以事务是自动的」——**不对**。中间件在单分片路由时会走本地事务（快且安全），只有真正跨片时才启用分布式事务协调，而跨片事务的性能与失败模式与本地事务完全不是一个量级。

**所以设计阶段要尽量让「一个业务写操作只命中一个分片」**（按业务主键同源分片就是这个目的）。跨片事务应该是异常情况，不是常态路径。
:::

## 2. 中间件提供的三种事务模式

以 ShardingSphere 为例，事务类型由配置决定，三种模式的定位完全不同：

| 模式 | 一致性 | 性能 | 适用 | 代价 |
| --- | --- | --- | --- | --- |
| `LOCAL`（默认） | 单分片强一致，跨片**不保证** | 最高 | 绝大多数场景（前提：写好单分片路由） | 跨片出问题时无回滚保障 |
| `XA` | 强一致（两阶段提交） | 明显下降 | 跨片写必须一致、且能接受性能损失 | 事务期间连接被占用；prepare 后宕机需人工介入 |
| `BASE`（Seata AT / 柔性事务） | 最终一致 | 介于两者之间 | 跨片写、允许短暂不一致 | 需要额外部署 Seata；存在中间态需业务可容忍 |

```yaml [sharding-transaction.yml]
# ShardingSphere-JDBC：事务模式由事务管理器决定（示例）
# ① 本地事务（默认）：不写额外配置
# ② XA：显式指定 XA 事务管理器
props:
  sql-show: true
# 事务类型通过 Spring 的事务管理器选择，见下方 Java 配置

# ③ Seata 集成：接入 Seata 作为事务协调器
#   application.yml 侧配置 seata.tx-service-group 等，见官方文档
```

```java [XaTransactionConfig.java]
@Configuration
public class XaTransactionConfig {

    /** XA 模式：跨片写场景下的强一致选择，代价是事务期间占用连接 */
    @Bean
    public TransactionTypeHolder transactionTypeHolder() {
        return new TransactionTypeHolder();
    }
}
```

::: tip 提示
三种模式**不是全局开关，而是按业务方法选择的**。一个系统里完全可以：下单（跨片）用 XA 或 BASE，发布文章（单分片）用 LOCAL。把「哪些方法需要跨片事务」列成一张表，评审时逐条确认——这比笼统地说「我们上了分布式事务」有用得多。
:::

## 3. XA 在 MySQL 上的四个硬限制

XA 看起来很美（强一致、标准协议），但落地时会撞到数据库本身的限制：

| 限制 | 表现 | 应对 |
| --- | --- | --- |
| 事务期间**连接被独占** | 跨片事务把每个分片的一条连接钉住，并发上不去 | 控制跨片事务的并发量；连接池预算要为它留额度 |
| **prepare 后宕机** | 悬而未决的事务需要人工或恢复流程处理 | 部署 `XA RECOVER` 巡检与恢复脚本 |
| **不能覆盖非数据库资源** | Redis、MQ 不参与 XA | 走业务补偿或本地消息表 |
| MySQL 8.x 的 XA 与 `binlog` 顺序 | 不同版本有过已知问题，升级需重点回归 | 升级前用跨片事务用例回归 |

```sql
-- 巡检未决的 XA 事务（在分片库上分别执行）
XA RECOVER;
-- 期望：正常时返回空集；非空说明有 prepare 后未提交的事务
```

## 4. 「跨资源事务」才是日常：中间件管不了的那一半

真实业务里更常见的写法是「写库 + 发消息 + 删缓存」，中间件事务只覆盖了「写库」这一段：

| 资源 | 能否参与中间件事务 | 正确做法 |
| --- | --- | --- |
| 分片数据库 | ✅ | 用 XA / BASE |
| 缓存（Redis） | ❌ | **先写库、事务提交后再删缓存** |
| 消息队列 | ❌ | 本地消息表 / 事务消息，消费端幂等 |
| 第三方接口 | ❌ | 幂等键 + 补偿任务 + 对账 |

::: danger 三条顺序纪律
1. **缓存删除必须在事务提交之后**（用 `afterCommit`），事务内删缓存会让并发读把旧值写回；
2. **消息发送要么在事务提交后，要么走本地消息表**，绝不能在事务内直接发（事务回滚了消息已经出去了）；
3. **消费端必须幂等**，因为「至少一次」投递是常态。

这三条与 [缓存设计](../../NoRelational/Redis/Advanced/CacheDesign/index.md) 里的一致性问题同源：**跨资源没有免费的强一致，只有可验证的最终一致。**
:::

## 5. 用故障注入验证「真的回滚了」

分布式事务最危险的写法是「看起来配了、实际没生效」。验证必须用**故障注入**，而不是正常路径跑一遍：

```text
用例设计（跨片写入 + 第二步失败）
  1. 业务操作同时写分片 A 与分片 B
  2. 在写 B 之前人为抛异常（提前准备的测试分支 / 测试替身）
  3. 断言：
     - 分片 A 中该业务的数据行数为 0
     - 分片 B 中该业务的数据行数为 0
     - 未决 XA 事务数为 0（XA RECOVER 返回空）
```

| 模式 | 期望结果 | 不符合时的含义 |
| --- | --- | --- |
| LOCAL | **不保证**（这正是要把它显式标出来的原因） | 如果生产路径会跨片，就是设计缺陷 |
| XA | 两侧都回滚、`XA RECOVER` 为空 | 有残留 → 事务管理器或恢复流程有问题 |
| BASE | 最终一致：短期内可能出现「A 有、B 无」，但补偿任务跑完后一致 | 补偿任务没跑 / 不幂等 |

::: danger 别用「事务注解存在」当验证
`@Transactional` 加了、配置也写了，都不代表跨片事务真的被协调。**唯一的判据是故障注入后断言两侧数据都不存在**，而且要把它固化成一条自动化用例，每次改动路由规则都跑。
:::

## 6. 验证方式汇总

```shell
# ① 路由是否跨片（决定需不需要分布式事务）
#   打开 SQL 日志，执行一次业务写操作，确认所有 DML 落在同一个数据源
#   期望：只有一行目标数据源；若出现两个 → 该操作会走跨片事务

# ② 未决事务巡检（XA 模式，在每个分片库执行）
mysql -h <shard_n> -e "XA RECOVER;"
#   期望：空集

# ③ 故障注入断言（见上节用例设计），期望两侧行数均为 0

# ④ 事务模式生效确认：把事务管理器换成 LOCAL 再跑同一条用例
#   期望：XA 模式回滚、LOCAL 模式下不复现回滚（能复现说明测试没测到点上）
```

第 ④ 条是**变异测试**：如果一个测试在「正确配置」和「故障配置」下都通过，那它什么都没验证。
