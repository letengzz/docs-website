## 与分库分表的分工

本专题解决的是**单机内的查询优化**：让一条 SQL 在单库单表上跑得更快。当优化已经把单机榨干（索引、执行计划、锁粒度都到位）却仍然装不下或写不进时，才轮到[分库分表](../Sharding/index.md)——那是把数据**分散到多个库表**的水平扩展方案，代价是永久失去跨分片 JOIN、全局排序与唯一约束。

判据很简单：**能用索引解决的，不要用分片解决**。分片之后本专题的手段依然有效，而且会变得更关键——每个分片都是一台独立的单机，落在单个分片上的查询仍要用执行计划和索引去调。

- [分库分表 · 概述与决策](../Sharding/Overview/index.md)：容量评估换算与「要不要拆」的决策树，明确单机优化的边界在哪
- [分库分表 · 跨分片查询](../Sharding/CrossShard/index.md)：深分页、JOIN、聚合在分片后的改写方式
- [数据库中间件](../../Middleware/index.md)：单机优化与分片都做完之后，如果剩下的痛点是「读多写少」「连接数吃紧」「需要压出真实容量」，那要解决的是**架构这一层**——读写分离、影子库压测、连接多路复用。它不替代优化，只在优化到顶之后接手

## 与高并发系统设计的分工（第 141 天补充）

本专题的粒度是**一条 SQL**：为什么慢、执行计划怎么读、索引为什么失效、深分页怎么改。它的结论形式是「这条语句从 X ms 降到 Y ms」。

[高并发系统设计 · 总览](../../../Backend/HighConcurrency/Overview/index.md) 处理的是**语句之上的那一层**：当请求量超过数据库能承受的量时，上层该发生什么——连接池耗尽时是排队还是快速失败、线程池会被慢 SQL 占满多久、读写的预算怎么在入口就分配好。

| 问题 | 本专题（SQL） | 高并发系统设计（过载） |
| --- | --- | --- |
| 时间尺度 | 一次查询的耗时 | 整个系统在持续高压下的稳态 |
| 因果位置 | **病因** | **死法**（连接池耗尽、线程堆积、级联超时） |
| 处置手段 | 索引、重写、分区、缓存结果 | 连接池上限与获取超时、隔离、读接口降级 |

::: danger 一条顺序不能反的判断
**P99 被慢 SQL 拖长时，先优化再考虑防线。** 如果瓶颈是「某条语句本来就要 800 ms」，那么加限流只会把错误从「慢」换成「被拒」，而问题一个也没解决。判断方法很便宜：**看数据库连接池的使用率**——连接池没满而接口慢，病因在语句；连接池被打满并且等待队列在涨，才轮到过载这一层接手。
:::

## 与「GraphQL 服务端工程」的分工（第 257 天补充）

本页管的是「**一条语句**怎么变快」：索引、重写、分区、执行计划。GraphQL 那一侧管的是「**一次请求要发多少条语句**」——两件事的优化手段完全不同，混在一起会导致「索引都建对了，接口还是慢」。

| 这件事 | 本页负责 | [GraphQL 性能一页](../../../Backend/GraphQL/Performance/index.md)负责 |
| --- | --- | --- |
| 一条语句从 80 ms 降到 8 ms | 是（索引、计划、重写） | 只决定这条语句带几个参数 |
| 一次请求从 201 条语句降到 2 条 | 不是——单条再快也救不了 201 条 | 是（DataLoader / 手工批量） |
| `IN (100 个 id)` 的执行计划 | 是（超过几千项会走全表扫） | 只决定批大小上限 |
| 深翻页 `offset 100000` | 是（`(sort_col, id)` 复合索引 + 行值比较） | 只决定用 cursor 还是 offset |

::: danger 注意
**N+1 不是「SQL 慢」，所以拿 `EXPLAIN` 查不出来。** 200 条语句每一条都走索引、每条 0.1 ms，加起来仍然是 20 ms 加 200 次往返；而单看任意一条的执行计划，都是完美的 `Index Scan`。判断它只能靠**按请求统计语句条数**，不是靠慢查询日志——慢日志里每一条都不慢。
:::

## 与「报表与自助分析工程」专题的分工（第 262 天补充）

本页优化「一条语句有多快」；[报表与自助分析工程](../../../Backend/ReportAnalytics/index.md)关心「一页报表要发多少条语句、翻到第几页、导出多少行」。单条语句的 `EXPLAIN` 再漂亮，也挡不住「20 个图表各查一次」和「第 500 页的 OFFSET」。

::: danger 一页一坑：拿单条 SQL 的优化去治分页
本机 40,000 行、有 `created_at` 索引、每页 20 行的中位耗时：

| 分页 | 耗时 | 相对首页 |
| --- | --- | --- |
| `OFFSET 0` | 0.033 ms | 1.0× |
| `OFFSET 10,000` | 0.295 ms | 8.9× |
| `OFFSET 30,000` | 0.823 ms | **24.9×** |
| keyset（`WHERE created_at > ?`） | 0.034 ms | 1.0× |

每一条语句单独看都是完美的 `Index Scan`，慢的是「跳过 30,000 行」这件事本身——它不在任何一条语句的执行计划里，而在调用方的翻页方式里。**索引优化治不了分页，只有换分页方式能治。**
:::
