## 与分库分表的分工

本专题解决的是**单机内的查询优化**：让一条 SQL 在单库单表上跑得更快。当优化已经把单机榨干（索引、执行计划、锁粒度都到位）却仍然装不下或写不进时，才轮到[分库分表](../Sharding/index.md)——那是把数据**分散到多个库表**的水平扩展方案，代价是永久失去跨分片 JOIN、全局排序与唯一约束。

判据很简单：**能用索引解决的，不要用分片解决**。分片之后本专题的手段依然有效，而且会变得更关键——每个分片都是一台独立的单机，落在单个分片上的查询仍要用执行计划和索引去调。

- [分库分表 · 概述与决策](../Sharding/Overview/index.md)：容量评估换算与「要不要拆」的决策树，明确单机优化的边界在哪
- [分库分表 · 跨分片查询](../Sharding/CrossShard/index.md)：深分页、JOIN、聚合在分片后的改写方式
- [数据库中间件](../../Middleware/index.md)：单机优化与分片都做完之后，如果剩下的痛点是「读多写少」「连接数吃紧」「需要压出真实容量」，那要解决的是**架构这一层**——读写分离、影子库压测、连接多路复用。它不替代优化，只在优化到顶之后接手

## 与高并发系统设计的分工（第 141 天补充）

本专题的粒度是**一条 SQL**：为什么慢、执行计划怎么读、索引为什么失效、深分页怎么改。它的结论形式是「这条语句从 X ms 降到 Y ms」。

[高并发系统设计 · 总览](../../../Backend/HighConcurrency/Overview/index.md) 处理的是**语句之上的那一层**：当请求量超过数据库能承受的量时，上层该发生什么——连接池耗尽时是排队还是快速失败、线程池会被慢 SQL 占满多久、读写的预算怎么在入口就分配好。

| 问题 | 本专题（SQL） | 高并发系统设计（过载） |
| --- | --- | --- |
| 时间尺度 | 一次查询的耗时 | 整个系统在持续高压下的稳态 |
| 因果位置 | **病因** | **死法**（连接池耗尽、线程堆积、级联超时） |
| 处置手段 | 索引、重写、分区、缓存结果 | 连接池上限与获取超时、隔离、读接口降级 |

::: danger 一条顺序不能反的判断
**P99 被慢 SQL 拖长时，先优化再考虑防线。** 如果瓶颈是「某条语句本来就要 800 ms」，那么加限流只会把错误从「慢」换成「被拒」，而问题一个也没解决。判断方法很便宜：**看数据库连接池的使用率**——连接池没满而接口慢，病因在语句；连接池被打满并且等待队列在涨，才轮到过载这一层接手。
:::
