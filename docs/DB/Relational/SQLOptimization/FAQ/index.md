# SQL 优化常见问题与最佳实践

本页汇总 SQL 优化中最常遇到的问题：索引建了不生效、EXPLAIN 看不懂、分页慢、JOIN 慢、锁等待、COUNT 慢等，并给出生产级最佳实践清单。

## 索引建了但 EXPLAIN 不走，为什么

| 原因 | 处理 |
| --- | --- |
| 函数/运算包裹索引列 | 改写 SQL，让索引列保持原样 |
| 隐式类型转换 | 统一字段类型，字符串用引号 |
| 前模糊 LIKE | 改为后模糊或全文索引 |
| 违反最左前缀 | 检查联合索引列顺序 |
| OR 含非索引列 | 补索引或拆 UNION |
| 选择性太低 | 优化器放弃是合理的，考虑组合条件 |
| 统计信息过期 | `ANALYZE TABLE` 更新 |
| 字符集不一致 | 统一 utf8mb4 |

## EXPLAIN 关键字段怎么看

```text
type：访问类型（ALL 最差）
key：实际索引（NULL 说明没走索引）
rows：预估扫描行数（越小越好）
Extra：Using filesort / Using temporary 要警惕
```

快速判断：

1. `type=ALL` → 全表扫描，先看能不能用索引。
2. `key=NULL` → 索引没生效，按上表排查。
3. `Using filesort` → 排序字段没进索引。
4. `Using temporary` → 分组/去重优化空间。

## 为什么加了索引写入变慢

每个索引在 INSERT/UPDATE/DELETE 时都要同步维护：

1. 索引越多写入越慢（尤其是联合索引/冗余索引）。
2. 用 `sys.schema_redundant_indexes` 查冗余并删除。
3. 高频写表控制索引数量（3~5 个以内）。
4. 批量写入用分批 + 批量提交，减少索引维护次数。

## 分页很慢怎么办

```text
LIMIT 100000, 20 很慢
```

1. 列表只显示上一页/下一页 → 游标分页（WHERE id > last_id）。
2. 必须跳页 → 延迟关联（先查 id 再回表）。
3. ORDER BY 字段加索引（联合索引包含 WHERE + ORDER BY）。
4. 限制最大 offset，超限拒绝。
5. COUNT(*) 慢 → 缓存/近似值/单独计数表。

## JOIN 查询慢

1. 被驱动表连接字段加索引。
2. 检查连接字段类型与字符集一致。
3. 避免 SELECT *，只取需要的列。
4. 复杂查询先过滤再 JOIN（子查询/CTE）。
5. 超过 5 表 JOIN，考虑拆解或物化。
6. 确认没有笛卡尔积（ON 条件完整）。

## 查询不慢但接口慢，怎么排查

```text
SQL 执行 10ms，接口却要 1 秒
```

1. **连接池**：连接获取等待（池满）。
2. **网络**：应用与数据库之间 RTT。
3. **锁等待**：当前读遇到长事务。
4. **ORM 层**：N+1 查询（循环里逐条查）。
5. **返回数据大**：SELECT * 拉回大量无用字段。
6. **序列化**：Java 对象转 JSON 耗时。

## COUNT(*) 太慢

```sql
SELECT COUNT(*) FROM orders;   -- 500 万行全扫
```

优化：

1. 业务可接受近似值：缓存/信息_schema 估算。
2. 计数表：写入事务里同步增减。
3. 按时间范围 COUNT：`WHERE created_at >= ...` 走索引。
4. 分库分表后用汇总库。

## 生产 SQL 优化最佳实践清单

::: tip SQL 优化十诫
1. 先 EXPLAIN 再动手，用数据说话。
2. 全表扫描（type=ALL）是红线，能走索引就走索引。
3. 联合索引：等值前置、范围后置、选择性高的在前。
4. 覆盖索引优先：只查需要的列，不回表。
5. 深分页用游标/延迟关联，OFFSET 限深。
6. 被驱动表连接字段必有索引，类型字符集一致。
7. 事务最小化：不把网络请求放进事务，监控长事务。
8. 慢查询日志 + 监控告警常态化，每周治理 TOP SQL。
9. 索引变更评审 + 灰度 + 回滚，关注写入性能。
10. 一次只改一个变量，优化前后都要验证与记录。
:::

## 验证方式

1. 用 EXPLAIN 给自己的三条慢查询打分（type/key/rows）。
2. 对照十诫逐项检查生产数据库，列出前三项待办。
3. 建立慢查询台账，两周后对比响应时间与扫描行数。
