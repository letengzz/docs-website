# 常见问题与分诊

风控的线上问题有一个共同特征：**症状在看板上都长得差不多**（拦截率变了、分数变了、队列长了），但根因可能在任何一段。这一页给一张分诊表和十二个高频问题，目的是把「先看哪里」变成机械动作，而不是靠谁经验多。

本页判据族 `RDQ-A` ~ `RDQ-H`，共 8 条。定义表见文末「本页判据」一节。

## 一、分诊表：先看现象，再看段

| 现象 | 先看哪里 | 大概率原因 | 第一处置 |
| --- | --- | --- | --- |
| 拦截率突然翻倍 | 决策日志的 `hits` 分布 | 某条规则命中暴增（名单批量导入 / 特征口径变了） | 停用该规则，保留其他守卫 |
| 拦截率突然归零 | 规则版本 + `degraded` 比例 | 热更新加载了空规则集 / 降级到无规则档 | 回滚版本指针，查加载日志 |
| 同一用户两次结论不同 | `feature_missing` 与 `list_version` | 名单节点间不一致 / 特征快照不同 | 统一快照版本，禁随机分桶 |
| 分数整体下移 | 特征分布 PSI | 某个特征大面积落默认值 | 修特征，先别动阈值 |
| 人工队列小时内积压 | 到达率 λ 与产能 | 某条规则把 REVIEW 面放大 | 收紧该规则的动作（改 CHALLENGE） |
| 改了规则但结论没变 | `rule_version` | 未真正加载 / 被更高优先级规则覆盖 | 查版本号，查 `hits` 是否为空 |
| 名单命中率掉到 0 | 哈希口径 | 名单写入用了明文、查询用了哈希（或反之） | 对齐哈希函数与盐 |
| p99 从 20 ms 涨到 200 ms | 分段耗时 | 特征存储慢 / 名单缓存击穿 | 加超时 + 本地缓存 |
| 误杀客诉集中爆发 | `reason_code` 聚类 | 一条规则过宽，或一个名单批次有问题 | 撤销该名单/规则，加白 + 通知 |
| 黑产明显绕过 | 分维度聚合 | 规则被试探、阈值被摸清 | 加聚合特征，改动作而非改阈值 |
| 新模型 AUC 涨但精确率降 | 校准曲线 | 分数未校准 / 阈值沿用了旧刻度 | 重做校准再定阈值 |
| 影子差异率 40% | 规则 diff | 改动比预期大（多改了条件） | 拆成两次小改动 |

## 二、高频十二问

### 1. 拦截率翻倍，第一件事是关掉风控吗

不是。第一件事是**看 `hits` 分布**，找出贡献最大的那条规则，只停它。全关会把所有守卫一起摘掉——包括那条唯一能拦住当前攻击的规则。

### 2. 为什么「规则改了没生效」

三个原因按概率排：**版本没切**（`rule_version` 还是旧的）、**被更高优先级规则先命中**（`first_hit` 短路）、**条件恒为假**（特征缺失导致 `MISSING`）。第三个最隐蔽，查 `feature_missing` 一眼就能看出来。

### 3. 缺特征为什么不能当 0 算

因为 `0` 是合法值。回落 0 会让「大于阈值」类规则永不命中（静默关停策略），让「小于阈值」类规则全部命中（全员拦截）。两个方向都是事故，正确做法是进 `REVIEW`。

### 4. 分数 0.9 是不是就代表 90% 是坏人

不是。评分卡的原始输出是 log-odds 或未校准的模型分，`0.9` 只代表「比 0.5 更可疑」。只有当分数**经过校准**（预测坏率 ≈ 实际坏率）时，才可以当概率用，见[评分卡](../Scorecard/index.md)。

### 5. 名单能不能直接当拒绝理由

可以，但必须满足三条：有 `expire_at`、有 `source`、有申诉路径。没有失效时间的名单三个月后会把换号的人继续拦在门外；没有来源的名单在申诉时说不清为什么拦。

### 6. 规则条数多了会不会变慢

会，但**不是主要瓶颈**。本机实测 80 条规则求值 8.3 µs，一次 Redis 往返 200~500 µs。**优化规则是省微秒，优化远程调用才是省毫秒**，见[在线服务](../Serving/index.md)。

### 7. 为什么加了倒排索引反而更慢

当规则条数（80）小于字段数（120）时，逐条短路比「按首条件建桶再查」更快——实测 33.91 µs vs 46.48 µs，**索引慢了 27%**。索引适合「规则远多于字段」的场景。

### 8. 降级应该 fail-open 还是 fail-closed

按依赖性质定，不要一刀切：黑名单 fail-closed（进复核），灰名单 fail-open，历史特征缺失进复核，模型服务挂了退回规则档，日志写失败继续决策。见[在线服务](../Serving/index.md)第四节。

### 9. 人工队列爆了，能直接放宽阈值吗

能，但**先改动作再改阈值**。把大批 `REVIEW` 降级为 `CHALLENGE`（用验证码换人工），代价是转化率小幅下降，而放宽阈值等于把已识别的风险放回线上。

### 10. 影子跑出来差异 40%，还能灰度吗

不能。40% 的差异说明改动幅度远超预期，通常是「顺手多改了一个条件」。拆成两次改动分别影子，每次差异控制在 5% 以内再灰度。

### 11. 误杀怎么证明「已经修好了」

**用回归样本证明**：每个确认的误杀进回归集，改完后跑一遍，全部返回期望动作。没有回归集的「已修复」只是「这次没再遇到」。

### 12. 风控指标都正常，是不是就没事

不是。最常见的隐形故障是**降级运行**：`degraded=true` 的比例悄悄涨到 30%，指标看起来「平稳」只是因为它平稳地错了。所以 `degraded` 必须是独立看板项 + 告警。

## 三、止血顺序：先降噪，不降守卫

事故里的动作顺序比动作本身更重要。推荐顺序：

```text
1. 定位（1 分钟）：看 hits 分布 + degraded 比例 + 规则版本
2. 隔离（2 分钟）：只停/回滚出问题的那一条规则或那一个名单批次
3. 止损（5 分钟）：对已误处置的用户撤销 + 加白（带 TTL）+ 通知
4. 验证（10 分钟）：用固定 fixture 复跑，确认四条基线请求回到预期
5. 复盘材料（当天）：decision_id 清单 + 规则 diff + 时间线
```

::: danger 注意
1. **不要在事故里「顺手优化」**。改一个参数和改三个参数，事后无法区分是哪一个起了作用。
2. **不要用「全量放宽」当止血**。放宽阈值会让攻击者立刻拿到「现在最松」的信号，几小时内损失可能超过误杀本身。
3. **撤销必须可追溯**。谁撤销的、撤销了哪批 `decision_id`、依据是什么，都要落库——否则「误杀治理」会变成「随机放行」。
:::

## 四、术语对齐

| 词 | 本专题的含义 | 常见混淆 |
| --- | --- | --- |
| 决策（decision） | 一次请求的最终动作 + 依据 | 与「规则命中」混用 |
| 命中（hit） | 某条规则的条件成立 | 与「处置」混用（命中不等于拒绝） |
| 处置（action） | PASS / CHALLENGE / REVIEW / REJECT | 与「结论」混用 |
| 名单（list） | 带来源与失效时间的确定性证据 | 与「规则」混用 |
| 分数（score） | 评分卡输出，需校准才可当概率 | 与「坏率」混用 |
| 误杀（false positive） | 正常请求被非 PASS 处置 | 与「拦截率」混用 |
| 漏过（false negative） | 坏请求被 PASS | 与「通过率」混用 |

## 本页判据

| 编号 | 判据 | 看什么现象 | 不满足时改哪里 |
| --- | --- | --- | --- |
| `RDQ-A` | 分诊表能指到段 | 每个现象都对应到具体段与第一处置 | 补表，事故时按表走 |
| `RDQ-B` | 止血先隔离单条规则 | 事故记录里能看到「只停了哪一条」 | 改流程，禁止全量关停 |
| `RDQ-C` | 撤销留痕 | 有撤销人、批次、依据三列 | 补表，接审批 |
| `RDQ-D` | 降级比例是独立看板项 | `degraded` 比例有曲线与告警 | 加指标，阈值 5% 告警 |
| `RDQ-E` | 术语有统一定义 | 团队文档里能查到本页术语表 | 对齐术语，写进 onboarding |
| `RDQ-F` | 事故后补回归样本 | 回归集条数随事故增长 | 建回归集，接 CI |
| `RDQ-G` | 不在事故中做多项变更 | 变更单显示单次只改一处 | 拆变更，事后单独发 |
| `RDQ-H` | 有固定 fixture 可复跑 | 四条基线请求可作为冒烟测试 | 固化 fixtures，接 CI |
