# 消息队列

<p style="text-align:center;"><img src="./assets/mq-logo.png" alt="消息队列" style="zoom:75%;" /></p>

工作流引擎产生的外部副作用（审批通过后发通知、清缓存、同步检索）也走同一条路：**在引擎事务内只写一行本地事件，事务外异步消费，消费端必须幂等**。为什么不能把发通知直接写在流程监听器里、为什么要给事件做幂等键，见 [工作流与规则引擎 · 与业务系统集成](../WorkflowEngine/Integration/index.md)——那边讲「引擎事务边界怎么划」，本专题讲「消息怎么保证不丢不重」。

**当 Kafka 的角色从「业务异步解耦」变成「数据链路的主动脉」时，关注点会变**：不再只看投递成功，而是看「能不能重放、分区数够不够撑住并行度、顺序保证到什么粒度」。这套用法（分区键决定顺序边界、`acks=all` 必须配 `min.insync.replicas`、保留期由下游重跑周期反推）见 [大数据生态 · 生态组件](/docs/DB/BigData/Ecosystem/index.md)。

## 与高并发系统设计的分工（第 141 天补充）

本专题讲的是**消息中间件这一层**：投递语义、消费幂等、副本与集群、顺序性怎么保证。它的判据形式是「一条消息会不会丢 / 会不会重」。

[高并发系统设计 · 排队与削峰](../HighConcurrency/QueueShaping/index.md) 回答的是**上游的决定**：哪些东西该放进队列、放进去之后「拒绝」变成了「延迟」这个交换值不值、以及削峰之后积压的账怎么平。它不写 MQ 的任何配置，只决定**要不要用、用在哪一段、允许积压多久**。

| 问题 | 本专题（MQ 本身） | 高并发系统设计（削峰决策） |
| --- | --- | --- |
| 回答 | 「消息怎么不丢不重」 | 「什么该异步、积压多久算事故」 |
| 关键指标 | 投递成功率、消费延迟、`lag` | **消息年龄**（不是队列长度）、积压的可容忍时长 |
| 典型错误 | 事务与消息不一致、消费端不幂等 | 把「必须立刻返回结果」的操作也异步化 |

::: danger 一条最容易做反的事
**把削峰当成了「问题已解决」**：队列只把**峰值推后**，它不降低总工作量。如果上游的**平均**到达率已经高于消费能力，队列会一直增长，直到磁盘写满或消息过期被丢——而此时系统看起来是「健康的」（没有错误、没有报警，只有一条缓慢上升的曲线）。所以那边写死了一条判据：**队列的告警对象是「最老消息的年龄」而不是「队列长度」**，并且消费端必须在处理前检查消息年龄、过期直接丢弃并计数，否则用户会收到几小时前的操作结果。
:::
## 与「遗留系统改造」专题的分工（第 147 天补充）
本专题讲**消息中间件这一层**：投递语义、消费幂等、副本与集群、顺序性怎么保证。

[遗留系统改造](../LegacyModernization/index.md) 只用到它的两条结论：**至少一次投递 + 消费侧幂等**，以及**顺序只在同一分区 / 同一键内成立**。用它的地方也只有两处：

| 边界问题 | 归本专题 | 归遗留系统改造 |
| --- | --- | --- |
| 「Kafka 怎么配 `acks` 和 `min.insync.replicas`」 | ✅ | — |
| 「跨库一致性用什么保证」 | 提供能力 | ✅ 结论是**本地事务 + 发件箱**，不是分布式事务 |
| 「消息会不会丢、会不会重」 | ✅ 投递语义 | 迁移期关心的是**能不能重放**、重放**幂不幂等** |
| 「CDC 连的是哪个库、什么版本」 | — | ✅ CDC 的版本约束与破坏性变更 |

一句话分工：**队列自身怎么选、怎么配，留本专题；拿它去保证「新旧两边一致」，去遗留系统改造。**

本页特有的一个坑：「**至少一次投递**」意味着**重复是常态**，这在本页是常识；但改造期的重放场景会把重复放大——回退时要执行一次**反向批量重放**，如果重放单元不是「整行覆盖」而是「累加」，重复就变成数据错误。这条在 [数据迁移的反向重放](../LegacyModernization/DataMigration/index.md) 里被写成硬纪律。
