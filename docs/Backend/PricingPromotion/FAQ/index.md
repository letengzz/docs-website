# 常见问题与分诊

计价问题有两个特点：**症状离原因很远**（用户说「少减了 5 块」，原因可能在规则版本、分摊算法、券库存三处），以及**同一症状有多个不同根因**（「价格不对」至少有七种可能）。

这一页给一张分诊表，把「症状」映射到「先查什么」，再补十二个高频问答与五条听起来对、实际错的建议。

![分诊：从症状到第一现场](../assets/pp-triage.svg)

本页判据族 `PPQ-A` ~ `PPQ-H`，共 8 条。定义表见文末「本页判据」一节。

## 一、分诊表

按「用户/运营/财务描述的那句话」直接定位第一现场：

| 症状（原话） | 第一现场 | 一条命令 / 一个查询 | 常见根因 |
| --- | --- | --- | --- |
| 「优惠少减了几块钱」 | 券选择 | 查 `price_quote.items_json` 里的 `candidates` | 贪心未达最优（2.3%）、券被互斥组挡掉 |
| 「结算价比详情页贵」 | 试算与结算 | 比 `quote.settle_amount` 与 `order.settle_amount` | 未锁价、改价未做时间化 |
| 「优惠后金额对不上订单总额」 | 分摊 | `SELECT * FROM v_alloc_check` | 各自四舍五入（29.43%） |
| 「退款退多了 / 退少了」 | 逆向分摊 | 比 `refund.amount` 与 `order_line_alloc.alloc_amount` | 重算而非读原分摊（28.59%） |
| 「券显示已抢光但我刚领到」 | 券库存 | `SELECT used,total FROM coupon_template WHERE id=?` | Redis 与 DB 不一致、无条件更新 |
| 「券用了两次」 | 核销幂等 | `SELECT count(*) FROM coupon_redeem WHERE instance_id=?` | 缺 `UNIQUE(instance,order)`、MQ 重投 |
| 「活动到点了没生效」 | 生效窗口 | 查 `start_at/end_at/tz` 与 `now()` | 右闭区间、时区写死、缓存未失效 |
| 「同一单两次打开价格不同」 | 顺序敏感 | 查规则排序键是否三级全序 | `PAYABLE` 口径 + Map 遍历顺序 |
| 「分账少了一百多」 | 承担分摊 | 比 `Σ 商家承担` 与 `优惠额` | 两套分摊实现（28.77%） |
| 「发票行金额加起来不对」 | 行实付 | 比 `Σ line_paid` 与 `trade_amount` | 运费/税混入优惠字段 |
| 「大促一开始就报错」 | 券库存热点 | 查单模板 TPS 与锁等待 | 单行热点更新，未分片 |
| 「客服补的单没有优惠」 | 补单路径 | 查补单是否走同一计价链 | 补单直写 `payable` |

::: tip 分诊的第一原则
**先确认「这个数是被算错的，还是被改错的」**。两者的排查路径完全不同：算错去查链路（规则、券、分摊），改错去查 `price_adjustment` 表与操作日志。90% 的「算错了」最后都发现是某次手工改价没登记。
:::

## 二、十二问

**Q1：金额到底用 `decimal` 还是整数分？**
整数分。`decimal` 解决表示精度，不解决舍入策略与守恒；而计价的核心矛盾是守恒与可重算，不是表示。展示层才转元。

**Q2：优惠分摊一定要守恒吗？差 1 分真的要紧吗？**
要紧。1 分不影响用户体验，但会让「Σ 行 = 订单额」这个断言失效；一旦这个断言不成立，退款、分账、开票、对账四条链全部失去校验依据。实测 29.43% 的订单会差 1~2 分。

**Q3：最大余数法会不会不公平？**
它的性质是「每行与理想份额的偏差 < 1 个最小单位」，且偏差分配由余数决定，与行顺序无关（同余时按索引，是可复现的确定性规则）。比「各自四舍五入 + 差额塞给第一行」公平得多。

**Q4：为什么不能让用户自己选券就行，系统不用算最优？**
可以让用户选，但**默认值必须是最优或接近最优**。默认选错等于静默多收钱，而用户不知道还有更省的选择。真正的折中是「系统给最优 + 展示候选与差额 + 允许改选」。

**Q5：券库存放 Redis，用 `DECR` 是不是就不会超发？**
`DECR` 本身是原子的，所以「扣减」不会超发；但「判断能不能扣」如果放在 `DECR` 之前（先 `GET` 判断），依然会超发。且 Redis 与 DB 双写会引入新的不一致。**唯一真相在 DB，Redis 只做加速读**。

**Q6：试算结果能不能直接放前端，提交时带回来？**
可以带回来做**校验**，但**不能作为计价依据**——前端可篡改。正确做法是带 `quote_id`，服务端按 id 取回自己存的 quote。

**Q7：锁价 30 分钟，用户 29 分钟时下单，库存没了怎么办？**
锁价不锁库存，所以会出现「价格有效但下不了单」。这是可接受的：提示「商品已售罄」比「价格变了」更容易被接受。

**Q8：规则能不能直接写 Java `if`？**
三五条可以，超过十条不行。判据是：**运营改一次要不要发版**。要发版就说明规则已经是数据了，只是被写进了代码。

**Q9：互斥组够用吗？还需要「叠加矩阵」吗？**
够用。叠加矩阵是 N² 个标记，组是 N 个标记。真要表达「A 与 B 可叠加、A 与 C 不可」这种非传递关系，用「三层组」（`GROUP_A` / `GROUP_B` / `GROUP_A|B`）比矩阵更可维护。

**Q10：退款时优惠怎么退？按比例还是按分摊？**
按**原分摊**。重算会差（28.59%），且差额方向随机——有时多退、有时少退，无法用一条规则修正。

**Q11：多币种要注意什么？**
三件事：minor unit 不同（日元 0 位、第纳尔 3 位）、汇率换算的舍入点、以及**不要跨币种做分摊**（一笔订单只能一个币种）。

**Q12：怎么证明计价引擎是对的？**
不是「跑通了下单」，而是三条：① 分摊守恒查询 0 行；② 同一 `quote_id` 重放金额相同；③ 四条负向验收真的会红。见[实战](../Practice/index.md)。

## 三、五条「听起来对」的错误建议

| 建议 | 为什么错 | 正确做法 |
| --- | --- | --- |
| 「先上线，金额差几分钱财务调一下」 | 财务调账没有来源，一年后变成无法解释的历史差额；且退款会继承错误 | 上线前把守恒断言接进 CI |
| 「用 `double` 最后 `toFixed(2)` 就和 `decimal` 一样」 | `toFixed` 只在最后一步，中间的比较与累加已经脏了 | 全程整数分 |
| 「优惠都算在订单级，展示时按比例分一下就行」 | 展示用的分摊与账用的分摊成了两套，退款一取就错 | 一套分摊，展示直接读它 |
| 「券核销失败就重试几次」 | 重试放大的是**副作用**，不是成功率；实测无幂等键时超时重试把执行放大 3 倍 | 先幂等，再重试 |
| 「规则冲突让运营自己保证」 | 运营看不到时间区间重叠，且人一定会配错 | 发布前跑冲突检测，非 0 阻断 |

## 四、上线自查（14 项）

```text
金额与精度
 1. 全链路金额字段是否都是整数（分），有无残留 float/double
 2. 舍入模式是否全局唯一，且只在分摊/税率两处调用
 3. 是否存在「应付直接赋值」的代码路径（应写 price_adjustment）

优惠计算
 4. 每条规则的 threshold_base 是否非空
 5. 规则执行顺序是否由 stage/priority/code 三级排序键决定
 6. 组内命中多条时是否记录淘汰候选
 7. 券叠加是否封顶，absorbed 是否有字段

分摊与逆向
 8. Σ line_alloc 是否等于各来源优惠额（v_alloc_check 为 0 行）
 9. 是否存在 d_i > p_i
10. 退款是否读原分摊而非重算

并发与幂等
11. 券核销是否条件更新（WHERE used < total）
12. (instance_id, order_id) 是否有唯一键
13. 幂等键保留期是否 ≥ 7 天

同源
14. 下单是否收 quote_id、是否校验 expire_at、是否落 price_version/rule_version/bucket
```

14 项里，**第 3、8、9、11 项**是最常见的漏项——它们都不会让功能跑不起来，只在事故时决定你有没有抓手。

## 五、本页判据

| 编号 | 看什么现象 | 判成什么 | 不满足时改哪里 |
| --- | --- | --- | --- |
| `PPQ-A` | 分诊表是否覆盖 12 类症状，每类是否有「一条查询」 | 缺覆盖即失败 | 按实际事故补行，不许写「联系开发」 |
| `PPQ-B` | 「少减了几块」是否能从 `quote` 的 `candidates` 直接看出原因 | 查不到即失败 | 返回候选与 `reason` 四值 |
| `PPQ-C` | 「退款多退」是否能一小时内定位到分摊行 | 定位不了即失败 | 退款单存 `line_alloc_id` |
| `PPQ-D` | 是否存在「先上线、账后调」的补偿流程 | 存在即失败：错误被固化 | 守恒断言进 CI，阻断发布 |
| `PPQ-E` | 手工改价是否 100% 有原因码与操作人 | 缺失即失败 | `price_adjustment` 非空校验 |
| `PPQ-F` | 分诊表里的每条查询是否都实际跑过（不是抄来的） | 未跑过即失败 | 逐条在预发环境跑一遍并记录 |
| `PPQ-G` | 14 项自查是否在发布单里逐项勾选 | 未勾选即失败 | 发布模板固化这 14 项 |
| `PPQ-H` | 是否存在「Redis 扣减 + DB 异步补写」的双写券库存 | 存在即失败 | 改为 DB 唯一真相 + 缓存只读 |
