# 四个维度与五个必失点

多租户的失效很少是「配错了」，而是**配好了、跑起来了、只在某个入口漏掉**。本页先把四条主线摊开，再用五个本机实测说明「漏」都发生在哪些缝里。

![四个维度与五个必失点](../assets/mt-overview.svg)

本页判据族 `MTO-A` ~ `MTO-H`，共 8 条。定义表在第七节。

## 一、四个维度，各判一件事

| 维度 | 判什么 | 谁负责 | 失效时的表象 | 怎么查 |
| --- | --- | --- | --- | --- |
| ① 隔离 | 这个租户能看见哪些行、能写进哪些行 | 库层的策略 + 应用的 `WHERE` | 看到别人的数据，或自己一行都看不到 | `pg_policies`、`EXPLAIN` 里的 `Index Cond` |
| ② 公平 | 一个租户的突发会不会拖慢别人 | 队列、线程池、连接池、限流器 | 某个租户一进来，全站 p99 起飞 | 按租户拆的延迟分位数 |
| ③ 计量 | 他做的事有没有被记成可结算的数 | 事件采集 + 聚合 + 账期 | 账单对不上、毛利算不出、客诉无据 | 账单行能不能追到事件 ID |
| ④ 生命周期 | 从开通到退出有没有留下证据 | 开通编排 + 状态机 + 归档 | 删了却删不干净、开了两次两个库 | 状态机可达性 + 残留对账 |

四条主线**不是并列的**，它们有硬依赖：隔离没做对，计量的账就没有可信度（你不知道记的是谁的量）；公平没做，计量会把「被饿死的租户」记成「用量很低」，账单反而更低。所以顺序永远是 **隔离 → 公平 → 计量 → 生命周期**。

::: tip 一句话分辨四条主线
隔离回答「他能不能看见」，公平回答「他能不能跑起来」，计量回答「他该付多少」，生命周期回答「他什么时候开始、什么时候彻底消失」。四件事的验收方式完全不同，不能合成一条。
:::

## 二、五个必失点（全部本机跑过）

### ① 上下文没设：同一条连接把上一个租户带了过来

池化的连接会被复用。如果上下文用**会话级**写法（`set_config(..., false)`），而某一次请求走了「不需要设上下文」的分支（健康检查、缓存命中、异步补偿），那条连接上残留的就是**上一个租户**。

```sql
-- 请求 1：正常设置上下文，读到 1,000 行
select set_config('app.tenant_id', 't3', false);
select count(*) from mt_shared.orders;          -- 1000

-- 请求 2：走缓存分支，忘了设 —— 没有任何报错
select count(*) from mt_shared.orders;          -- 1000，但这是 t3 的数据
```

实测结果就是两行 `1000`：第二个请求看到的不是「空」，而是**别人的 1,000 行**。这类缺陷在测试环境极难复现，因为测试环境的并发路径与缓存命中率都和线上不同。

### ② 上下文是空串：一行都看不到

同一个策略，把上下文设成**空串**：

```sql
select set_config('app.tenant_id', '', false);
select count(*) from mt_shared.orders;          -- 0（全表 30 万行）
```

策略写的是 `tenant_id = nullif(current_setting('app.tenant_id', true), '')`，空串经 `nullif` 变成 `null`，`tenant_id = null` 恒为 `null`，所以**一行都不返回**。

这是「fail-closed」的正确行为，但它表现出来的样子是**列表全空、详情 404**——和「这个租户确实没有数据」完全一样。线上排查时，第一个被怀疑的通常是「数据被删了」，而真正的原因是异步线程里没拿到上下文。

::: danger 这两条必须分开验
1. **「没设」与「设成空串」是两种结果**：前者读到别人的数据（越权），后者读到 0 行（功能故障）。用一个断言只能覆盖其中一种。
2. **不要用 `current_setting(...) is null` 判「复位了吗」**：`SET LOCAL` 在事务结束后留下的是空串而不是 `null`，必须写 `nullif(current_setting('app.tenant_id', true), '')`。
:::

### ③ 策略被关掉：一次 `ALTER` 就把 30 万行全放出去

同一个查询，RLS 开着与关掉：

| 状态 | 单次查询 | 返回行数 |
| --- | --- | --- |
| `FORCE ROW LEVEL SECURITY` | **0.049 ms** | 463 |
| `DISABLE ROW LEVEL SECURITY` | **56.361 ms** | 234,299 |

慢 **1,149 倍**、多读 **506 倍**的行。注意这个数字的方向：**关闭隔离不会让系统更快，而是让它慢得离谱**——因为它在做一件根本不该做的事（全表聚合）。

这条也解释了为什么「策略被误关」很难被性能监控发现：如果这个接口平时就慢，56 ms 会被当成「正常波动」。

### ④ 大租户的点查：同一条 SQL，96 倍差距

在同一个库、同一张表、同一个索引上，只把租户换成一个占 40% 数据量的租户：

| 租户 | 查询耗时 | 返回行数 |
| --- | --- | --- |
| 普通租户（1,000 行） | **0.049 ms** | 463 |
| 大租户（200,000 行） | **4.723 ms** | 88,400 |

**96 倍**。这条是本专题反复出现的隐藏主线：**数据量本身就是一种噪声邻居**，而且它绕过所有应用层的限流器——限流器数的是请求数，不是行数。

大租户的查询还会让优化器改换计划：返回 20% 的行时，`Index Only Scan` 不再划算，退化成 `Parallel Seq Scan`，于是它开始消耗**所有**租户共享的 buffer 与 CPU。

### ⑤ 备份基线随租户数线性膨胀

schema-per-tenant 模式跑 300 个租户后，一次 `pg_dump --schema-only`：

```shell
docker exec schemalab-pg bash -c "time pg_dump -U postgres -d mtlab --schema-only -f /tmp/schema.sql"
# real 0m0.523s
wc -l /tmp/schema.sql   # 26560
du -h /tmp/schema.sql   # 492K
```

**26,560 行 DDL、492 KB、0.52 秒**——平均每个租户往备份基线里加了 **88 行**。这个数字本身不大，但它是**每次**备份、**每次**恢复演练、**每次**迁移都要过的量，而且它对「新增一个租户」是线性增长，对「新增一列」是 300 倍放大。

共享表模式下同一份备份只有一张表的 DDL。

## 三、判定链：七个问题，按顺序问

排查任何「多租户不对」的问题，按这个顺序问，比乱试快得多：

1. **谁在连？** `select session_user`。连接池共用账号时，审计里分不清租户。
2. **谁在干活？** `select current_user`。与 `session_user` 不同，说明有 `SET ROLE` 或安全定义函数。
3. **上下文取到了吗？** `nullif(current_setting('app.tenant_id', true), '')` 返回的是值、空串还是 `null`。
4. **策略在不在、`FORCE` 了吗？** `pg_policies` 看策略，`pg_class.relforcerowsecurity` 看开关。
5. **这条 SQL 走哪个索引？** 计划里 `Index Cond` 有没有带上租户列——它决定大租户会不会拖垮别人。
6. **配额扣在哪一层？** 网关、服务、数据库三层扣减的语义完全不同（见 [配额执行](../QuotaEnforcement/index.md)）。
7. **账单能不能追到事件？** 追不到就说明计量口径与业务口径之间断了一环（见 [计量与账单](../MeteringBilling/index.md)）。

::: warning 第 5 问最容易被跳过
「查询慢」的第一反应通常是「加索引」。但多租户场景下，索引往往已经在了，真正的问题是**租户之间的数据量差了两个数量级**，同一条 SQL 对 A 是索引点查、对 B 是全表扫描。先看计划，再谈索引。
:::

## 四、一条请求该由哪一层兜住：归属表

| 现象 | 归属 | 先改哪里 |
| --- | --- | --- |
| 看到了别的租户的数据 | ① 隔离 | 策略是否 `FORCE`、上下文是否空串、有没有 `BYPASSRLS` 角色 |
| 列表全空、详情 404 | ① 隔离 | 上下文是否被异步线程丢掉；策略是否 fail-closed 到 0 行 |
| 某个租户一进来全站慢 | ② 公平 | 共享队列改每租户轮转；入口按租户限流；大租户走专属池 |
| 配额总是差一点点超 | ③ 计量 | 扣减是否原子；是不是「先查后改」 |
| 账单比实际用量多 0.5% | ③ 计量 | 事件有没有按 `event_id` 去重 |
| 删了租户但报表里还有 | ④ 生命周期 | 删除传播清单；缓存与副本是否在清单内 |
| 同一个租户开了两个库 | ④ 生命周期 | 开通是否幂等；有没有唯一约束兜底 |

## 五、三种不该「做多租户」的场景

多租户是一种成本，不是一种荣誉。以下三种情况用别的办法更省：

1. **客户数量个位数、且都是大客户**：直接一客户一套部署（独立库 + 独立实例）。省下来的隔离代码与排查成本，远大于机器钱。
2. **合规要求「数据物理隔离」且不可协商**：这类要求无法用行级策略满足（策略是逻辑的），必须独立库或独立实例，别在共享表上做妥协。
3. **只有一个客户，但要求「多工作区」**：那是**同一个租户内的分组**，不是多租户。把 `workspace_id` 当成第二级维度，不要引入第二套隔离机制。

## 六、五步起步（半天能做完）

1. **盘上下文**：把所有设上下文的位置列出来，确认哪些是事务级、哪些是会话级、哪些根本没设。
2. **盘策略**：`select relname, relrowsecurity, relforcerowsecurity from pg_class where relrowsecurity`，找「开了没 `FORCE`」的表。
3. **盘入口**：找出所有 `BYPASSRLS` 角色与分析库连接，逐个确认它们是否该存在。
4. **盘请求分布**：按租户统计 QPS 与平均返回行数——这一步就能看出谁是噪声源、谁是大租户。
5. **盘账**：随便挑一行账单，试着把它追到一个具体的事件 ID。追不到，说明计量链路有断点。

## 七、本页判据

| 编号 | 判据 | 看什么现象 | 不满足时改哪里 |
| --- | --- | --- | --- |
| `MTO-A` | 四条主线各有明确的负责人与配置位置 | 有一张「维度 → 谁配 → 怎么查」的表 | 补归属表；否则出问题只会互相等 |
| `MTO-B` | 上下文「没设」与「设成空串」分别有断言 | 两条负向用例都能跑出预期结果 | 见 [租户上下文](../TenantContext/index.md) 的四个断点 |
| `MTO-C` | 所有含租户列的表都 `FORCE` 了策略 | `relrowsecurity` 与 `relforcerowsecurity` 成对核对 | 对含租户列的表加 `FORCE` |
| `MTO-D` | 每条高频 SQL 都看过执行计划 | 计划里 `Index Cond` 带租户列 | 补复合索引（租户列在前） |
| `MTO-E` | 有按租户拆分延迟的能力 | 能看到「某租户 p99」而不只是全局 p99 | 指标加租户标签（注意基数） |
| `MTO-F` | 账单行可追到事件 | 随机一行账单能列出事件 ID | 补计量的溯源字段 |
| `MTO-G` | 已知的 `BYPASSRLS` 角色全部登记 | 清单里每个角色都有理由与负责人 | 收掉分析库以外的 `BYPASSRLS` |
| `MTO-H` | 有一份可复跑的盘点脚本 | 第 6 节的五步能在半天内跑完 | 见 [实战](../Practice/index.md) 的验收序列 |
