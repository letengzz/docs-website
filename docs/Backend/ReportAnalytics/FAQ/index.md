# 常见问题与分诊

本页收的是「被问过三次以上」的问题。每问给一句结论、一段理由、一条可执行验证；不给「看情况」。

本页判据族 `RPQ-A` ~ `RPQ-H`，共 8 条。

## 一、三步分诊：先分类，再查数

| 现象 | 先分到哪一类 | 第一步查什么 |
| --- | --- | --- |
| 「两个地方数不一样」 | 口径 / 快照 / 权限 | 三处的 `snapshot_id` 与 `version_id` 是否相同 |
| 「数偏大，大约整数倍」 | 关联膨胀 | 去掉 `JOIN` 后行数是否等于业务对象数 |
| 「数偏小，少一整块」 | 过滤吞行 | 分组里有没有 `(未知)` 组，各组之和是否等于总数 |
| 「页面很慢，但命中率 90%+」 | 回退路径 | `fallback_rate` 与回退 p95 的日趋势 |
| 「导出和页面不一致」 | 同源 | 导出的行数与页面可见行数是否相等 |
| 「邮件里的数变了」 | 快照 | 投递记录指向 `snapshot_id` 还是「现场查」 |

分诊的价值在于**它把「查数据」变成「查结构」**：六类现象各自对应一个可执行断言，而不是打开 SQL 客户端碰运气。

## 二、十二个判断题

**Q1：同一个报表，页面和导出差 3 行，为什么？**

先看权限视图是否同一个。最常见原因是页面走 `v_orders_secure`（含 RLS），导出走 `orders`（不含）。验证：两条 SQL 的行数比对。若相等而数字不等，再看导出是否在生成后做了二次过滤（比如「去掉合计行」）。

**Q2：合计行和明细行之和不等，差得还很多。**

过滤位置错了：先聚合后裁剪。判据是「合计行 = 明细行之和」，见[下钻与权限](../DrillPermission/index.md)。

**Q3：金额虚高 2 倍多，是不是数据重复了？**

不一定是重复入库，多半是 `JOIN` 一对多。本机典型值 2.344 倍。验证：`SELECT COUNT(*) FROM a JOIN b USING(id)` 与 `SELECT COUNT(*) FROM a` 的比值。**不要用 `SUM(DISTINCT amount)` 修**——那会变成偏低 19.7%。

**Q4：某个维度整块不见了。**

`WHERE col <> 'x'` 把 NULL 行吞了（NULL 与任何值比较都是 `unknown`）。本机 40,000 行里 5,714 行是 NULL（14.29%）。改用 `IS DISTINCT FROM`，或在分组时 `COALESCE(col,'(未知)')`。

**Q5：日报和月报加起来对不上。**

两个可能：时区切日不同（UTC 30 天 vs +08 31 天），或月报用了「月末快照」而日报是实时的。先对齐 `timezone` 与 `snapshot_id`，再谈数字。

**Q6：报表改了口径，历史月报要不要重算？**

不重算。历史月报引用的是当时的 `version_id`，重算等于篡改历史。要对比就做「版本并存对照」，见[报表定义](../ReportDefinition/index.md)。

**Q7：订阅能不能每次发送时重新查一次，保证是最新的？**

不能。本机实测同一区间两次执行差 **14.66%**。订阅发的应该是快照；要「最新」，就提高快照生成频率，而不是在发送时重查。

**Q8：命中率 95%，为什么用户还是说慢？**

命中率的分母是「请求」，慢的是「回退请求」。必须同时看 `fallback_rate` 与回退 p95。另外，命中率可以被「只统计热门查询」轻易做到 99%，见[预聚合](../AggregateHit/index.md)。

**Q9：自助查询要不要开放给业务？**

先满足三个条件：有行数预估、有数据库层超时、分页用 keyset。三条缺一条，开放的结果都是「数据库被打挂 + 用户抱怨慢」。

**Q10：导出要不要限流？限多少？**

要。本机仿真：到达 8 次/分、2 个 worker 时，不设上限的 p95 是 783 s；上限 5 时 p95 66 s、拒绝 24.2%。「上限 20」并不更好——拒绝率几乎一样（21.9%），只是把拒绝推迟到 3 分钟后。

**Q11：导出的文件要不要留在服务器上？**

不留。文件 24 小时后自动删，记录长留。用户要的是「拿到文件」，不是「服务器上有一份」。留存越久，「删除请求」要处理的副本越多。

**Q12：报表要不要建版本目录（像 Spring5/Spring6 那样）？**

不要。换代的是产品与方言，判据没变。需要版本目录的是「同一份代码两套写法」的主题，见[目录页](../index.md)的「版本组织」一节。

## 三、四个反例（评审时最常被写进来的）

| 反例 | 为什么错 | 正确写法 |
| --- | --- | --- |
| `SUM(DISTINCT amount)` 修膨胀 | 值去重会合并同额订单，从偏高变偏低 | 先在业务对象粒度聚合，再 `JOIN` |
| 订阅存 `report_code` 取最新 | 历史报表被静默改写 | 存 `version_id`，升级要显式动作 |
| 前端按角色隐藏敏感列 | 接口仍返回，抓包即得 | `SELECT` 白名单 + 服务端掩码 |
| 导出文件放公开桶 | 链接可被转发且无法吊销 | 私有桶 + 15 分钟签名 |

## 四、术语表

| 术语 | 含义 | 易混点 |
| --- | --- | --- |
| 粒度 grain | 一行代表什么业务对象 | 与「分区」不是一回事 |
| 快照 snapshot | 某次生成的定格结果 | 不是「物化视图」，物化视图会被刷新 |
| 回退 fallback | 没有可用预聚合，改查明细 | 不是「降级」，是正常路径的一种 |
| 行膨胀 fan-out | 一对多关联导致的行数放大 | 与「重复数据」不同，数据本身没重复 |
| 水位 watermark | 数据到达的边界时刻 | 与「数据日期」不同，一个是到达，一个是归属 |

## 五、本页判据

| 编号 | 判据 | 为什么要它 | 怎么验证 |
| --- | --- | --- | --- |
| `RPQ-A` | 每个「数不一样」的工单先落到六类现象之一 | 不分类就只能盲查 | 工单模板含「现象分类」字段 |
| `RPQ-B` | 反例清单进评审检查表 | 四个反例都「看起来合理」 | 评审记录引用本页反例 |
| `RPQ-C` | 口径问题的回答必须带 `version_id` | 没有版本就没有共同语言 | 答复中出现具体版本号 |
| `RPQ-D` | 粒度问题的回答必须写明「一行是什么」 | 否则两边在讨论不同对象 | 答复含 `grain` 描述 |
| `RPQ-E` | 权限问题的回答必须区分「页面 / 接口 / 导出」三入口 | 三入口常常不同源 | 三处行数比对结果 |
| `RPQ-F` | 导出问题的回答必须给排队与限额的具体数 | 「加机器」不是答案 | 答复含 p95 与上限值 |
| `RPQ-G` | 术语表与库内其他专题一致 | 「快照」在两册含义不同会误导 | 与[指标平台](../../MetricPlatform/index.md)术语比对 |
| `RPQ-H` | 每条回答附一条可执行验证 | 结论不可验证等于没回答 | 任取一条 Q，能照抄 SQL |
