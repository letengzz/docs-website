# 契约演进与兼容

<p style="text-align:center;"><img src="./assets/contract-evolution-logo.png" style="zoom:75%;" /></p>

接口一旦有人调用，它就不再属于你。**契约演进**（Contract Evolution）处理的正是「契约必须变、但调用方不能被打断」这件事：先判断一次改动到底打不打人，再决定用哪一种机制承载它，最后给旧版本一条可执行的下线路径。

这一页不讲「REST 该怎么设计」——那是 [API 设计规范](../../Tools/APIDesign/Overview/index.md) 的地盘。这里讲的是**已经上线的接口、消息与表结构，怎么在不破坏既有消费者的前提下继续长大**。

## 事实与口径速览（2026-10 核对）

| 事实 | 口径 | 对本专题的意义 |
| --- | --- | --- |
| `Deprecation` 响应头 | [RFC 9745](https://www.rfc-editor.org/rfc/rfc9745.html)，值为结构化字段日期 `@<Unix 秒>` | 废弃是**机器可读**的信号，不是公告 |
| `Sunset` 响应头 | [RFC 8594](https://www.rfc-editor.org/rfc/rfc8594.html)，值为 HTTP-date | 与 `Deprecation` **日期格式不同**，混写会静默失效 |
| `Link` 关系类型 | [RFC 8288](https://www.rfc-editor.org/rfc/rfc8288.html)：`rel="deprecation"` / `rel="successor-version"` | 「看哪份文档、新接口在哪」两个问题各有一个头 |
| Schema Registry 兼容模式 | `BACKWARD`（默认）/ `FORWARD` / `FULL` / `NONE`，每种都有 `_TRANSITIVE` 变体 | 兼容性是**方向性**的，先确定「谁先升级」 |
| Protobuf 字段编号 | 编号一经发布不得复用，删除字段要写 `reserved` | 复用编号是**静默数据错乱**，比报错更糟 |
| Google AIP-180 | 明确定义「向后兼容」与资源名、字段、枚举的变更规则 | 大厂公开的兼容性清单，可直接当评审表 |
| 语义化版本 2.0.0 | 主版本 = 破坏性变更 | 契约文件的版本号可用于**机器比对**，但不等同于接口版本 |

::: warning 一个前置结论，能省掉三个月返工
**如果你的接口还没有任何外部调用方，不要做版本管理。** 版本机制的成本是「永久维护 N 套语义」，它只在有**你控制不了的消费者**时才划算。内部单体应用里发 `v2` 通常只是把重构成本转嫁给了自己。
:::

## 与本专题的分工（接口契约 vs 法律合同）

- **这里的 `Contract` 指服务之间的接口契约**：字段增删、弃用窗口、消费者清点、兼容性闸门。
- **法律合同的「版本」要求完全不同**：它不是为了「让旧客户端还能跑」，而是为了证明「客户签的是哪一版字节」。接口契约允许并行支持两个版本多年；法律合同一旦签署，那一版就永久冻结，改一个字节即失效。
- 相同点只有一个：**都要有版本号与快照**。但接口契约的版本可以「灰度并行」，合同的版本只能「作废 + 重签」。
- 如果两套东西共用一个「版本号生成器」，会出问题：接口版本号通常是 `v2`、`2026-10-01` 这类粗粒度标识，而合同需要「每次渲染一版」的细粒度编号。

::: danger 这一页特有的一个坑
**把 `Contract` 的重命名当成小事**。接口契约里改一个字段名，有弃用期兜底；法律合同里改一处措辞就是新版本，必须重新走签署。二者共用同一个「模板/契约」表时，一次「顺手优化措辞」会让已签合同的正文与数据库里的模板对不上。正确做法：签署侧只引用**冻结的版本快照**，不引用「当前模板」。见电子签署 · 合同模型（页面待补）。
:::

## 与「开放平台 · 版本与弃用」的分工（第 222 天补充）
| 这一页讲的 | 开放平台专题讲的 |
| --- | --- |
| 内部服务之间怎么加字段、怎么容忍未知字段 | 对外**已经发出去**的版本怎么弃用 |
| 契约是**双方同时升级**的（同一个发布窗口） | 契约是**对方不升级**也要能跑（可能几年） |
| 兼容性靠 CI 里的 breaking-change 检测 | 兼容性靠**公告期 + Sunset 头 + 410** |
| 可以「灰度一个消费者」 | 不能灰度，只能按客户固定版本 |

**这一页特有的一个坑**：把内部的「加字段不算破坏性变更」直接搬到对外接口。对内确实如此（消费者跟着发布）；对外不成立——客户的 `switch` 遇到未知枚举值直接抛异常。所以对外新增枚举值之前，**必须在文档里明确写「客户端必须容忍未知值」**，否则它属于破坏性变更。三类变更的判定表见[版本与弃用](../OpenPlatform/VersionLifecycle/index.md)。

## 与电子签署专题的分工（第 217 天补）

两册都会出现「版本」，但**版本作用的对象**完全不同。先看这张表再决定读哪册：

| 问题 | 该读哪册 | 关键差异 |
| --- | --- | --- |
| 接口 v1 与 v2 怎么共存、什么时候下线 | 本页 | 版本是**路由上的选择**，调用方可以选 |
| 同一份合同改了金额，旧签名还算不算 | [电子签署与合同存证](../ESignature/index.md) | 版本是**字节上的快照**，签名不可迁移 |
| 弃用公告怎么写、Sunset 头怎么给 | 本页 | 变更影响的是**调用方代码** |
| 已发出的合同怎么作废、怎么重签 | [会签流程](../ESignature/SigningFlow/index.md) | 变更影响的是**已签的字节** |

一句话判据：**API 版本可以并存，合同快照不能并存**。同一份合同不允许两个「当前版本」同时可签——那会让两个人各签一份不同的文件，而系统认为都有效。

::: danger 把「快照」当成「版本号」的后果
把合同快照做成 `contract.version = 2` 这种自增字段，是最常见的一种错法：旧快照的字节没有被保留，只剩一个数字。当第一位签署人事后主张「我签的时候金额是 12 万」，你手里只有当前这版 15 万的字节和一个 `version=2`——**数字不能证明任何事**。正确做法是每版快照独立存字节与 `sha256`，并用 `parent_sha` 串起来（见[合同模型](../ESignature/ContractModel/index.md)）。
:::

## 与「指标平台与语义层」专题的分工（第 242 天补充）

两个「版本」容易混：**接口版本管「调用方怎么调」，口径版本管「这个数怎么算」**。两者独立演进，组合起来才有风险——`/v2` 的接口完全可能调着 v1 的口径。

| 维度 | 本页（接口契约） | 指标平台口径版本 |
| --- | --- | --- |
| 标识 | URL 版本 `/v1` `/v2`、Header | `metric_version.version` + `effective_from` |
| 变更影响 | 调用方代码 | 历史数字是否需要重述 |
| 弃用方式 | 公告期 + `410 Gone` | `effective_to` 封口，历史仍可查 |
| 兼容策略 | 新旧并存、字段只增不删 | 新旧口径并存、旧口径可复算 |

**一页一坑**：接口升到 `/v2` 时顺手把口径也改了，两组版本号就对不上——排查「为什么 v2 接口的数和 v1 报表差 4%」要翻三份文档。正确做法是维护一张「接口版本 × 口径版本」矩阵，任一侧变更都要在矩阵里登记。见[版本、生效期与回溯](../MetricPlatform/Version/index.md)。

## 与「承保与保单管理」专题的分工（第 247 天补充）

条款版本与接口契约版本长得像，处理方式完全不同。这一页讲接口，那一册讲条款：

| 问题 | 读哪一册 | 本页不重复讲 |
| --- | --- | --- |
| 保险条款的版本、生效期、停售 | [险种、条款与责任](../UnderwritingPolicy/ProductModel/index.md) | 条款是**数据**，不是 API 版本 |
| 为什么条款版本不建独立文档目录 | [承保与保单管理](../UnderwritingPolicy/index.md) | 版本目录只服务「同一份代码两套写法」 |
| 接口的兼容性、弃用、灰度 | 本页 | 条款没有「向后兼容」这回事 |

::: danger 本页特有的一个坑：「版本」在两个领域里的兼容性方向相反
接口版本讲**向后兼容**——`v1` 的生命周期要尽量长，老客户端还能用；条款版本讲**不可回溯**——2026A 上线不意味着 2024A 失效，但它也**不能**给 2024A 的保单「兼容」新条款。把接口那套「新版本兼容旧调用」的思路搬到条款上，就会写出「按现行条款赔付历史保单」这种错误实现，而它在系统里表现为「一切正常」。
:::

## 与「配置、定价与报价工程」专题的分工（第 251 天补充）

| 关注点 | 本册（合同版本演进） | CPQ 专题 |
| --- | --- | --- |
| 版本对象 | 条款文本的版本与兼容性 | 报价的 `rev`（改配产生的版本） |
| 变更语义 | 新旧条款能否共存、如何废弃 | 合同变更新增而不修改（补充协议） |
| 冻结什么 | 版本号 + 兼容性声明 | 版本号 + **条款全文哈希** |
| 谁读 | 法务、合规 | 销售、财务、审计 |

本册讲「条款怎么演进」，CPQ 侧只讲「合同签下的那一刻冻结了哪一版」。

::: warning 引用「最新版」是最贵的省事
合同若只存条款模板 ID，模板一改，**所有历史合同都会「条款变了」**。CPQ 侧的口径是「版本号 + 全文 SHA-256」：正文存版本，哈希用来证明「当时这份文本没被改过」。补这一列时要注意给历史行回填真实哈希，`DEFAULT ''` 会让所有历史合同的哈希相同——看起来有值，实际不可校验。
:::

## 与「招投标与电子采购交易工程」专题的分工（第 252 天补充）

| 关注点 | 本册（合同版本演进） | 招投标专题 |
| --- | --- | --- |
| 版本来源 | 条款模板迭代、补充协议 | 招标文件版本与澄清文件 |
| 冻结对象 | 条款号 + 兼容性声明 | 招标文件版本 + 投标文件哈希 |
| 变更语义 | 补充协议新增、旧条款保留 | 「实质性条款不得谈判」 |
| 谁读 | 法务、合规 | 评标委员会、审计 |

本册讲合同**签下之后**怎么演进；招标侧要回答的是**签下之前**谈了什么。两册的交点是「签约那一刻冻结了哪些文本」。

::: warning 合同要能证明「签的就是投的」
若合同只存正文与模板 ID，事后无法回答「中标人投的报价与承诺，有没有在签约时被改掉」——而这正是条例禁止的实质性条款谈判。可校验的做法是三条一起落：`contract.award_id`（哪次中标）、`contract.tender_doc_hash`（哪版招标文件）、`contract.bid_doc_hash`（哪份投标文件）。少第三条，改一个付款条件也只是「合同变更」，看不出来。补这三列时注意给历史行**回填真实哈希**，`DEFAULT ''` 会让所有历史合同的哈希相同——看起来有值，实际不可校验。
:::

## 与「招聘与人才获取工程」专题的分工（第 253 天补充）

招聘册的对外接口不多，但**每一份 Offer 都是一份契约**——只不过它是法律意义上的要约，不是 API 契约。两册共用「契约」这个词，判的却是完全不同的东西：本册判「旧调用方会不会被打断」，招聘册判「这份要约能不能撤回、失效、改条款」。

| 问题 | 本册（契约演进） | 招聘与人才获取册 |
| --- | --- | --- |
| 改了什么 | **判**：四类契约面（REST / 消息 / 表结构 / SDK） | **判**：Offer 条款（薪资、试用期、报到日） |
| 能不能不兼容地改 | **判**：破坏性判据 + 弃用期 | **判**：九状态里哪几步不可逆（四次） |
| 旧版本怎么下线 | **判**：弃用公告、双写、灰度、下线 | 不判（Offer 过期是业务失效，不是版本下线） |
| 谁受影响 | **判**：调用方清单 | **判**：候选人、用人经理、审批人三方 |
| 变更要不要留证 | **判**：变更日志与兼容矩阵 | **判**：`offer_change` 留痕与四次不可逆的时点 |

一个容易被忽略的重叠：**招聘系统的接口一旦被外部 ATS 或猎头平台对接，「Offer 状态」就成了对外契约面**。此时给它加一个状态值就是破坏性变更——外部系统按九状态做的状态机映射会因为多了一个值而走到 default 分支。本册的「加枚举值算不算破坏性」判据在这里直接适用，且结论是**算**（消费方通常用穷举 switch）。

::: danger 一个只在本页成立的坑
**把 Offer 的条款变更当成「接口字段更新」处理。** 接口字段更新可以兼容地加一个可选字段、也可以双写一段时间；Offer 条款不行——它一旦发出，任何改动都是**对已生效要约的修改**，必须走「撤回 → 重新发出」并保留两次的完整快照，而不是原地 `update` 覆盖。

本册的兼容策略在业务契约上是失效的：你不能「双写两份 Offer 让候选人挑」，也不能「旧版条款保留 90 天再下线」。更危险的是原地覆盖会让 `offer_change` 留痕失去对照基准——争议时无法证明「候选人接受的是哪一版」。27 份薪资带宽越线的记录里，破下限的那部分直接触到《劳动合同法》第二十条（试用期工资不得低于本单位同岗最低档或约定工资的 80%），此时唯一能自证的就是两个版本的快照。

一句话：**演进可以向后兼容，要约只能向前重发。**
:::

延伸阅读：[Offer：九状态与四次不可逆](../Recruiting/Offer/index.md)、[需求变更留痕 `req_change`](../Recruiting/Requisition/index.md)。

## 与「GraphQL 服务端工程」的分工（第 257 天补充）

本页讲的是 REST 的契约演进：`/v1` → `/v2`、字段兼容窗口、废弃公告期。GraphQL 走的是另一条路——**不开版本，用 schema 自己演进**。两者的判据不同，不要互相套。

| 这件事 | 本页（REST） | [GraphQL 服务端](../GraphQL/index.md) |
| --- | --- | --- |
| 破坏性变更的隔离手段 | 新路径前缀 `/v2` | `@deprecated` + 新字段名，旧字段留着 |
| 「谁还在用旧字段」的判据 | 网关访问日志按路径统计 | 内省 + 字段级调用计数（[总览](../GraphQL/Overview/index.md) 的版本表） |
| 契约的机器可读形式 | OpenAPI 文档 | SDL 本身，且**可被客户端拉取** |
| 兼容性检查 | 两个 spec 文件做 diff | 两个 SDL 做 diff（`graphql-inspector` 一类工具） |

::: danger 注意
**把 REST 的「开 v2」搬到 GraphQL 上，会得到一个最坏的结果。** 两个端点意味着两份 schema、两套 resolver、两条监控线，而客户端的查询是按字段走的——它不会因为你换了端点就不再用旧字段。GraphQL 里唯一需要「版本目录」的情形是**实现代际**（如 [graphql-js 16 线 / 17 线](../GraphQL/Graphql16/index.md)），不是契约代际。
:::

## 与税务与发票工程的分工

合同版本与税率版本是两套并存的版本线：

| 这件事 | 本页负责 | 税务专题负责 |
| --- | --- | --- |
| 版本对象 | 条款、价格、SLA | 税目、税率、征收方式 |
| 兼容策略 | 新旧版本并存、灰度切换 | 按 `issue_date` 取当时有效税率，不重算历史票 |
| 变更影响 | 履约与结算 | 含税价不变时，税额变化直接吃掉收入 |

::: danger 注意
合同只写「含税价 113 万元」而不写税率，是把税率风险留给了自己：税率从 13% 降到 9% 时，客户仍按 113 万付款，你的不含税收入从 100 万涨到 103.67 万（好事）；反过来从 9% 升到 13%，不含税收入从 103.67 万掉到 100 万，而合同没有任何条款可以调价。
:::
