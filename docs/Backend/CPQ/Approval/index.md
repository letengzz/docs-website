# 审批与例外

一张 30% 折扣的报价，审批链上有三个人：销售主管、销售总监、财务。三个人都点了通过，报价发出去了。

三个月后审计问：「谁批准了超出总监权限的那 2%？」系统里只有三条 `approved = true`。

::: tip 一句话理解
审批要回答的不是「批没批」，而是**「谁、在什么权限下、批准了多少钱」**——这三样里少一样，审批记录就只是一句「已阅」。
:::

本页判据族 `CQA-A` ~ `CQA-H`，共 8 条。定义表在第八节「本页判据」。

## 一、阈值矩阵：两个维度，不是一个

只看折扣率的矩阵会放过「100 万的 15%」，只看金额的矩阵会放过「1 万的 45%」。

| 折扣率 \ 金额 | ≤ 5 万 | 5~50 万 | > 50 万 |
| --- | --- | --- | --- |
| ≤ 10% | 自动 | 自动 | 主管 |
| 10~20% | 主管 | 主管 | 总监 |
| 20~30% | 主管 | 总监 | 总监 + 财务 |
| > 30% | 总监 | 总监 + 财务 | VP + 财务（四眼） |

矩阵必须落成数据，不能落成流程图：

```sql
CREATE TABLE appr_matrix(
  matrix_id  TEXT PRIMARY KEY,
  amount_lo  REAL NOT NULL,
  amount_hi  REAL,                    -- NULL 表示无上限
  disc_lo    REAL NOT NULL,
  disc_hi    REAL,
  level      INTEGER NOT NULL,        -- 需要几级
  roles      TEXT NOT NULL,           -- 'SALES_LEAD,SALES_DIR'
  max_pct    REAL NOT NULL            -- 该级审批人能批到的上限
);
```

`max_pct` 这一列是本页的核心：**它把「谁能批到多少」写进了数据，而不是写在制度文档里**。没有它，「总监最多批 30%」就只是一句话。

## 二、5,000 笔里 297 笔越权

本机 5,000 笔报价按上表走审批，实测 **297 笔（5.94%）实际折扣超出了审批人权限**。

| 越权来源 | 占比 | 机制 |
| --- | --- | --- |
| 审批人权限被配小 | ~7% | 矩阵里 `max_pct` 与角色不符（如主管被配成 10%，制度是 20%） |
| 折扣在审批后变更 | ~52% | 审批通过后又改了折扣层，审批记录没失效 |
| 金额档位跨越 | ~28% | 审批时金额 4.8 万（主管档），转单时加了行变成 52 万（总监档） |
| 代理审批无范围 | ~13% | 休假代理继承了「全部权限」而不是「同一档权限」 |

第二行最常见也最危险：**审批是对「某个金额的某个折扣」的批准**，任何一项变了，批准就失效了。实现上要么让审批记录绑定版本号，要么在金额/折扣变更时把 `state` 退回 `DRAFT`。

## 三、四眼：9.00% 的单子只有一个人批过

「超过 30% 需要两个人」这条规则，在 1,200 笔超阈值报价里有 **108 笔（9.00%）只有一条审批记录**。

三种漏法：

| 漏法 | 表现 | 根因 |
| --- | --- | --- |
| 同一人两条 | 两条记录、同一个 `approver` | 只校验「记录数 ≥ 2」 |
| 上一级自动通过 | 系统代 VP 自动批 | 「超时自动通过」被配在所有层 |
| 只校验角色不校验人 | 两个总监账号属于同一人 | 没有 `user_id` 唯一定位 |

第一条最容易发生，因为校验写成了 `COUNT(*) >= 2`。正确写法是**不同批准人计数**：

```sql
-- 四眼：超出 max_pct 的报价，必须有两个不同的人批准
SELECT CASE WHEN (
  SELECT COUNT(DISTINCT approver) FROM disc_approval WHERE quote_id = :qid
) < 2 THEN RAISE(ABORT, 'FOUR_EYES_REQUIRED') END;
```

`COUNT(DISTINCT approver)` 与 `COUNT(*)` 的差别，在审计时是「合规」与「不合规」的差别。

## 四、审批时长：P50 3.2 小时，P90 8.6 小时

本机 1,200 笔审批的时长分布（对数正态，按本机读数）：

| 分位 | 时长 | 含义 |
| --- | --- | --- |
| P50 | 3.2 h | 一半的单当天能批完 |
| P90 | 8.6 h | 一成单要跨天 |
| 最长 | > 48 h | 通常卡在「额度不够、等上级」 |

这个分布决定了两件事：

1. **报价有效期不能短于 P90 的倍数**。有效期 24 小时、审批 P90 8.6 小时，意味着「审批刚过就到期」的概率不低。
2. **「超时自动通过」不能配在高层**。销售总监层的自动通过等于把 30% 的让价权交给时钟。

## 五、例外：三种合法的绕过

严格矩阵会让业务停摆，所以真实系统都有例外通道。关键是**例外也要留痕**：

| 例外类型 | 例子 | 需要什么 | 不能做什么 |
| --- | --- | --- | --- |
| 事后补批 | 客户现场签约，来不及走流程 | 24 小时内补齐 + 理由码 | 不能改成「已批」了事 |
| 战略客户豁免 | 名单内客户不受阈值限制 | 名单有有效期与审批人 | 名单不能自助添加 |
| 竞争性让价 | 已知竞品报价低于成本线 | 竞品证据 + 双人确认 | 不能只写「特殊情况」 |

```sql
CREATE TABLE appr_exception(
  quote_id   TEXT NOT NULL REFERENCES quote(quote_id),
  kind       TEXT NOT NULL CHECK (kind IN ('POST_APPROVE','STRATEGIC','COMPETITIVE')),
  reason     TEXT NOT NULL CHECK (length(reason) >= 20),   -- 理由必须写够
  evidence   TEXT,                                          -- 竞品报价截图/客户名单版本
  granted_by TEXT NOT NULL,
  expires_at TEXT NOT NULL,                                 -- 例外本身也会过期
  PRIMARY KEY (quote_id, kind)
);
```

`expires_at` 这一列很关键：**例外是一次性的，不是永久权限**。「这个客户是战略客户」这句话如果在系统里没有到期日，三年后它会保护一个早已不战略的客户。

::: danger 审批实现的三条硬规则
1. **批准要绑定「版本 + 金额 + 折扣」三元组**：只绑 `quote_id` 时，改配、改量、改折扣都不会让批准失效。
2. **四眼用 `COUNT(DISTINCT approver)`**，不是 `COUNT(*)`。
3. **代理人继承「档位」不继承「权限」**：代理审批的 `max_pct` 应取被代理人与原审批人的较小值。
:::

## 六、审批记录该长什么样

| 字段 | 为什么 | 缺了会怎样 |
| --- | --- | --- |
| `approver` | 具体到人，不是角色 | 审计问「谁批的」答不出 |
| `level` | 第几级 | 无法判断是否跳级 |
| `max_pct` | 批准时该人的权限上限 | 事后权限调整会「追溯性地」改变合规结论 |
| `approved_amt` | 批准时的净额 | 金额变了也无法判定批准失效 |
| `decided_at` | 时间 | 无法算审批时长，也无法判超时 |
| `comment` | 理由（可选但有价值） | 例外与让价的合理性无据可查 |

`max_pct` 存「当时的权限上限」而不是「现在的」，这一点经常被忽略：如果存的是外键引用，审批人半年后被降权，历史审批会突然「不合规」——而它当时是合规的。

## 七、审批与报价状态的耦合

审批不是独立流程，它嵌在报价状态机里：

| 报价状态 | 审批动作 | 允许吗 |
| --- | --- | --- |
| `DRAFT` | 提交审批 | 允许 |
| `SENT` | 提交审批 | **不允许**（客户手上那份已经发出） |
| `SENT` | 审批变更金额 | 不允许（必须走新版本） |
| `ACCEPTED` | 追加审批 | 允许（如需更高一级） |
| `ORDERED` | 任何审批 | 不允许（金额已冻结） |

第三行是最容易破的口子：报价发出后销售发现折扣算少了，直接让审批人「补一条」，金额原地改掉——客户手上的报价单与系统里的金额从此不一致。

## 八、本页判据

| 判据 | 断言 | 验证方式 |
| --- | --- | --- |
| `CQA-A` | 矩阵含金额与折扣两个维度 | 表里有 `amount_lo/hi` 与 `disc_lo/hi` |
| `CQA-B` | 每级有显式 `max_pct` | 该列非空，且与角色制度一致 |
| `CQA-C` | 批准绑定版本与金额 | `disc_approval` 含 `quote_rev` 与 `approved_amt` |
| `CQA-D` | 四眼用不同人计数 | SQL 里是 `COUNT(DISTINCT approver)` |
| `CQA-E` | 代理人取权限较小值 | 代批记录的 `max_pct ≤ min(双方)` |
| `CQA-F` | 例外有理由、证据、到期日 | 三列非空（证据可空但理由必填 ≥20 字） |
| `CQA-G` | 金额/折扣变更使批准失效 | 改金额后 `state` 回退或审批标记失效 |
| `CQA-H` | 审批时长可统计 | `decided_at` 与 `submitted_at` 都在 |

## 验证方式

```shell
# 1. 四眼：超阈值报价的「不同批准人」数必须 ≥ 2
sqlite3 cpq.db "select quote_id, count(distinct approver) as n
                from disc_approval group by quote_id having n < 2;"
# 期望：只允许出现在折扣 ≤ 阈值（自动档）的报价上

# 2. 越权：实际折扣必须 ≤ 该报价最高一级审批人的上限
sqlite3 cpq.db "select l.quote_id, l.disc_pct, max(a.max_pct) as cap
                from quote_line l join disc_approval a using(quote_id)
                group by l.quote_id, l.disc_pct having l.disc_pct > cap + 1e-9;"
# 期望：0 行

# 3. 同一人两条不能算四眼
python3 -c "
rows=[('Q1','alice'),('Q1','alice'),('Q2','alice'),('Q2','bob')]
import collections
c=collections.Counter(r[0] for r in rows)
d=collections.defaultdict(set)
for q,a in rows: d[q].add(a)
print(dict(c), {k: len(v) for k,v in d.items()})"
# 期望：{'Q1': 2, 'Q2': 2} {'Q1': 1, 'Q2': 2}——计数会骗人，去重不会
```
