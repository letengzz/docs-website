# 申报与四单一致

报关单不是一份孤立文件：它要同时被商业发票、装箱单、提单三份单证支撑。任何一栏只被一份单证支撑，那一栏就是口径分叉点——出事时，你无法用第二份材料证明自己是对的。

本页讲申报的四个要素、四单一致的核对方式、计量单位这个「不改一个字却差 1,000 倍」的坑，以及回执状态与修撤单的处理。

::: tip 一句话理解
申报的本质是**把三份商业单证压缩成一份行政单证**。压缩必然丢信息，所以每一栏都必须能指回原始单证；指不回去的栏，就是将来要举证时找不到证据的栏。
:::

## 一、四单一致：每一栏要有两份支撑

![四单一致：报关单、发票、装箱单、提单](../assets/cu-declare.svg)

| 栏位 | 报关单 | 商业发票 | 装箱单 | 提单 | 只被一份支撑的风险 |
| --- | --- | --- | --- | --- | --- |
| 品名与规格 | 有 | 有 | 有 | 有 | 低（四份互证） |
| 数量与单位 | 有 | 有 | 有 | 有 | 低，但**单位**必须逐字一致 |
| 成交金额 | 有 | 有 | 无 | 无 | 中：改一处无人发现 |
| 币制与汇率 | 有 | 有 | 无 | 无 | 中：币制写错，金额差一个数量级 |
| 毛重 / 净重 | 有 | 无 | 有 | 有 | 中：三处都能算，三个结果 |
| 原产国 | 有 | 有 | 无 | 无 | 高：直接决定能否享协定税率 |

本机四单核对读数：

| 类型 | 票数 | 占比 | 后果 |
| --- | --- | --- | --- |
| 发票金额与报关单不一致 | 378 | **3.15%** | 付款卡住，或按错的金额缴税 |
| 提单数量与报关单不一致 | 278 | **2.32%** | 触发查验，或短装被当溢装 |
| 计量单位错（千件 ↔ 件） | 177 | **1.47%** | 完税价格差 1,000 倍 |

第三类最危险：单票平均完税价格 **172,225.46 元**，单位错一位就变成 **1.72 亿元**。它不改一个字符，只改一个单位，任何「金额校验」都通过——因为金额本身算得没错，是**数量**错了。

## 二、申报期限与四个日期

| 日期 | 定义 | 用在哪里 | 写错的后果 |
| --- | --- | --- | --- |
| 运输工具申报进境日 | 船到港、舱单申报 | 14 天申报期的起点 | 起算错，滞报金算错 |
| 申报日（海关接受申报日） | 电子数据被接受 | 汇率所属月、税率适用日 | 跨月时税率与汇率都可能变 |
| 缴款期限届满日 | 完成申报起 15 日内 | 滞纳金起点 | 逾期天数算错 |
| 放行日 / 结关日 | 允许提离 / 舱单核销 | 「清没清」的判定 | 把放行当结关（本机 95.53%） |

::: warning 「申报日」不等于「递交日」
企业把数据发出去是「递交」，海关接受才是「申报」。中间可能隔几小时，也可能隔几天（退单重报）。滞报金的截止日是**海关接受申报之日**，不是企业发送之日。这两个时间在系统里的字段必须分开，否则争议时无法自证。
:::

## 三、回执：报关单不是「提交成功」就结束了

```text
发送 ──► 入库回执 ──► 审结回执 ──► 税单生成 ──► 放行回执 ──► 结关回执
  │          │             │
  └─ 退单 ◄──┘             └─ 挂起（补证/查验/估价）
```

| 回执 | 含义 | 系统里该记什么 | 常见错误 |
| --- | --- | --- | --- |
| 入库 | 报文进了海关系统 | 回执号 + 时间 | 只记「成功」，不记回执号 |
| 审结 | 单证审核通过 | 审结时间 | 把「入库」当「审结」 |
| 税单 | 税款确定 | 税单号 + 三税金额 + 缴款期限 | 税单金额与本地重算值不校验 |
| 放行 | 允许提离 | 放行时间 | 当成终态 |
| 结关 | 舱单核销完成 | 结关时间 | 从不采集，永远不知道是否结关 |

最后一行是本册反复强调的那件事：**「结关」这个回执在很多系统里根本没被采集**，于是「已清关」的统计永远偏高。

## 四、修撤单：唯一合法的回退路径

| 动作 | 触发场景 | 必须留痕 | 对下游的影响 |
| --- | --- | --- | --- |
| 修改 | 金额、数量、税号填错 | 改单前后值、原因、操作人、时间 | 税单需重出，已缴的退补 |
| 撤销重报 | 单证主体错误 | 撤销原因 + 新单号关联 | 滞报期从撤销之日重新起算 |
| 后续核查改单 | 放行后发现归类/价格问题 | 核查文号 | 补税 + 滞纳金 |

```sql
CREATE TABLE decl_amend (
  amend_id   INTEGER PRIMARY KEY,
  decl_id    TEXT NOT NULL,
  kind       TEXT NOT NULL CHECK (kind IN ('MODIFY','CANCEL','POST_AUDIT')),
  field_name TEXT NOT NULL,
  old_value  TEXT,
  new_value  TEXT,
  reason     TEXT NOT NULL,
  operator   TEXT NOT NULL,
  amended_at TEXT NOT NULL
);
-- 放行之后仍允许改单，但必须存在 POST_AUDIT 记录
SELECT d.decl_id FROM declaration d
WHERE d.state = 'RELEASED'
  AND EXISTS (SELECT 1 FROM decl_amend a WHERE a.decl_id=d.decl_id)
  AND NOT EXISTS (SELECT 1 FROM decl_amend a WHERE a.decl_id=d.decl_id AND a.kind='POST_AUDIT');
```

## 五、四单一致的自动化核对

四单一致不能靠人眼看，要落成可执行的比对：

```sql
-- 1) 金额：报关单项合计 vs 发票金额（整数分，容差 0）
SELECT d.decl_id, d.invoice_fen, SUM(i.amount_fen) AS item_fen
FROM declaration d JOIN decl_item i ON i.decl_id = d.decl_id
GROUP BY d.decl_id
HAVING d.invoice_fen <> SUM(i.amount_fen);

-- 2) 数量：报关单数量 vs 提单数量（同一单位才能比）
SELECT i.decl_id, i.qty, b.qty AS bl_qty, i.unit, b.unit
FROM decl_item i JOIN bl_item b
  ON b.bl_no = (SELECT bl_no FROM declaration WHERE decl_id = i.decl_id)
 AND b.line_no = i.line_no
WHERE i.unit = b.unit AND i.qty <> b.qty;

-- 3) 单位：同品名在不同单证上的单位必须逐字一致
SELECT i.decl_id FROM decl_item i JOIN bl_item b ON b.line_no = i.line_no
WHERE i.unit <> b.unit;
```

第 3 条是本页最该上线的一条：**单位不一致比数量不一致更常见，也更致命**。数量差 5% 会被发现，单位差 1,000 倍会被当成「这票货值这么多」。

## 六、判据：本页的八条

本页判据族 `CUD-A` ~ `CUD-H`，共 8 条。它们都在回答「四份单据能不能对上同一件事」。

| 编号 | 判据 | 不满足时改哪里 |
| --- | --- | --- |
| `CUD-A` | 报关单与商品项分表，表头存金额合计、商品项存明细 | `declaration` / `decl_item` 两表 |
| `CUD-B` | 表头金额 = 商品项金额之和（容差 0） | 校验 SQL 返回 0 行 |
| `CUD-C` | 数量与单位同时存，单位不省略 | `qty` + `unit` 两列非空 |
| `CUD-D` | 四单的同一行用 `line_no` 对齐，不靠品名匹配 | `decl_item.line_no` 与 `bl_item.line_no` 可比 |
| `CUD-E` | 申报日与递交日分列 | `sent_at` 与 `accepted_at` 两列 |
| `CUD-F` | 回执状态逐条落库（含回执号与时间） | `decl_receipt` 表 |
| `CUD-G` | 修撤单有前后值与原因，且不可物理删除 | `decl_amend` 表 + 只插不改 |
| `CUD-H` | 放行后改单必须有 `POST_AUDIT` 记录 | 校验 SQL 返回 0 行 |

## 七、验证方式

```shell
# 1. 单位错一位的放大倍数（本机单票平均完税价格 172,225.46 元）
python3 -c "
p=172225.46
print(round(p,2), round(p*1000,2))"
# 期望输出：172225.46 172225460.0

# 2. 三类不一致的占比（本机 3.15% / 2.32% / 1.47%）
python3 -c "
n=12000
for k,c in (('发票',378),('提单',278),('单位',177)):
    print(k, round(c/n*100,2))"
# 期望输出：发票 3.15 / 提单 2.32 / 单位 1.47

# 3. 数量与单位必须同时比对：只比数量会漏掉「1,000 件 vs 1 千件」
sqlite3 :memory: "CREATE TABLE d(qty INT, unit TEXT); INSERT INTO d VALUES(1000,'件'),(1,'千件');
SELECT COUNT(*) FROM d WHERE qty<>1000; SELECT COUNT(*) FROM d WHERE unit='千件';"
# 期望输出：0 然后 1（数量比不出来，单位能）
```

第 3 步是这一页的要点：**如果只按数量比对，第一条查询返回 0 行，看起来「完全一致」**。
