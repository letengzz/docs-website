# 分布式缓存深入

<p style="text-align:center;"><img src="./assets/dc-logo.png" style="zoom:75%;" /></p>

分布式缓存解决的是「缓存不再只有一个进程、一份数据」之后出现的全部新问题：**多个实例各自的本地缓存怎么失效、缓存节点之间怎么路由、缓存与数据库之间怎么收敛、缓存整体挂掉时业务还能不能活**。本专题讲的是这四类问题的判据与做法，不讲 Redis 的命令（那是 [Redis 专题](../../DB/NoRelational/Redis/index.md) 的职责）。

::: tip 一句话理解
单机缓存的问题是「怎么少查一次库」，分布式缓存的问题是「**同一份数据存在好几处，你怎么知道每一处都是对的**」。前者的答案是一行代码，后者的答案是一套失效链路加一组观测指标。
:::

## 学习路径

1. **先读 [总览](./Overview/index.md)**：先判断你的项目**到底需不需要**把缓存搬出进程。多数项目不需要，这比学会多级缓存更重要。
2. **要做容量规划或选型的读 [拓扑与路由](./Topology/index.md)**：路由表放在哪，决定了你以后扩容的代价。
3. **已经有多实例的读 [多级缓存深入](./MultiLevel/index.md)**：本地那一层是全部难点的来源。
4. **动手写代码前必读 [一致性方案深入](./Consistency/index.md)**：脏读窗口不长，但一旦被写进缓存就长期存在。
5. **流量大的补充 [热点与倾斜治理](./HotKey/index.md)**，做稳定性的读 [缓存层韧性](./Availability/index.md)。
6. **上线前对照 [可观测与容量治理](./Observability/index.md)** 把指标补上，再走一遍 [实战](./Practice/index.md) 的 C1~C12 断言。

## 与在线协作任务看板的分工

本页讲**缓存与广播的通用机制**：多级缓存、发布订阅、以及「缓存与数据库谁先写」的取舍。

[在线协作任务看板 · 实时网关](../../../project/Complete/TeamBoard/RealtimeGateway/index.md) 用的是**同一套 Redis 发布订阅，但用途完全不同**：它**不做缓存**，只做**跨实例的消息扇出**——多实例部署时，一条改动必须能到达「持有这条 WebSocket 连接的那个实例」，而那个实例是谁只有 Redis 知道。于是两支的分工是：

| 维度 | 本页（缓存视角） | 任务看板（扇出视角） |
| --- | --- | --- |
| 关心的失败 | 击穿 / 穿透 / 雪崩、脏读、一致性窗口 | **丢消息**与**消息早于提交**（后者会产生「别人的界面比广播更旧、刷新又好了」这种最难查的缺陷） |
| 数据能重建吗 | 能——缓存丢了回源即可 | **不能**——推出去的这一帧没有任何持久化，丢了就是这一端的缺口，只能靠 `seq` 检测 + 追平补上 |
| 与事务的关系 | 常见做法是「先写库再删缓存」 | 写死**提交之后再广播**；发布订阅在事务里发等于把未提交状态暴露出去 |

::: tip 一句话分辨该找哪一页
问「**这份数据丢了能不能回源**」：能 → 是缓存问题，看本页；不能 → 是消息问题，看 [实时网关](../../../project/Complete/TeamBoard/RealtimeGateway/index.md) 的 `seq` 与追平一节。
:::

## 与「实时协作与冲突解决」专题的分工（第 151 天补充）

本页管的是「缓存与数据库谁先写、失效怎么广播」，[实时协作与冲突解决](../../Backend/RealtimeCollaboration/index.md) 管的是「多实例之间怎么把同一份增量送到每个客户端」。两者都用 Redis 发布订阅，但承载的东西不同：

| 维度 | 本页 | 实时协作专题 |
| --- | --- | --- |
| 广播内容 | 「这个 key 失效了」 | 「这个文档的第 N 条更新」 |
| 丢失后果 | 读到旧值，直到下一次过期 | 客户端内容落后，直到主动重拉 |
| 是否持久 | 不持久（丢了靠过期兜底） | 更新必须先落库，广播只是通知 |
| 判据 | 缓存与库的差异有上界 | `seq` 连续、断线可追平 |

一句话结论：**缓存失效广播可以丢（有 TTL 兜底），协作更新广播不能丢（丢了就是内容缺失）**。所以后者的正确形态是「落库 + 广播通知去拉」，而不是「把内容塞进 pub/sub 就算完」。

::: warning 容易混用的一处
本页的「先删缓存再更新库 / 先更新库再删缓存」讨论的是**读写竞态**；协作链路里对应的问题叫「先广播还是先落库」，答案没有二选一：**必须落库成功后再广播**。
:::

## 与「租户边界」章节集的分工（第 155 天补充）

| 维度 | 本页 | 「租户边界」章节集（第 155 天） |
| --- | --- | --- |
| 回答的问题 | 缓存与数据库的一致性、失效策略、集群与热点 | 多租户下 key 的租户段、失效广播的租户携带、锁 key 的租户段 |
| 一致性 | 缓存与库谁先写、延迟双删 | 删除后由下次读回填，天然收敛到库；不用「发新值」的方式失效 |
| 锁 | 分布式锁的实现与租约 | 锁 key 必须带租户——不带时不是数据错，而是**跨租户互相阻塞**，表现为偶发超时 |
| 热点 | 热 key 拆分与本地缓存 | 本地缓存 key 必须是含租户的复合键，且 TTL 不超过 60 秒 |

一句话结论：**本页讲「缓存怎么和库保持一致」，章节集讲「缓存怎么不把两个租户的数据混成一份」**。

::: danger 这一页特有的坑
锁 key 少一段租户，后果不是「读到了别人的数据」，而是「A 的操作让 B 排队」——监控上只看到偶发超时，几乎不可能从指标反推到 key 命名。
:::


::: tip 与「分布式锁与选主」专题的分工（第 159 天补充）
本页的「缓存重建锁」是分布式锁的一个**特例**：抢不到锁的请求允许「直接回源算一次」，因为最坏结果只是多算一遍、多打一次库。通用锁（新增的 [分布式锁与选主](/docs/Backend/DistributedLock/Overview/index.md)）讨论的是「抢不到必须等」的那一类——因为那里的临界区有不可重复的外部副作用。

| 场景 | 抢不到锁的行为 | 看哪里 |
| --- | --- | --- |
| 缓存重建、热点 key 回源 | 直接回源（降级），不等待 | 本页 |
| 库存扣减、发券、定时任务 | 必须等待或快速失败，不允许并发 | [分布式锁与选主](/docs/Backend/DistributedLock/Overview/index.md) |
| 缓存删除失败后的补偿 | 重试 + 过期兜底 | 本页 |

一条常被忽略的联系：本页多级缓存里的「本地锁 + Redis 锁」双层写法，在 [租约与续期](/docs/Backend/DistributedLock/Lease/index.md) 的视角下仍然要回答「停顿超过 TTL 会怎样」——缓存场景能容忍（多算一次），业务写场景不能（会写错），这是两类锁唯一真正的分界线。
:::


## 与「状态管理与数据流」专题的分工

本页是**服务端缓存**：穿透、击穿、雪崩、多级一致、Redis 集群。浏览器内的同构问题（缓存多久算新鲜、写后谁失效、跨标签页怎么广播）归 [状态管理与数据流](/docs/Frontend/StateDataFlow/index.md) 的 [缓存失效](/docs/Frontend/StateDataFlow/CacheInvalidation/index.md)。

| 概念 | 服务端（本页） | 浏览器（专题） |
| --- | --- | --- |
| 穿透 | 空值缓存 / 布隆过滤器 | 一次性数据不该缓存（验证码、下载链接） |
| 击穿 | 互斥重建 | 同 key 并发重取合并 |
| 雪崩 | TTL 抖动 + 降级 | 大前缀失效导致的请求风暴 |

::: warning 「空值缓存」在两侧的语义不同
服务端缓存空值是为了挡穿透，通常 30~60 秒；浏览器端把「空结果」缓存下来，用户看到的是**一段时间的假空列表**（比如刚建完数据，列表还是空的）。前者是保护，后者是缺陷。前端要区分「确实是空」与「还没取到」，否则会把 `[]` 当成有效结果缓存。
:::

## 与高并发系统设计的分工（第 141 天补充）

本专题把缓存当作**读放大**的解法：同一份数据被读了 N 次，用缓存把它变成 1 次；以及多级缓存之间的新鲜度问题。

[高并发系统设计 · 过载行为与有损服务](../HighConcurrency/OverloadBehavior/index.md) 关心的是缓存在**过载时的角色**——它是第二道防线，但**它会先于数据库一起被打穿**：缓存命中率一掉，全部请求同时回源，而这恰好发生在系统最脆弱的时候（这就是缓存雪崩为什么是过载事故的放大器，而不是一个独立的缓存问题）。

| 问题 | 本专题（缓存） | 高并发系统设计（过载） |
| --- | --- | --- |
| 解决什么 | 同样的读重复了 N 次 | 不同的写来了 10 万次 |
| 过载时的表现 | 穿透 / 雪崩 / 热 key 打散单个分片 | 回源流量无上限 → 打穿数据库 → 上游线程池堆满 |
| 处置位置 | 键过期策略、逻辑过期、多级缓存、互斥重建 | 回源限流、热点识别与拆分、**回源请求也要有配额** |

::: danger 一条最贵的误判
「有缓存」不是「有容量」。缓存的容量写在**命中率**上，而命中率是**输入**而不是**保证**：只要访问模式一变（新数据冷启动、热 key、宕机后的空缓存），命中率会在几秒内掉到 0，此时系统真正的容量是**数据库的容量**。所以那边写死了一条：**回源路径必须有自己的限流，且它的配额要按数据库的水位线反推**，不能按缓存命中时的 QPS 给。
:::
