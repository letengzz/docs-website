# 总览：缓存的四条边界

这一页回答一个选型问题：**什么时候应该把缓存从进程里搬出去，什么时候搬出去反而更糟**。搬出去之后，一致性、路由、热点、韧性这四件事才会依次变成问题——它们是「分布式」这三个字的代价，不是缓存本身的代价。

::: tip 一句话理解
进程内缓存的问题只有一个：**别的进程改了数据，我不知道**。分布式缓存把这个问题交给了共享存储，代价是引入了网络、路由与容量三件事。选型的本质是选「你想面对哪一种问题」。
:::

## 缓存的四种位置

把缓存按「离谁近」分成四种位置，它们在**延迟、容量、一致性难度**三个维度上单调变化：

| 位置 | 典型形态 | 读延迟 | 容量 | 一致性难度 | 跨实例可见 |
| --- | --- | --- | --- | --- | --- |
| 客户端 | 浏览器 HTTP 缓存、App 本地库 | 最低 | 受用户设备限制 | 靠 TTL 与版本号，几乎不可控 | 否 |
| 进程内（L1） | Caffeine、Guava Cache、`Map` | 纳秒~微秒 | MB 级 | **最高**（要广播才能删） | 否 |
| 远程共享（L2） | Redis、Memcached、云托管缓存 | 亚毫秒~毫秒 | GB~TB 级 | 中等（一次删除即可） | 是 |
| 数据库自带 | InnoDB Buffer Pool、查询缓存 | 微秒 | 与库同机 | 最低（由数据库保证） | 是 |

::: warning 说明
上表的「一致性难度」是相对值。**进程内缓存最难，不是因为它不可靠，而是因为「删除」这个动作在进程外部无法直接执行**——你只能通知它自己去删，而通知是会丢的。
:::

## 四种位置各自解决什么问题

### 客户端缓存解决「重复请求」

同一个用户反复访问同一资源，浏览器与 App 已经缓存过。此时服务端做什么优化都收效有限，因为**请求根本没到服务端**。

这一层的判据是「资源是否可长期不变」：静态资源用内容哈希做文件名 + 长效强缓存；接口用 `ETag` + 协商缓存。反过来，**个人化接口绝不能进客户端强缓存**，否则换账号会出现串号——这与安全相关，不是体验问题。

### 进程内缓存解决「同一进程的重复计算」

同一实例上，同一个热点 key 每秒被读几千次。把它放进进程内存，后续请求连网络都不需要。

代价有三条：

1. **每个实例各有一份**，n 个实例就有 n 份副本要分别失效；
2. **占用堆内存**，会直接抬高 GC 压力（详见 [高性能 Java](../../HighPerformanceJava/index.md)）；
3. **进程重启即归零**，形成一次「小规模冷启动」。

### 远程共享缓存解决「跨实例一致」

多实例部署后，进程内缓存无法共享，于是把缓存放到所有实例都能访问的地方。此时「删一次就全生效」重新成立，这也是**绝大多数项目应该停在哪一层**的答案。

### 数据库自带缓存解决「对用户透明」

InnoDB Buffer Pool 让热数据不出内存，但单机容量有限。这部分属于数据库话题，本文只用来对照：**如果回源压力主要由数据库承担，先看 Buffer Pool 命中率，再决定要不要上缓存**，顺序反了会白花很多力气。

## 什么时候不该把缓存搬出进程

以下情况里，引入 Redis 往往**净收益为负**：

1. **单实例部署，且数据量小**：进程内缓存已经够用，多引入一个中间件只是多一个故障点。
2. **数据写多读少**：缓存命中率天然很低，缓存只是「让写路径多一次删除操作」。
3. **一致性要求接近强一致**：例如账户余额的实时校验。缓存与库之间必然存在窗口，这时应当**直连数据库并靠索引解决性能**，而不是加缓存再想办法消除窗口。
4. **量大但访问不集中（长尾）**：命中率低到无法覆盖内存成本。判据是「**Top 1% 的 key 是否承载了 80% 以上的请求**」，如果不满足，先做访问分布分析。
5. **团队没有观测能力**：缓存出问题时比数据库出问题更难定位（它不报错、只是「有点不对」）。没有命中率与回源指标之前，贸然上多级缓存是把故障模式从「显性」变成「隐性」。

::: danger 三个最常见的误判
1. **「接口慢就加缓存」**——先看慢在 SQL、序列化、还是网络。加缓存会把一个能定位的问题变成一个不好定位的问题。正确做法是先跑一次耗时分解。
2. **「加了缓存就不怕高并发了」**——缓存会在**冷启动、批量失效、大促开盘**三个时刻把流量原样放大到数据库。不加限流的缓存，只是把故障推迟到流量峰值。正确做法是缓存与限流同时上线。
3. **「命中率 90% 说明缓存很健康」**——命中率是结果指标。请同时看**回源 QPS**：命中率不变但流量涨了三倍时，回源量也涨了三倍，数据库压力同步上升。正确做法是两个指标同屏看。
:::

## 从单机缓存走向分布式缓存的三步

如果判断需要往外走，建议按下面顺序推进，每一步都可回滚：

1. **先补观测，再动结构**。在引入任何共享缓存之前，把「回源 QPS」「接口耗时分解（SQL / 序列化 / 网络）」两项指标接上。没有基线，无法判断后续改动是有效还是巧合。
2. **先单层（L2）跑通，再考虑加 L1**。绝大多数项目在 L2 一层就能达到目标；L1 带来的一致性成本需要用明确的收益来换（通常是热点 key 的延迟）。参照 [多级缓存深入](../MultiLevel/index.md) 的三条失效路线评估。
3. **最后做韧性加固**。限流、超时熔断、降级兜底、预热脚本，在 L1/L2 都跑稳之后补齐，判据见 [缓存层韧性](../Availability/index.md)。

## 一张判断表

| 你的情况 | 建议的第一选择 | 为什么 |
| --- | --- | --- |
| 单实例、数据量小、读多写少 | 进程内缓存（Caffeine） | 零网络开销，一致性压力最小 |
| 多实例、读多写少、可容忍秒级不一致 | 单层 Redis（Cache Aside） | 删一次全生效，复杂度最低 |
| 多实例 + 少量极端热 key，延迟敏感 | L1 + L2 两级 | 用「短 TTL + 广播失效」换取延迟 |
| 数据量超出单机内存，需要水平扩展 | 分片集群或代理方案 | 路由问题必须正面解决，见 [拓扑与路由](../Topology/index.md) |
| 一致性要求接近强一致 | 不加缓存，改索引与读写分离 | 消除窗口比补偿窗口更便宜 |
| 访问高度长尾、命中率注定很低 | 不加缓存，做访问分布分析 | 缓存不解决长尾 |

## 验证方式

判断自己是否真的需要往外走，可以先用一条命令量化「重复度」：

```shell
# 从应用日志或网关日志里统计「同一资源路径」的重复次数
# 取访问量最高的 1% 路径，看它们占总访问量的比例
awk '{print $7}' access.log | sort | uniq -c | sort -rn > path_rank.txt

# 总请求数
awk '{s+=$1} END {print "total:", s}' path_rank.txt

# 前 1% 的路径贡献了多少请求
total_paths=$(wc -l < path_rank.txt)
top_n=$(( total_paths / 100 + 1 ))
head -n "$top_n" path_rank.txt | awk '{s+=$1} END {print "top1%:", s}'
```

预期结果：如果 `top1%` 占总量的比例**低于 50%**，说明访问分布过于长尾，缓存收益有限，应当先解决长尾的成因（例如改成分页、收敛查询维度），而不是先上缓存。比例高于 80% 时，缓存的收益基本确定。
