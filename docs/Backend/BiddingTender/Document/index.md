# 招标文件与资格条件：条件写进标书的那一刻，竞争范围就定了

一份招标文件 180 页，其中真正的「门槛」只有 4 行：

```text
1. 注册资本不低于 1000 万元；
2. 近 3 年具有本地同类项目业绩不少于 3 个；
3. 在本市设有分公司（提供营业执照）；
4. 具备 ISO9001 质量管理体系认证。
```

这 4 行决定了谁能进来。剩下的 176 页——技术参数、合同条款、报价格式——只决定进来的这几家怎么比。

::: tip 一句话理解
资格条件的本质是**用一句可以写进标书的话，替换掉一次本应发生的竞争**。所以它必须同时满足两个条件：与合同履行相关（合法），且不指向特定主体（公平）。前者靠条文，后者靠数据。
:::

本页判据族 `BTD-A` ~ `BTD-H`，共 8 条。

## 一、资格预审与资格后审：两个时点，两种失败

| 方式 | 什么时候审 | 优点 | 失败形状 |
| --- | --- | --- | --- |
| 资格预审 | 发售文件前 | 不合格的不浪费编制标书的成本 | 通过者少于 3 个要重新招标，前期工作全废 |
| 资格后审 | 开标后由评标委员会审 | 流程短、潜在投标人不知谁在投 | 不合格的标书照样占用评标工作量，且废标争议集中在开标后 |

法规对预审有一条硬约束：**通过资格预审的申请人少于 3 个的，应当重新招标**（条例第十九条）。这条规则的本意是保证竞争，但在实现时容易退化成「保证数字」——只要条件写得够窄，通过人数就会刚好卡在 3。

### 本机读数：两条「本地」条件值多少竞争

用 4,000 家供应商样本模拟（注册资本、ISO9001、本地业绩、本地分公司四个属性独立分布）：

| 条件组合 | 通过率 | 折算到 40 家潜在投标人 | 400 次开标的流标率 |
| --- | --- | --- | --- |
| 四条全上 | 8.88% | **3.5 家** | **33.00%** |
| 去掉「本地业绩 ≥3」与「本地分公司」 | 43.75% | 17.5 家 | 0.00% |

同一个项目、同一批供应商，**只删掉两条与合同履行无关的条件，投标人从 3.5 家变成 17.5 家，流标率从 33% 变成 0**。

而这个变化在系统里**看不出任何异常**：两种情况下都是「资格审查通过，进入下一环节」。差别只在于通过的是 3 家还是 17 家——而 3 家刚好满足「不少于 3 个」的门槛。

::: danger 把「通过 3 家」当成结论，是本页最贵的错误
1. **只看人数不看基数**：通过 3 家、潜在 40 家（7.5%）与通过 3 家、潜在 4 家（75%）是两件完全不同的事。系统必须同时存「通过数」与「报名/获取文件数」。
2. **把「本地业绩」写成加分项而不是资格项**：条例第三十二条第（三）项禁止「以特定行政区域或者特定行业的业绩、奖项作为加分条件或者中标条件」——加分也不行。
3. **资格条件不留版本**：澄清时改了条件却不升版本，会导致「按旧条件通过、按新条件评标」，事后无法解释。
:::

## 二、条例第三十二条：七种「不合理条件」

这一条是判定资格条件合法性的核心，七种情形逐条对应一个可检查的字段：

| # | 条文要点 | 系统里怎么发现 |
| --- | --- | --- |
| 1 | 提供有差别的项目信息 | 同一项目对不同投标人发出的澄清内容不一致 |
| 2 | 资格、技术、商务条件与项目特点或合同履行无关 | 条件字段与合同标的无映射关系 |
| 3 | 以特定区域或行业的业绩、奖项作为加分或中标条件 | 条件里出现行政区划、行业名称 |
| 4 | 对不同投标人采取不同的资格审查或评标标准 | 同一项目存在多个 `tender_doc.version` 且未公告 |
| 5 | 限定或指定特定的专利、商标、品牌、原产地、供应商 | 技术参数里出现品牌名或型号 |
| 6 | 非法限定所有制形式或组织形式 | 条件里出现「国有」「本地注册」等字样 |
| 7 | 其他不合理条件 | 兜底条款，靠人工复核 |

第 3、5、6 项可以做成**关键词 + 结构**的双重检查：

```sql
-- 资格条件里出现行政区划或品牌指向（需配合 qual_json 的结构化存储）
SELECT doc_id, json_extract(j.value, '$.text') AS cond
FROM tender_doc, json_each(tender_doc.qual_json) j
WHERE json_extract(j.value, '$.text') LIKE '%本市%'
   OR json_extract(j.value, '$.text') LIKE '%本地%'
   OR json_extract(j.value, '$.text') LIKE '%省内%'
   OR json_extract(j.value, '$.type') = 'brand';
```

关键词法会误报——「本地化服务团队」在运维项目里是合理要求。所以本册的口径是：**命中即提示，由人判断**，但**必须留判断记录**（谁判的、依据什么），否则下一任接手的人只能重新猜一遍。

## 三、实质性条款：星号背后的废标权

招标文件里带 `*` 的条款叫**实质性条款**，不满足即废标。它是招标人手里最锋利的工具，也是最容易伤到自己的工具：

| 用法 | 后果 |
| --- | --- |
| 星号条款与核心功能相关（如「支持国密算法」） | 合理，能筛掉不合格产品 |
| 星号条款指向品牌或型号（如「等效于 XX 品牌 YY 型号」） | 违反条例第三十二条第（五）项 |
| 星号条款过多（每条都要单独举证） | 投标人无法判断哪些会废标，有效投标骤减 |
| 星号条款在澄清中新增 | 实质改变招标要求，必须顺延截止时间 |

一个可用的判定方式是给每条星号条款打两个标记：

```json
{
  "clause_id": "T-17",
  "text": "支持国密 SM2/SM3/SM4 算法",
  "substantive": true,
  "linked_requirement": "R-03",     // 对应哪条功能需求
  "brand_ref": null                  // 指向品牌时填品牌名
}
```

`linked_requirement` 为空且 `substantive = true`，就是一条「没有功能依据的废标条款」——这正是条例第三十二条第（二）项要禁止的东西。

## 四、两种评标办法：算法完全不同

| 办法 | 适用 | 算法 | 风险 |
| --- | --- | --- | --- |
| 经评审的最低投标价法 | 技术规格标准统一、差异小 | 满足实质性要求者中取最低价 | 低价中标后偷工减料 |
| 综合评分法 | 技术差异大、需要权衡 | 各项加权求和 + 价格分 | 权重与汇总口径可被操纵 |

综合评分法的价格分有几种算法，选哪一种必须写死在招标文件里：

```text
低价优先法：价格分 = 评标基准价 / 投标价 × 价格权重
            （评标基准价 = 满足招标文件要求且投标价格最低的投标报价）
平均值法：  价格分 = 价格权重 × (1 - |投标价 - 评标基准价| / 评标基准价)
```

**两种算法对同一组报价给出完全不同的排序**。低价优先法是反比曲线（800 万基准时，1,000 万得 24 分），平均值法在基准价附近近似线性、偏离越多扣得越快。招标文件里只写「价格分 30 分」而不写算式，等于把最关键的一步留给评委自由裁量。

### 客观分与主观分必须分开

| 类型 | 例子 | 能不能复核 | 本机不一致率 |
| --- | --- | --- | --- |
| 客观分 | 证书数量、业绩个数、注册资金 | 能（数一遍就知道） | **9.13%**（238 / 2,606） |
| 主观分 | 方案可行性、创新性 | 只能看评分理由 | 不适用 |

9.13% 的客观分不一致率意味着：**每 11 份标书里就有 1 份的客观分打错了**。这不是评委水平问题，是流程问题——客观分应该由系统按规则算出，评委只做确认，而不是手工填。

## 五、文件版本与澄清的耦合

招标文件至少要落三个版本维度：

| 维度 | 字段 | 为什么必须分开 |
| --- | --- | --- |
| 文档版本 | `tender_doc.version` | 澄清/修改后必须升版（条例第二十一条） |
| 规则版本 | `score_rule_version` | 评分办法可以单独修订，需独立追溯 |
| 发布状态 | `published_at` / `status` | 未发布的版本不得作为评标依据 |

三者的关系是：**评标时必须引用「投标截止时刻有效的那个版本」**，而不是「最新版本」。这一条在澄清频繁的项目里最容易错——评标系统默认取最新版，而最新版可能是评标开始后才改的。

```sql
-- 取「投标截止时刻有效」的文件版本（半开区间，含生效时点）
SELECT doc_id, version, score_rule
FROM tender_doc
WHERE project_id = :pid
  AND published_at <= :deadline
  AND (superseded_at IS NULL OR superseded_at > :deadline)
ORDER BY version DESC
LIMIT 1;
```

`superseded_at > :deadline` 这个写法（而不是 `>=`）是关键：澄清在截止时刻同一秒生效时，旧版本失效、新版本生效，边界必须只归一边。

## 六、一份可判定的招标文件长什么样

| 部分 | 必须结构化到什么程度 |
| --- | --- |
| 资格条件 | 每条一个对象：类型、阈值、依据、是否实质性 |
| 实质性条款 | 每条挂一个功能需求 ID，或标记为「无依据」 |
| 评分办法 | 项、权重、打分方式、小数位、汇总口径五项齐全 |
| 合同条款 | 关键条款（付款、违约、验收）可定位到条号 |
| 澄清记录 | 发出时间、影响范围、是否顺延 |

五部分里，只有第 4 项通常还是纯文本。这不是技术限制，是**没有下游消费者**——合同条款的机器可读版本在签约时才需要，而那时已经来不及补。

## 七、本页判据

| 判据 | 断言 | 验证方式 |
| --- | --- | --- |
| `BTD-A` | 资格条件以结构化列表存储 | `qual_json` 可被 `json_each` 展开为 ≥1 条 |
| `BTD-B` | 每条条件都标了类型与阈值 | 展开后 `type` / `value` 均非空 |
| `BTD-C` | 实质性条款必须挂功能需求 | `substantive = true` 且 `linked_requirement` 为空的条件数为 0（或已登记例外） |
| `BTD-D` | 评分办法含汇总口径与小位数 | `score_rule` 里能读到 `aggregate` 与 `round` 两个键 |
| `BTD-E` | 客观分可由规则复算 | 用证书数重算的客观分与 `score.obj_score` 一致 |
| `BTD-F` | 澄清必须升版本 | 存在澄清记录的项目，`version` 至少为 2 |
| `BTD-G` | 评标引用截止时刻的版本 | 评标记录里的 `doc_version` ≤ 该时刻最大版本 |
| `BTD-H` | 通过人数与获取文件人数同时留存 | 两张计数都能查到，且通过数 ≤ 获取数 |

## 验证方式

```shell
# 1. 条件可展开（期望 ≥1 行）
sqlite3 bt.db "select count(*) from tender_doc, json_each(tender_doc.qual_json);"

# 2. 无依据的实质性条款（期望 0，或只剩登记过的例外）
sqlite3 bt.db "select count(*) from tender_doc, json_each(tender_doc.qual_json) j
               where json_extract(j.value,'\$.substantive') = 1
                 and json_extract(j.value,'\$.linked_requirement') is null;"

# 3. 评分办法必须含汇总口径（期望输出 aggregate 与 round）
sqlite3 bt.db "select score_rule from tender_doc where doc_id='D1';"
```

第 2 步的 SQL 里 `\$` 是 shell 转义，在 `sqlite3` 交互式里直接写 `$.substantive` 即可。这类转义错误常被误判成「SQL 写错了」，实际是 shell 提前把 `$` 吃掉了。
