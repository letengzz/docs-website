# 采购方式与限额：规避招标的四种形状

一个 1,200 万元的改造项目，被拆成 4 个 290 万元的标段，分别用竞争性磋商、询价、直接采购完成。**每一笔都低于 400 万元的施工招标限额，每一笔的审批单都齐全，账上也看不出问题。**

只有把四笔放在一张表上看，才会发现：同一个采购人、同一个品目、同一个季度、四个标段的施工内容互为前后工序。

::: tip 一句话理解
「要不要招标」不是看单笔金额，是看**这个采购能不能被合并**。系统里如果只存了「每个标段的估算价」，它就永远只能回答「这一笔合不合规」，回答不了「这四笔是不是一件事」。
:::

本页判据族 `BTM-A` ~ `BTM-H`，共 8 条。

## 一、两套限额，两个体系

「多少金额必须招标」在中国有两套并行规则，适用对象不同，混用是最常见的口径错误：

| 体系 | 依据 | 施工 / 工程 | 货物 | 服务 |
| --- | --- | --- | --- | --- |
| 依法必须招标的工程建设项目 | 发改委 16 号令第五条 | 400 万元 | 200 万元 | 100 万元 |
| 政府采购（中央预算单位） | 集中采购目录及标准 | 400 万元 | 200 万元 | 200 万元 |

差异最大的是**服务**：16 号令是 100 万元，政府采购口径是 200 万元。一个 150 万元的监理服务，在工程建设项目里必须招标，在政府采购货物服务口径下可以不走公开招标。

::: warning 限额是「单项合同估算价」，不是「项目总投资」
16 号令第五条的措辞是「**单项合同估算价**」。一个总投资 2 亿元的项目，如果监理合同只有 80 万元，监理这一项就不在必须招标范围内——但施工、货物可能都在。按「总投资」判断，会把不该招的招了，也会把该招的漏掉。
:::

### 同一项目里「可以合并」的采购

16 号令第五条还有一句常被漏读的话：

```text
同一项目中可以合并进行的勘察、设计、施工、监理
以及与工程建设有关的重要设备、材料等的采购，
合同估算价合计达到前款规定标准的，必须招标。
```

这句话把判定从「横向看单笔」变成了「先纵向看能否合并，再横向看合计」。**能不能合并，是个业务判断，不是一个金额判断**——这正是系统最难处理的地方（见第四节）。

## 二、四种方式与它们的法定入口

达到限额之后，还有四条路，每条都有自己的门槛：

| 方式 | 法定入口 | 常见误用 |
| --- | --- | --- |
| 公开招标 | 默认路径 | 无 |
| 邀请招标 | 条例第八条：技术复杂/特殊要求/受自然地域限制，只有少量潜在投标人；或采用公开招标费用占合同金额比例过大 | 把「不想让太多人知道」说成「技术复杂」 |
| 竞争性谈判 / 磋商 | 非依法必须招标项目、或依法必招项目招标失败后 | 对依法必招项目直接用 |
| 单一来源 | 条例第九条五项：不可替代的专利或专有技术、采购人能自行建设生产提供、已通过招标选定的特许经营投资人能自行提供、需向原中标人采购否则影响配套、国家规定的其他情形 | 把「一直用这家，换起来麻烦」说成「影响配套」 |

条例第九条最后一句值得单独抄下来：

```text
招标人为适用前款规定弄虚作假的，属于招标投标法第四条规定的规避招标。
```

**「编一个理由」本身就是违法行为**，不是程序瑕疵。所以系统里「方式选择」这一步必须留下**理由与依据**，而不只是一个枚举值。

## 三、规避招标的四种形状

本机把 1,351 条采购需求（合计 36.64 亿元）跑了一遍，规避行为可以归成四类：

| 形状 | 做法 | 系统里长什么样 | 能不能机检 |
| --- | --- | --- | --- |
| 化整为零 | 拆成多包，每包低于限额 | 多笔小额、同品目、时间接近 | 能（同采购人 + 同品目 + 时间窗） |
| 方式降级 | 达到限额却走邀请/磋商/单一来源 | 方式字段与金额不匹配 | 能（金额 vs 方式规则） |
| 名目转换 | 把工程写成货物或服务 | 品目字段与实际内容不符 | 难（要读合同文本） |
| 时间错位 | 把一个大项目分到两个年度 | 跨年度、同品目、金额相接 | 能（跨年窗口，但需要预算年度表） |

### 本机读数

| 指标 | 值 |
| --- | --- |
| 需求条数 / 估算价合计 | 1,351 条 / 36.64 亿元 |
| 达到公开招标标准 | 531 条（39.30%） |
| 达标准但未走公开招标 | **69 条（12.99%），3.65 亿元** |
| 方式分布 | 公开 45.97% / 邀请 24.13% / 磋商 20.50% / 单一来源 9.40% |
| 单一来源占金额 | 4.47% |

值得注意的是「单一来源占条数 9.40%，占金额 4.47%」——**条数与金额不成比例，说明单一来源多用在碎小采购上**。这是一个有用的信号：如果反过来（条数少、金额大），就要去看是不是大项目在走单一来源。

### 拆分识别的口径之争

第一版规则是「同采购人 + 同品目 + 90 天内 + 各单 < 限额 + 合计 ≥ 限额」，结果命中 145 组、真拆分只有 11 组，**精度 7.59%**——几乎不可用。

问题不在阈值，在**窗口怎么切**。调整成「60 天窗 + ≥3 包 + 每包 ≥25% 限额 + 合计 ≥1.5×限额」后：

| 规则版本 | 命中窗口 | 组级召回 | 窗口精度 |
| --- | --- | --- | --- |
| ≥3 包即算（粗规则） | 253 | 91.11% | 明显偏低（大量重复窗口） |
| 60 天窗 + 25% 下限 + 1.5 倍合计 | **217** | **91.11%** | **63.59%** |
| 90 天窗 + 无限额下限 | 145 | 24.44% | 7.59% |

三行读数说明一件事：**「窗口」是这条规则里最像业务的参数，也是最容易被随手写死的参数**。90 天看起来更宽松，实际因为把太多无关采购卷进来，反而把真拆分淹没了。

::: danger 三个常见写法，都错在「只看单笔」
1. **只校验「金额 vs 方式」**：这能抓住方式降级，抓不住化整为零——因为每一包都合法。
2. **用「项目总投资」判限额**：会把一个 2 亿元项目里的 80 万元监理也拉进招标，浪费竞争成本。
3. **把窗口写成固定 30 天**：拆分方只要把间隔拉到 35 天就绕过去了。窗口应当由**业务周期**（预算年度、施工季节、合同履约期）决定，而不是由「看起来合适」决定。
:::

## 四、标段划分：合法的切分与违法的切分

切分标段本身是合法的，甚至是鼓励的（让中小企业有机会参与）。条例第二十四条的措辞是：

```text
招标人对招标项目划分标段的，应当遵守招标投标法的有关规定，
不得利用划分标段限制或者排斥潜在投标人。
依法必须进行招标的项目的招标人不得利用划分标段规避招标。
```

判定「合法切分」与「规避招标」的分界线，本册采用三条可判定的条件：

| 条件 | 合法切分 | 规避招标 |
| --- | --- | --- |
| 能否独立实施 | 每标段可独立施工/供货/验收 | 必须连着做，切开就要二次进场 |
| 是否有独立标的 | 每标段有独立的工程量清单或技术规格 | 共用一份清单，只是把金额除以 N |
| 是否面向更多主体 | 切开后潜在投标人增多 | 切开后还是那几家，甚至更少 |

三条里前两条能半自动判（比对清单指纹、比对工序依赖），第三条要靠「投标人集合」的历史数据。

## 五、数据模型：三张表回答「能不能合并」

```sql
CREATE TABLE purchase_project (
  project_id   TEXT PRIMARY KEY,
  name         TEXT NOT NULL,
  category     TEXT NOT NULL CHECK (category IN ('工程','货物','服务')),
  estimate     REAL NOT NULL CHECK (estimate > 0),
  method       TEXT NOT NULL CHECK (method IN ('公开招标','邀请招标','竞争性磋商','单一来源')),
  method_basis TEXT,              -- 方式选择的依据（条例第八/九条的具体情形）
  limit_amount REAL NOT NULL,     -- 立项时的限额快照，不随后续标准调整
  package_of   TEXT REFERENCES purchase_project,  -- 同一项目的父项目
  deadline     TEXT NOT NULL
);

CREATE TABLE demand_item (            -- 需求明细：拆分的证据在这里
  item_id    TEXT PRIMARY KEY,
  project_id TEXT NOT NULL REFERENCES purchase_project,
  buyer_id   TEXT NOT NULL,
  category   TEXT NOT NULL,
  subitem    TEXT NOT NULL,          -- 品目细分，缺了它就只能按大类合并
  estimate   REAL NOT NULL,
  plan_date  TEXT NOT NULL,
  mergeable  INTEGER NOT NULL DEFAULT 1   -- 业务判断：能否与同期同类合并
);
```

三个字段是这套模型的关键：

1. **`limit_amount` 是快照**：限额标准会随政策调整，事后审计要看「当时的标准」，不能看现在的。
2. **`subitem` 必须细到能判断「是不是一件事」**：只到「货物 / 工程 / 服务」这一层，任何两条需求都能被说成「不同品目」。
3. **`mergeable` 是人工判断，但要留痕**：把它做成默认 1，任何标「不可合并」的都要填理由。

### 一条能跑的拆分检测

```sql
-- 同一采购人、同一品目、60 天窗内 ≥3 包、每包 ≥25% 限额、合计 ≥1.5×限额
WITH win AS (
  SELECT a.item_id, a.buyer_id, a.subitem, a.estimate,
         a.plan_date AS d0,
         (SELECT SUM(b.estimate) FROM demand_item b
           WHERE b.buyer_id = a.buyer_id AND b.subitem = a.subitem
             AND julianday(b.plan_date) - julianday(a.plan_date) BETWEEN 0 AND 60
             AND b.estimate >= 0.25 * a_limit.limit_amount) AS win_sum,
         (SELECT COUNT(*) FROM demand_item b
           WHERE b.buyer_id = a.buyer_id AND b.subitem = a.subitem
             AND julianday(b.plan_date) - julianday(a.plan_date) BETWEEN 0 AND 60
             AND b.estimate >= 0.25 * a_limit.limit_amount) AS win_cnt
  FROM demand_item a
  JOIN purchase_project a_limit ON a_limit.project_id = a.project_id
  WHERE a.estimate < a_limit.limit_amount
)
SELECT buyer_id, subitem, d0, win_cnt, win_sum
FROM win
WHERE win_cnt >= 3 AND win_sum >= 1.5 * (SELECT limit_amount FROM purchase_project LIMIT 1)
ORDER BY win_sum DESC;
```

它有三个必须写对的地方：`julianday(...) BETWEEN 0 AND 60`（半开窗，左闭右开才不会重复计数）、`>= 0.25 * limit`（排除碎小需求带来的假阳性）、以及 `estimate < limit`（已经超限额的单笔不在这条规则里，它由「方式 vs 金额」那条规则负责）。

## 六、把「方式选择」做成可解释的一步

一个可用的方式选择界面必须回答四问，缺一不可：

| 问题 | 落到哪 | 答不上来的后果 |
| --- | --- | --- |
| 这个项目属于哪个体系（16 号令 / 政府采购） | `project.regime` | 限额取错整套 |
| 单项合同估算价是多少 | `project.estimate` | 限额判定失据 |
| 有没有可合并的同期同类采购 | `demand_item.mergeable` | 拆分识别失效 |
| 不走公开招标依据哪一条 | `project.method_basis` | 无法举证 |

第四问最容易被做成一个自由文本框，然后所有人都填「项目特殊」。可用的做法是**枚举 + 必填说明**：枚举限定在条例第八条、第九条的具体情形里，选了之后必须再填「为什么符合」。

## 七、本页判据

| 判据 | 断言 | 验证方式 |
| --- | --- | --- |
| `BTM-A` | 每个项目都落了限额快照 | `limit_amount IS NULL` 的行数为 0 |
| `BTM-B` | 达限额的项目方式必须是公开招标或已举依据 | 达限额且方式 ≠ 公开且 `method_basis` 为空的行数为 0 |
| `BTM-C` | 需求明细细到子品目 | `subitem` 为空的 `demand_item` 行数为 0 |
| `BTM-D` | 拆分检测的窗口参数可配置且落库 | 参数表里能查到 `window_days` / `min_packages` / `min_ratio` |
| `BTM-E` | 「不可合并」必须填理由 | `mergeable = 0` 且理由为空的行数为 0 |
| `BTM-F` | 标段必须有父项目 | `package_of IS NOT NULL` 的标段都能找到父项目 |
| `BTM-G` | 方式分布可按条数与金额双口径统计 | 两个口径的报表都能出数，且合计一致 |
| `BTM-H` | 单一来源占比异常时能报警 | 条数占比与金额占比差异 > 3 倍触发提示 |

## 验证方式

```shell
# 1. 限额快照不为空（期望 0）
sqlite3 bt.db "select count(*) from purchase_project where limit_amount is null;"

# 2. 达限额却未公开招标且无依据（期望 0，或只剩已审批的例外）
sqlite3 bt.db "select count(*) from purchase_project
               where estimate >= limit_amount and method <> '公开招标'
                 and (method_basis is null or method_basis = '');"

# 3. 方式分布双口径（两个数应当都出得来）
sqlite3 bt.db "select method, count(*), round(sum(estimate)/10000,2)
               from purchase_project group by method order by 2 desc;"
# 期望：四行，条数合计 = 项目总数；金额合计与总估算价一致
```

第 3 步的意义在于：**只出条数不出金额的报表，会掩盖「大项目都走了单一来源」这种情况**。两个口径必须一起看。
