# 公告、发售与澄清：五个法定期限，落在两种「日」上

一个项目 2026 年 9 月 28 日发公告，投标准备期写了「20 日」，截止时间落在 10 月 18 日。

从字面看，20 日是够的。但这 20 天里有 7 天国庆法定假日，实际只有 10 个工作日——如果招标文件里写的是「20 个工作日」，截止时间应该是 10 月 26 日。

::: tip 一句话理解
招投标里的「日」是有歧义的：**法规写的「日」默认是自然日，但监管检查与投标人感受用的是工作日**。系统如果只存一个截止日期，就把这个歧义永久封存在了一个字符串里。
:::

本页判据族 `BTL-A` ~ `BTL-H`，共 8 条。

## 一、五个期限，一张表

| 期限 | 要求 | 依据 | 起算点 |
| --- | --- | --- | --- |
| 文件发售期 | ≥5 日 | 条例第十六条 | 开始发售之日 |
| 投标准备期 | ≥20 日 | 招标投标法第二十四条 | 招标文件开始发出之日 |
| 澄清/修改 | ≥15 日前发出，不足则顺延 | 条例第二十一条 | 投标截止时间 |
| 资格预审文件澄清 | ≥3 日前发出 | 条例第二十一条 | 申请文件截止时间 |
| 中标候选人公示 | ≥3 日 | 条例第五十四条 | 收到评标报告后 3 日内开始 |

还有两个容易被忘掉的：**异议答复 3 日**（条例第二十二条、第五十四条）、**合同签订 30 日**（招标投标法第四十六条）。它们不在「投标前」，但同样有硬时限。

## 二、本机读数：三个期限的实际违约率

对 500 个模拟项目按 2026 年放假日历折算：

| 检查项 | 违约项目数 | 占比 |
| --- | --- | --- |
| 公告期折算后不足 5 个工作日 | 128 / 500 | **25.60%** |
| 投标准备期不足 20 日 | 63 / 500 | 12.60% |
| 澄清在截止前不足 15 日发出且未顺延 | 132 / 500 | **26.40%** |

第一个数字最值得注意：**25.60% 的项目「公告挂了 5 天」，但折算只有 3~4 个工作日**。这不是有人故意违规，而是系统按自然日算、检查按工作日算——**两边都没错，结论不同**。

### 一个具体的日期算例

```text
2026-09-28（周一）发公告，+20 自然日
→ 截止 2026-10-18（周日）
→ 区间内工作日 10 天（含 10-01 至 10-07 共 7 天法定假日）

若按「20 个工作日」理解
→ 截止 2026-10-26（周一）
→ 比正确口径多 5 个工作日
```

两种理解相差 8 天，而这个差别在系统里只体现为一个 `deadline` 字段的取值。**如果这个字段是人手工填的，那么填错不会有任何提示。**

## 三、澄清与修改：最容易漏掉「顺延」

条例第二十一条的完整逻辑是两段：

```text
澄清或者修改的内容可能影响资格预审申请文件或者投标文件编制的，
招标人应当在提交资格预审申请文件截止时间至少 3 日前，
或者投标截止时间至少 15 日前，以书面形式通知所有获取资格预审文件
或者招标文件的潜在投标人；不足 3 日或者 15 日的，
招标人应当顺延提交资格预审申请文件或者投标文件的截止时间。
```

第二段是**强制顺延**，不是「可以顺延」。而系统实现里最常见的三个漏洞：

| 漏洞 | 表现 | 后果 |
| --- | --- | --- |
| 只记「已发出」不记「距截止几天」 | 澄清记录有时间戳，但没人算差值 | 26.40% 的项目实际不足 15 日 |
| 只通知「已报名的」 | 没报名的获取者收不到 | 违反「通知所有获取文件的潜在投标人」 |
| 顺延后不更新下游 | 截止时间改了，开标时间、保证金到账截止没改 | 开标时出现「截止已延但系统仍按原时间拒收」 |

第三条是最隐蔽的：**顺延是一个事务，不是一次字段更新**。它至少要同步改三处：投标截止时间、开标时间、保证金到账截止时间。

```sql
-- 顺延必须在一个事务里改三处，且留痕
BEGIN;
UPDATE purchase_project
   SET deadline = :new_deadline
 WHERE project_id = :pid AND deadline = :old_deadline;   -- 乐观锁：防止并发重复顺延
INSERT INTO deadline_change(project_id, old_deadline, new_deadline, reason, changed_by, changed_at)
VALUES (:pid, :old_deadline, :new_deadline, :reason, :uid, :now);
COMMIT;
```

`AND deadline = :old_deadline` 这个条件是关键：两个管理员同时点「顺延 3 天」，没有它就会顺延 6 天。

## 四、工作日不是 `weekday() < 5`

一个能用的日历表至少要有三层：

| 层 | 内容 | 例子 |
| --- | --- | --- |
| 周末规则 | 哪些星期几休息 | 中国大陆周六周日 |
| 法定节假日 | 具体日期 | 2026-10-01 至 2026-10-07 |
| 调休上班日 | 周末但上班 | 2026-10-10（周六）、2026-10-11（周日） |

第三层最容易被漏掉。**只减法定假日、不加调休上班日，会把工作日算少**——2026 年国庆前后各有一天调休，漏掉它们会让所有跨节假日的项目都「差一天」。

```sql
CREATE TABLE work_calendar (
  cal_date   TEXT PRIMARY KEY,
  is_workday INTEGER NOT NULL CHECK (is_workday IN (0,1)),
  note       TEXT            -- '法定假日' / '调休上班' / '周末'
);

-- 统计 [a, b) 区间内的工作日数（左闭右开，避免重复计边界）
SELECT COUNT(*) FROM work_calendar
WHERE cal_date >= :a AND cal_date < :b AND is_workday = 1;
```

::: danger 三个日期写法，每一个都会差一天
1. **`BETWEEN a AND b`** 会把两端都算进去，20 日的区间会数出 21 天。期限计算必须用 `>= a AND < b`。
2. **用 `date('now','+20 day')`** 直接算截止：SQLite 的 `+20 day` 是自然日加法，跨夏令时/节假日都不会调整。要做工作日加法，只能查表逐日累加。
3. **把「截止时刻」写成 `2026-10-18`**（只有日期）：开标判定到秒时会默认按 `00:00:00`，等于把截止提前了一整天。截止必须是带时分的完整时间戳。
:::

## 五、公告内容的一致性

同一项目在不同媒介发布的公告，内容必须一致（条例第十五条）。这一条在系统里对应的是「一份公告、多个发布渠道」还是「多份公告、各写各的」：

| 做法 | 一致性 | 改一处要改几处 |
| --- | --- | --- |
| 一份主公告 + 渠道分发记录 | 天然一致 | 1 处 |
| 每个渠道各存一份正文 | 靠人保证 | N 处（N = 渠道数） |

第二种做法在实践中一定会分叉：主站改了截止时间，地方交易中心那版没改。**判定方式很简单——把各渠道的正文做哈希，不一致就报。**

```sql
SELECT project_id, COUNT(DISTINCT content_hash) AS versions
FROM announcement_channel
GROUP BY project_id
HAVING COUNT(DISTINCT content_hash) > 1;
```

## 六、把期限做成「可判定的对象」

不要存「截止时间」，要存「期限」：

| 字段 | 含义 | 例子 |
| --- | --- | --- |
| `rule_code` | 哪条法定期限 | `PREP_20D` |
| `start_at` | 起算点 | 招标文件发出时间 |
| `duration` | 时长 | 20 |
| `day_basis` | 日 / 工作日 | `calendar` / `workday` |
| `computed_at` | 计算出的截止时刻 | 2026-10-18 09:30:00 |
| `source` | 依据条号 | 招标投标法第二十四条 |

有了这六个字段，「这个期限够不够」就变成一个可以随时重算的查询，而不是一次性的手工判断。**重算能力是审计时唯一的自证方式**——一年后有人问「当时为什么定在 10-18」，你能算出 20 个自然日、能列出那 7 天假日、也能说明这 20 日是自然日不是工作日。

## 七、本页判据

| 判据 | 断言 | 验证方式 |
| --- | --- | --- |
| `BTL-A` | 每个期限都落了起算点与口径 | 期限表里 `start_at` / `day_basis` 均非空 |
| `BTL-B` | 公告期折算 ≥5 个工作日 | 折算后不足的项目数为 0 |
| `BTL-C` | 投标准备期 ≥20 日 | 差值 <20 的项目数为 0 |
| `BTL-D` | 澄清不足 15 日必须顺延 | 不足 15 日且 `deadline` 未变更的记录数为 0 |
| `BTL-E` | 顺延同步改了截止与开标时间 | 两者不一致的项目数为 0 |
| `BTL-F` | 工作日按日历表计算 | 代码中不出现 `weekday()` 直接判定工作日的写法 |
| `BTL-G` | 多渠道公告正文一致 | 同一项目多个 `content_hash` 的组数为 0 |
| `BTL-H` | 公示期 ≥3 日 | `public_to - public_from < 3` 的行数为 0 |

## 验证方式

```shell
# 1. 工作日折算（需要 work_calendar 已灌当年日历）
sqlite3 bt.db "select count(*) from work_calendar where cal_date like '2026-10%' and is_workday=1;"
# 期望：2026 年 10 月的工作日数（含调休上班日），与国务院办公厅通知一致

# 2. 公告期不足 5 个工作日的项目（期望 0）
sqlite3 bt.db "select count(*) from announcement where period_workdays < 5;"

# 3. 顺延后截止与开标时间不一致（期望 0）
sqlite3 bt.db "select count(*) from purchase_project p
               join bid_opening o on o.project_id = p.project_id
               where p.deadline <> o.open_at;"
# 开标必须与截止同一时间（招标投标法第三十四条），这一条同时是「顺延是否同步」的检查
```

第 3 步把两个规则合并成一个断言：**开标时间等于截止时间**既是法条要求，也是「顺延有没有同步」的探测器。
