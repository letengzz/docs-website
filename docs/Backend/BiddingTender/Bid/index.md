# 投标与保证金：钱没到账，标书就不算到

投标人 09:28 上传了标书，系统回执「递交成功」。09:29 财务从基本账户转出 10 万元保证金，跨行到账时间 09:31。

开标时系统显示：**投标 1 家被拒收——保证金未在截止前到账。**

::: tip 一句话理解
「递交」和「有效」是两件事：递交看的是**文件到达服务器的时刻**，有效看的是**保证金到达招标人账户的时刻**。两个时刻之间隔着一整条银行清算链路，而这条链路的时间不受投标人控制。
:::

本页判据族 `BTB-A` ~ `BTB-H`，共 8 条。

## 一、四道门：什么时候算「投进来了」

一份投标要穿过四道门，每一道都可能把标书挡在外面：

| 门 | 判定依据 | 失败后果 | 谁的责任 |
| --- | --- | --- | --- |
| 递交 | 服务器接收时刻 ≤ 截止时刻 | 拒收（条例第三十六条） | 投标人 |
| 密封/加密 | 文件完整、CA 证书有效 | 拒收 | 投标人 |
| 保证金 | 招标人账户入账时刻 ≤ 截止时刻 | 按招标文件约定，通常拒收 | 投标人 + 银行 |
| 解密 | 开标窗口内解密成功 | 视为撤销投标（按文件约定） | 投标人 + 平台 |

四道门的**判定时刻各不相同**，这是所有争议的来源。系统如果只记一个 `submitted_at`，就无法回答「他是几点几分几秒到的」。

## 二、保证金的三条硬约束

| 约束 | 数值 | 依据 |
| --- | --- | --- |
| 上限 | 不得超过招标项目**估算价**的 2% | 条例第二十六条 |
| 施工招标的封顶 | 最高不超过 80 万元 | 《工程建设项目施工招标投标办法》第三十七条 |
| 退还时限 | 合同签订后 5 日内，退还保证金**及银行同期存款利息** | 条例第五十七条 |

注意第一行的措辞：基数**是估算价，不是投标报价**。一个 5,000 万元的标段，投标人报 4,800 万元，保证金仍按 5,000 万 × 2% = 100 万元计算，而不是按 96 万元。

还有两条容易漏的：

- **撤回**（截止前）：招标人应在收到书面撤回通知之日起 5 日内退还（条例第三十五条）；
- **撤销**（截止后）：招标人可以不退还投标保证金。

「撤回」与「撤销」一字之差，一个退钱一个不退，系统里必须是两个状态而不是一个布尔值。

## 三、本机读数：退还是最容易忘的一步

1,800 份投标、保证金合计 8,079.12 万元：

| 指标 | 值 |
| --- | --- |
| 保证金总额 / 笔均 | 8,079.12 万元 / 44,884.01 元 |
| 逾期退还（超过 5 日） | **419 笔（23.28%）** |
| 平均逾期 / 最长逾期 | 4.3 天 / 27 天 |
| 累计资金占用 | **7,447.75 万元·天** |
| 按 LPR 3.45% 折算利息 | 7,039.66 元 |
| 同规模改用保函（1.5%/年、占用 60 天） | 199,211.23 元 |

三个观察：

1. **23.28% 的逾期率不是「偶尔忘」**，是流程里根本没有「到期提醒」这个环节。合同一签，所有人的注意力都转到履约上去了。
2. **单笔利息很小（平均十几元），累计资金占用很大（7,447 万元·天）**。这就是「不记账的成本」——它不进任何一张报表，但确实占用了投标人的资金。
3. **保函比现金贵**：同样规模，保函费 19.9 万元，现金占用的利息成本只有 0.7 万元。所以「鼓励用保函」的政策动机不是省钱，是**降低投标人的资金门槛**——中小企业拿不出几十万现金压两个月，但拿得出两千元保函费。

::: warning 「退还」不是一个动作，是三个
1. **退未中标人**：合同签订后 5 日内（条例第五十七条）。
2. **退中标人**：同样是合同签订后 5 日内，不是「履约完毕后退」。
3. **退撤回人**：收到书面撤回通知后 5 日内（条例第三十五条）。

三类的起算点不同，如果只做一个 `refund_at` 字段而不区分类型，到期日就算不对。
:::

## 四、数据模型：把「到账」和「递交」分开

```sql
CREATE TABLE bid (
  bid_id        TEXT PRIMARY KEY,
  project_id    TEXT NOT NULL REFERENCES purchase_project,
  bidder_id     TEXT NOT NULL REFERENCES bidder,
  submitted_at  TEXT NOT NULL,          -- 服务器接收时刻（唯一判定依据）
  client_time   TEXT,                   -- 客户端自报时刻，仅作证据，不参与判定
  price         REAL NOT NULL CHECK (price > 0),
  decrypt_ok    INTEGER NOT NULL DEFAULT 1,
  withdraw_at   TEXT,                   -- 截止前撤回
  revoke_at     TEXT,                   -- 截止后撤销
  doc_hash      TEXT NOT NULL,
  UNIQUE (project_id, bidder_id)
);

CREATE TABLE bid_bond (
  bond_id      TEXT PRIMARY KEY,
  bid_id       TEXT NOT NULL UNIQUE REFERENCES bid,
  kind         TEXT NOT NULL CHECK (kind IN ('现金','保函','保险')),
  amount       REAL NOT NULL CHECK (amount > 0),
  paid_at      TEXT,                    -- 招标人账户入账时刻
  refund_due   TEXT NOT NULL,           -- 按类型算出的应退日
  refunded_at  TEXT,
  interest     REAL DEFAULT 0           -- 同期存款利息
);
```

两个设计决定值得说明：

**`client_time` 存但不判定。** 它是争议时的重要证据（能证明投标人「以为」自己准时），但判定必须用服务器时间——否则改本机时钟就能绕过截止时间。

**`refund_due` 是算出来的，不是填出来的。** 它由 `kind`、合同签订日、撤回日三者推导，写入时固化。这样「逾期」就变成一个 `refunded_at > refund_due` 的查询，而不是一次人工回忆。

### 保证金上限的强制

```sql
CREATE TRIGGER trg_bond_over_cap BEFORE INSERT ON bid_bond
WHEN NEW.amount > MIN(
       0.02 * (SELECT p.estimate FROM purchase_project p
                 JOIN bid b ON b.project_id = p.project_id
                WHERE b.bid_id = NEW.bid_id),
       800000)
BEGIN SELECT RAISE(ABORT, 'BOND_OVER_CAP'); END;
```

`MIN(2% × 估算价, 80 万)` 这个写法同时覆盖了两条约束：一般项目按 2%，施工项目在 2% 超过 80 万时取 80 万。**把两条规则写成一个 `MIN`，比写两个 `WHEN` 分支更不容易漏。**

## 五、到账时刻从哪来

这是本页最难的一步。银行的到账通知有三种形态：

| 形态 | 时间精度 | 能否作为判定依据 |
| --- | --- | --- |
| 实时清算回单（网银/银企直连） | 秒 | 能 |
| 日终对账单 | 日 | 不能（只知道当天到了） |
| 人工查询截图 | 分钟 | 不能（可篡改） |

所以「保证金是否按时到账」这条判据，**只有在接了实时回单的前提下才成立**。没接的情况下，只能退化成「按招标人确认时间」，而这在争议时几乎无法举证。

一个折中的工程做法是**双时间戳**：

```text
bank_credit_at   银行回单上的入账时间（权威）
platform_seen_at 平台收到回单的时间（用于发现延迟）
```

两者差异突然变大（比如某天所有回单都晚了 2 小时），说明是通道问题而不是某个投标人的问题——这个信号在排查「为什么那天有 5 家被判迟到」时非常有用。

## 六、联合体与保证金：一个主体，多份责任

联合体投标的保证金有两个坑：

| 坑 | 表现 | 正确做法 |
| --- | --- | --- |
| 从成员账户转出 | 保证金不是从牵头人基本账户转的 | 招标文件应明确「由牵头人转出」，否则按无效处理 |
| 联合体协议后补 | 投标时没有协议，中标后补 | 协议必须在递交时一并提交，否则主体资格不成立 |

条例第三十七条还规定：资格预审后联合体增减、更换成员的，其投标无效。这一条在系统里对应的是**联合体成员快照**——投标时存一份成员列表与股权比例，后续变更只能作废重投。

## 七、本页判据

| 判据 | 断言 | 验证方式 |
| --- | --- | --- |
| `BTB-A` | 递交时刻只用服务器时间 | 判定代码中不出现 `client_time` |
| `BTB-B` | 保证金不超 2% 且不超 80 万 | 超限行数为 0（触发器强制） |
| `BTB-C` | 撤回与撤销是两个状态 | 表里能查到 `withdraw_at` 与 `revoke_at` 两列 |
| `BTB-D` | 应退日按类型推导 | `refund_due` 与 `kind` 的对应关系可复算 |
| `BTB-E` | 逾期退还可见 | 能查出 `refunded_at > refund_due` 的笔数与天数 |
| `BTB-F` | 利息随本金一并退还 | `interest > 0` 的退还记录占比符合约定 |
| `BTB-G` | 同一投标人同一项目只能投一次 | `UNIQUE(project_id, bidder_id)` 存在 |
| `BTB-H` | 联合体成员有快照 | 联合体投标能查到递交时的成员列表 |

## 验证方式

```shell
# 1. 保证金超限（期望 0）
sqlite3 bt.db "select count(*) from bid_bond bn
               join bid b on b.bid_id=bn.bid_id
               join purchase_project p on p.project_id=b.project_id
               where bn.amount > min(0.02*p.estimate, 800000);"

# 2. 逾期退还的笔数与累计天数（期望能出数，用于月度跟踪）
sqlite3 bt.db "select count(*), sum(julianday(refunded_at)-julianday(refund_due))
               from bid_bond
               where refunded_at is not null and refunded_at > refund_due;"

# 3. 卡在「已递交未到账」的投标（最危险的状态）
sqlite3 bt.db "select count(*) from bid b join bid_bond bn on bn.bid_id=b.bid_id
               where b.submitted_at is not null and bn.paid_at is null;"
# 期望 0；不为 0 说明存在「文件收了、钱没到」的悬空投标
```

第 3 步查的是一个**必须为空**的状态：文件已接收但保证金未到账。这类记录一旦存在，开标时到底算不算有效投标，取决于人工判断——而那正是争议的起点。

## 参考资料

- 《中华人民共和国招标投标法实施条例》第二十六条：投标保证金不得超过招标项目估算价的 2%，有效期与投标有效期一致；境内投标单位以现金或支票形式提交的应从其基本账户转出。
- 《中华人民共和国招标投标法实施条例》第三十五条（撤回与退还 5 日）、第三十七条（联合体）、第五十七条（合同签订后 5 日内退还保证金及银行同期存款利息）。
- 《工程建设项目施工招标投标办法》（七部委令第 30 号）第三十七条：投标保证金一般不得超过投标总价的 2%，最高不得超过 80 万元人民币。
- 《中华人民共和国招标投标法》第二十九条：投标人在招标文件要求提交投标文件的截止时间前，可以补充、修改或者撤回已提交的投标文件。
