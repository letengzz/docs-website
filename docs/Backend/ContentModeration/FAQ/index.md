# 常见问题与分诊

审核系统的故障有个共同特征：**现象都很像，原因差很远**。「有违规内容没被删」可能是采样、可能是阈值、可能是策略没生效、也可能是处置失败了。

这一页先给一张分诊表（现象 → 先跑什么 → 翻哪页），再给十二个高频问题，最后是止血顺序与术语表。

本页判据族 `CMF-A` ~ `CMF-H`，共 8 条。

## 一、现象分诊表

| 现象 | 先跑什么 | 最常见真因 | 翻哪页 |
| --- | --- | --- | --- |
| 违规内容大量存在 | 抽 100 条已放行内容人工复核 | 阈值过高或策略未生效 | [策略](../PolicyVerdict/index.md) |
| 加了词表但没用 | 用变体样本打一遍归一化 | 归一化缺步骤（零宽/繁简） | [文本](../TextNormalization/index.md) |
| 视频「审过了」但画面违规 | 查 `moderation_frame` 的帧数与时间戳 | 抽帧间隔大于片段时长 | [媒体](../MediaModeration/index.md) |
| 同一条内容被审了很多次 | 查 `moderation_case` 按 `content_hash` 分组 | 唯一键缺 `intent` 或没建在库上 | [接入](../Intake/index.md) |
| 人审排队几小时 | 算 ρ = 到达率 ÷ 产能 | ρ > 0.85，或分池不均衡 | [队列](../ReviewQueue/index.md) |
| 用户说「内容没了但没人通知」 | 查 `moderation_action_log` 与通知表 | 处置了但通知失败 | [处置](../Enforcement/index.md) |
| 误杀后恢复不了 | 查内容是否被物理删除 | 处置做成了 `DELETE` | [处置](../Enforcement/index.md) |
| 申诉积压 | 查 `moderation_appeal.due_at` 过期数 | 复核人不足或申诉未分诊 | [处置](../Enforcement/index.md) |
| 误杀率突然「变好」 | 查分母是否换了 | 分母从「已处置」换成「提交总量」 | [度量](../Metrics/index.md) |
| 两个审核员结论总不一致 | 算 kappa，不看你一致率 | 判据不可执行、培训不足 | [队列](../ReviewQueue/index.md) |
| 策略改了但没生效 | 查 `policy.state` 是否 `ACTIVE` | 新版本还在 `SHADOW` | [策略](../PolicyVerdict/index.md) |
| 审核服务挂了，业务也挂了 | 断开机审跑一次提交 | 没有降级通路，直接 500 | [总览](../Overview/index.md) |

分诊表的读法是**从上往下**：先确认「有没有审」，再确认「审得对不对」，最后才是「处置有没有生效」。跳过第一步直接调模型，是最常见的白费功夫。

## 二、高频十二问

**1. 关键词表和模型，先上哪个？**
先上关键词 + 白名单，跑通「灰区→人审→处置→申诉」的闭环，再接模型。顺序反了会在没有恢复路径的情况下引入不可解释的判定。

**2. 阈值调多少合适？**
不看「准确率」，看「每天愿意付多少人时」。20,000 条/天、灰区 25.5%、30 秒/条，是三档 `[0.40,0.80)` 下的 27.4 人时；人不够就把下限抬高（减少灰区），而不是把上限降低（放过违规）。

**3. 为什么归一化之后误杀变多了？**
去标点会把相邻两句粘成一个关键词。本机实测误杀率从 7.69% 涨到 23.08%。修法是保留句末标点作边界，先切句再归一化。

**4. 拼音缩写怎么审？**
归一化对它无效（本机 0% 命中）。只能靠行为特征（高频、模板化、新号）与账号画像，不要指望词表。

**5. 视频抽多少帧？**
抽帧间隔要小于「你想抓到的最短违规片段」。想抓 0.5 秒，间隔必须 ≤ 0.5 秒（即 ≥2 fps）；1 fps 时 0.5 秒片段只有 50.9% 命中。

**6. 为什么「删了还能搜到」？**
搜索索引是异步的。处置必须带一条「N 分钟内搜索不可见」的 SLA，并把它写进验收。

**7. 申诉期内要不要先恢复内容？**
不要。申诉期内状态不变（不加严也不恢复），否则「申诉即认罪」或「申诉即放行」都会让指标失真。

**8. 谁来执行撤销？**
必须是与原下架人不同的第二人。同一个人可下架可恢复，审计上无法区分纠错与放水。

**9. 误杀率能不能直接报申诉成功率？**
不能。它只覆盖「愿申诉且复核正确」的那部分，是下界。要报就报「抽检估计 + 区间 + 样本量」。

**10. 策略灰度按什么分桶？**
按 `subject_id` 哈希，保证同一用户不跳变。按请求随机分桶会让同一用户一会严一会松。

**11. 审核挂了能不能先放行？**
不能默认放行。放行意味着故障窗口内的内容没有审核记录，事后无法补审、无法统计影响面。正确做法是拒绝新提交或降级为人审。

**12. 需要给模型结果做缓存吗？**
需要，但键必须是 `(content_hash, model_version, policy_version)`。少一个维度就会在模型升级后返回旧结果。

## 三、止血五步

线上出现「违规内容大面积可见」时，按这个顺序做，**不要跳步**：

1. **先止血再定位**：把该场景的策略切到保守档（上限调低），或用上一版 `ACTIVE` 策略。目标是让新增违规停下来。
2. **确认范围**：按 `scene` + 时间窗统计受影响内容量，决定是否需要批量重判。
3. **批量重判**：用新策略对时间窗内的 `moderation_case` 重跑，产出待处置清单。重判要写新的 `verdict` 行（带新 `policy_version`），不要覆盖旧行。
4. **批量处置**：按清单执行状态迁移，走同一个幂等守卫；每批不超过 1,000 条，处置后抽查 20 条。
5. **写清楚记录**：时间窗、策略版本、影响条数、处置条数、恢复条数。这份记录是后续所有解释的唯一依据。

::: danger 止血时最常犯的三个错
1. **直接改数据库**：绕过状态机与审计，事后无法解释「谁在什么时候改了什么」。
2. **一次性处置全量**：10 万条一起改，出了错无法回滚。按批走，每批留检查点。
3. **只改阈值不重判**：新阈值只影响新内容，已放行的违规内容仍在线上。
:::

## 四、术语表

| 术语 | 含义 | 易混点 |
| --- | --- | --- |
| 漏放（FN） | 违规内容被判为通过 | 与「漏检」不同，后者指模型没检出特征 |
| 误杀（FP） | 合规内容被判为违规 | 与「限流」不同，限流不是误杀 |
| 灰区 | 分数落在两条阈值之间的内容 | 不等于「不确定」，它是**必须人审** |
| ρ（利用率） | 到达率 ÷ 处理能力 | 不是 CPU 使用率 |
| kappa | 校正后的一致性系数 | 不是一致率 |
| 内容寻址 | 用内容哈希定位存储 | 不是「按 ID 查」 |
| 存活规则 | 合并多条记录时每个字段取谁的值 | 与「去重」不是一回事 |
| 影子策略 | 只算分不生效的策略版本 | 不是灰度，灰度是生效但只对小部分人 |
| 级联 | 处置一条内容时连带影响的对象 | 不是「批量处置」 |
| 回流 | 把申诉/复核结果变成训练或评估样本 | 不是「归档」 |

## 五、上线前自查清单

二十项里，前五项是**必须**，其余按场景取舍：

| # | 检查项 | 判据 |
| --- | --- | --- |
| 1 | 有 `moderation_case` 账本 | 每条提交都能查到一行 |
| 2 | 有恢复路径且演练过 | 演练记录含执行人、耗时、审计条数 |
| 3 | 唯一键建在库上 | 并发 20 次提交只产生 1 条 case |
| 4 | 判定结果含 `signals` 与 `span` | 任取一条能在原文高亮 |
| 5 | 审核故障时业务不 500 | 断开机审返回 202 或降级 |
| 6 | 三档 band 覆盖完整 | `A2` 为 0 行 |
| 7 | 策略可按 `scene` 配置 | 改一个场景不影响其他 |
| 8 | 新策略先 `SHADOW` | 有影子期记录 |
| 9 | 回滚是一行状态切换 | 耗时 < 1 分钟 |
| 10 | 归一化有原文字符映射 | 命中能回到原文区间 |
| 11 | 零宽字符被清理 | 插入 U+200B 的样本照常命中 |
| 12 | 视频抽帧间隔 ≤ 目标片段时长 | 配置里可查 |
| 13 | 图像三路并联 | 关掉 OCR 后漏放上升 |
| 14 | 短文本去重用 Jaccard | 阈值 0.5 时召回 ≥95% |
| 15 | 人审 ρ 有告警 | ρ > 0.85 触发 |
| 16 | 时延报 p95 | 报表无均值单列 |
| 17 | 抽检覆盖两路 | `audit_sample` 有 `auto_pass` 与 `human_pass` |
| 18 | 撤销需第二人 | 触发器拒绝同人操作 |
| 19 | 处置有通知且含申诉入口 | 通知模板逐项核对 |
| 20 | 指标带样本量与分母 | 报表表头可见 |

## 六、本页判据

| 编号 | 判据 | 为什么要它 | 怎么验证 |
| --- | --- | --- | --- |
| `CMF-A` | 分诊表必须先判「有没有审」再判「审得对不对」 | 顺序反了会白调模型 | 分诊表前两行都与「是否落库」有关 |
| `CMF-B` | 每条现象对应一条可执行命令 | 不可执行的分诊等于没有 | 随机抽 3 行，命令能跑 |
| `CMF-C` | 止血顺序中「先止血」在「定位」之前 | 定位耗时以小时计 | 值班手册顺序一致 |
| `CMF-D` | 批量处置必须分批（≤1,000/批）并可回滚 | 全量处置出错无法回滚 | 处置脚本有 `--batch` 参数 |
| `CMF-E` | 重判写新 `verdict` 行，不覆盖旧行 | 覆盖会毁掉证据 | 重判后同一 case 有多行判定 |
| `CMF-F` | 上线条目的前五项是硬门槛 | 缺一项就不该上线 | 发布检查单勾选状态 |
| `CMF-G` | 术语表至少覆盖十个易混词 | 术语不统一会导致口径分叉 | 术语表行数 ≥ 10 |
| `CMF-H` | 每个「常见问题」都指向具体页面或判据 | 否则回答无法复核 | 十二问中至少八问带链接 |

## 七、验证方式

```shell
# 1) 分诊表里的命令至少能跑通三条（以「查重复审核」为例）
sqlite3 /tmp/cm.db "SELECT content_hash, COUNT(*) c FROM moderation_case
                     GROUP BY content_hash HAVING c > 3 LIMIT 5;"
# 预期：0 行或少量行；有大量行说明唯一键没生效

# 2) 止血顺序的第 1 步：切回上一版 ACTIVE 策略
sqlite3 /tmp/cm.db "UPDATE policy SET state='RETIRED' WHERE policy_id='ugc.comment' AND state='ACTIVE';
                    UPDATE policy SET state='ACTIVE' WHERE policy_id='ugc.comment' AND version=1;"
sqlite3 /tmp/cm.db "SELECT policy_id, version, state FROM policy WHERE policy_id='ugc.comment';"
# 预期：只有一行 ACTIVE
```

```sql
-- 3) 批量处置必须可统计（用于止血记录）
SELECT action, COUNT(*) FROM moderation_action_log
 WHERE created_at >= '2026-11-07T00:00:00Z' GROUP BY action;
-- 预期：每个动作一行，总数与处置清单一致
```
