# 常见问题与最佳实践

## 高频问题

### 1. 小项目能用 DDD 吗？

能用但通常不值得。DDD 的固定成本（建模讨论、对象转换、分层纪律）不随项目大小缩水。判据是**业务复杂度**而不是团队规模：规则多、会演化、要长期维护的系统，哪怕两个人写也值得建模；反之，几十人的团队做 CRUD 中台，DDD 只会让大家怨声载道。先读[概述](../Overview/index.md)的「不该用」清单。

### 2. 贫血模型到底有什么问题？我一直这么写也没事。

业务简单时确实没事——贫血模型的问题在**业务复杂后**才显现：同一条规则被复制到 N 个调用点、状态被随处 set 导致非法状态频繁出现、新人无法从代码读出业务规则。判据见[仓储一章](../Repository/index.md)的对照表。注意纠偏方式是**渐进的**：先把最核心的一两个聚合做成充血，不必全盘推翻。

### 3. 聚合到底怎么切？有没有可操作的步骤？

有，三步（详见[聚合设计](../Aggregate/index.md)）：

1. 列出该领域所有**不变量**（「任何时候都必须为真」的条件）；
2. 不变量必须**在同一事务内**成立的，归入同一聚合；
3. 检查：聚合超过五条不变量 → 太大，考虑拆；一个不变量需要跨两个聚合维护 → 切错了，合并或改事件。

### 4. 限界上下文是一个微服务吗？

不一定是。「上下文 ↔ 微服务」是**一种**映射，模块化单体里上下文就是一个包。正确顺序是：先划上下文（逻辑边界），再决定部署形态（物理边界）——而且默认先不拆，见[落地架构](../Architecture/index.md)。

### 5. 领域服务和应用服务区别记不住，有没有一句话？

**应用服务知道「谁在调、开不开事务、发不发消息」，领域服务只知道「业务规则本身」**。把方法名念给业务人员：听得懂 → 领域层；涉及流程设施 → 应用层。详见[战术设计](../TacticalDesign/index.md)。

### 6. DDD 和 MyBatis 能一起用吗？

能。仓储模式不绑定 ORM：MyBatis 实现仓储接口完全可行（Mapper 封装在仓储实现内部，领域层只见接口）。MyBatis 的用法见 [MyBatis 专题](../../Java/Frame/MyBatis/index.md)。

### 7. 事件消费失败怎么办？

Outbox 模式下事件**必然可重投**，所以消费方必须幂等（按事件 ID 去重）。超过重试次数进死信/告警，人工介入。完整链路见[领域事件](../DomainEvent/index.md)。

### 8. 事件溯源（Event Sourcing）是什么？要用吗？

事件溯源把「事件」从通信手段升级为**唯一事实来源**（存状态变迁序列，当前状态由重放得出）。它带来审计、时间旅行等能力，也带来版本迁移、快照、重放性能等一整套复杂度。**默认不用**；审计与合规需求极强、事件模型天然稳定的领域（账务、风控）再评估。

## 反模式清单

::: danger 十大反模式
1. **表镜像建模**：模型 = 数据库表的逐字段映射，模型失去行为。
2. **上帝聚合**：把一个业务对象的所有关联数据塞进一个聚合，事务互相阻塞。
3. **无 setter 却有 setXxx**：领域对象留着一排公开 setter，充血名存实亡。
4. **事件泛滥**：上下文内部的方法调用也走事件，链路调试成本剧增。
5. **假防腐层**：防腐层里直接透传外部模型对象，翻译层名存实亡。
6. **共享大内核**：多个上下文共享一大坨「公共实体库」，改一处全线回归。
7. **微服务化早于建模**：先拆服务再补模型，拆分依据是调用次数而非限界上下文。
8. **DDD 框架化**：以为引入某个框架就算落地 DDD，模型讨论一次没开过。
9. **仓储 DAO 化**：仓储接口长满 `updateXxxField`，聚合整体一致性的保证失效。
10. **读侧也走聚合**：列表页用聚合逐条重建，性能崩坏后反过来怪 DDD。
:::

## 上线前自查表

| # | 检查项 | 通过判据 |
| --- | --- | --- |
| 1 | 每个上下文有术语表且与代码命名一致 | 抽查 5 个核心类名能在术语表里找到 |
| 2 | 每个聚合有不变量清单（≤5 条）且每条有测试 | 领域层测试覆盖全部不变量 |
| 3 | 状态字段无公开 setter | `grep` 检查通过 |
| 4 | 聚合间无对象引用（只存 ID） | 编译期 import 检查通过 |
| 5 | 事务方法只写一个聚合根 | `@Transactional` 审查通过 |
| 6 | 模块边界有 `verify()` 测试且进 CI | 构建失败可复现（故意违规一次） |
| 7 | 跨上下文事件走 Outbox 且消费幂等 | 重投一次数据状态不变 |
| 8 | 读侧查询不走聚合重建 | 列表接口 P95 达标 |
| 9 | 领域层无 IO 与框架依赖 | import 检查通过 |
| 10 | 「要不要 DDD」的结论有记录 | 设计文档中写明核心子域判断 |

## 一句话总结

::: tip
DDD 不是「更多的层和更多的类」，而是**把业务规则放回模型里、把模型边界画清楚、把边界变成可执行的测试**。三件事都做到，架构自然浮现；只做到第一件，你只是多写了几层包。
:::
