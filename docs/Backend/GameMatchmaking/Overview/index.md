# 总览：三个「他有多强」与七个写入点

凌晨两点，值班工程师收到一条工单：「我连胜十把，段位没动，是不是有挂？」他打开后台，看见这名玩家的 MMR 从 1,504 涨到了 1,600，而显示分只从 1,502 变成 1,518——因为在 1,500 分这个区间，段位晋升需要 100 分，而系统只把 MMR 的 1/7 映射成显示分。三个数都是对的，玩家看到的那个恰好是最不敏感的那个。

**匹配系统的复杂度不在「谁更强」，而在于它必须同时维护三套「强」的定义，并且让三套之间的换算关系是可解释的、稳定的、能事后复算的。** 推荐系统只需要一个排序，匹配系统需要三个可比较的量加一张可对账的表。

::: tip 一句话理解
MMR 是**估计**，显示分是**承诺**，段位是**分位数**。估计可以天天变，承诺必须一次说清，分位数只在赛季边界重划。
:::

## 一、九个数字，三个来源

![三个「他有多强」：真实实力、隐藏 MMR、显示段位分](../assets/mk-dupe.svg)

一局对局结束后，系统里会同时出现九个数字：

| 问题 | 口径一 | 口径二 | 口径三 | 本机实测的差距 |
| --- | --- | --- | --- | --- |
| 他有多强 | 真实实力（未知） | 隐藏 MMR | 显示段位分 | 段内跨度 **327 分** |
| 这局多公平 | 纸面胜率 | 局内实力跨度 | 赛后分数变化 | 跨度 >500 分的局 **2.4%~44.7%** |
| 他排第几 | 分数排名 | 段位排名 | 榜单名次 | 同分并列最大 **27 人** |

九个数字里，**只有「显示段位分」是承诺给玩家的**，其余八个都是从数据里算出来的。算错了不会报错——它会安静地变成一个「看起来完全正常」的段位。

### 为什么不能只留一个

很多人第一反应是「统一口径」：配对、结算、展示都用 MMR。这在真实系统里做不到，因为三者的更新频率与容错完全不同：

| 口径 | 更新频率 | 谁在用 | 换掉它的后果 |
| --- | --- | --- | --- |
| 真实实力 | 不变（不知道） | 评测、实验 | 拿它配对等于作弊，实验结论无法迁移 |
| 隐藏 MMR | 每局 | 配对、风控 | 直接公开 → 玩家开始「算分」而不是「打游戏」 |
| 显示段位分 | 每局或每段 | 玩家、奖励、社交 | 只留 MMR → 玩家看不到进度，流失 |

所以正确做法不是「统一」，而是**三个都存、明确谁是权威、换算关系单独成表**。这也是本册反复出现的模式：`player` 存 `mmr` 与 `rd`（而不是只存算好的段位），`season_point` 与 `mmr` 分开记，`mmr_history` 按 `reason` 分四类（而不是只存最终值）。

::: danger 三个「只存结果」的建模错误
1. **只存 `tier` 不存 `mmr`**：赛季一改分档线，历史段位无法重算；玩家来问「我上赛季为什么是钻石」，你只有「钻石」两个字，没有依据。
2. **只存一个 `score` 字段**：配对用 MMR、展示用 LP、奖励用赛季分，三者混在一个字段里，任何一次调整都要靠人工还原。
3. **只存 `delta` 不存 `before` / `after`**：`mmr_history` 只记增量，「这局之前他多少分」永远查不到，回滚与申诉都没有依据。本册的 `trg_settle_apply` 强制同时写三列。
:::

## 二、七段链上，失败都长什么样

| 段 | 输入 | 输出 | 典型失败 | 谁能发现 |
| --- | --- | --- | --- | --- |
| 建池 | 玩家点击匹配 | `queue_ticket`（含分快照） | 快照取的是「进池时的分」，中途结算了也不更新 | **几乎无人发现** |
| 评分 | 一局胜负 | `player.mmr` | K 值写死，强者上分太慢 | 玩家抱怨「赢了不加分」 |
| 配对 | 池内票据 | `match` | 窗口放宽后凑出跨度 500 分的局 | 玩家抱怨「队友太菜」 |
| 开局 | 十个人 | `match_player` | 有人没点确认，局卡在 RUNNING | 显性（能看见） |
| 结算 | 对局结果 | `settle_log` | 重试导致重复加减分 | **几乎无人发现** |
| 赛季 | 时间边界 | `season_id` | 跨零点对局归错季 | **几乎无人发现** |
| 榜单 | 全量分数 | 名次 | 同分排序不稳定，两次刷新名次不同 | 玩家截图对比 |

后三段里有两段的失败「几乎无人发现」，是因为它们不影响任何一局的正确性：分数自洽、记录自洽、榜也刷了，只是**多加了分、归错了季、名次飘了**。本机读数里，无幂等键的结算在网关重试 3 次后从 1,518 变成 1,554——而所有 `match` 行的状态都是 `SETTLED`，看起来一切正常。

## 三、四个必失的接缝

匹配系统有四道接缝，只要不专门处理，就一定会裂：

1. **分数的接缝**：MMR 与显示分之间。本机把显示分取整到 10 分，与 MMR 的平均差 2.50 分——单看不致命，但它意味着「同一显示分的两个人，MMR 可能差 10 分」，而配对只看 MMR。
2. **人数的接缝**：5v5 的队伍里有人掉线。按队均分算，4v5 的胜率 50.21%（几乎没惩罚）；按队总分算，只剩 **7.29%**。选错实力函数，掉线判定全线失效。
3. **时间的接缝**：赛季边界与对局时长。一场 42 分钟的对局跨过零点，按开始与按结束会给出两个赛季。
4. **重试的接缝**：网关超时与客户端重连之间。玩家看到的「网络错误」在服务端可能已经成功，重试是常态而不是异常。

::: warning 一个反直觉的结论
**分差越大，Elo 越不准。** 本机把预测胜率分五档回测：预测 60%~80% 的对局，实际胜率 **72.2%**；预测 80%~100% 的，实际 **90.6%**。也就是说，模型系统性地**低估强者**——因为 400 分标尺是线性近似的，而真实实力差在尾部是指数的。这不是 bug，是模型假设的边界；知道它，才会在「炸鱼检测」里用别的信号而不是只看胜率。
:::

## 四、判据族 `MKO-A ~ MKO-H`

本页判据族 `MKO-A` ~ `MKO-H`，共 8 条。它们描述「三个分数是否都被留存、且换算关系可复算」。

| 编号 | 判据 | 怎么验 |
| --- | --- | --- |
| `MKO-A` | `player` 同时存 `mmr` 与 `rd`，段位是**算出来的**而不是写进去的 | 全表检索无 `tier` 的直接赋值语句 |
| `MKO-B` | 显示分与 MMR 的换算关系写在视图或函数里，且只有一处 | 改换算系数只需改一处，两处结果同步变化 |
| `MKO-C` | `mmr_history` 至少记 `before` / `after` / `reason` 三列 | 任取一行，`after − before` 等于对应的 `settle_log.delta` |
| `MKO-D` | 对局行带 `season_id`，不由结算时刻推导 | 23:58 开赛的对局，`season_id` 与开赛时刻同季 |
| `MKO-E` | 结算记录以 `(match_id, player_id)` 为主键 | 同一对同一人第二次插入报唯一约束 |
| `MKO-F` | 队伍实力函数在代码里只有一处，且注明「均值或总和」 | 4v5 的期望胜率能算出一个数，不是两套 |
| `MKO-G` | 榜单排序键含 `player_id` 兜底 | 同分两行，两次查询顺序一致 |
| `MKO-H` | 同一 `match_id` 的重复提交被唯一键挡住 | 相同 `idem_key` 第二次插入报错 |

## 五、验证方式

```shell
# 1. 三个分数是否都在（期望 3 个字段，且段位是生成列）
sqlite3 :memory: "
create table player(mmr real, rd real,
  tier text generated always as (case when mmr>=1800 then '王者'
    when mmr>=1600 then '宗师' else '钻石' end) virtual);
insert into player(mmr,rd) values (1810,60);
select mmr, rd, tier from player;"
# 期望输出：1810.0|60.0|王者

# 2. 换算关系是否只有一处（期望 2 行同比例）
sqlite3 :memory: "
create table p(id int, mmr real);
insert into p values (1,1500),(2,1800);
select id, mmr, round(1000 + (mmr-1000)*0.7) as lp from p;"
# 期望输出：1|1500.0|1350.0 与 2|1800.0|1560.0

# 3. 结算能否写第二次（期望报唯一约束）
sqlite3 :memory: "
create table settle_log(match_id text, player_id text, delta real,
  primary key(match_id, player_id));
insert into settle_log values ('M1','P1',16);
insert into settle_log values ('M1','P1',16);"
# 期望输出：Error: stepping, UNIQUE constraint failed: settle_log.match_id, settle_log.player_id (19)
# 退出码 19——拦住它的不是「查不到」，是「插不进」
```

三步的输出就是本册的起点：**段位必须能重算、换算必须唯一、结算必须只有一次**。任何一步拿不到期望值，后面九章的判据都不成立。
