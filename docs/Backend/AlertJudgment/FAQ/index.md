# 常见问题：八个被反复问到的判断题

这八问几乎每季度都会被问一次，答案都指向同一条原则：**先把身份和出口定下来，再谈阈值**。

本页判据族 `ALQ-A` ~ `ALQ-H`，共 8 条。

## 一、Prometheus 够用吗，什么时候要自研

**先用现成的，直到你被三件事之一卡住**：

| 卡点 | 表现 | 现成方案的上限 |
| --- | --- | --- |
| 基数 | 单实例序列数 > 数百万，内存扛不住 | Prometheus 单机按内存算，通常百万级序列 |
| 多租户 | 每个团队要独立视图与配额 | 原生多租户需要 Thanos/Mimir 一类方案 |
| 判定逻辑 | 需要跨时间窗的复杂状态（如「连续 3 天都高」） | PromQL 表达力可以，但规则会变得不可读 |

第三条常被低估：写在 YAML 里的复杂 PromQL 是不可测试、不可复用的。当一条规则需要 30 行表达式和 5 个 `and` 时，它应该变成一个服务，而不是一段配置。

## 二、`for` 到底设多少

**按业务反推，不按经验值**：`for ≈ 可容忍最短真故障 × 0.7`，同时满足 `for ≥ 2 × 步长` 与 `for ≤ 响应预算 / 3`。

三个数取交集。若交集为空（业务要求 30 秒的故障也报，但步长是 60 秒），那不是配置问题，是**采集成本问题**——必须先降步长，再谈 `for`。详见[规则状态机](../RuleState/index.md)。

## 三、告警发了，但没人看到，问题在哪

按四段排查，顺序不能反：

1. **有没有认领字段**：没有 → 派发链缺一段，先补字段（见[路由](../Routing/index.md)）。
2. **有没有解析到人**：通知只发到了群，没有 `@` 具体的人 → 路由配置问题。
3. **有没有在值班表里**：解析到的人当时不在岗 → 值班表有洞或时间区错了。
4. **通道有没有回执**：无回执的通道只能算知会 → 换通道或加确认动作。

四步里前三步都能用 SQL 查，第四步只能靠通道能力。

## 四、同一故障每天来一次，怎么办

先分清是「同一故障」还是「同一现象」：

- **指纹相同**：那是复发性故障，应该改的是**根因**，不是告警。把它标记为 `recurring`，每月统计一次，进排期。
- **指纹不同**：说明指纹里有易变标签（pod、实例），按[指纹](../Fingerprint/index.md)那一页修。
- **指纹相同但时间规律**：常见于定时任务、批处理窗口。正确做法是**在窗口内置静默**（有到期时间），而不是关掉告警。

最差的处理是「把阈值调高到它不再触发」——那会让真正的恶化也一起消失。

## 五、抑制和静默怎么选

看「这个判断该由谁负责」：

| 场景 | 选 | 理由 |
| --- | --- | --- |
| 根因告警存在时，衍生告警不该发 | 抑制 | 逻辑稳定，可写进规则文件评审 |
| 今晚要发版，已知会有 10 分钟抖动 | 静默 | 一次性、有明确时间窗、有人负责 |
| 长期不想看某类告警 | **两个都不对** | 应该删规则或降级为工单 |

第三行是重点：抑制和静默都是「临时的信息裁剪」，不是「永久的功能下线」。用它们做长期屏蔽，等于把一个探测器悄悄拆掉。

## 六、告警要不要发到大群

**不要发「告警」，可以发「状态」**。

- 告警是**指派**：它必须有责任人，发到群里就没有责任人了。
- 状态是**知会**：一张「当前 P0/P1 列表」的看板或定时播报，适合放群。

判据：这条消息需要有人「立刻做点什么」吗？需要 → 发给个人；不需要 → 发群或看板。

## 七、P0~P3 分级够用吗

**够用，但分级的依据常常写错**。

正确的分级依据是**影响的用户面 × 可绕过性**，不是「技术严重程度」：

| 级别 | 依据 | 响应 |
| --- | --- | --- |
| P0 | 核心链路不可用，无法绕过 | 立刻叫醒 |
| P1 | 核心链路降级，有绕过方案 | 30 分钟内 |
| P2 | 非核心功能异常 | 当班处理 |
| P3 | 趋势性风险，尚未影响用户 | 排期 |

常见错误是「按指标越线程度分级」：CPU 90% 就定 P1。CPU 高不一定影响用户——它应该是「容量类 P3」，而不是「可用性 P1」。

## 八、谁来监控告警系统本身

**三条心跳，缺一不可**：

1. **规则在评估吗**：一条 `always firing` 的 Watchdog 告警，它停了就说明评估停了。
2. **通知能出去吗**：定期发一条测试通知到每个通道，失败即告警（用另一条通道发）。
3. **有人在看吗**：`acked_at` 的空置时长 p99，超过阈值说明派发链断了。

第 3 条最容易被忽略：前两条能证明「系统在跑」，只有第三条能证明「系统在起作用」。

::: danger 监控告警系统的告警，不能走同一条通道
用同一个 Alertmanager、同一个通道去监控它自己，会在通道故障时同时失去「告警」和「关于告警的告警」。至少要有第二条独立通道（例如一个只发短信的最小脚本）。
:::

| 编号 | 判据 | 为什么要它 | 怎么验证 |
| --- | --- | --- | --- |
| `ALQ-A` | 自研的触发条件是「基数 / 多租户 / 判定复杂度」三者之一 | 否则是重复造轮子 | 有书面决策记录 |
| `ALQ-B` | `for` 由业务反推，且三个约束都写下来 | 经验值不可解释 | 规则注释含三行算式 |
| `ALQ-C` | 通知必须有「解析到唯一人」的能力 | 群通知不等于派发 | 任一通知可查接收人 |
| `ALQ-D` | 复发性故障进排期，不用调阈值掩盖 | 调阈值会连恶化一起藏起来 | 有 `recurring` 标记与月度统计 |
| `ALQ-E` | 长期屏蔽必须删规则或降级，不用静默 | 静默是临时手段 | 静默最长有效期有上限 |
| `ALQ-F` | 告警只发给责任人，状态才发群 | 群通知会稀释责任 | 路由目标是个人/值班组 |
| `ALQ-G` | 分级依据是用户面 × 可绕过性 | 按指标程度分级会误判 | 分级表有这两列 |
| `ALQ-H` | 告警系统自身有三条心跳，且走独立通道 | 同通道会同时失效 | 三条心跳都能看到最近一次成功时间 |

## 十、验证方式

```shell
# 1) 「有人在看」的度量：最久未被认领的 firing 实例
sqlite3 alerts.db "SELECT id, service, fired_at FROM alert_instance
  WHERE state='firing' AND acked_at IS NULL
  ORDER BY fired_at LIMIT 5;"
# 预期：最早的一条不超过 15 分钟。超过 = 派发链断了，不是「告警太多」
```

```text
# 2) Watchdog 心跳是否还在
ALERTS{alertname="Watchdog",alertstate="firing"}
# 预期：恒为 1。变成空 = 评估或通知链路已停
```

```sql
-- 3) 静默有效期是否被滥用
SELECT id, matcher_key, starts_at, ends_at FROM silence
WHERE julianday(ends_at) - julianday(starts_at) > 30;
-- 预期：0 行。有行 = 把静默当长期屏蔽用
```

第三条是一个组织问题的技术投影：超过 30 天的静默，几乎总是「不想修但也不想被叫」。
