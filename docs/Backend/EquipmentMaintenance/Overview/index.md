# 总览：七段链与三个「好了」

<p style="text-align:center;"><img src="../assets/em-logo.png" alt="设备维护与可靠性工程" style="zoom:75%;" /></p>

设备管理的所有争议，最后都会落回同一句话：「**这台设备现在到底算不算好？**」生产说好——它在转；维修说不好——它上周停了三次；财务说很好——它的账面净值还在。三句话都对，因为它们量的根本不是同一件事。

本页判据族 `EQM-A` ~ `EQM-H`，共 8 条，定义在第七节。

## 一、三个「好了」：动作、状态、判断

![七段维护链：七段里五段的失败是安静的](../assets/em-chain.svg)

| 层次 | 判断依据 | 谁在判断 | 错了会怎样 |
| --- | --- | --- | --- |
| **动作好了** | 工单状态到了 `CLOSED` | 维修班组 | 关闭了一张「其实只临时处理」的工单，下次故障在三天后 |
| **状态好了** | 设备当前 `RUNNING` | 生产班组 | 能转，但振动已进 C 区，下一次失效在两周内 |
| **判断好了** | β、间隔、备件、冗余四件事同时成立 | 维护工程 | 这四个条件不成立时，前两个「好了」只是运气 |

前两个是**事件的闭合**，第三个是**规律的确认**。系统如果只记前两个，最后会得到一个很奇怪的局面：工单关闭率 98%、设备在线率 99%，但非计划停机一年比一年多。

::: tip 一句话分清
**「修好了」是关于过去的一次性事实；「不会再这样坏」是关于未来的一个可被推翻的假设。** 维护工程的全部工作，是把第二个变成可检验的假设——用 β、间隔、备件与冗余四个参数把它钉住。
:::

## 二、七段链：每一段的产物与失败方式

| 段 | 关键动作 | 产物 | 失败方式 | 多久之后暴露 |
| --- | --- | --- | --- | --- |
| ① 建 | 编位置号、编设备号、定关键性 | 台账 | 只有一层「设备清单」，没有位置树 | 想按产线汇总停机时 |
| ② 定 | 选策略、算间隔、排到期日 | 维护计划 | 全部设成「每月一次」 | 一年后维护费涨、故障没降 |
| ③ 检 | 设测点、定阈值、记数值 | 点检记录 | 只记「已检查」勾 | 出事后翻不到任何数值 |
| ④ 修 | 报修、派工、开工、完工、关单 | 工单 + 停机区间 | 停机不挂工单 | 算 MTTR 时发现没有时长 |
| ⑤ 备 | 定安全库存、领用、修复回库 | 库存 + 流水 | 关键件零库存 | 停机 6 小时后才发现要等 21 天 |
| ⑥ 算 | 定分母、取并集、拆 OEE | 报表 | 分母各写各的 | 两个部门月度会上吵 |
| ⑦ 验 | 拟合 β、算冗余、回写间隔 | 参数 | 从不回写 | 每年重复同一个错误决定 |

七段里只有第 ④ 段会当场报错（关单必须填完工时间）。**其余六段的共同点是：不做也不会有人来问。** 这正是这类系统最难推动的原因——它的价值全部体现在「没发生的事」上。

## 三、四个基础量：先把定义钉死

设备工程里最常被混用的四个词，来自 RAMS 框架：

| 量 | 英文 | 定义 | 本机读数（200 台 / 一年） |
| --- | --- | --- | --- |
| 可靠度 | Reliability, R(t) | 在 `[0, t]` 内不失效的概率 | 由 Weibull 描述，β = 2.2 时 900 h 内约 37% 存活 |
| 可用度 | Availability, A | 可工作时间 ÷ 应工作时间 | 负荷口径 **99.70%**、日历口径 **81.75%** |
| 可维修度 | Maintainability, M(t) | 给定时间内修好的概率 | 由 MTTR 分布描述，本例 MTTR **56.9 min** |
| 维护性 | Maintenance supportability | 备件、工具、人力到位的能力 | 备件即时满足率 **71.9%** |

::: danger 四个量里最容易错的是「可用度」
`A = MTBF / (MTBF + MTTR)` 只在「单台、可修复、稳态」三个前提下成立。同一个 200 台车间的同一批停机数据，能算出三个都「正确」的可用率：

- 日历口径：`85,939,298 / 105,120,000 = 81.75%`（把周末不排产也算成「应工作」）
- 负荷口径：`85,939,298 / 86,198,400 = 99.70%`（先扣掉计划停机）
- MTBF 口径：`17,147 / (17,147 + 56.9) = 99.67%`（按事件平均）

极差 **17.92 个百分点**。三个数字都能自圆其说，所以报表上**必须同时给出分母**，否则开会时一定吵。
:::

## 四、五个必失点（每条都有本机读数）

### 4.1 停机区间求和，而不是取并集

一次停机常被登记成两条：机械故障 + 等备件。本机 200 台设备、5,012 条停机事件：

| 口径 | 数值 | 说明 |
| --- | --- | --- |
| 区间直接求和 | 285,172 min | 每条记录各算一遍 |
| 区间并集 | 259,102 min | 同一设备重叠部分只算一次 |
| 重复计入 | **26,070 min = 9.1%** | 28% 的事件带并发归因 |

9.1% 的误差不会让报表崩掉，它只会让「停机最多的前五台」排序出错——而排错序的直接后果是改善资源投错了设备。

### 4.2 短停机被丢弃，MTBF 虚高

| 过滤条件 | 事件数 | MTBF | 可用率 |
| --- | --- | --- | --- |
| 不过滤 | 5,012 | 285.8 h | 99.67% |
| 忽略 < 5 min | 4,089 | 350.3 h | 99.67% |
| 忽略 < 15 min | 3,367 | 425.4 h | 99.68% |

`< 5 min` 的事件只占条数 18.4%、占时长 1.0%，却能让 MTBF 涨 **22.6%**，而可用率几乎不动。**这说明 MTBF 与可用率在短停机面前是脱钩的**：一个只看「多久坏一次」，一个还看「坏一次修多久」。

### 4.3 点检完成率不等于检查做了

本机 60 台设备 × 30 天 = 1,800 条应检：

- 实际记录 1,635 条 → 完成率 **90.8%**
- 其中落在交班前 10 分钟内的 **1,037 条 = 63.4%**
- 连续漏检超过 3 天的空档 **6 处，最长 12 天**

完成率越高、且越集中在交班前，越说明这套点检是「补出来」的。

### 4.4 报修不去重，维修工时被放大

1,623 条上报，按 `(设备, 故障码, 15 分钟窗口)` 合并后剩 1,199 张工单，合并 **26.1%**。若按「每张工单平均时长 × 工单数」统计维修工时，会虚增 **35.4%**。

### 4.5 关键件没有安全库存

2,400 次备件需求里，即时满足 1,726 次，缺件 **674 次**（满足率 **71.9%**）。缺的那 674 次里有相当一部分直接变成等件停机——**而等件停机在停机报表里通常被记成「其他」**。

## 五、五个「先别上系统」的判据

在买 CMMS/EAM 之前，先看这五条能不能自己回答。五条里超过两条答不上来，上系统只会把混乱搬进数据库：

1. **同一台设备，你在三个地方（资产册、财务、车间看板）的编号是不是同一个？**
2. **一次停机，你能说出它的开始时刻是谁记的、精度到分钟还是班次？**
3. **B 类以上设备，有几台做过失效分布分析（哪怕只有 10 个失效样本）？**
4. **最近一年，有没有哪条维护计划因为失效数据被改过间隔？**
5. **关键备件的安全库存，是按服务水平算的还是按「感觉」填的？**

## 六、最小起步三步

不需要先建完台账再动。三步之内就能跑出一个能对账的闭环：

```shell
# 1) 建最小七表（设备、计划、工单、停机、备件、领用、点检）
sqlite3 /tmp/mnt.db < schema.sql
# 期望：.tables 输出 7 张 eq_ 开头的表

# 2) 只灌 10 台 A 类设备 + 近 90 天停机
sqlite3 /tmp/mnt.db "SELECT count(*) FROM eq_asset WHERE criticality='A';"
# 期望：10（先做 A 类，别一次全铺）

# 3) 算一次「并集口径」的可用率
sqlite3 /tmp/mnt.db "SELECT ROUND(100.0*(8760*10 - sum((julianday(end_at)-julianday(start_at))*24))/(8760*10),2)
                      FROM eq_downtime WHERE end_at IS NOT NULL;"
# 期望：一个 95~99.9 之间的数；与车间口头数字差 5 个点以上，说明分母或并集口径不一致
```

## 七、判据清单

| 编号 | 判据 | 怎么验 |
| --- | --- | --- |
| `EQM-A` | 台账同时有「功能位置」与「设备」两层，且停机可按位置向上汇总 | 位置树有 `parent_id`，停机表挂在设备上、设备挂在位置上 |
| `EQM-B` | 三个「好了」分别有字段承载，不共用一个状态位 | `wo.state` / `asset.status` / `plan.next_due_at` 三者独立 |
| `EQM-C` | 可用率报表必须同时给出分母与时区口径 | 报表字段含 `basis` 与 `tz` |
| `EQM-D` | 停机时长按区间并集计算，不是求和 | 同一设备重叠区间只计一次 |
| `EQM-E` | 短停机（< 5 min）计入条数统计，并在 MTBF 页面单独披露 | MTBF 页有「含/不含短停」两行 |
| `EQM-F` | 点检记录带测点、数值、判定与测量时刻 | `eq_inspect` 四列齐全，且 `at` 是测量时刻 |
| `EQM-G` | 报修有去重键，重复上报合并成一张工单 | `(asset_id, fault_code, 时间窗)` 唯一 |
| `EQM-H` | 可靠性参数（β、间隔）有回写路径到维护计划 | `eq_plan.interval_h` 能追溯到一次参数校准记录 |

## 八、验证方式

```shell
# 1) 三个分母的可用率应各不相同
sqlite3 /tmp/mnt.db "SELECT ROUND(100.0*sum(CASE WHEN end_at IS NULL THEN 0 ELSE (julianday(end_at)-julianday(start_at))*24 END),1)
                        AS down_h FROM eq_downtime;"
# 期望：一个远小于 8760×台数 的数；若大于，说明有区间没闭合

# 2) 同一设备不应同时存在两条未闭合停机
sqlite3 /tmp/mnt.db "SELECT asset_id, count(*) FROM eq_downtime WHERE end_at IS NULL GROUP BY asset_id HAVING count(*)>1;"
# 期望：0 行

# 3) 短停机占比（用于 MTBF 披露）
sqlite3 /tmp/mnt.db "SELECT ROUND(100.0*sum(CASE WHEN (julianday(end_at)-julianday(start_at))*1440 < 5 THEN 1 ELSE 0 END)/count(*),1)
                      FROM eq_downtime WHERE end_at IS NOT NULL;"
# 期望：10~25 之间（低于 5 说明采集粒度是班次而非分钟）

# 4) 点检的「补录指纹」：交班前 10 分钟集中度
sqlite3 /tmp/mnt.db "SELECT ROUND(100.0*sum(CASE WHEN substr(at,12,2) IN ('13','21') THEN 1 ELSE 0 END)/count(*),1)
                      FROM eq_inspect;"
# 期望：< 30%；若 > 60%，完成率再高也不可信
```

::: warning 验证不是「跑通就行」
上面四条里，第 3、4 条是**证伪型**验证——它们不证明你做对了，只在你做错时报警。维护系统的验收必须包含至少一条这种「反向指标」，否则所有检查都会变成「有记录 = 合格」。
:::
