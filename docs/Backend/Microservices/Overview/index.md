# 微服务概述与服务拆分

微服务（Microservices）是一种软件架构风格：**把单体应用拆成一组小而自治的服务，每个服务围绕一个业务能力独立开发、独立部署、独立扩展**，服务之间通过轻量级通信（HTTP/RPC 或消息队列）协作。它解决的是大型单体在组织规模、发布频率、故障隔离上的瓶颈，同时也引入了分布式环境特有的复杂度。

![微服务总体架构](../assets/ms-architecture.svg)

## 单体架构的痛点

| 问题 | 表现 |
| --- | --- |
| 代码膨胀 | 一个应用几十万行代码，新人上手慢，合并冲突频繁 |
| 发布耦合 | 改一行代码要重新发布整个应用，风险波及全部功能 |
| 扩展粒度粗 | 只有“性能瓶颈模块”需要扩容，却要整机扩容 |
| 技术栈锁定 | 全应用只能用一种语言、一个框架 |
| 故障放大 | 某个模块内存泄漏，整个应用不可用 |

## 微服务的优势

1. **独立部署**：订单服务可以一天发布多次，不影响其他服务。
2. **独立扩展**：促销时只扩容订单与库存服务。
3. **故障隔离**：一个服务宕机，配合熔断降级不拖垮全局。
4. **技术异构**：不同服务可以用不同语言与数据库。
5. **团队自治**：小团队负责小服务，职责清晰。

## 微服务引入的新复杂度

| 复杂度 | 对应组件 |
| --- | --- |
| 服务地址会变，怎么找到对方 | 注册中心 |
| 配置散落各服务，怎么统一管理 | 配置中心 |
| 统一入口、鉴权、限流 | API 网关 |
| 实例多份，调用选哪个 | 负载均衡 |
| 一个服务故障导致雪崩 | 熔断、限流、降级 |
| 一次请求跨多个服务，怎么排障 | 链路追踪 |
| 跨服务数据一致性 | 分布式事务 / 最终一致 |
| 环境与部署 | 容器化 + CI/CD + K8s |

::: tip 一句话理解
微服务不是“把单体拆小”，而是“**按业务能力切分后，把分布式带来的新问题系统地解决掉**”。只拆服务、不上基础设施，等于只拿到了缺点。
:::

## 服务拆分原则

### 1. 按业务能力拆，不按技术层拆

错误示范：`user-api`、`user-service`、`user-dao` 三个服务（按技术层拆，改一个需求要跨三个服务发布）。

正确示范：`user-service` 一个服务包含用户领域完整的 API、逻辑、数据访问，对外暴露接口。

### 2. 参考领域驱动设计（DDD）的限界上下文

把业务划分为多个**限界上下文（Bounded Context）**，每个上下文一个服务，上下文之间的概念可以重名但各自独立建模。例如电商：

```text
订单上下文（订单、订单项、支付状态）
库存上下文（库存、入库、出库）
账户上下文（账户、余额、流水）
```

### 3. 按变化频率与团队边界拆

- 一起改的需求放同一个服务；不同团队负责的不同模块拆开。
- 康威定律：系统结构会趋同于组织的沟通结构。

### 4. 数据库按服务拆分

每个服务拥有**自己的数据库**（Database per Service），禁止多个服务直连同一张表；跨服务数据通过 API 或事件同步。

### 5. 拆分粒度宁粗勿细

刚拆分时粒度可以大一些（如订单域先拆成一个服务），运行稳定后再继续细拆。过早拆成几十个微服务是常见失败原因。

## 拆分时机与信号

| 信号 | 说明 |
| --- | --- |
| 团队规模 | 超过两个团队共同维护一个代码库 |
| 发布频率 | 每周都要发布，但发布流程越来越慢 |
| 扩展差异 | 部分模块明显需要独立扩容 |
| 故障范围 | 频繁出现“小模块搞挂整个应用” |
| 数据边界清晰 | 业务上下文已经能画出清晰的边界 |

## 从单体到微服务的演进路径

```text
单体应用
  → 模块化单体（代码内分模块，禁止跨模块直连）
  → 抽取辅助服务（报表、消息、鉴权等独立出去）
  → 核心业务按限界上下文拆分
  → 基础设施补齐（注册中心 → 网关 → 配置中心 → 链路追踪）
  → 容器化与 CI/CD 落地
```

不要“大爆炸式重构”：优先采用**绞杀者模式（Strangler Fig）**，新功能走微服务，老功能逐步迁移。

## 微服务与相关概念的区别

| 概念 | 区别 |
| --- | --- |
| SOA | 微服务是 SOA 的轻量化演进，强调去 ESB、按业务拆分、独立部署 |
| 模块化单体 | 仍是单进程单部署，只是代码结构清晰；适合拆分过渡期 |
| 服务网格 | 把熔断、限流、流量治理下沉到 Sidecar 代理（如 Istio），是微服务治理的下一代形态 |
| Serverless / 函数计算 | 更细粒度的函数级拆分，免运维，适合事件驱动场景 |

## 易错点与最佳实践

::: danger 常见错误
1. **为拆而拆**：团队 3 个人、应用 2 万行代码，拆成 10 个服务只会增加成本。
2. **按技术层拆分**：api/service/dao 三个服务，改一个字段要联动发布。
3. **共享数据库**：多个服务读写同一张表，拆了跟没拆一样，且无法独立扩展。
4. **直接 RPC 硬编码地址**：不引入注册中心，实例变化就断链。
5. **一次重构到位**：大爆炸式重构风险极高，应该绞杀者式渐进迁移。
6. **忽略分布式测试**：只做单服务单元测试，联调阶段大量问题爆发。
:::

::: tip 落地建议
先画一张「业务能力地图」：每个能力的作用域、数据归属、团队归属、变更频率；再决定哪些能力可以成为独立服务，哪些应该留在单体里。
:::

## 验证方式

1. 对现有系统画上下文边界图，找出 2~3 个可独立抽取的服务候选。
2. 为候选服务写「独立部署、独立扩展、独立故障」三项评估，判断是否值得拆分。
3. 在 demo 环境完成一次“单体 → 抽取 1 个服务”的演练，验证接口联调与回滚。
