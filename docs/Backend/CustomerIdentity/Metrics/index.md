# 度量与验收：四个率与一条成本线

归并系统最危险的状态不是「效果差」，而是「**效果差但看上去在工作**」——每天都有客户被合并，报表显示「合并 1.2 万对」，没人知道其中有多少是错的，因为错的那部分不会报错，只会让某个人收到别人的订单短信。

要打破这个状态，只需要四件事：四个率的**分母说清楚**、一条**成本线**、一个**人工队列**、一套**回归集**。

::: tip 一句话理解
指标不是越多越好。归并只需要回答两个问题：**该合并的合并了没有（覆盖率、召回）**，**不该合并的合并了没有（精度、误合并率）**。其余都是这两件事的分解。
:::

## 一、四个率，四个分母

| 率 | 定义 | 分母 | 本机读数 | 谁看 |
| --- | --- | --- | --- | --- |
| 覆盖率 | 候选对里包含多少真实对 | 全部真实对 | 94.3% | 算法 |
| 召回 | 最终合并了多少真实对 | 全部真实对 | 78.9% | 算法 / 业务 |
| 精度 | 合并的对里有多少是真的 | 全部合并对 | 100.0% | 业务 / 风控 |
| 误合并率 | 每万个客户里错并了几次 | 客户数 | 0（0.60 阈值） | 风控 / 合规 |

分母写错的四种常见形态：

- **召回用「候选对」当分母**：算出 95%，实际是对全部真实对的 71%。候选对本身就是筛过的，用它当分母等于自己给自己打分。
- **精度只看人工抽检的样本**：抽的是「看起来可疑」的对，精度会系统性偏低；抽的是「看起来很像」的对，精度会系统性偏高。
- **误合并率用「合并次数」当分母**：合并次数取决于阈值，阈值一调指标就"改善"，与真实风险无关。
- **覆盖率与召回混用**：覆盖率是分块的上限，召回是端到端的结果。混用会导致「分块改坏了」被误判成「打分改坏了」。

## 二、人工队列：1.3% 的对，决定 100% 的体验

本机在 0.60 / 0.70 两档之间做了人工档：

| 档位 | 候选对数 | 占候选 | 处理方式 |
| --- | --- | --- | --- |
| ≥ 0.70 | 59,971 | 75.6% | 自动合并 |
| 0.60 ~ 0.70 | 1,065 | 1.3% | 人工复核 |
| < 0.60 | 18,293 | 23.1% | 丢弃 |

**人工档只占 1.3%**，这是可运营的。如果一个系统的人工档占到 30%，它一定会被放弃——审核员三天后开始乱点，误合并率反而高于全自动。

队列的三个运营参数：

| 参数 | 取值建议 | 理由 |
| --- | --- | --- |
| 每人每日处理量 | 200~400 对 | 超过 400 对，判断质量断崖下降 |
| 单对展示字段 | ≤ 6 个 | 超过 6 个，审核员开始看分值 |
| 队列积压告警 | > 3 天量 | 积压意味着「不确定」被搁置，等于默认不合并 |

## 三、分层抽样：精度必须按分数分层测

只抽一个总样本算精度，会得到一个「看起来不错」的数，掩盖最危险的那一层。正确做法是按分数分层，每层独立估计：

```sql
-- 分层抽样：每层 200 对，人工标注
WITH buckets AS (
  SELECT a_id, b_id, score,
         CASE WHEN score >= 0.90 THEN 'A'
              WHEN score >= 0.70 THEN 'B'
              WHEN score >= 0.60 THEN 'C'
              ELSE 'D' END AS bucket
    FROM candidate_pair
   WHERE state = 'open'
)
SELECT bucket, count(*) AS pairs
  FROM buckets
 GROUP BY bucket
 ORDER BY bucket;
```

本机读数：A 档（≥0.90）20,396 对、B 档（0.70~0.90）39,575 对、C 档（0.60~0.70）1,065 对、D 档 18,293 对。**A 档也要抽**——误合并最集中的地方恰恰是「看起来很像」的对（共用号码 + 同姓），它在 A 档里。

::: danger 没有负样本的精度是假精度
本机有个反例：0.70 以上精度 100.0%、误合并 0——看起来完美。原因是这份数据里「同号不同人」的组合几乎都落在 0.45（只有手机一项），根本到不了 0.70。换句话说，**这个 100% 是数据分布给的，不是规则给的**。

必须专门造对抗样本：同号不同姓、同名不同号、同号同名但证件不同、证件号复用。每条都要能在回归集里跑出「拒绝合并」的结果。
:::

## 四、一条成本线：把两个率合成一个数

四个率要汇报，但决策要一个数：

```text
总成本 = 误合并数 × 单次误合并成本 + 漏合并数 × 单次漏合并成本
```

本机（400 元 / 40 元）：

| 阈值 | 误合并 | 漏合并 | 总成本 |
| --- | --- | --- | --- |
| 0.45 | 6,644 | 10,839 | 3,091,160 |
| 0.60 | 7 | 15,012 | 603,280 |
| 0.70 | 0 | 16,070 | 642,800 |
| 0.90 | 0 | 55,645 | 2,225,800 |

这条线有三个用法：**选阈值**（取最低点）、**评变更**（新规则的总成本必须低于旧规则）、**谈预算**（做一次人工复核能降多少成本，值不值得加人）。

## 五、漂移：模型不变，数据会变

归并规则是静态的，数据是动态的。三类漂移会让半年前调好的阈值失效：

| 漂移 | 表现 | 监控方式 |
| --- | --- | --- |
| 新号段 | 新放号的手机号段与旧号段格式不同，归一化规则失效 | 手机号前 3 位分布，出现新前缀即告警 |
| 改名潮 | 某入口允许用户随时改名，姓名不再稳定 | 姓名变更率日环比 |
| 共用号码增加 | 新业务（如校园、园区）大量使用统一号码 | 号下不同姓名数 ≥ 5 的号码数量 |

第三种最隐蔽。本机数据里 150 个共用号码承载了 1,405 条记录；如果某个业务上线后这个数字翻倍，所有基于手机号的规则都会同时退化——而阈值没变、代码没变、报表只会显示「合并数变多了」。

## 六、回归集：50 对就够

不需要几万条标注，**50 对精心挑选的样本**就能挡住 90% 的回归事故：

| 类型 | 条数 | 期望 |
| --- | --- | --- |
| 同人不同写法（简繁、空格、错字） | 10 | 合并 |
| 同号不同人（共用号码） | 10 | 不合并 |
| 同名不同人（同城同名） | 10 | 不合并 |
| 换号 + 改名（无共同字段） | 10 | 不合并（可接受漏） |
| 证件相同、其他全不同 | 10 | 合并 |

每次改归一化、块键、权重、阈值，都跑一遍这 50 对，结果必须与期望一致。这份集合比任何指标都值钱——它是**唯一能在 3 秒内告诉你「这次改动坏了什么」的东西**。

## 判据

本页判据族 `CIS-A` ~ `CIS-H`，共 8 条，逐条可判定：

| 编号 | 判据 | 怎么判 |
| --- | --- | --- |
| `CIS-A` | 四个率各有明确分母，写在指标字典里 | 指标字典含公式与分母说明 |
| `CIS-B` | 精度按分数分层评估，每层 ≥ 200 对 | 分层抽样脚本可跑 |
| `CIS-C` | 回归集 ≥ 50 对，含五类对抗样本 | 每次变更自动跑，全绿才发版 |
| `CIS-D` | 成本参数有业务签字，阈值由成本线推出 | 成本表与阈值同版本 |
| `CIS-E` | 人工队列占比可监控，超过 10% 触发规则复核 | 看板有该指标 |
| `CIS-F` | 共用号码数量、最大簇、新号段三类漂移有告警 | 三条查询在巡检里 |
| `CIS-G` | 每次规则变更出「变更前/后」双读数 | 变更记录含两版指标 |
| `CIS-H` | 人工复核结果回填训练/规则，不是只写日志 | 复核结论进入规则迭代 |

## 验证方式

先算清三个率的分母，再验证「人工档只占 1.3%」这个可运营性判断：

```shell
# 1) 三个率
python3 - <<'PY'
truth, auto, cand_hit = 76041, 59971, 71706
print("覆盖率 =", round(cand_hit / truth * 100, 1))      # 期望 94.3
print("召回 =", round(auto / truth * 100, 1))            # 期望 78.9
print("人工档占比 =", round(1065 / 79329 * 100, 1))      # 期望 1.3
PY

# 2) 本页判据 8 条
grep -o 'CIS-[A-H]' docs/Backend/CustomerIdentity/Metrics/index.md | sort -u | wc -l

# 3) 全库判据不撞号
python3 utils/audit/judgeidcheck.py --root . | tail -1
```

预期输出：第一条依次打印 `覆盖率 = 94.3`、`召回 = 78.9`、`人工档占比 = 1.3`；第二条 `8`；第三条 `E=0`。若召回算出来接近覆盖率，说明你把「候选覆盖」当成了「最终合并」。
