# 总览：七段链与三个「收了多少钱」

一个顾客在货架前站了三十秒，拿起一瓶水走到收银台。扫码、报价、付款、打票——四秒钟。这四秒里系统做了十几个决定：这个 SKU 今天的价是多少、会员有没有折、满 30 减 5 要不要触发、现金要不要抹到角、这单算哪一天的营业额。

在电商系统里，这十几个决定由**一个下单请求**完成，任何一步出错都返回错误码。在门店里，这十几个决定由**一台可能正在断网的终端**完成，任何一步出错都不返回错误码——票照样打得出来，顾客照样拿着水走了。

::: tip 一句话理解
收银系统的核心不是「把商品加进购物车」，而是**在离线、多终端、有现金、有找零、有退货的条件下，让同一笔钱在三个地方算出同一个数**。
:::

## 一、为什么门店必须当成独立系统

| 维度 | 线上订单 | 门店小票 |
| --- | --- | --- |
| 网络 | 假设可用，失败即重试 | **假设会断**，断网必须继续营业 |
| 价格 | 服务端实时算 | 终端本地算，价目靠下发 |
| 支付 | 单一渠道回调 | 现金 + 多个渠道 + 混合，还要找零 |
| 时间 | 一个 `created_at` | 开单、结账、上传三个时间，可能跨日 |
| 库存 | 中心库存，预占 | 门店本地有一份，与中心对不齐是常态 |
| 退货 | 线上原路退回 | 可能跨店、可能只退一件、可能退现金 |
| 对账 | 与渠道对 | 与渠道 + 与钱箱 + 与收银员对 |

七个维度里有五个是**线上没有的约束**。把门店当成「线上的一个渠道」，最常见的后果是：用 `created_at` 当营业日、用一个 `amount` 存三个口径、用应用层校验代替数据库约束。这三件事会在第一次盘点时同时爆掉。

## 二、七段链与它们的失败形态

| 段 | 关键判断 | 失败形态 | 谁先发现 |
| --- | --- | --- | --- |
| 开 | 这个钱箱现在归谁 | 显性：不开班不能收现 | 收银员 |
| 价 | 这一版价目算不算数 | **安静**：用旧价照收 | 月底毛利分析 |
| 收 | 这张票属于哪一次结账 | 半显性：挂单丢了顾客会吵 | 顾客 |
| 折 | 优惠按什么顺序、余数给谁 | **安静**：差 1 分 | 日结 / 退货时 |
| 付 | 实收与应收差在哪 | **安静**：多收记成第二笔 | 对账 |
| 退 | 这单还能退多少 | **安静**：退到负数 | 盘点 |
| 结 | 钱箱与系统差多少 | **安静**：被当成手抖 | 内审 / 长差累积 |

「安静」的意思是：**没有任何一处会抛异常**。票能打、单能结、报表能出，只有数不对。

### 为什么「安静」比「报错」更危险

报错会被处理，安静的偏差会被**解释掉**。本机实测里有一组特别典型的读数：

- 价目滞后单 1,837 笔，净额 −440.68 元（看起来「几乎没错」）
- 同样的单子按双向拆开：少收 2,145.95 元、多收 2,586.63 元，双向 4,732.59 元
- 也就是说，**净额只暴露了真实问题的 9.3%**

任何以「本月差异率」为 KPI 的门店管理，都会在这一步失效：差异率的分母是销售额，分子是净额，正负相抵之后永远好看。

## 三、三个「收了多少钱」与它们之间的桥

| 口径 | 数据来源 | 什么时候成立 | 差在哪 |
| --- | --- | --- | --- |
| 小票应收 `payable` | 收银端计算并落库 | 结账瞬间 | 与实收的差 = 凑整 + 找零 |
| 钱箱现金 `cash` | 收银员点钞 | 班结时 | 与应收的差 = 长短款 |
| 渠道到账 `settled` | 支付机构 T+1 结算单 | 次日 | 与实收的差 = 手续费 + 掉单 |

三者之间的关系可以写成一个恒等式：

```text
Σ payable
  = Σ tender(全部方式)
  = Σ cash_counted − 长短款 + Σ settled + 手续费
```

这个恒等式有三个用途，缺一不可：

1. **收银端自检**：`Σ payable = Σ tender`，不成立说明有单没付完或有单付重了。
2. **班结自检**：`期初 + 现金收 − 现金退 − 缴款 = 点钞 − 长短款`，不成立说明有现金流水没记。
3. **日结对账**：`Σ settled + 手续费 = Σ 电子 tender`，不成立就去查掉单与手续费口径。

::: danger 四个最容易写错的字段
1. **`rounding` 不能并进 `discount`**：凑整是「为了收现金更方便」，优惠是「让利」。并在一起，退货时会把凑整的钱也退给顾客（实测 2,064 笔发生凑整，6.88%）。
2. **`payable` 不能存成「实收」**：顾客给 100 元买 87.5 元的东西，`payable` 是 87.5，`tender` 是 100，`change` 是 12.5。存成同一个字段，钱箱永远差。
3. **`biz_date` 不能由 `created_at` 推导**：跨零点的 152 笔单，按开单日与按结账日归属，**100% 不同**。
4. **`ticket_no` 必须含终端号**：不含终端号时，两台终端各自从 1 发号，实测重号率 11.62%。
:::

## 四、一张票的最小字段集

下面这九组字段，少任何一组都会在某个环节算不出数：

```sql
CREATE TABLE ticket (
  ticket_id     TEXT PRIMARY KEY,        -- 全局唯一（建议 ULID / 雪花）
  store_id      TEXT NOT NULL,           -- 哪家店
  terminal_id   TEXT NOT NULL,           -- 哪台终端（票号唯一性的组成部分）
  ticket_no     TEXT NOT NULL,           -- 终端本地票号，形如 S01-T03-000123
  biz_date      TEXT NOT NULL,           -- 营业日，不是自然日
  opened_at     TEXT NOT NULL,           -- 开单（挂单从这里算时长）
  closed_at     TEXT,                    -- 结账（为空 = 挂单中）
  price_ver     INTEGER NOT NULL,        -- 算这张票时用的价目版本
  gross         REAL NOT NULL,           -- 原价合计
  discount      REAL NOT NULL DEFAULT 0, -- 优惠合计（不含凑整）
  rounding      REAL NOT NULL DEFAULT 0, -- 凑整（可为负）
  payable       REAL NOT NULL,           -- 应收 = gross - discount + rounding
  status        TEXT NOT NULL,           -- HELD / PAID / VOID / REFUNDED
  UNIQUE (store_id, biz_date, ticket_no) -- 这条唯一键比任何应用层校验都可靠
);
```

`price_ver` 是最容易被省略、又最不该省略的字段。它的作用不是「记录用了哪版价」，而是**在三个月后有人投诉「那天卖贵了」时，能一次查出是价目没同步还是标价错了**。没有它，只能全表比对，最后不了了之。

## 五、营业日：三口径与一个切点

门店的「今天」不等于自然日。原因很实际：夜班收银员在 23:50 开的单，可能 00:05 才结账；00:20 那单卖给的是夜宵客，但店长第二天早上来对账时，会把它算进「昨天夜班」。

| 口径 | 定义 | 适合谁 | 风险 |
| --- | --- | --- | --- |
| 自然日（`created_at` 日期） | 按服务器时间切 | 技术排查 | 与店长对账口径不一致 |
| 营业日（`biz_date`） | 按门店切点（常见 04:00）切 | 门店运营、财务 | 切点写错，跨日单全错 |
| 上传日（`uploaded_at` 日期） | 按数据到达中心的时间切 | 数据平台 | 断网补传会把三天数据算成一天 |

本机实测：30,000 笔里跨零点结账 152 笔、23 点后开单 1,293 笔（4.31%）。这 152 笔按开单日与按结账日归属，**100% 不同**——不是「偶尔差一点」，是「每一笔都差」。

::: tip 切点怎么定
定切点的原则只有一条：**切点必须落在客流最低、且不跨班次的时刻**。便利店通常 04:00（夜班结束前），餐饮通常 05:00，商场店通常跟自然日一致（22:00 闭店，不会跨零点结账）。切点写进 `store.biz_cut_hour`，由终端算 `biz_date`，不留给服务端猜。
:::

## 六、七段链的判据

本页判据族 `RSO-A` ~ `RSO-H`，共 8 条。八条都能被单独判定，任何一条不成立就不算这篇文档写完。

| 判据 | 断言 | 验证方式 |
| --- | --- | --- |
| `RSO-A` | 小票表同时存 `gross` / `discount` / `rounding` / `payable` 四个字段 | `SELECT` 四列均存在且 `payable=gross-discount+rounding` 违例 0 |
| `RSO-B` | `biz_date` 由门店切点算出，不由 `created_at` 推导 | 构造 00:05 结账单，`biz_date` 为其前一日 |
| `RSO-C` | 票号唯一键含 `store_id` + `biz_date` + `terminal_id` | 两台终端同序号插入，第二笔被拒 |
| `RSO-D` | 支付方式是可枚举值而非自由文本 | `method` 有 `CHECK IN (...)`，非法值被拒 |
| `RSO-E` | 每张票的原价 = 明细行合计 | 违例 SQL 返回 0 行 |
| `RSO-F` | 应收 = 支付合计（容差 0.001） | 违例 SQL 返回 0 行 |
| `RSO-G` | 退款与销售分表，不写负数小票 | `refund` 表存在且有 `ticket_id` 外键 |
| `RSO-H` | 三口径可各自独立求和，且差异可解释 | 三个 `SUM` 跑得出，差值能归入凑整 / 手续费 / 长短款 |

## 七、验证方式

```shell
# 1. 四个金额字段的勾稽（期望输出 0）
sqlite3 :memory: "
create table t(gross real, discount real, rounding real, payable real);
insert into t values (19.8, 3.0, -0.8, 16.0), (9.9, 0, 0, 9.9), (45.0, 0, 0, 45.0);
select count(*) from t where abs(payable - (gross - discount + rounding)) > 0.001;"
# 期望：0

# 2. 营业日切点：00:05 的单应归前一日
python3 - <<'PY'
from datetime import datetime, timedelta
cut = 4
def biz_date(ts, cut):
    return (ts - timedelta(hours=cut)).date().isoformat()
print(biz_date(datetime(2026, 11, 2, 0, 5), cut))   # 期望 2026-11-01
print(biz_date(datetime(2026, 11, 2, 4, 5), cut))   # 期望 2026-11-02
PY

# 3. 三口径求和（在实战库上跑，期望三行都能出数）
sqlite3 rp.db "
select 'payable', round(sum(payable),2) from ticket
union all select 'cash', round(sum(amount),2) from tender where method='CASH'
union all select 'settled', round(sum(amount)*0.9962,2) from tender where method<>'CASH';"
```

第 2 步的两个日期就是营业日的全部逻辑：**先减切点小时数，再取日期**。写成 `date(created_at)` 的系统，会在每个跨零点的夜班出错，而且只在月底盘账时被发现。
