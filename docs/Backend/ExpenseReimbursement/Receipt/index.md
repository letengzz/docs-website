# 票据与查验：一张票的五个属性

一张发票进系统，最少要回答五个问题：它是真的吗、抬头对吗、税号对吗、金额与业务对得上吗、是不是已经报过。前三个问题有官方接口兜底，后两个只能靠系统自己——而**真正造成损失的，几乎都在后两个**。

这一页从「票号怎么解析」讲到「一票一报怎么落成约束」，中间给出去重的三种口径与它们的代价。

## 一、数电票的 20 位号码不是一串随机数

《国家税务总局关于推广应用全面数字化电子发票的公告》（2024 年第 11 号，2024-12-01 施行）规定，数电票号码为 20 位：

| 位次 | 含义 | 举例 |
| --- | --- | --- |
| 第 1-2 位 | 公历年度后两位 | `25`（2025 年） |
| 第 3-4 位 | 开票方所在省级税务局区域代码 | `32`（江苏） |
| 第 5 位 | 开具渠道等信息 | `0` / `1` / `2` |
| 第 6-20 位 | 顺序编码 | 15 位流水 |

这张表解释了一件很实际的事：**「只取后 8 位去重」会跨年、跨省撞号**。后 8 位只是 15 位流水码的尾部，不同省份、不同年份的号码完全可能相同。

### 用读数说明代价

本机构造 29,720 行发票（原始 28,000 + 合法「同店同额同日」600 + 真重复 1,120），三种去重口径：

| 口径 | 删除行数 | 应删 | 误删 | 误删率 |
| --- | --- | --- | --- | --- |
| 完整 20 位票号 | 1,120 | 1,120 | 0 | 0.00% |
| 票号后 8 位 | 19,720 | 1,120 | **18,600** | **62.58%** |
| 商家 + 金额 + 日期 | 1,723 | 1,120 | 603 | 2.03% |

第二个口径删掉了 **62.58%** 的发票——这已经不是「去重」，是「删库」。它不会报错，因为票号后 8 位确实相同；它只会在某个月末被发现：**这个月的费用怎么只有上个月的三分之一**。

第三个口径（三键）误删 2.03%，看起来可以接受，但它误删的是真票——「同一家酒店、同一价格、同一天开两间房」在差旅场景里非常常见，本机就构造了 600 组。被误删的票据无法报销，员工只能重开，重开的票号变了、日期变了，跨期问题随之而来。

::: danger 去重键的三条纪律
1. **用完整票号，不用后 8 位、不用票号+金额**：票号本身就是唯一键，加任何字段都是在削弱它。
2. **票号唯一约束必须在数据库层**，不能靠应用层「先查后插」——并发下必失效。
3. **红冲票不是重复票**：负数票与蓝票的票号不同，去重键要能容纳「一蓝一红」两条记录。
:::

## 二、一票一报：一个 UNIQUE 索引值多少钱

```sql
-- 一票一报：数据库层硬约束，应用层只负责给出友好提示
CREATE TABLE invoice (
  invoice_id INTEGER PRIMARY KEY,
  claim_id   INTEGER NOT NULL REFERENCES expense_claim(claim_id),
  inv_no     TEXT NOT NULL,
  inv_date   TEXT NOT NULL,
  seller     TEXT NOT NULL,
  amount     REAL NOT NULL CHECK (amount > 0),
  title      TEXT NOT NULL,
  tax_no     TEXT NOT NULL CHECK (length(tax_no) = 18),
  invoice_kind TEXT NOT NULL CHECK (invoice_kind IN ('SPECIAL','NORMAL','E_TICKET','RAIL')),
  is_red     INTEGER NOT NULL DEFAULT 0 CHECK (is_red IN (0,1)),
  verified_at TEXT,
  UNIQUE (inv_no, is_red)          -- 同一票号允许「蓝 + 红」各一条
);
```

`UNIQUE (inv_no, is_red)` 而不是 `UNIQUE (inv_no)`，是为了容纳红冲：一张蓝票被全额红冲时，红票的票号与蓝票不同，但如果系统用「原票号 + 标记」记录红冲关系，就要允许两条共存。

插入时的正确写法：

```sql
INSERT INTO invoice(claim_id, inv_no, inv_date, seller, amount, title, tax_no, invoice_kind)
VALUES (:claim_id, :inv_no, :inv_date, :seller, :amount, :title, :tax_no, :kind)
ON CONFLICT (inv_no, is_red) DO NOTHING;
-- 然后按 inv_no 回查，把「已存在」翻译成「这张票已经在 BX-2026-0007 里报过」
```

回查这一步是体验的关键：只返回「插入失败」，员工不知道票去哪了；返回「已在某张单里报过」，员工自己能处理。

本机读数：真重复 1,120 行、涉及金额 523,781 元（占发票总额 3.87%）。**一个 UNIQUE 索引，一年挡住 52 万重复报销**——这是本专题性价比最高的一行 DDL。

## 三、验真：能查什么、不能查什么

全国增值税发票查验平台的边界，比大多数人以为的窄：

| 能力 | 说明 |
| --- | --- |
| 可查范围 | 最近 5 年内开具的发票 |
| 频次限制 | 每份发票每天最多查验 5 次 |
| 时效 | 当日开具、当日可查；离线开票的数据未上传时会「查无此票」 |
| 返回内容 | 票面要素（金额、税额、购销方），**不含**「这张票是否已报销」 |

最后一行是关键：**查验平台只回答「税务局有没有这张票」，不回答「这张票是不是你的业务」**。所以验真只是第一道门，后面还有抬头、税号、相关性三道。

```sql
-- 验真结果落库：不覆盖原值，只追加验真流水
CREATE TABLE invoice_verify (
  verify_id   INTEGER PRIMARY KEY,
  inv_no      TEXT NOT NULL,
  result      TEXT NOT NULL CHECK (result IN ('MATCH','MISMATCH','NOT_FOUND','ERROR')),
  checked_at  TEXT NOT NULL,
  raw_json    TEXT,                    -- 原始返回，便于事后举证
  operator    TEXT NOT NULL
);
```

保留 `raw_json` 不是为了调试，是为了**举证**：税务质疑某张票时，你要能拿出「当时查验返回的就是这些字段」，而不是「我们系统显示已验真」。

::: warning 「每日 5 次」的限流会打到批量补验
历史票据批量补验时，同一张票被多个单据引用（一票多行）就会重复调用，第 6 次直接失败。正确做法是**按票号去重后再验**，并且把结果缓存到 `invoice_verify`，同一票号当天只调一次。
:::

## 四、抬头与税号：能报 ≠ 能扣

| 缺陷 | 本机读数 | 后果 |
| --- | --- | --- |
| 抬头与公司全称不一致（少字、多「市」、写成简称） | 624 张（5.20%） | 不得作为税前扣除凭证 |
| 税号错（长度对但字符错） | 372 张（3.10%） | 专票进项不得抵扣，已抵扣要做进项转出 |
| 抬头为个人 | 215 张（1.79%） | 完全不可抵，且需并入工资代扣个税 |

三类合计 1,211 张（10.09%）。抬头为个人的 397,750 元，在增值税上一分不能抵；税号错的按专票 6% 估算，进项转出约 38,954.72 元。

### 校验规则要写在提交前

```sql
-- 提交时校验：抬头必须与「公司主体表」精确匹配，税号必须 18 位且校验位正确
SELECT c.company_name, c.tax_no
FROM company_entity c
WHERE c.is_active = 1
  AND c.company_name = :title          -- 精确匹配，不做模糊
  AND c.tax_no = :tax_no;
-- 返回 0 行 → 拒绝提交，并给出「最接近的 3 个候选」让员工改
```

「精确匹配 + 候选提示」比「模糊匹配自动纠正」安全得多：后者会把「某某科技（上海）有限公司」自动纠成「某某科技有限公司」，看起来贴心，实际上是**替你伪造了一张票的抬头**。

### 18 位统一社会信用代码的校验位

统一社会信用代码第 18 位是校验码，用前 17 位按加权因子计算：

```text
字符集：0-9 与 A-Z（去掉 I、O、S、V、Z 共 31 个字符）
权重：  [1,3,9,27,19,26,16,17,20,29,25,13,8,24,10,30,28]
校验：  sum(值 × 权重) mod 31 → 映射回字符集
```

只校验「长度 18」是不够的：本机构造的 372 张错税号里，绝大多数长度都是 18，只是中间某一位错了。校验位能在提交时拦住其中约 96%（剩下一部分是「校验位也恰好算对」的极小概率）。

## 五、票种与场景：四种票，四种处理

| 票种 | 典型场景 | 特殊处理 |
| --- | --- | --- |
| 增值税专用发票（数电） | 住宿、会议 | 可抵进项；需在税务数字账户确认用途 |
| 增值税普通发票（数电） | 餐饮、市内交通 | 不可抵进项；可作税前扣除凭证 |
| 航空运输电子客票行程单 | 机票 | 按票价 + 燃油附加费计算，不含机场建设费抵扣规则不同 |
| 铁路电子客票 | 火车 | 数电票形态，票面含乘车人身份信息，需脱敏存储 |

四类票的**可抵扣性不同、必填字段不同、验真接口相同**。把它们塞进一张 `invoice` 表是对的，但必须有一个 `invoice_kind` 字段驱动后续规则，不能靠「金额是否含税」来猜。

## 六、红冲与重开：三条不能合并的路径

| 情形 | 正确做法 | 错误做法 |
| --- | --- | --- |
| 票开错了，对方重开 | 原票标记 `is_red=1` 关联红票，新票新票号入账 | 直接删原票、插新票（审计轨迹断裂） |
| 部分退款 | 红票金额 = 退款金额，与原票关联 | 用负数明细冲减（费用净额化） |
| 票丢失 | 取得开票方发票记账联复印件 + 证明 | 让员工「再开一张」（重复票） |

第一条的 `is_red` 标记 + 原票号外键，是三条路径里唯一能同时满足「一票一报」与「红冲可追溯」的建模方式。

## 七、判据族 `EXR-A ~ EXR-H`

本页判据族 `EXR-A` ~ `EXR-H`，共 8 条。八条都能被单独判定，任何一条不成立就不算这篇文档写完。

| 判据 | 断言 | 验证方式 |
| --- | --- | --- |
| `EXR-A` | 票号按完整 20 位存储与去重，不截断 | `length(inv_no) = 20`，去重键为完整票号 |
| `EXR-B` | 票号唯一约束在数据库层，并发下仍生效 | 并发插同一票号两次，第二次失败 |
| `EXR-C` | 红冲票与蓝票可共存且可关联 | `UNIQUE(inv_no, is_red)`，红票挂原票号 |
| `EXR-D` | 验真结果只追加，保留原始返回 | `invoice_verify` 有 `raw_json`，无 UPDATE |
| `EXR-E` | 抬头精确匹配公司主体，不做模糊纠正 | 与 `company_entity` 等值比较 |
| `EXR-F` | 税号 18 位且校验位通过 | 构造 1 位错的税号，被拒 |
| `EXR-G` | 票种驱动规则，不靠金额猜 | 四类票各一条用例，规则不同 |
| `EXR-H` | 一票多行时不重复调用验真接口 | 同一票号当天只调一次，命中缓存 |

## 八、验证方式

```shell
# 1. 完整票号去重 vs 后 8 位去重
sqlite3 :memory: "
create table i(no text);
insert into i values ('25320000000000000001'),('25320000000000000002'),
                     ('25320000000000000001'),('25320000000000000011');
select count(*) as 总行, count(distinct no) as 完整票号去重,
       count(distinct substr(no,-8)) as 后8位去重 from i;"
# 期望：4 | 3 | 2 —— 后 8 位把 00000011 和 00000001 的尾部混在一起了

# 2. 一票一报：插两次同一票号
sqlite3 :memory: "
create table inv(id integer primary key, no text not null, red int not null default 0,
                 unique(no, red));
insert into inv(no) values ('25320000000000000001');
insert into inv(no) values ('25320000000000000001');"
# 期望：UNIQUE constraint failed: inv.no, inv.red

# 3. 税号长度校验（弱校验，先用它兜底，校验位再补一层）
sqlite3 :memory: "select length('91310000MA1K35QX8N') = 18;"
# 期望：1
```

第 1 步的 `4 | 3 | 2` 是一个可以背下来的数字：**后 8 位去重会把不同票合并**。真实数据里这个比例是 62.58%，因为票号流水的尾部重复率远高于本例。
