# 常见问题与分诊

这一页按「症状 → 先查哪一段 → 一条可执行命令」组织。推荐系统的排查难点不是「不知道原因」，而是**四段的症状高度相似**——都表现为「推得不准」。下面每一问都给一个能在十分钟内跑出结论的检查。

本页判据族 `RCQ-A` ~ `RCQ-H`，共 8 条。定义表见文末「本页判据」一节。

## 一、分诊表：先定位段，再谈方法

| 症状 | 先查 | 一条命令 | 判定 |
| --- | --- | --- | --- |
| 点了没反应，下次还推同一个 | 曝光去重 / 已读过滤 | `select count(*) from rec_exposure where user_id=? and item_id=?` | 曝光有记录但没过滤 → 后处理问题 |
| 全是老爆款，新品不出现 | 召回配额 | `select channel, count(*) from rec_candidate where request_id=? group by 1` | 某通道占比 100% → 融合/配额问题 |
| 离线 AUC 涨，线上不动 | 样本/特征 | 双跑比对 `diff_rows` | 非 0 → 特征不一致 |
| 分数都挤在一起 | 校准 | `pred_mean` vs `actual` | 比值 > 1.5 → 校准问题 |
| p99 抖动，偶发超时 | 召回并行/降级 | `histogram_quantile(0.99, rec_stage_duration_ms)` | 某一路 p99 突增 → 该路下游 |
| 返回条数不足 10 | 兜底池 | `rec_fallback_total` | 突增 → 召回或排序挂了 |
| 实验指标大起大落 | SRM | χ² 检验 | p < 0.001 → 分流 bug |
| 新用户首页很差 | 会话特征 | 第 2 次请求的 CTR | 与老用户差 > 30% → 实时特征未生效 |

## 二、为什么「换个更强的模型」常常没用

因为**召回决定了天花板**。如果用户想点的东西根本不在候选池里，排序模型再强也只能在池子里挑。判别方法：算「候选池覆盖率」（点击物品是否在候选集内，见[召回](../Recall/index.md))第六节）。低于 85% 时，任何排序优化都是白费。

反过来，如果覆盖率已经 95%，那排序才是瓶颈。**先算这个数，再决定投人**。

## 三、为什么 AUC 涨了 0.02，线上 CTR 一点没变

三个常见原因，按概率排序：

1. **提升集中在长尾位置**。AUC 是全候选集上的排序能力，而线上只看前 10。检查方法：单独算 NDCG@10 与「前 10 位内的 AUC」。
2. **候选集变了**。新模型上线时若同时调了召回配额，AUC 的提升可能来自「更容易的候选」，不是模型。
3. **位置偏差**。离线评估用的是历史位置的数据，新模型可能只是更擅长「预测历史位置」，而不是「排得更好」。

## 四、负采样之后分数为什么不能直接用

因为负采样改变了样本里正负的比例，而模型学的是「样本里的概率」。实测：真实 CTR 2.963%、负采样 1:4 后预测均值 17.69%，高估 **5.97 倍**；减掉 `log(8.19)` 的先验后回到 2.99%。

```python
# 正确的修法：打分侧减先验，不重训
p_true = 1 / (1 + math.exp(-(raw_logit - math.log(K))))
```

注意 `K = 1 / 负样本保留比例`。写反方向（乘 K）会让偏差从 6 倍变成 1/6，看起来「更接近 0」但依然是错的。

## 五、位置能不能当特征

**训练时可以，打分时不可以。**

- 训练时把 position 当特征，模型会学到「位置高 → 点击高」，这部分是偏差不是信号。
- 更稳妥的做法是**不用 position 作特征，改用 IPS 权重**（`1/propensity`）来纠偏（见[排序](../Ranking/index.md))第五节）。
- 如果一定要用，必须做**位置消融实验**：训练时去掉 position，比较 GAUC。掉很多说明模型原本在抄答案。

## 六、新品到底该怎么起量

三段式，缺一不可：

1. **内容先验**：用标题/图像 embedding 找相似物品，拿邻居 CTR 作初始分（不是结论）。
2. **固定配额**：召回层给 `min_quota`，且位置随机化——否则你测的是位置不是物品。
3. **统计淘汰**：`shows ≥ 200` 且 CTR 置信上界低于类目均值才淘汰，避免小样本误杀。

实测的反面教材：50 个物品里 10 个新品真实 CTR 8.40%，但在「按历史 CTR 排序」的系统里观测 CTR 只有 0.81%，曝光量是老品的 1/633——**这不是新品不行，是系统只让它们在最差的位置出现了一次**。

## 七、实验能不能「每天看一眼，显著就停」

不能。实测 A/A 实验（真实无差异）：只看一次误报 **4.85%**，每 300/组看一次、最多看 10 次，误报涨到 **18.1%**。

三种合规做法：固定期限（中途只看护栏）、序贯检验（always-valid p-value）、分组序贯（调整 α 边界）。**「显著就停」等价于把 α 从 0.05 抬到 0.2 左右。**

## 八、延迟突然变差，先看哪里

按这个顺序，一般三步内能定位：

1. **分段**：四段各自的 p99，看是哪一段。
2. **候选数**：`rec_candidate_count` 的 p50 是否掉了。掉了说明召回超时在丢通道（不报错）。
3. **下游**：某一路召回的依赖（向量库/Redis）的 p99。

最常见的原因是「加了一路召回」：串行时它加在总和里，并行时它决定 p99。加通道前必须评估它的 p99 成本（见[在线服务](../Serving/index.md))）。

## 九、兜底池该放什么

放**预生成的、按人群粗分组的静态列表**，不放「实时查热度」——因为热度服务可能就是挂掉的那个。

四段人群（新用户/活跃/沉默/未知）各一份，10 分钟刷新，进程内再留一份硬编码常量。最后一层听起来很土，但它是唯一能在「Redis 挂、模型挂、特征挂」时还返回内容的方案。

## 十、什么时候可以判定「这个特征废了」

三个信号任意一个成立：

1. **PSI > 0.2**（对冻结基线），说明分布已经漂移。
2. **缺失率 > 5%**，说明上游不稳定。
3. **去掉它 GAUC 不变**，说明它没有贡献。

第 3 条最容易被忽略：模型里的特征重要性高，不代表它对排序有贡献——它可能只是在拟合「用户活跃度」这个已经在别的特征里的信息。

## 本页判据

| 编号 | 判据 | 看什么现象 | 不满足时改哪里 |
| --- | --- | --- | --- |
| `RCQ-A` | 分诊表可执行 | 每个症状有一条命令与判定阈值 | 补命令，别只写「检查一下」 |
| `RCQ-B` | 先算候选覆盖率再换模型 | 有覆盖率指标与阈值 | 补 SQL，低于 85% 先修召回 |
| `RCQ-C` | AUC 提升要落到前 10 位 | 同时看 NDCG@10 | 加前 10 位指标 |
| `RCQ-D` | 校准方向可验证 | `pred/actual` 在 0.9~1.1 | 检查 K 的方向（除还是乘） |
| `RCQ-E` | 位置消融有结论 | 去 position 后 GAUC 变化可量化 | 做一次消融 |
| `RCQ-F` | 新品三段式齐备 | 先验 + 配额 + 统计淘汰 | 缺哪段补哪段 |
| `RCQ-G` | 停止规则非「显著就停」 | 实验配置里有期限/序贯方案 | 改实验流程 |
| `RCQ-H` | 延迟排查有固定顺序 | 分段 → 候选数 → 下游 | 写成 runbook |
