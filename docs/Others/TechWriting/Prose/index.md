# 语言与表达

语言这一层只有一个目标：**让读者不必猜。** 技术文档不追求「写得好听」，追求**每个句子只有一个可能的读法**——歧义在散文里是风格，在操作手册里是事故。

## 一、好句子的三个机械指标

不必争论「文笔」，下面三条是可以数的：

| 指标 | 阈值 | 超标后的真实代价 | 怎么查 |
| --- | --- | --- | --- |
| 单句长度 | ≤ 40 字（含标点） | 读到句末忘了句首，需要回读 | 按 `。！？` 切分后数字符 |
| 一句一事 | 每句 1 个谓语核心 | 「因为……所以……但……而且」型长句无法判定哪条是结论 | 数连词 |
| 主语明确 | 动作有执行者 | 「需要配置好」——谁配？什么时候配？ | 找「被 / 由 / 需要」 |

::: tip 一句话判据
**一句话读完需要回读，这句话就该拆。** 回读是读者付出的额外成本，而成本会累积成「不读了」。
:::

![句子长度的四档：从可扫描到不可读，40 字是分界线](../assets/tw-prose-ladder.svg)

## 二、把形容词换成数量词

这是技术写作里收益最高的一条改写规则。形容词不可验收，数量词可以：

| 原句（形容词） | 改写（数量词 / 布尔） | 为什么更好 |
| --- | --- | --- |
| 服务应保持稳定 | 三个容器 `running`，错误率 < 0.5%（5 分钟窗口） | 可判定 |
| 性能有明显提升 | P95 从 820ms 降到 210ms（同机、同数据量） | 可复核 |
| 尽快处理 | 15 分钟内响应，2 小时内给出结论 | 可追责 |
| 配置比较简单 | 改 1 个文件 2 行，不需要重启 | 可预估成本 |
| 支持多种数据库 | 支持 MySQL 8.0+ / PostgreSQL 15+ | 可核对 |
| 有一定风险 | 失败时需手工回滚 2 张表，约 20 分钟 | 可决策 |
| 文档比较完整 | 7 个模块齐全，含 24 项验收判据 | 可验收 |
| 建议使用新版本 | 使用 3.5.x（3.4 于 2026-08 EOL） | 可追溯 |

::: danger 三个最爱混进文档的词
**「相关」「方面」「进行」**——它们几乎从不携带信息：

- 「相关配置」→ 具体是哪几个键；
- 「性能方面的问题」→ 是延迟、吞吐还是内存；
- 「进行验证」→ 验证什么、看到什么算通过。

改写方法：删掉词之后读一遍，如果意思没变，这个词就该删。
:::

## 三、术语纪律

术语混乱是长篇文档最常见的「隐性成本」：读者要花精力判断「这两个词是不是一回事」。

1. **首次出现给英文原文**：「幂等（Idempotency）」——之后只用中文；
2. **全篇只用一种写法**：`判据` 与 `验收标准` 不要混用，选一个；
3. **缩写首次展开**：`SLO（Service Level Objective，服务等级目标）`；
4. **长文附术语表**：五个以上专有名词就给一张两列表。

```markdown
| 术语 | 含义 | 本文为什么用这个词 |
| --- | --- | --- |
| 判据 | 可被第二个人跑出同样结果的判定条件 | 与「标准」「要求」区分：它必须可执行 |
| 口径 | 一个数字的采集对象、时间与方式 | 防止两次测量不可比 |
```

## 四、加粗、列表、代码标记的分工

强调手段一旦滥用，就等于没有强调。三条纪律：

| 手段 | 只用于 | 滥用后的症状 |
| --- | --- | --- |
| **加粗** | 结论、易错点、必须记住的一句话 | 满页黑体，读者直接跳过 |
| 行内代码 | 命令、文件名、字段名、字面值 | 把普通名词也标成代码，视觉噪音 |
| 列表 | 三项以上的并列 | 两句因果也拆成列表，逻辑断裂 |

一条经验值：**一屏内加粗不超过 5 处**。超过就说明这一屏有 5 个「重点」，等于没有重点。

## 五、被动句、名词化与套话

这三种写法会让句子「看起来正式」，实际把执行者藏了起来：

| 类型 | 反例 | 改写 |
| --- | --- | --- |
| 被动无主语 | 配置需要被检查 | 执行 `promtool check config`，返回 `SUCCESS` |
| 名词化 | 对日志进行分析 | 用 `grep` 过滤 `ERROR` 行 |
| 套话开头 | 为了更好地满足业务需求，我们…… | 直接说做了什么、为什么 |

::: warning 「我们」和「大家」
「我们认为」「大家注意」在个人博客里没问题，在需要交接的文档里是噪音：读者不知道「我们」是谁，也不知道出问题该找谁。**换成角色名**：值班 SRE、后端负责人、平台组。
:::

## 六、中英混排与标点

技术文档里中英混排几乎不可避免，统一四条即可：

1. 中文句子用全角标点（，。：；），英文与代码用半角；
2. 中文与英文/数字之间加一个空格：`使用 Redis 7.4 版本`；
3. 代码、命令、字段名一律放进反引号，避免与正文混淆；
4. 引号统一用「」，代码里的字符串用 `"`。

## 七、十二个高频病句

| # | 病句 | 问题 | 改写 |
| --- | --- | --- | --- |
| 1 | 如果配置不正确可能会导致启动失败 | 「可能」让结论失效 | 配置缺少 `db.url` 时启动失败，日志出现 `MissingPropertyException` |
| 2 | 建议在测试环境先验证 | 没说是谁、什么时候 | 上线前由提测人在预发环境跑 `smoke.sh`，全绿才可发 |
| 3 | 该功能已开发完成 | 完成 ≠ 可交付 | 接口可用，未接入鉴权（见第 4 节） |
| 4 | 由于网络原因导致超时 | 把结论当原因 | 超时源于客户端 3s 超时小于服务端 8s 处理时间 |
| 5 | 如上所述 | 读者可能没读上文 | 复述一句结论，再给链接 |
| 6 | 系统会自动处理 | 自动到什么程度 | 失败重试 3 次、间隔 2s，之后进死信队列 |
| 7 | 请注意数据安全 | 无法执行 | 导出文件必须脱敏手机号与身份证，见脚本 `mask.py` |
| 8 | 目前不支持 | 缺时间与替代 | 当前版本（3.5）不支持；替代方案：先用视图聚合 |
| 9 | 经过排查，问题已解决 | 缺根因与判据 | 根因：连接池上限 10 被打满；判据：`pool_active` 回落到 2 |
| 10 | 相关文档见附件 | 附件会丢 | 给仓库内路径或长期链接 |
| 11 | 尽量避免频繁重启 | 「尽量」= 没有约束 | 单日重启不超过 1 次，且需在变更窗口内 |
| 12 | 用户体验更好 | 技术文档不谈体验 | 首屏可交互时间从 3.1s 降到 1.2s |

## 八、验证方式

三条机械检查，跑完再交稿：

```shell
# ① 句长：统计超过 60 字的句子（粗略按中文句号切分）
python3 - <<'PY'
import re, sys
text = open('你的文档.md', encoding='utf-8').read()
sents = [s for s in re.split(r'[。！？]', text) if s.strip()]
long = [(len(s), s[:30]) for s in sents if len(s) > 60]
print(f'句子总数 {len(sents)}，超长 {len(long)}')
for n, s in long[:5]:
    print(n, s)
PY
# 期望：超长句为 0，或每一句都能说明"为什么必须长"
```

```shell
# ② 形容词与模糊量词：任何命中都是一处空判据
grep -oE '正常|稳定|较快|适当|若干|左右|大概|尽量|明显|相关' 你的文档.md | sort | uniq -c
# 期望：无输出
```

```shell
# ③ 术语一致性：同一个概念两种写法会立刻暴露
grep -c '验收标准' 你的文档.md; grep -c '判据' 你的文档.md
# 期望：两者只有一个非零
```
