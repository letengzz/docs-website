# 需求拆分与验收条件

需求页的目标不是「把功能列全」，而是**把每个功能拆到「能不能验收」一眼可判的程度**。方法与术语沿用 [完整项目交付 · 需求拆分](../../../../docs/Others/ProjectDelivery/Requirements/index.md)：用户故事过 INVEST，验收条件写 Given/When/Then。

## 一句话定位

三类角色（读者、作者、管理员），四条主链路（写作发布、阅读与检索、评论互动、运营管理）。本页把每条链路拆成可独立验收的用户故事，并明确**第一期不做**什么——需求页里没写「不做」的，默认都会被当成「该做」。

## 角色与故事地图

| 角色 | 是谁 | 核心诉求 |
| --- | --- | --- |
| 读者 | 匿名访问者 / 登录用户 | 搜得到、读得快、评得了 |
| 作者 | 登录的写作者 | 写得顺（Markdown）、发得稳（草稿→发布）、看得到反馈 |
| 管理员 | 站点负责人 | 管内容（下架/置顶）、管评论（审核/删除）、看数据（访问量） |

## 核心用户故事与验收条件

### US-01 作者写文章（第 2 周核心）

> 作为作者，我可以用 Markdown 写文章并保存草稿，以便分多次完成一篇长文。

```text
Given 作者已登录并有写作权限
When 提交 POST /api/admin/posts（title + markdown 正文）
Then 返回 201 与文章 ID，状态为 DRAFT，正文按原文存储

Given 存在状态为 DRAFT 的文章
When 作者再次 PUT 提交修改
Then 内容更新且 updated_at 变化，状态仍为 DRAFT

Given 未登录
When 访问任意 /api/admin/* 接口
Then 返回 401，响应体走统一错误结构
```

### US-02 发布与可见性

> 作为作者，我可以把草稿发布，以便读者看到它。

```text
Given 状态为 DRAFT 的文章
When 作者点击发布（POST /api/admin/posts/{id}/publish）
Then 状态变为 PUBLISHED，published_at 写入当前时间

Given 一篇 PUBLISHED 文章
When 匿名读者请求 GET /api/posts/{slug}
Then 返回 200 与渲染所需数据；已登录用户与匿名用户看到相同内容

Given 状态为 DRAFT 的文章
When 匿名读者按 slug 访问
Then 返回 404（不是 403——不暴露「这篇存在但你看不见」）
```

:::danger 注意
草稿对匿名返回 **404 而不是 403**：403 等于告诉外部「这个 slug 存在」，未发布文章的 slug 泄露本身就算信息泄露。判据写进验收清单 A 类。
:::

### US-03 阅读与渲染（第 2 周）

> 作为读者，我看到的文章是排版正确、代码高亮、图片可加载的渲染结果。

验收条件：

1. Markdown 标题/列表/表格/代码块渲染正确，代码块按语言高亮；
2. 正文中的外链图片不阻塞首屏（懒加载）；
3. **渲染在服务端完成**（前台是 SSR，HTML 直出含正文），用 `curl` 看 HTML 源码必须包含正文文本——这是 SEO 判据，不是锦上添花；
4. 渲染必须**消毒（sanitize）**：提交含 `<script>` 的 Markdown，页面上不得执行。

### US-04 评论（第 3 周核心）

> 作为登录读者，我可以对文章评论并回复他人，回复在楼中楼里展示。

```text
Given 一篇 PUBLISHED 文章且读者已登录
When 提交评论（内容 1~500 字）
Then 返回 201，评论出现在文章评论列表

Given 评论 A 与其对 A 的回复 B
When 拉取评论列表
Then B 挂在 A 的 children 内，层级固定两级（B 的回复并排平铺在 A 楼层内）

Given 未登录读者
When 提交评论
Then 返回 401，前端引导登录
```

### US-05 全文搜索（第 3 周核心）

> 作为读者，我可以用中文关键词搜到包含该词的已发布文章。

```text
Given 已发布文章《MySQL 索引深入》正文包含「覆盖索引」
When 请求 GET /api/search?q=覆盖索引
Then 结果包含该文章，且命中片段高亮返回

Given 搜索词为空或纯空格
When 请求 /api/search
Then 返回 400 与「搜索词不能为空」

Given 搜索词 100 字
When 请求 /api/search
Then 截断到最大长度并正常返回（不 500）
```

### US-06 运营管理（第 3-4 周）

> 作为管理员，我可以下架违规文章、删除垃圾评论、看到访问量。

验收条件：下架后前台 404；评论删除后楼中楼同步消失（软删除）；访问量计数为文章维度的浏览数（Redis 计数 + 定时回写，判据见架构页）。

## 非功能需求（可验收写法）

| 维度 | 要求 | 验收方式 |
| --- | --- | --- |
| 性能 | 文章详情页 P95 < 300 ms（缓存命中时 < 50 ms），搜索 P95 < 500 ms | k6 脚本 + 阈值门禁（第 3 周） |
| SEO | SSR 直出含正文；每篇文章有 canonical、description；sitemap.xml 可访问 | curl 断言 + 线上工具复检 |
| 安全 | 全部输入校验；富文本消毒；评论接口限流（同 IP 每分钟 ≤ 10 条） | 用例矩阵 + 压测验证限流生效 |
| 可用性 | 数据库迁移可回滚（迁移六步法）；静态资源带指纹 | 部署演练 |
| 兼容 | 前台支持近两年主流浏览器；移动端可读 | 人工验收清单 |

## 范围裁剪：第一期明确不做

| 不做 | 理由 | 归宿 |
| --- | --- | --- |
| 多媒体上传与图床 | 存储与 CDN 是独立工程，第一期正文图片用外链 | 第 5 周后再议 |
| 站内私信 / 通知中心 | 评论即可满足核心互动 | 不做 |
| Elasticsearch 集群 | 数据量（个人博客）远未到 MySQL 全文索引的舒适区之外 | 架构页写明升级触发条件 |
| 多主题 / 插件系统 | 定制化需求，与「能上线」无关 | 永久不做 |

:::tip 提示
范围裁剪的判据来自 [完整项目交付 · 需求拆分](../../../../docs/Others/ProjectDelivery/Requirements/index.md) 的 L1/L2/L3 分级：以上四项全部是 L2（砍掉不影响主链路验收）。凡是砍掉会导致某条验收条件无法判定的，都不能裁。
:::

## 验证方式

本页的验证在第 2-3 周随代码落地：每个 US 的 Given/When/Then 会一一映射为接口测试用例（映射表在进展记录里维护），**故事数量与用例数量对得上**是第 3 周验收的判据之一——避免「需求写了十条、测了三条」。
