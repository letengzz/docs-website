# 实时监控大盘

周期 5（第 121-150 天）的从 0 到 1 完整项目：**指标采集 + 可视化看板 + 告警通知**。它要回答的是每个系统都会遇到、但很少被正面回答的那个问题——**当线上变慢时，值班的人第一眼看什么、从哪往下查**。

::: warning 本项目只有文档，没有代码
`project/` 是**纯文档目录**：下面所有章节讲的都是「这个项目怎么做出来」——配置内容、查询语句、目录结构、命令与判据全部写在正文里，但**仓库不存放源码、脚本、SQL 与构建文件**。
正文里出现「运行 `xxx`」时，指的是**先在你的工程里按本节内容创建好该文件**，再执行。
:::

## 一句话定位

一套自建的监控告警系统：从被监控目标采集指标，经时序库存储，由查询与规则引擎判定，最终呈现为三张必看大盘与一组会响的告警。月末交付判据：**一键起、三张大盘可用、告警真的响过一次、按文档能从零复现**。

## 为什么是监控大盘

| 备选项目 | 为什么不选 / 为什么选它 |
| --- | --- |
| 又一个业务系统（订单、内容） | 第 91-120 天刚做完一个完整业务系统，重复的不是技术而是**问题类型** |
| 消息中间件 / 网关 | 更偏「用现成产品」，自建价值不高 |
| **监控大盘** | 它天然是**多组件协作**项目：采集器、时序库、查询语言、规则引擎、通知渠道、前端可视化——每一层都有自己的技术判断点；同时它有一个其他项目少见的特性：**做得好不好，用「有没有人每天打开它」就能判断**，验收标准极其诚实 |

## 技术选型

| 层 | 选型 | 一句话理由 |
| --- | --- | --- |
| 指标采集 | **拉模型（Pull）+ 标准化 `/metrics` 端点** | 目标存活状态天然可见（抓不到就是 down），与主流生态一致 |
| 时序存储 | **单机时序库起步（Prometheus 形态）** | 30 天周期内数据量可控；引入远程存储会显著抬高运维面 |
| 查询与规则 | **指标查询语言 + recording / alerting rule** | 规则与查询同源，避免「大盘上看到的现象」和「告警判定的条件」两套口径 |
| 告警路由 | **Alertmanager 形态：分组 + 抑制 + 静默** | 抑制与分组是不吵的关键；缺了它，告警会迅速失去可信度 |
| 可视化 | **Grafana 形态的三张大盘** | 大盘的价值在「组织方式」而不在工具，本项目重点写组织方式 |
| 后端（自定义采集与看板服务） | **Spring Boot 4.1 + Java 25** | 复用后端模板；本项目需要它来暴露业务指标与提供大盘数据接口 |
| 部署 | **Docker Compose 一键起** | 与上个项目同构，减少「换项目就要重学部署」的成本 |

::: tip 提示
选型的完整论证（含「为什么不用推模型」「为什么先不上 K8s」「为什么不做自研时序存储」）在 [需求拆分与技术选型](./Requirements/index.md)，这里只放结论。
:::
